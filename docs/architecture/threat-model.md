# Szop — Threat model

What Szop protects, who can act on it and through which path, and what guards each way in. The rules themselves, and why they were chosen, are in [ADR 0012](../decisions/0012-security-baseline.md); this page shows whom each rule stops. Acronyms are explained in the [glossary](../glossary.md).

**Keeping it current:** every phase that adds an actor or an entry point (share links, the WebSocket, a new workflow, a new AWS role) updates this page, as part of the definition of done's "living docs" item.

**A visitor becomes a user in steps** ([ACC-1](../requirements/functional-requirements.md#acc-1), [ACC-2](../requirements/functional-requirements.md#acc-2)): a **visitor without a session** has nothing stored and sees the seed data; their first change gives them an **anonymous session** and a workspace, which makes them a **guest**; registering turns the guest into a **registered user**. Guests and registered users both hold a session cookie and a workspace, so they appear together below as **users with a session**.

## What we protect

- **Users' data and accounts:** lists, templates, catalogs, email addresses, password hashes, sessions.
- **The app's secrets:** the Better Auth secret, `szop_app`'s database password and the database's master password. The first two live only in SSM Parameter Store: Terraform writes each through a write-only argument, so it is never in Terraform state, git or logs, and it is rotated by bumping its version ([ADR 0030](../decisions/0030-domain-and-base-infrastructure-details.md), decision 10; [ADR 0038](../decisions/0038-app-on-ecs-and-rds-details.md)). The master password is created and kept by RDS in Secrets Manager, and never enters the state either. [Who can reach which secret](#who-can-reach-which-secret) lists the readers.
- **The AWS account and its bill.**
- **The Terraform state** in the bucket `szop-tfstate-ntrtcr`: a map of the whole infrastructure, and the record a wrong or lost copy of would make Terraform recreate or orphan resources.
- **The integrity of the repository:** `main`, version tags, the images built from them.
- **The email sender's reputation** in SES, and its daily sending quota.

## Who can reach which secret

A secret's value is readable by whoever holds `ssm:GetParameter(s)` on the parameter or `secretsmanager:GetSecretValue` on the secret, and by the process that receives it in its environment. Reading the table by secret:

| Secret | Where it lives | Who can read the value | Who cannot |
|---|---|---|---|
| **`szop_app`'s password** | SSM Parameter Store `/szop/db-app-password`, a `SecureString` that Terraform writes from base through a write-only argument | the owner; the task execution role (`ssm:GetParameters` on that parameter only), which ECS uses to put it in the environment of the app's container and of `db-setup`'s; those two processes, in their environment | the plan role (the explicit deny `DenySecretValues`); the deploy role, which cannot read it through the API (it can `ssm:DescribeParameters`, which returns metadata only) but can run a task that receives it ([Risks accepted](#risks-accepted-on-purpose)); the task role; anyone with only the Terraform state |
| **The master password** | Secrets Manager `rds!db-…`, created and rotated by RDS because the instance has `manage_master_user_password`; never in the state | the owner; the task execution role (`secretsmanager:GetSecretValue` on `rds!db-*`, only on a secret tagged `project` = `szop` and `group` = `demo`, the tags RDS copies from the instance), which gives it only to a container whose task definition names it, and only `szop-demo-db-setup` does; `db-setup`'s process, for the seconds it runs | the app's container, which never receives it; the plan role (`DenySecretValues`); the deploy role, which lets RDS create the secret (`secretsmanager:CreateSecret` on `rds!db-*`, only through an AWS service, `aws:ViaAWSService`, so it cannot call Secrets Manager for such a secret itself) and cannot read it through the API, but can run a task that receives it ([Risks accepted](#risks-accepted-on-purpose)) |
| **The Better Auth secret** | SSM Parameter Store `/szop/better-auth-secret`, written the same way | the owner; from PH-18, the task execution role | the plan role, the deploy role and the task role |

The master user is used once per deploy, by `db-setup`, and never by the app: using it in the app is the practice AWS advises against, since a compromised app could create roles that survive a password change ([ADR 0038](../decisions/0038-app-on-ecs-and-rds-details.md)). `szop_app` has `LOGIN` and owns the database, and has no `SUPERUSER`, `CREATEROLE` or `CREATEDB`, and no `rds_superuser` membership.

## Entry points, checked against STRIDE

STRIDE names six kinds of threat: **S**poofing (pretending to be someone else), **T**ampering (changing data one should not), **R**epudiation (denying having done something, with no record to prove it), **I**nformation disclosure (seeing data one should not), **D**enial of service (making the service unavailable) and **E**levation of privilege (gaining rights one should not have). Each entry point is checked once against all six; "—" means the category does not apply there. Decisions without an ADR number are ADR 0012's.

## Risks accepted on purpose

- **No audit trail of user actions.** The request log keeps 7 days of requests, not who changed what; that is enough for a demo.
- **A per-email login limit can lock a victim out** for 15 minutes at a time; the victim can still reset the password (decision 14).
- **The breach check fails open** when its service cannot be reached, so an outside outage never blocks registration (decision 11).
- **The cross-site check defends browsers only.** Page scripts are the only code that cannot set `Sec-Fetch-Site` or `Origin`: any other program can, so it passes the check at will. Scripts calling the API directly are met by sessions, rate limits and quotas instead (ADR 0025, decision 1).
- **Fastify's own warnings can log a raw URL.** The request log's serializer hides query values on every line that carries the request, but when a route sends a reply twice, Fastify's error and warning put the raw URL, token included, in the message itself. No route does that today; PH-18 extends the end-to-end test to Better Auth's token routes ([OP-053](https://github.com/luiki-dev/szop/issues/26); ADR 0025, decision 6).
- **The logged `host` can be forged.** Behind the load balancer, Fastify's `request.host` reads `X-Forwarded-Host`, which the load balancer passes on from the client, so the log's `host` field, and any URL derived from it, is the client's to choose; the cross-site check compares the raw `Host` instead, and PH-18 sets Better Auth's base URL explicitly ([OP-053](https://github.com/luiki-dev/szop/issues/26); ADR 0025, decision 2).
- **Rate-limit counters live in memory** and reset when the container restarts (decision 15), until [PH-39](../roadmap.md#ph-39-redis-in-the-stack) brings Redis: from then they live in ElastiCache, shared by every task and gone when the demo is destroyed. Redis then joins this model as a second data store, reached only from the tasks, with an AUTH token and TLS ([ADR 0036](../decisions/0036-scalability-and-isolation.md), decisions 6 and 8).
- **`terraform plan` can run arbitrary code** with the plan role, which is read-only and reads neither secrets, logs, costs nor the account's contact details (decision 17; [ADR 0032](../decisions/0032-ci-access-and-teardown-details.md), decision 5). Any same-repository PR can edit `infra/`, and its plan runs in CI. Such a program could also alter the text of the plan comment, which the comment job's permissions bound: it holds only `pull-requests: write` and no AWS credentials.
- **The plan output is public.** `infra-plan.yml` prints the plan into a public job log and a PR comment ([ADR 0010](../decisions/0010-ci-cd.md), decision 14): resource names, IDs and settings, never secret values, which never enter the state ([ADR 0008](../decisions/0008-hosting.md), decision 22). The role denies take back what `ReadOnlyAccess` would show beyond that.
- **The role ARNs, and so the account ID, appear in the public logs.** GitHub echoes a `uses:` step's `with:` inputs, so the credentials step of `infra-plan` and `demo-down` prints `role-to-assume` before the account ID is masked with `::add-mask::`; every later log line shows `***`. The account ID is not a secret, and an ARN opens nothing without an OIDC token that only a job of this repository can get ([ADR 0032](../decisions/0032-ci-access-and-teardown-details.md), decision 8).
- **The plan of `infra/base` does not show drift.** It runs with `-refresh=false`, so the plan role never reads live resources, the Better Auth secret included; a change made outside Terraform shows only in the owner's local plan ([ADR 0032](../decisions/0032-ci-access-and-teardown-details.md), decision 11).
- **An approved `demo-up` runs the branch's Terraform with the deploy role.** The role's trust for `demo` has no branch condition, so the owner's reading of the code before *Approve and deploy* is the gate. What such code can reach is bounded by the role's policies: the demo's own tagged resources and two kinds of records in the zone, never IAM, base or billing, and a runaway bill is met by the budget alerts and the nightly destroy ([ADR 0034](../decisions/0034-network-and-demo-up-details.md)).
- **ACM cannot restrict tagging to creation.** The deploy role may add the demo's tags to an existing certificate, which would bring that certificate within its reach. Accepted because the account holds no certificate outside the demo: base keeps none ([ADR 0030](../decisions/0030-domain-and-base-infrastructure-details.md), decision 5).
- **The deploy role can run any code with both database passwords in reach.** It registers task definitions of the families `szop-demo-*`, pushes any image to the registry `szop` and passes the task execution role, which can read the RDS-managed master secret and `szop_app`'s password. So `ecs:RunTask` is limited to the family `szop-demo-db-setup` in the cluster `szop-demo`, but that limits which family runs (and `--overrides` can change the command), not what code runs with the secrets: a task definition registered by an approved `demo-up` could name any image it pushed. Accepted as part of trusting the deploy role, whose gate is the owner reading the branch's code before *Approve and deploy* ([ADR 0034](../decisions/0034-network-and-demo-up-details.md); [ADR 0038](../decisions/0038-app-on-ecs-and-rds-details.md)).
- **The execution role reads the master secret by name and by tag.** Its read covers `rds!db-*` in the account, but only a secret tagged `project` = `szop` and `group` = `demo`: RDS copies the instance's tags onto the secret it creates, so a database outside the demo stays out of reach unless it carries the demo's tags. Only a task definition that names a secret gets it, and only the deploy role registers task definitions.
- **The root filesystem of the task is writable**, because ECS Exec does not work with `readonlyRootFilesystem`. The API runs as `node`, and its files belong to root, so a compromised app cannot change its code; it can write to scratch places such as `/tmp`. Compose and CI keep `read_only: true`, which still proves the app writes nothing to disk ([ADR 0038](../decisions/0038-app-on-ecs-and-rds-details.md), refining [ADR 0028](../decisions/0028-container-image-details.md), decision 10).
- **The plan role can pull the image.** `DenyDataReads` takes back RDS log files, Performance Insights and DynamoDB items, but leaves `ecr:BatchGetImage` and `ecr:GetDownloadUrlForLayer`: the image holds only the public code, and a plan's output is public anyway.
- **The task has a public IP address** and its security group allows HTTPS out to anywhere, since the demo has no NAT gateway and no VPC endpoints ([ADR 0008](../decisions/0008-hosting.md), decision 16). Nothing connects in except the load balancer, on the app's port; the cost is that a compromised app could send data out.
- **Claude Code's deny rules and push hook can be worked around** by a command written in another form, such as a subshell or a script ([ADR 0015](../decisions/0015-git-push-guard-hook.md)); they catch mistakes, while the rulesets and the deploy approval are the real boundaries (decision 19).
- **The health route is public** and tells anyone whether the database is reachable, which migration it holds and, since PH-12d, which commit the image was built from; none of it is data, and the migration's name reveals nothing an attacker can use ([ADR 0020](../decisions/0020-database-details.md), decision 5). The commit tells an attacker which code to read for weaknesses, but the repository is public and the demo runs for hours, not months, so knowing the version adds little to what reading `main` gives. The commit is what lets the redeploy watch script see which version answers. The liveness route, `/api/live`, says nothing but that the process runs.
- **The container image is not scanned for known vulnerabilities** (CVEs, Common Vulnerabilities and Exposures) yet. Dependabot keeps the Node base image and the npm packages current, and the image holds only production dependencies; a scanner and a Dockerfile linter are a candidate, [OP-090](https://github.com/luiki-dev/szop/issues/194) ([ADR 0028](../decisions/0028-container-image-details.md), decision 5).
- **The local database uses well-known credentials** (`szop`), committed in `compose.yaml` and `.env.example`; it holds throwaway data and is bound to `127.0.0.1`, so only the developer's own machine can reach it ([ADR 0020](../decisions/0020-database-details.md), decision 9).
