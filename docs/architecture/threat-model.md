# Szop — Threat model

What Szop protects, who can act on it and through which path, and what guards each way in. The rules themselves, and why they were chosen, are in [ADR 0012](../decisions/0012-security-baseline.md); this page shows whom each rule stops. Acronyms are explained in the [glossary](../glossary.md).

**Keeping it current:** every phase that adds an actor or an entry point (share links, the WebSocket, a new workflow, a new AWS role) updates this page, as part of the definition of done's "living docs" item.

**A visitor becomes a user in steps** ([ACC-1](../requirements/functional-requirements.md#acc-1), [ACC-2](../requirements/functional-requirements.md#acc-2)): a **visitor without a session** has nothing stored and sees the seed data; their first change gives them an **anonymous session** and a workspace, which makes them a **guest**; registering turns the guest into a **registered user**. Guests and registered users both hold a session cookie and a workspace, so they appear together below as **users with a session**.

## What we protect

- **Users' data and accounts:** lists, templates, catalogs, email addresses, password hashes, sessions.
- **The app's secrets:** the Better Auth secret and the database password. The Better Auth secret lives only in SSM Parameter Store: Terraform writes it through a write-only argument, so it is never in Terraform state, git or logs, and it is rotated by bumping its version ([ADR 0030](../decisions/0030-domain-and-base-infrastructure-details.md), decision 10).
- **The AWS account and its bill.**
- **The Terraform state** in the bucket `szop-tfstate-ntrtcr`: a map of the whole infrastructure, and the record a wrong or lost copy of would make Terraform recreate or orphan resources.
- **The integrity of the repository:** `main`, version tags, the images built from them.
- **The email sender's reputation** in SES, and its daily sending quota.

## Who can act, and through which path

| Actor | Path in | Can reach | Guarded by |
|---|---|---|---|
| **Visitor without a session** | `/api/*`, `/api/auth/*`; the SPA's files on every other path | the seed data; creating a guest; registering, logging in, resetting a password | lazy creation and per-IP limits ([ADR 0003](../decisions/0003-abuse-protection.md)); limits per target email and the daily email cap (ADR 0012, decision 14); never revealing which accounts exist (decision 12) |
| **User with a session** (guest or registered) | `/api/*` with their own session cookie | their own workspace only | the access layer and scoped repositories (decisions 3–5); composite foreign keys (decision 6); quotas and per-session limits (ADR 0003) |
| **Collaborator or share-link holder** (later, [SHR](../requirements/functional-requirements.md#sharing-shr)) | `/api/lists/:listId/*` | one list, within their role | `requireListAccess` with roles (decision 4) |
| **Malicious website** open in the user's browser | the user's cookies, frames, the `Referer` header | requests sent in the user's name, the app shown inside its page | `SameSite=Lax`; the `Sec-Fetch-Site` or `Origin` check, which answers 403 to an unsafe request marked `same-site` as well as `cross-site`; JSON-only bodies, which answer 415 to a form's body (decision 7; [ADR 0025](../decisions/0025-web-security-baseline-details.md), decisions 1 to 3); `frame-ancestors 'none'` and `no-referrer` (decision 8) |
| **Network attacker** | between the browser and the load balancer | a session sent over plain HTTP | HTTPS only, with HTTP redirected ([ADR 0008](../decisions/0008-hosting.md)); HSTS and the `Secure` cookie (decisions 7 and 8) |
| **Reader of leaked data** | a database dump, CloudWatch Logs | tokens, secrets, password hashes | hashed tokens and share links; tokens hidden in the query strings of logged URLs, where every value, and every parameter without a value, is redacted (decision 9; ADR 0025, decision 6); secrets redacted and never in Terraform state (ADR 0008); scrypt password hashes |
| **Owner** | AWS IAM Identity Center, GitHub admin | everything | the guardrails catch mistakes: rulesets ([ADR 0009](../decisions/0009-git-workflow.md)), the deploy approval (decision 16), budget alerts and the nightly teardown, which runs in `demo-teardown` ([ADR 0010](../decisions/0010-ci-cd.md); [ADR 0032](../decisions/0032-ci-access-and-teardown-details.md), decisions 6 and 7) |
| **Claude Code**, with the owner's credentials | `git push`, `gh` on the owner's machine | branches and PRs; anything the owner's credentials allow | `CLAUDE.md`, backed by deny rules (decision 19) and the push hook ([ADR 0015](../decisions/0015-git-push-guard-hook.md)); the rulesets: no direct pushes to `main`, no moved tags (ADR 0009); the reviewer on `demo` (decision 16) |
| **Compromised dependency** | install scripts and code on the owner's machine, in CI runners, in the running app | the owner's credentials, CI tokens, the app's secrets | pnpm's install-script allowlist; no installs in jobs holding AWS credentials (decision 18), which `infra-plan` and `demo-down` follow: Terraform, the AWS CLI, git and jq only ([ADR 0032](../decisions/0032-ci-access-and-teardown-details.md)); the reviewer on `demo` (decision 16); the Dependabot cooldown (ADR 0010) |
| **Dependabot** | PRs | a malicious update reaching `main` | the 7-day cooldown, CI, and the owner's review (ADR 0010) |
| **CI workflow** | a same-repository PR: `infra-plan.yml` assumes `szop-ci-plan` through OIDC; a job in the `demo-teardown` environment on `main`: `demo-down.yml` assumes `szop-ci-deploy` | the plan role: read access to the infrastructure, with explicit denies on secret values, log contents, S3 objects outside the state, billing and cost, and the account's contact details; the deploy role: the demo's state and lock file in the state bucket, and a listing of the bucket's key names, nothing in IAM, nothing on base's resources, nothing on billing (the demo's resources join in PH-12) | the trust policies, by the token's `sub`: `repo:luiki-dev/szop:pull_request` for the plan role and `repo:luiki-dev/szop:environment:demo-teardown` for the deploy role, each with `aud` `sts.amazonaws.com`, exact values and no wildcard; the explicit denies; the environment `demo-teardown` limited to `main`, which is what keeps a branch from using the deploy role, since a trust policy cannot tell branches apart for an environment's token; the deploy role does not trust `demo` until that environment exists with its reviewer; fork PRs get no token; no installs and no project scripts in jobs holding AWS credentials, and the comment job, which holds a write token, has no AWS access; [ADR 0032](../decisions/0032-ci-access-and-teardown-details.md), decisions 3 to 5, 8 and 10 |
| **Contributor from a fork** | PRs from a fork | nothing beyond the PR itself | fork PRs get no secrets and no OIDC token; the owner's review (ADR 0010) |

## Entry points, checked against STRIDE

STRIDE names six kinds of threat: **S**poofing (pretending to be someone else), **T**ampering (changing data one should not), **R**epudiation (denying having done something, with no record to prove it), **I**nformation disclosure (seeing data one should not), **D**enial of service (making the service unavailable) and **E**levation of privilege (gaining rights one should not have). Each entry point is checked once against all six; "—" means the category does not apply there. Decisions without an ADR number are ADR 0012's.

## Risks accepted on purpose

- **No audit trail of user actions.** The request log keeps 7 days of requests, not who changed what; that is enough for a demo.
- **A per-email login limit can lock a victim out** for 15 minutes at a time; the victim can still reset the password (decision 14).
- **The breach check fails open** when its service cannot be reached, so an outside outage never blocks registration (decision 11).
- **The cross-site check defends browsers only.** Page scripts are the only code that cannot set `Sec-Fetch-Site` or `Origin`: any other program can, so it passes the check at will. Scripts calling the API directly are met by sessions, rate limits and quotas instead (ADR 0025, decision 1).
- **Fastify's own warnings can log a raw URL.** The request log's serializer hides query values on every line that carries the request, but when a route sends a reply twice, Fastify's error and warning put the raw URL, token included, in the message itself. No route does that today; PH-18 extends the end-to-end test to Better Auth's token routes ([OP-053](https://github.com/luiki-dev/szop/issues/26); ADR 0025, decision 6).
- **The logged `host` can be forged.** Behind the load balancer, Fastify's `request.host` reads `X-Forwarded-Host`, which the load balancer passes on from the client, so the log's `host` field, and any URL derived from it, is the client's to choose; the cross-site check compares the raw `Host` instead, and PH-18 sets Better Auth's base URL explicitly ([OP-053](https://github.com/luiki-dev/szop/issues/26); ADR 0025, decision 2).
- **Rate-limit counters live in memory** and reset when the container restarts (decision 15).
- **`terraform plan` can run arbitrary code** with the plan role, which is read-only and reads neither secrets, logs, costs nor the account's contact details (decision 17; [ADR 0032](../decisions/0032-ci-access-and-teardown-details.md), decision 5). Any same-repository PR can edit `infra/`, and its plan runs in CI.
- **The plan output is public.** `infra-plan.yml` prints the plan into a public job log and a PR comment ([ADR 0010](../decisions/0010-ci-cd.md), decision 14): resource names, IDs and settings, never secret values, which never enter the state ([ADR 0008](../decisions/0008-hosting.md), decision 22). The account ID is masked with `::add-mask::` in the plan and destroy jobs, and the role denies take back what `ReadOnlyAccess` would show beyond that.
- **The plan of `infra/base` does not show drift.** It runs with `-refresh=false`, so the plan role never reads live resources, the Better Auth secret included; a change made outside Terraform shows only in the owner's local plan ([ADR 0032](../decisions/0032-ci-access-and-teardown-details.md), decision 11).
- **Claude Code's deny rules and push hook can be worked around** by a command written in another form, such as a subshell or a script ([ADR 0015](../decisions/0015-git-push-guard-hook.md)); they catch mistakes, while the rulesets and the deploy approval are the real boundaries (decision 19).
- **The health route is public** and tells anyone whether the database is reachable and which migration it holds; neither is data, and the migration's name reveals nothing an attacker can use ([ADR 0020](../decisions/0020-database-details.md), decision 5).
- **The container image is not scanned for known vulnerabilities** (CVEs, Common Vulnerabilities and Exposures) yet. Dependabot keeps the Node base image and the npm packages current, and the image holds only production dependencies; a scanner and a Dockerfile linter are a candidate, [OP-090](https://github.com/luiki-dev/szop/issues/194) ([ADR 0028](../decisions/0028-container-image-details.md), decision 5).
- **The local database uses well-known credentials** (`szop`), committed in `compose.yaml` and `.env.example`; it holds throwaway data and is bound to `127.0.0.1`, so only the developer's own machine can reach it ([ADR 0020](../decisions/0020-database-details.md), decision 9).
