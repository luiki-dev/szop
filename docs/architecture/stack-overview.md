## 1. The big picture

Szop is three running things plus one shared library:

1. **The frontend** — a React single-page application (SPA). The browser downloads it once as static files (HTML, JavaScript, CSS); from then on, JavaScript draws every screen and switches between them without full page reloads.
2. **The backend** — a Node.js program built with Fastify. It exposes a REST API: URLs such as `GET /api/lists/42` or `PATCH /api/lists/42/items/7` that accept and return JSON.
3. **The database** — PostgreSQL, where all data lives.
4. **The shared package** — TypeScript code that both the frontend and the backend import: the data shapes (Zod schemas) and pure rules (how to sort a list, how to compute totals).

The frontend never touches the database. The backend never draws screens. The shared package never does input/output — it only describes and computes.

## 3. Who talks to whom

```
Browser (React SPA)
   │  HTTPS + JSON, session cookie attached automatically
   ▼
Fastify API ── SQL (via Drizzle) ──► PostgreSQL
   │
   └── AWS SDK ──► Amazon SES (verification, password reset)

Later: Fastify API ── WebSocket push ──► Browser ("list 42 changed")
```

- The browser only ever talks to the API, over HTTPS.
- The API is the only thing that talks to the database.
- The shared package is not a running service; it is code *used by* both sides: Vite bundles it into the frontend, and the API runs it from its TypeScript source, by tsx in development and by Node's type stripping in production.

## 4. Lifecycle of opening the app

1. The browser requests `https://example.com/` and receives a small HTML file that references the JavaScript bundle. The API answers every path of the app this way, `/lists/42` as much as `/`, with the same `index.html` (the *SPA fallback*), so a reload or a shared link to any page works: the server does not know the app's routes, and React Router picks the page in the browser ([ADR 0023](../decisions/0023-production-build-and-serving-details.md), decision 6).
2. The bundle loads; React starts and React Router looks at the URL to decide which page to show.
3. The app asks Better Auth: "is there a session?" The browser sends the session cookie, if it has one.
4. The lists page mounts and calls `useLists()`. TanStack Query sees nothing cached, calls the API client, which sends `GET /api/lists`.
5. The response arrives, TanStack Query caches it, React re-renders with the data.
6. A first-time visitor has no session, so step 5 returns an empty list and the catalog shows the read-only seed data — nothing has been stored for them yet. Only when they make their **first change** does the API client ask Better Auth for an **anonymous** session: the server creates an anonymous user and a workspace copied from the seed data, sets a session cookie, and the change is sent. This *lazy creation* means visits that change nothing (search engine crawlers, link previews) cost the database nothing — see [ADR 0003](../decisions/0003-abuse-protection.md).

## 5. Lifecycle of a request: checking an item off

1. **Click.** The checkbox component calls `checkItem.mutate({ listId: 42, id: 7, checked: true })` (a TanStack Query mutation from the `useCheckItem()` hook).
2. **Optimistic update.** Before the server answers, the hook updates the cached list: item 7 becomes checked and the shared ordering rules move it from the list to the haul. The screen updates instantly.
3. **HTTP request.** The API client sends `PATCH /api/lists/42/items/7` with `{ "checked": true }` and the session cookie.
4. **Fastify hooks.** The request passes through Fastify's lifecycle: `onRequest` (our auth hook asks Better Auth for the session and attaches the user) → body parsing → **validation** against the Zod schema (invalid input is rejected with 400 here, before our code runs) → `preHandler` → the **route handler**.
5. **Access layer and service.** The handler asks the access layer whether this user may work on list 42: `requireListAccess(user, 42, "shopper")` returns the list owner's workspace, or 404 if the list is not theirs (in the MVP, only the owner passes). It then calls `itemsService.update(ctx, 42, 7, { checked: true })`. The service loads item 7 within list 42 and that workspace (not there → 404), checks the list is not archived (→ 409), and asks the repository to save it.
6. **Repository and database.** Drizzle builds `UPDATE list_items SET checked = true WHERE workspace_id = … AND list_id = 42 AND id = 7` and PostgreSQL executes it.
7. **Response.** The updated item is serialized through the response schema and sent back as JSON.
8. **Reconciliation.** TanStack Query replaces its optimistic guess with the server's answer. If the request failed, it rolls the cache back and the app shows a message.

## 6. Node.js, Express, Fastify and NestJS — how they relate

They are layers, not competitors on the same level:

```
NestJS                 application framework: modules, dependency injection, decorators
  │ runs on top of
Express  or  Fastify   web frameworks: routing, middleware/hooks, request/response helpers
  │ run on top of
Node.js  (http module) runtime: raw sockets and bare HTTP requests/responses
```

- **Node.js** can already serve HTTP with its built-in `http` module, but you would parse URLs, bodies and headers by hand.
- **Express** (2010) is the classic minimal web framework: a chain of *middleware* functions `(req, res, next)` that each handle or pass the request on. Still the most used by sheer numbers; simple, but older and without built-in validation or types.
- **Fastify** is a modern alternative to Express at the same level: routes declare **schemas** (validation and fast serialization), a fixed sequence of **hooks** replaces free-form middleware, and **plugins** with encapsulation provide modularity. It is faster and TypeScript-friendly. Szop uses Fastify directly.
- **NestJS** is one level higher: an opinionated application framework that uses Express (default) or Fastify underneath for HTTP, and adds structure — modules, controllers, providers, dependency injection, guards, pipes.

A Java analogy, if it helps:

| Node world | Java world (roughly) |
|---|---|
| Node.js `http` module | Servlet API |
| Express / Fastify | Lightweight frameworks like Javalin or Spark |
| NestJS | Spring Boot |

**Fastify's request lifecycle**, in order: `onRequest` → `preParsing` → (body parsed) → `preValidation` → (schema validation) → `preHandler` → **handler** → `preSerialization` → (response serialized) → `onSend` → `onResponse`. `onError` runs if anything throws. Hooks registered inside a plugin apply only to that plugin's routes (encapsulation) — that is how, for example, "all routes in this module require a registered user" can be expressed.

**How Szop's API is put together.** A Fastify *instance* is the app. A *plugin* is a function that receives the instance (and options) and adds routes or hooks to it. *Encapsulation* means that what a plugin adds stays inside it unless the plugin says otherwise. Szop's `buildApp` is a factory: it creates the instance and registers the plugins, one per feature, handing each the services it needs as options. That is how a test gets the same app as production, only with fakes passed in. `inject()` then runs a fake HTTP request through the whole app, with no network involved. The reasons are in [ADR 0019](../decisions/0019-api-skeleton-details.md), decision 1; the tests are described in the [testing guide](../development/testing.md).

**Escaping encapsulation with `fastify-plugin`.** Encapsulation is usually what you want: one feature's hooks stay with that feature's routes. A security rule wants the opposite: it must reach every route, the SPA's files and the not-found handler too. Wrapping a plugin with `fastify-plugin` (`fp(plugin, { name })`), a small helper from the Fastify team, tells Fastify not to give the plugin a context of its own, so what it adds lands on the instance that registered it, here the root app. Szop's `security/` plugins are wrapped this way and registered before any route ([ADR 0025](../decisions/0025-web-security-baseline-details.md), decision 8). Calling a plain function on the root app would have the same effect without the dependency; `fastify-plugin` is the idiomatic way, and the one Fastify's own plugins use.

**pino, the logger.** Fastify's built-in logger is pino, which writes one JSON object per line for every event, so a log aggregator can search the fields instead of parsing prose. Szop's API logs every request twice, as `incoming request` and `request completed`, both carrying the same request ID (all but the load balancer's health checks), which is how you follow one request through the log. JSON is hard to read in a terminal, so only the `dev` script pipes the output through pino-pretty; the app itself always writes JSON, and so does production ([ADR 0019](../decisions/0019-api-skeleton-details.md), decision 3).

**tsx in development, type stripping in production.** In development, `tsx` runs the API's `.ts` files directly, with no compile step, and `tsx watch` restarts the API whenever a file changes; that watch mode is why development uses it ([ADR 0005](../decisions/0005-development-environment.md), decision 9). In production, Node runs the same files itself: `node src/server.ts` uses Node's own *type stripping*, stable since Node 24.12, which replaces every type annotation with spaces as it loads a file, so lines and columns, and the stack traces, stay exact. Szop's code already keeps to what stripping allows (no TypeScript-only syntax that generates code, `.ts` import specifiers), and pnpm links `packages/shared` into place as a symlink to its source, so nothing has to be compiled: no build step, no `dist/` that can go stale, and production runs the very files the tests run ([ADR 0023](../decisions/0023-production-build-and-serving-details.md), decision 1). The catch is that Node refuses to strip types in files under `node_modules`, so the container image must keep the workspace's symlinks. Neither tsx nor Node checks types: `pnpm typecheck` runs the TypeScript compiler for that.

## 7. Kinds of state in a frontend

"State" is any data that can change while the app runs and that the screen depends on. The key to a clean frontend is knowing **who owns each piece**:

| Kind | What it is | Szop examples | Owner in Szop |
|---|---|---|---|
| **Server state** | A *copy* of data whose source of truth is the server. Can go stale; must be fetched, cached and refreshed. | Lists, items, catalog, categories | TanStack Query |
| **URL state** | What is encoded in the address bar. Survives reloads, can be bookmarked and shared. | Which list is open | React Router |
| **Local UI state** | Belongs to one component and dies with it. | Is this dialog open? What is typed in the add-item input? | `useState` in the component |
| **Global client state** | Client-only data many unrelated components need, that is *not* a copy of server data. | Nothing yet (a theme could become one) | Would be React Context or a store like Zustand — deliberately not used yet |

Why this matters: libraries such as Redux became famous partly because apps kept **server data** in a global store and hand-wrote the fetching, caching and invalidation. Once server state is handed to a dedicated tool like TanStack Query, very little truly *global* state is left — which is why Szop has no global store.

## 8. The shared package and Zod

A Zod schema is a single definition that gives you two things:

```ts
const ItemPatch = z.object({ checked: z.boolean().optional(), name: z.string().min(1).optional() });
type ItemPatch = z.infer<typeof ItemPatch>;   // a compile-time TypeScript type
ItemPatch.parse(body);                         // a runtime check that throws on bad input
```

TypeScript types vanish at runtime, so they cannot protect the server from a malformed request; Zod checks can. Defining schemas once in `packages/shared` means the form, the API client, the Fastify route and the OpenAPI description all agree by construction.

The API already uses Zod for one job of its own: checking its **configuration**. At startup, `loadConfig` in `apps/api/src/config.ts` validates the environment variables against a Zod schema and returns a typed config object, so `port` is a number from there on. Every variable is required, with no defaults, and a bad or missing one stops startup with a message that names the variable and never shows its value, since a value might be a secret ([ADR 0019](../decisions/0019-api-skeleton-details.md), decision 2).

Since [PH-05](../roadmap.md#ph-05-spa-skeleton) the package holds its first schema that both sides use, `healthSchema` in `packages/shared/src/health.ts`: the body of `GET /api/health`. It is a **discriminated union**, a choice between shapes told apart by one field, here `status`: `{ status: "ok", database: { status: "up", schemaVersion } }` when the database answers and `{ status: "error", database: { status: "down" } }` when it does not. The web app's client parses every answer with it, so a body of another shape is an error instead of a guess, and the TypeScript type `Health` comes from the same definition. The API's health test parses the real responses with it, so the API fails its own test when it drifts from the contract; the Mock Service Worker handlers in the web tests that return a valid health body are typed `Health`, so a fake that drifts fails the type check ([ADR 0021](../decisions/0021-spa-skeleton-details.md), decision 1). Because the package is consumed from source, both `apps/web` and `apps/api` import `@szop/shared` and get the `.ts` file, with no build step in between.

## 9. Data access: Drizzle and PostgreSQL

- **PostgreSQL** is a relational database: tables, rows, foreign keys between them, transactions that make several changes succeed or fail together.
- **Drizzle** is a TypeScript *object-relational mapper (ORM)* that stays close to SQL. Tables are declared in TypeScript; queries read like SQL (`db.select().from(items).where(eq(items.listId, 42))`) and are fully typed from the table definitions.
- **Composite foreign keys** make the database itself keep workspaces apart. Every workspace-owned table has a unique key on `(workspace_id, id)`, and an item points at its category through both columns: `(workspace_id, category_id) → categories (workspace_id, id)`. An item can then only point at a category of its own workspace; PostgreSQL refuses anything else, even if the application forgets to check. A plain foreign key on `category_id` alone would accept any workspace's category.
- **Migrations** are versioned SQL files that evolve the database schema step by step. Drizzle generates them from changes to the table definitions; they are committed and applied in order on every environment.
- **Locally and in CI**, PostgreSQL runs in a container started from `compose.yaml`. Drizzle's migrations are SQL files in `apps/api/drizzle/`, applied when the API starts and recorded in `drizzle.__drizzle_migrations`. A **connection pool** keeps a few connections open and lends them to queries, so each query does not pay for a new connection. Tests use a **template database**: migrated once, copied for each test worker, and emptied before each test. See [Drizzle](../development/tools/drizzle.md), [Docker Compose and PostgreSQL](../development/tools/docker-compose.md) and [testing](../development/testing.md).
- **TLS to the database** encrypts the connection and proves the server is the real one. The server presents a certificate; the client checks that it was signed by a **certificate authority (CA)** it trusts and that it names the host it connected to. With `DATABASE_TLS=verify-full` the API trusts only the CAs in Amazon's RDS bundle, committed as `apps/api/certs/rds-global-bundle.pem`, and refuses any other certificate, so even a server inside the network cannot pose as the database. Locally the container speaks no TLS, so `DATABASE_TLS=none`.

## 10. Authentication: sessions and cookies

- On login, Better Auth creates a **session** row in the database and sends the browser a **cookie** holding the session's identifier.
- The cookie is `HttpOnly` (JavaScript cannot read it, so injected scripts cannot steal it), `Secure` (sent only over HTTPS) and `SameSite=Lax`. `Lax` withholds the cookie from requests other sites trigger in the background (a form posted to us, an image, a script's `fetch`), but still sends it when the user follows a link to us from elsewhere, so they arrive logged in. "Site" means the registrable domain, so every subdomain of the same domain counts as the same site. `SameSite` alone is therefore not a full defence against cross-site request forgery; see [section 13](#13-web-security-in-the-browser).
- The browser attaches the cookie to every request to our domain automatically. The server looks the session up and knows who is asking. Logging out, or revoking a session, simply deletes the row.
- **Anonymous users** are real users with a flag: they get a session and a workspace without email or password, until they register.

## 11. The monorepo

One Git repository holds `apps/web`, `apps/api` and `packages/shared`, plus the end-to-end tests in `e2e/` and the Terraform code in `infra/`. A change to a shared schema, the API route using it and the form using it can land in one commit and be checked together — which is the whole point of TypeScript end to end.

The three packages, and `e2e/`, are **pnpm workspaces**: pnpm links them to each other, so `apps/api` imports `packages/shared` like any installed library, except that it is the live source code in the same repository. `apps/api` is the first package that exists. Its name is `@szop/api`: the `@szop/` scope cannot clash with a package on the npm registry ([ADR 0019](../decisions/0019-api-skeleton-details.md), decision 7). `pnpm -r` runs a script in every package, and Vitest runs every package's tests from the root: it treats each package (and the push hook) as a **project**, today `api` and `hooks`, so one `pnpm test` runs them all, and `pnpm test:coverage` adds the coverage report. How the tests are written and run is in the [testing guide](../development/testing.md); the project layout is [ADR 0019](../decisions/0019-api-skeleton-details.md), decision 5. The development tooling around the stack (pnpm, TypeScript configuration, tsx, ESLint, Prettier, Docker Compose) is decided in [ADR 0005](../decisions/0005-development-environment.md). The [setup guide](../development/setup.md) installs them, and each tool has its own explanatory page in [`docs/development/tools/`](../development/tools/).

The testing tools (Vitest, Testing Library, Mock Service Worker, Playwright, fast-check, StrykerJS) and how the tests are layered are decided in [ADR 0007](../decisions/0007-testing-strategy.md). They get their own pages under `docs/development/tools/` too, next to a testing guide in `docs/development/testing.md`.

## 12. Where Szop runs

Szop runs on **AWS** (Amazon Web Services), but not all the time: it is a **demo environment** that is created when the owner wants to show or try something, and destroyed a few hours later. Everything about it is written down as code, so creating it again gives exactly the same result. The decisions are in [ADR 0008](../decisions/0008-hosting.md), the binding summary in [architecture.md](architecture.md#5-deployment). This section explains the concepts.

### Infrastructure as code and Terraform

**Infrastructure as code (IaC)** means describing servers, networks and databases in text files kept in git, instead of clicking them together in a web console. **Terraform** reads those files (written in its own language, HCL) and makes the cloud match them:

- `terraform plan` compares the files with what exists and shows what it would create, change or delete.
- `terraform apply` does it. `terraform destroy` deletes everything the configuration created.
- Terraform remembers what it created in a **state** file: a map from each resource in the code to the real object on AWS. Without it, Terraform could not tell its own bucket from a stranger's and would try to create everything again. Szop keeps the state in an S3 bucket (AWS's file storage), so the owner's machine and CI see the same state, and the bucket's versioning keeps every earlier copy.
- The **backend** is where a module's state lives; Szop's point at one bucket, one key per module. A **state lock** stops two runs from writing the same state at once: before a run, Terraform creates a small `.tflock` file next to the state, and a second run finds it and stops. (The **provider lock file**, `.terraform.lock.hcl`, is something else: it pins the provider's exact version, like `pnpm-lock.yaml`.)
- A **provider** is the plugin that talks to one platform's API (here the AWS provider). A **root module** is one folder of configuration applied on its own, with its own state.
- A **data source** (`data "aws_route53_zone" …`) *reads* something that already exists and that this module does not manage, where a `resource` block creates and owns its object. `infra/demo` uses one to find base's hosted zone by its name, `dzwoniec.com`. The alternative, reading base's outputs from its state with `terraform_remote_state`, would give whoever runs the demo read access to base's whole state; a lookup by name needs only the permissions to read what it looks up. The cost is that the name is written in both modules, and a rename in base breaks the demo's next plan, loudly ([ADR 0034](../decisions/0034-network-and-demo-up-details.md)).
- A **precondition** in a resource's `lifecycle` block is a check Terraform runs before it creates or changes the resource, failing with your own message. The demo's load balancer listener uses one to refuse an apply that does not say which commit it deploys. Terraform skips it on a destroy, so a teardown needs no commit.

Szop's configuration is split into three root modules by how long their resources live: **bootstrap** (created once: the state bucket and budget alerts), **base** (permanent and cheap: image registry, domain, email identity, the Better Auth secret, logs, IAM roles) and **demo** (created for a session and destroyed after it: network, load balancer, container, database with its RDS-managed password). Destroying the demo can never touch the other two.

Bootstrap has a chicken-and-egg problem: it creates the bucket that states live in, so its own first apply keeps the state in a local file, which then moves into the bucket ([ADR 0029](../decisions/0029-aws-account-and-terraform-bootstrap-details.md)). The commands are in the [runbook](../operations/demo-environment.md#applying-bootstrap) and the tool on the [Terraform page](../development/tools/terraform.md).

### The AWS account

An **AWS account** is the container every resource, permission and bill belongs to. Szop has one of its own, so nothing else shares its costs or permissions ([ADR 0029](../decisions/0029-aws-account-and-terraform-bootstrap-details.md)).

- **Regions.** AWS runs separate copies of most services in each **region**, a group of data centers in one area. A resource lives in one region; Szop's live in Frankfurt (`eu-central-1`). A few services are **global** (IAM, billing, Organizations): their console pages have no region.
- **The root user** is the email address the account was opened with. It can do everything, no policy limits it, and it is used only for the few tasks only it can do, behind multi-factor authentication (MFA).
- **IAM Identity Center** is AWS's single sign-on (SSO). People sign in once at an access portal, with MFA, and get credentials for an account through a **permission set** (here `AdministratorAccess`). Those credentials expire after a few hours. The alternative, an **access key**, works until someone deletes it, which is why a leaked key is the most common way AWS accounts are compromised; Szop has none. `aws sso login` gives the CLI and Terraform the same short-lived credentials.
- **AWS Organizations** groups accounts under one management account. Szop has one account, but Identity Center needs an organization to hand out account access, so enabling it created one.
- **AWS Budgets** watches the bill. Szop's budget, `szop-monthly`, emails the owner when the month's forecast passes $5 or the actual cost passes $10. It ignores credits on purpose: counted after credits, a forgotten demo would cost "$0" until the credits ran out.

### Domains, DNS and email authentication

A **domain name** such as `dzwoniec.com` is rented, a year at a time, from a **registrar**, which records it in the **registry** that runs its top-level domain (Verisign for `.com`; the Internet Corporation for Assigned Names and Numbers (ICANN) accredits both). The registration says which **name servers** answer for the domain: the servers that hold its DNS records. Route 53 is both Szop's registrar and its DNS service ([ADR 0030](../decisions/0030-domain-and-base-infrastructure-details.md)).

- **The hosted zone** is Route 53's container for one domain's records, served by four name servers that Route 53 picks when the zone is created. Buying the domain created the zone, and the registration points at its four servers. A new zone would get four other servers, and the domain would stop resolving until the registration was changed to match; that is why `infra/base` imported the existing zone instead of creating one, and why Terraform refuses to destroy it.
- **Record types:** an **A** record maps a name to an IPv4 address, and Route 53's **alias** form of it points at an AWS resource such as a load balancer, following its changing addresses. A **CNAME** says "this name is another name", **TXT** holds free text that other systems read (SPF and DMARC live there), **MX** (Mail Exchanger) names the servers that receive the domain's mail, and **CAA** (Certification Authority Authorization) names the certificate authorities allowed to issue certificates for the domain. Szop's CAA allows only Amazon's, so another authority refuses even if someone passes its checks.
- **A null MX**, `0 .`, says the domain receives no mail at all, so a sender gives up at once instead of retrying for days.

Email was built without proof of who sent a message: anyone can write any address in the `From` line. Three DNS-published mechanisms let a receiving server check it:

- **DKIM** (DomainKeys Identified Mail): the sender signs each message, and the receiver checks the signature against a public key published in DNS under the signing domain (`d=`). SES signs Szop's mail for `dzwoniec.com`, with its keys behind three CNAME records that point at Amazon.
- **SPF** (Sender Policy Framework): a TXT record listing the servers allowed to send with the domain as the **envelope sender**, the hidden return address that bounces go to. SES uses its own `amazonses.com` as envelope sender, so nothing sends with `dzwoniec.com` there, and Szop's SPF record, `v=spf1 -all`, allows no one.
- **DMARC** (Domain-based Message Authentication, Reporting and Conformance): a TXT record at `_dmarc.<domain>` telling receivers what to do with a message whose `From` domain is not backed by a passing DKIM or SPF check for the same domain (**alignment**; "relaxed" alignment lets a subdomain count as the same domain). Szop's, `p=reject`, asks receivers to refuse such messages. Szop's own mail passes through DKIM; a forgery in its name passes neither and is rejected.

### Static hosting: the landing page

`dzwoniec.com` itself serves a **static** page, one that is only files: HTML, CSS, a script and a picture, the same for every visitor, with no server code that runs per request ([ADR 0044](../decisions/0044-landing-page-details.md)). A static page needs no application server and no database, so it can be served by any host of files; Szop's is on **GitHub Pages**, GitHub's free host for them.

- **Deployment.** A workflow, `pages.yml`, uploads the folder `apps/landing/` as a Pages **artifact** and a second job deploys it. The page has no build step: what is in the folder is what visitors get. The alternative, publishing a branch, can serve only a repository's root or its `docs/` folder, which here hold the application and the documentation.
- **DNS.** The apex of a domain cannot be a CNAME, so Route 53 holds **A** and **AAAA** records with GitHub's addresses; `www` is a CNAME to Pages, which redirects it to the apex. A **TXT** record proves that the owner's account controls the domain, so no one else's Pages site can claim it.
- **The certificate.** Pages obtains its own, from **Let's Encrypt**, a free certificate authority that issues and renews certificates automatically. AWS's certificates (ACM) work only inside AWS services and cannot be exported, so they cannot serve the page. Because of the CAA record ([above](#domains-dns-and-email-authentication)), Let's Encrypt refuses to issue unless the record names it, so the apex's record allows `amazon.com` and `letsencrypt.org`. A CAA record on a name takes precedence over its parent's, and `szop.dzwoniec.com` has one of its own, so the app's name stays with Amazon.
- **The status dot.** The page asks the demo whether it answers: `fetch` of `https://szop.dzwoniec.com/api/health`. The page and the demo are on different **origins**, and the application sends no **CORS** headers, so a normal request would be blocked and its result unreadable. A `no-cors` request is still sent, and the browser hands the page an **opaque response**: it cannot read the status or the body, but it knows the request completed. One more header decides whether it does: **`Cross-Origin-Resource-Policy`** (CORP), with which a server says who may receive its responses. Helmet's default, `same-origin`, makes the browser block the response and fail the `fetch` as if nothing had answered, so the dot would stay grey while the demo runs; `/api/health` therefore sends `same-site`, which admits pages of the same site (`dzwoniec.com` and its subdomains) and no other site, while every other route keeps `same-origin` ([ADR 0046](../decisions/0046-health-answer-for-the-landing-page.md)). If the demo is down there is no DNS record, so the request fails; if the request outlives five seconds it is cancelled. So the page can tell "an answer" from "none", and nothing more: a `503` from the load balancer while the tasks start counts as an answer. Reading the status would need CORS headers on `/api/health`, which a later phase can add.
- **No redirect.** While the demo is down, `szop.dzwoniec.com` has no DNS record and shows a browser error. Redirecting it to the page would need a second Pages site (one site serves one domain) or CloudFront, plus a way to put the record back when the demo is destroyed; the owner left it out.

### The demo's network and load balancer

What PH-12b builds, from the outside in, with the reason for each piece. The exact values are in the [architecture](architecture.md#5-deployment).

- **The VPC and its address range.** A VPC is a private network that only your account's resources live in. Its size is a **CIDR block** (Classless Inter-Domain Routing), an address and a prefix length: `10.0.0.0/16` means "every address starting `10.0.`", 65,536 of them. `10.x.x.x` is a range reserved for private networks, so it never clashes with a public address. The VPC has DNS support and DNS hostnames switched on, which RDS and the container need.
- **Subnets and availability zones.** A subnet is a slice of the VPC's range that lives in exactly one availability zone (AZ). Szop's four are `/24` slices (256 addresses each, 251 usable: AWS keeps five) in two AZs, `eu-central-1a` and `eu-central-1b`, because the load balancer must span two and so must RDS's subnet group later. Two subnets are **public** (`10.0.0.0/24`, `10.0.1.0/24`) and two **private** (`10.0.10.0/24`, `10.0.11.0/24`); the private ones hold the database since PH-12c.
- **What makes a subnet public.** Nothing in the subnet itself: a **route table** is a list of rules, "traffic for this range goes there", and a subnet follows the table it is associated with. An **internet gateway** (IGW) is the VPC's door to the internet. The public route table has one rule besides the built-in local route, `0.0.0.0/0` (every address) through the gateway, and the two public subnets are associated with it. The private subnets have no table of their own, so they use the VPC's main one, which only knows the local route: nothing in them can reach the internet or be reached from it. A resource in a public subnet also needs a public address to use the door, and these subnets do not hand one out by default; the load balancer gets its own. There is no **NAT** (Network Address Translation) gateway, which would let private resources reach the internet for about $32 a month, and no endpoints: the demo's private subnets need no way out ([ADR 0008](../decisions/0008-hosting.md), decision 16).
- **Security groups.** A security group is a firewall that is attached to a resource and is **stateful**: it lists who may connect in, and the replies to an allowed connection go back without a rule. Everything not allowed is refused. The load balancer's group allows ports 443 and 80 from anywhere and, since PH-12c, has one rule for traffic out: the app's port, to the tasks' group, which in turn is the only source the database's group admits.
- **The application load balancer, listeners and actions.** An ALB is the one public address of the app. Each **listener** waits on a port and protocol and applies an **action** to the requests it receives: *forward* them to targets, *redirect* them, or answer with a *fixed response*. Szop's port-80 listener redirects to HTTPS (a 301); its port-443 listener ends TLS, with a certificate and a **TLS policy** that names the protocol versions and ciphers it accepts, and, since PH-12c, forwards every request to the container (before, it answered with a fixed placeholder page). An internet-facing ALB needs the internet gateway to exist first, or its creation fails; the code says so explicitly (`depends_on`).
- **A certificate by DNS validation.** ACM issues a certificate only to whoever controls the name. In *DNS validation* ACM names a CNAME record, `_<token>.szop.dzwoniec.com`, that must exist in the domain's zone; Terraform writes it into base's zone from the certificate's `domain_validation_options`, and a separate validation resource waits until ACM has seen it and issued the certificate. The HTTPS listener uses the validation resource's certificate, so it cannot be created too early. ACM gives the same name and value to the same account and domain every time, so a record left behind by an interrupted teardown is simply taken over by the next run.
- **An alias record.** `szop.dzwoniec.com` is an `A` record in alias form: it holds no address but the load balancer's name, and Route 53 answers with the load balancer's current addresses, which AWS changes over time. An alias is allowed where a CNAME is not (at a zone's root), and Route 53 charges nothing for queries that an alias answers with an AWS resource.

### ECS and RDS: the app and its database

What PH-12c adds, with the reason for each piece ([ADR 0008](../decisions/0008-hosting.md), [ADR 0038](../decisions/0038-app-on-ecs-and-rds-details.md)).

**Running the container: ECS**

- **Cluster, task definition, task, service.** A **cluster** is the named group everything runs in; with Fargate it holds no servers, only a name. A **task definition** is a blueprint with a name, its **family**: which image, how much CPU and memory, which environment variables and secrets, where the log goes, which roles. A task definition is never edited: every change registers a new **revision** of the family (`szop-demo-app:1`, `:2`), and a destroyed one is only marked inactive, which costs nothing. A **task** is one running copy of a revision, with an ID, a lifetime and, once it stops, a stopped reason. A **service** is a manager that keeps a wanted number of tasks of one task definition running, replaces a task that stops, registers each with the load balancer's target group and, when the revision changes, starts the new tasks before stopping the old. Szop's service starts with a wanted count of 0, and `demo-up` raises it to 2 after the database is ready.
- **Fargate.** An ECS task runs either on servers you manage (EC2) or on **Fargate**, where you state the CPU and memory and AWS finds the machine and isolates the task. Szop asks for 0.25 vCPU and 512 MB, the smallest size, and pays per second.
- **`awsvpc` networking.** The task gets its own network interface with its own private address in a subnet, as if it were a small server, so a security group attaches to the task itself, and the target group registers it by IP address (target type `ip`). Szop's task also asks for a public address: with no NAT gateway, a public address is the task's way out to ECR, CloudWatch and the secret stores, while its security group lets nothing in except the load balancer.
- **The execution role and the task role.** Two roles do different jobs. The **task execution role** is used by ECS around the container, before the code runs: it pulls the image, creates the log stream and fetches the secrets. The **task role** is what the code in the container uses when it calls AWS, and today allows only ECS Exec's messaging channels. Keeping them apart means the app cannot read what ECS read for it: the master password reaches `db-setup` through the execution role, and the app's container never receives it.
- **ECS `secrets`.** A container definition lists `secrets` as a name and a `valueFrom`, the ARN of an SSM parameter or a Secrets Manager secret (with `:password::` to pick one key of a JSON secret). ECS fetches the value when the task starts and sets it as an environment variable, so the task definition holds only where the secret is, never the value. A changed secret reaches a task when it next starts.
- **One-off tasks.** `aws ecs run-task` starts a task from a task definition once, outside any service. It runs its command, stops, and leaves an exit code, `0` for success. `db-setup` is one: the same image as the app with another command, started by `demo-up`, which waits for it to stop and checks the code before it starts the app.
- **ECS Exec.** `aws ecs execute-command` opens a shell inside a running container, for debugging. An agent that ECS adds to the task opens the session over Systems Manager's message channels, which is why the task role holds the four `ssmmessages:` actions and the owner's machine needs the Session Manager plugin. The agent writes into the container, so ECS Exec does not work with a read-only root filesystem: Szop keeps the root filesystem writable on ECS and read-only in Compose. The [runbook's debugging chapter](../operations/demo-environment.md#debugging) shows the commands.

**The database: RDS**

- **Instance, subnet group, parameter group.** An RDS **instance** is the managed server: Szop's is PostgreSQL on a `db.t4g.micro` with 20 GB of disk, encrypted, in one availability zone, deleted at every teardown. A **subnet group** names the subnets RDS may place it in; RDS requires subnets in two zones, so Szop's group holds the two private subnets, and nothing can reach the instance from the internet. A **parameter group** holds the server's settings; the default one for PostgreSQL 15 and later has `rds.force_ssl` on, so the server refuses a connection without TLS, and the app checks the server's certificate against Amazon's bundle (`DATABASE_TLS=verify-full`).
- **The managed master password.** When an instance is created, someone must choose the password of its first account, the **master user** (`szop_admin`). With `manage_master_user_password`, RDS generates it, keeps it in Secrets Manager and deletes it with the instance, so it never passes through Terraform and its state; the state holds only the secret's ARN. The master user is a powerful account: it can create roles and databases, though RDS withholds a real `SUPERUSER`.
- **Why the app has a role of its own.** If the app used the master user, a flaw in the app would let an attacker create roles that survive a password change. So `db-setup` uses the master user once per deploy to create **`szop_app`**, which owns the database `szop` (it needs to, since the app creates its own tables when it migrates) and cannot create roles or databases. This is **least privilege**: each identity gets what its job needs.
- **Passing a password to PostgreSQL.** `CREATE ROLE … PASSWORD 'secret'` sends the password in the statement's text, and a failed statement is written to the server's log with its text. PostgreSQL also accepts a password already hashed in its own format, a SCRAM-SHA-256 verifier. `db-setup` computes the verifier inside the task and sends that, so the cleartext never reaches the server. Salted Challenge Response Authentication Mechanism (SCRAM) is also how the app logs in: the server checks that the client knows the password without the password being sent.

### A demo session, step by step

1. **Build and push.** The Dockerfile builds the image; it is pushed to ECR, tagged with the commit hash. The `demo-up` workflow runs this step (the build in a job with no AWS credentials, the push only if the image is missing) and the next ones at the press of a button, after the owner's approval ([ADR 0010](../decisions/0010-ci-cd.md)).
2. **Spin up.** `terraform apply` in `infra/demo` creates the network, security groups, load balancer, database and ECS service, requests its certificate, and points `szop.dzwoniec.com` at the load balancer. The whole `demo-up` run took about 9 minutes from the approval on the first demo, 5 of them for the database; a redeploy took about 3 on PH-12c's defaults. The service is created with no task yet.
3. **Set up and start.** `demo-up` runs `db-setup`, a one-off task that creates the app's database role, then raises the service's count to 2. ECS pulls the image, reads the secrets and starts the two tasks, one in each availability zone. Each app takes the migration lock, runs its migrations (the second finds nothing left to do), then starts serving. Once `/api/live` answers, the load balancer sends traffic to it; `demo-up` then waits until `/api/health`, the readiness check, answers ok with the commit it deployed, which also means the app reaches its database ([ADR 0036](../decisions/0036-scalability-and-isolation.md), decision 4; [running several instances](#21-running-several-instances) explains liveness and readiness). On a redeploy this step is a rolling deploy, described there too.
4. **Use.** The browser opens `https://szop.dzwoniec.com`: the same app as locally, with the same one-origin setup.
5. **Tear down.** `terraform destroy` removes everything created in step 2. The logs stay in CloudWatch for a week. If a session is forgotten, the nightly `demo-down` workflow destroys it ([ADR 0010](../decisions/0010-ci-cd.md)).

### How CI gets into AWS

A workflow that plans or destroys infrastructure needs AWS credentials. The obvious way, an access key stored as a GitHub secret, is the one Szop avoids: a key works from anywhere until someone deletes it, so a leak is a standing break-in. Szop uses a handshake in which GitHub vouches for the job and AWS hands out credentials that expire ([ADR 0010](../decisions/0010-ci-cd.md), decision 15; [ADR 0032](../decisions/0032-ci-access-and-teardown-details.md)).

- **OIDC federation.** OpenID Connect (OIDC) lets one party, here GitHub, tell another, here AWS, who is asking. For each job that asks, GitHub issues a short-lived signed token whose **claims** say which repository the job belongs to (`sub`, the *subject*, such as `repo:luiki-dev@290870182/szop@1380292421:pull_request` or `repo:luiki-dev@290870182/szop@1380292421:environment:demo-teardown`; with GitHub's *immutable subject*, the owner and the repository carry their numeric IDs after the `@`, so a repository recreated under the same name is not the same subject) and who the token is for (`aud`, the *audience*, `sts.amazonaws.com`). In `infra/base`, an **OIDC provider** tells AWS to trust tokens signed by `token.actions.githubusercontent.com`. The job then calls the **Security Token Service (STS)**, AWS's service for temporary credentials, which checks the token's signature and hands out credentials for a role. A job gets one only when `permissions: id-token: write` is granted to that job; Szop grants it per job, never per workflow.
- **A role has two policies that do different work.** The **trust policy** says *who may assume the role*: for Szop's CI roles, tokens from the provider whose `sub` and `aud` equal exact values, so a job from another repository, or a workflow of this one that the condition does not name, is refused. The **permission policies** say *what the role may do* once assumed. Both must allow the action. The plan role (`szop-ci-plan`) trusts pull requests of this repository and may read everything; the deploy role (`szop-ci-deploy`) trusts two environments and may touch the demo's state and the demo's own resources.
- **Explicit denies win.** In IAM an **explicit deny** beats every allow, wherever the allow comes from. The plan role is given AWS's broad `ReadOnlyAccess` because `terraform plan` must read the whole infrastructure, and a few explicit denies then take back what a public log must not show: secret values, log contents, billing and the account's contact details. Without the denies, adding a service to `ReadOnlyAccess` would silently widen the role.
- **Access Analyzer's policy validation.** IAM Access Analyzer checks a policy document against AWS's own rules and reports errors, security warnings, warnings and suggestions, for example a trust policy that could be narrower. `ci.yml`'s `plan` job sends every IAM policy of a pull request's plan to it and lists the findings in the PR comment, so a change to a role is checked in the PR that makes it; an error or a security warning blocks the PR ([22. Scanning for vulnerabilities and misconfigurations](#22-scanning-for-vulnerabilities-and-misconfigurations)).
- **GitHub environments with branch rules.** A token's subject names an **environment**, not the workflow file, so the trust policy alone cannot tell which branch's code is running. The environment `demo-teardown` therefore allows deployments from `main` only, and a branch's job that names it is refused by GitHub before any token is issued. Rules like this live in GitHub's settings, not in the code, so the deploy role's trust policy also checks the token's `ref` claim, the branch it ran from, and accepts only `refs/heads/main` ([GitHub settings](../development/github-settings.md#environments)). GitHub also creates a missing environment the first time a job names it, with no protection, which is why the deploy role trusts an environment only after it exists.
- **A gate for a branch you cannot pin.** `demo-up` is pressed on the branch being checked, so its environment, `demo`, allows any branch, and the deploy role's trust for it has no `ref` condition. What stands in for the branch rule is a **required reviewer**: the job waits at *Review deployments* until the owner approves, and the owner reads the code first. The approval is the gate, which is why the environment must exist with its reviewer before the trust does.
- **Tag-based conditions.** An IAM policy statement can carry a **condition** on the tags of what it touches. `aws:RequestTag/group` is a tag in the request that creates something; `aws:ResourceTag/group` is a tag on the existing resource. The deploy role may create a load balancer only if the request tags it `project` = `szop` and `group` = `demo`, and change or delete one only if it already carries both. Base and bootstrap carry `project` = `szop` too, so that tag alone would not keep the role away from them; `group` = `demo`, which only the demo module's provider sets, does. Not every action supports tag conditions: where one does not, the policy limits it to `eu-central-1` or to a named record in the zone instead.
- **Scheduled workflows.** A workflow with `on: schedule:` and a cron line runs without anyone pressing a button. `demo-down` runs every night, so a demo nobody remembers is destroyed. Scheduled runs always use the workflow file on `main`, GitHub may start them late, and in a public repository GitHub disables them after 60 days without activity.

## 13. Web security in the browser

A browser runs code from many sites side by side and sends each site's cookies automatically. Most web attacks abuse one of those two facts. The rules Szop follows are in [ADR 0012](../decisions/0012-security-baseline.md) and `architecture.md`; who they stop is in the [threat model](threat-model.md).

- **Cross-site request forgery (CSRF).** A page on another site makes the victim's browser send a request to Szop, for example a hidden form posting "delete this list". The browser attaches the victim's cookie, so without a defence the request runs in their name. Szop refuses every request that changes data unless the browser says it came from Szop's own pages: browsers add a `Sec-Fetch-Site` header that page scripts cannot forge, with the older `Origin` header as a fallback. Changes must also be sent as JSON, which a plain HTML form on another site cannot produce.
- **Content Security Policy (CSP).** A response header listing where the page may load scripts, styles, images and frames from. Szop allows only its own files and no inline scripts, so even if an attacker managed to inject HTML into a page, the browser would refuse to run their script. `frame-ancestors 'none'` stops other sites from showing Szop inside a frame, which defeats *clickjacking*: tricking a user into clicking a button they cannot see.
- **HTTP Strict Transport Security (HSTS).** A response header telling the browser to use only HTTPS for this domain for a year. After the first visit, a typed `http://` address never goes out unencrypted, so nobody on the network can intercept that first request.
- **`Referrer-Policy: no-referrer`.** Browsers normally tell the next site which page the user came from, in the `Referer` header. A password-reset link carries its token in the URL, so Szop asks the browser never to send it.
- **`@fastify/helmet`** sets all these headers in one place, with safe defaults for the smaller ones.

**How fetch metadata works.** Every request a current browser sends carries `Sec-Fetch-*` headers saying where it comes from. `Sec-Fetch-Site` says how the page that sent it relates to the server: `same-origin` (a page with the same scheme, host and port), `same-site` (another subdomain of the same registrable domain), `cross-site` (any other site) or `none` (the user typed the address or opened a bookmark). The browser writes these headers itself, and page scripts cannot set or change any header whose name starts with `Sec-`, so a malicious page cannot pass its request off as Szop's own. Szop accepts a request that changes data (POST, PUT, PATCH, DELETE) only when it is marked `same-origin`; without the header, it falls back to `Origin`, whose host must equal the request's `Host`; a request with neither is refused ([ADR 0025](../decisions/0025-web-security-baseline-details.md), decisions 1 and 2). The classic defence is a *CSRF token*: a random value the server puts into each page and expects back with every change, which another site cannot read. It works, but it is state to create, store and send. With the app and its API on one origin, and every supported browser sending `Sec-Fetch-Site`, the browser's own header answers the same question without any state, which is why newer frameworks, Go's standard library among them, check it instead. The check protects browsers only: any program other than a page script can write these headers, so a script calling the API directly passes it and is met by sessions, rate limits and quotas instead.

**Simple requests, and why bodies must be JSON.** Before a page's script sends another site a request that a plain HTML form could not have sent, the browser asks that site first, with an `OPTIONS` request called a *preflight*, and sends the real request only if the site agrees; that is Cross-Origin Resource Sharing (CORS). A *simple request* skips the question: a GET, HEAD or POST whose body has one of the three content types a form can send, `application/x-www-form-urlencoded`, `multipart/form-data` and `text/plain`. Forms are older than CORS, so browsers still send them to any site without asking. A body with `Content-Type: application/json` is not simple, so another site's page can send it only after a preflight, which Szop never approves. Fastify parses JSON and plain text out of the box; Szop removes the plain-text parser, which leaves JSON as the only body it accepts, and every other content type gets `415 Unsupported Media Type` ([ADR 0025](../decisions/0025-web-security-baseline-details.md), decision 3). Together with the `Sec-Fetch-Site` check this is defence in depth: either alone would stop a forged form.

**The CSP written out.** Helmet comes with a default policy and lets you override single directives. Szop turns those defaults off and writes the whole policy itself: `default-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`. Helmet's defaults allow inline styles and `data:` fonts and images, which Szop rules out; with overrides, the real policy would be half helmet's defaults, which an upgrade can change and which can be read only in its source. Written out, the policy sits in one file and a test checks the exact header. One consequence reaches the build: Vite normally inlines small images and fonts into the bundle as `data:` URIs, which `'self'` would block, so `assetsInlineLimit: 0` makes it write them as separate files instead ([ADR 0025](../decisions/0025-web-security-baseline-details.md), decisions 4 and 5).

**The client's address behind a proxy.** In AWS the browser talks to the load balancer, and the load balancer opens its own connection to the API, so the address the API sees on the connection is the load balancer's, not the user's. A proxy passes the original address on by appending the address it saw to the `X-Forwarded-For` header: `X-Forwarded-For: <client>, <first proxy>, …`. But a client can send that header itself, with any addresses it likes, and the proxy appends to whatever it received. So only the entries on the right, written by proxies you trust, can be believed. Fastify's `trustProxy` option names those proxies. It used to accept a number of hops, "believe the last entry", but Fastify 5.12, the version Szop uses, ignores a number and trusts nothing: a hop count cannot tell whether the connection really came through the proxy, so a client reaching the API directly could write a forged `X-Forwarded-For` and have its last entry believed. Trusting by address fixes that. Fastify starts from the connection's address and walks the header from the right only while the address in hand is a trusted proxy. Through the load balancer (`10.0.1.5`, inside the trusted range), the next entry to the left is the address it saw, and that one counts; a client connecting directly is not a trusted proxy, so its own address counts and its header is ignored. Szop's `TRUSTED_PROXIES` setting lists those addresses: the VPC's range in AWS, `none` locally ([ADR 0025](../decisions/0025-web-security-baseline-details.md), decision 7).

## 14. Styling: Tailwind, components and design tokens

What Szop looks like is described in [visual-design.md](visual-design.md) and decided in [ADR 0013](../decisions/0013-visual-design.md) and [ADR 0022](../decisions/0022-ring-tail-redesign.md). This section explains the ideas behind the tools.

- **Where styles can come from.** A browser applies CSS from three places: a stylesheet file (`<link rel="stylesheet">`), a `<style>` element in the page, or a `style` attribute on an element. Libraries that write styles in JavaScript (CSS-in-JS) create `<style>` elements while the app runs. Szop's Content Security Policy ([section 13](#13-web-security-in-the-browser)) allows only stylesheet files from its own origin, which shuts that door, so every style must exist before the app runs.
- **Tailwind CSS builds that stylesheet.** Instead of naming a class and writing its CSS elsewhere (`.item-row { padding: 12px 16px; }`), you write small classes that each do one thing straight in the markup: `<li class="px-4 py-3 min-h-14 border-t">`. At build time Tailwind scans the source files and generates CSS for exactly the classes it finds, nothing else, so the stylesheet stays small however large Tailwind's vocabulary is. Variants prefix a class with a condition: `dark:bg-gray-900` applies only in dark mode, `lg:flex` only from 1024 px wide, `motion-safe:transition` only when the user hasn't asked for reduced motion. The price is long class lists, which is why they live inside components, written once.
- **Headless components carry the hard part.** A dialog looks simple, but it must move keyboard focus into itself, keep it there, close on Escape, hide the page behind it from screen readers and give focus back when it closes. A **headless** library such as Base UI does all of that and draws nothing; the app supplies the looks. **shadcn/ui** then supplies looks for Base UI's components, as source code copied into the project rather than a package: you can open `button.tsx` and change it, which is also how you learn what it does.
- **Design tokens keep it consistent.** A token is a named value: `--primary` instead of `#3F7357`. Szop's tokens come in two tiers. The **palette** is Tailwind's colors (`gray-500`, plus Szop's own `fur` and `sage-700`); the **semantic roles** (`primary`, `muted-foreground`, `border`, `warning`) say what a color is *for*, and point into the palette. Components use only roles (`bg-primary`), so dark mode is just a second set of role values, and a new brand color changes one line.
- **How a role reaches a class.** In Szop's `index.css` a role is a CSS variable on the page's root, `--primary: var(--color-sage-700)`, with a second value under `:root.dark`, the page's root carrying the class `dark`. Tailwind's `@theme inline` block then declares `--color-primary: var(--primary)`, which is what makes the class `bg-primary` exist; because the class reads the variable rather than a fixed color, it changes the moment the class does. The palette's colors are written in **OKLCH**, a color space built so that equal steps look equally different to the eye; the browser converts them to the screen's colors. The page `/design` shows every role as it is now.
- **Who sets the class, and when.** The user picks System, Light or Dark in the menu, kept in `localStorage`. The choice must be on the page before the browser paints it, or the page flashes light before turning dark, and the app's JavaScript bundle arrives too late for that. So a few lines in `public/color-scheme.js` run first, from a `<script src>` at the top of `<head>`: a classic script, which the browser runs before going on, unlike the bundle, a module script, which runs after the page is parsed. They cannot sit inline in `index.html`, because the CSP refuses inline scripts; a file from Szop's own origin is allowed. Files in Vite's `public/` folder are served as they are, without a hash in the name. After that, `src/shell/color-scheme.ts` does the same job in the app and, while the choice is System, listens to the `prefers-color-scheme` media query and switches the class when the system does.
- **Copied code, checked like ours.** `shadcn init` and `shadcn add` write files into the project and may change `index.css` and `package.json`; everything they write is read and trimmed to what Szop uses before it is committed ([shadcn/ui](../development/tools/shadcn-ui.md)). Base UI's `CSPProvider` tells its components not to render `<style>` elements, and the little CSS they would have needed is in the stylesheet.

## 15. How fast is fast enough

"Fast" becomes testable once it is a number. Szop's numbers are [NFR-3](../requirements/functional-requirements.md#nfr-3); this section explains them.

- **Core Web Vitals** are Google's three measures of how a page *feels*: **LCP** (Largest Contentful Paint, when the main content appears), **INP** (Interaction to Next Paint, how fast a tap gets a visible response) and **CLS** (Cumulative Layout Shift, how much content jumps around while loading). Each has a "good" threshold.
- **Lighthouse**, built into Chrome's DevTools, loads a page while simulating a mid-range phone on a slow 4G connection and reports these numbers. Its results vary a little from run to run, so Szop runs it by hand during the demo check rather than as a CI gate.
- **A performance budget** stops slowness creeping in. The JavaScript needed for the first screen is the main *cause* of a slow start on a phone, and its size is the same on every build, so CI fails a PR that pushes it over 200 KB compressed. A library that would quietly double it is caught in review, not by a user. The check is a small plugin in the Vite build: it starts from the entry chunk, follows the chunks it imports statically (chunks loaded later with `import()` do not count), compresses them with Brotli and adds up the sizes, so every `pnpm build` prints the number and fails above the limit, locally and in CI's `build` job ([ADR 0023](../decisions/0023-production-build-and-serving-details.md), decision 4).
- **Compression and caching do the rest.** The build writes Brotli and gzip copies of every text file, and the server sends the smallest the browser accepts. Vite puts a hash of each file's content in its name (`index-3f9a1c.js`), so such files can be cached for a year: a changed file gets a new name. Only `index.html`, which names them, is `no-cache`: the browser keeps it but checks it with its ETag on every load.
- **Precompression** means compressing once, at build time, instead of on every request. Since it happens once, the build can afford the strongest and slowest settings (Brotli quality 11, gzip level 9), which a server compressing per request could not. The browser lists what it can decode in the `Accept-Encoding` header (`gzip, deflate, br, zstd` in Chrome), and the server picks the `.br` copy, the `.gz` copy or the plain file accordingly, adding `Vary: Accept-Encoding` so caches keep the variants apart ([ADR 0023](../decisions/0023-production-build-and-serving-details.md), decision 3).
- **`immutable` versus `no-cache`.** A fingerprinted file (one with a content hash in its name) can never change under the same name, so it is sent with `Cache-Control: public, max-age=31536000, immutable`: the browser keeps it for a year and never asks again. `index.html` cannot be fingerprinted, since its address is the app's address, so it is sent with `no-cache`, which, despite the name, lets the browser keep a copy but makes it ask the server before every use. The question is cheap: the browser sends back the copy's ETag, a version tag, and the server answers `304 Not Modified` with no body while it is current. A deploy therefore reaches the next page load at once, while the large files come from the browser's cache ([ADR 0023](../decisions/0023-production-build-and-serving-details.md), decision 5).

## 16. CI/CD: checking every change

**Continuous integration (CI)** means every change is built and checked automatically, as soon as it is proposed, so a broken change is found within minutes rather than after it is merged. **Continuous delivery (CD)** goes one step further: every change that passes the checks can be released or deployed at the push of a button. Szop runs CI in GitHub Actions today; CD arrives with [PH-12b](../roadmap.md#ph-12b-network-and-the-demo-up-button), after [PH-11](../roadmap.md#ph-11-ci-access-to-aws-and-the-teardown-safety-net) gave CI its access to AWS and the nightly teardown. The decisions are in [ADR 0010](../decisions/0010-ci-cd.md) and [ADR 0018](../decisions/0018-ci-details.md); the day-to-day guide is [CI/CD](../development/ci-cd.md). This section explains the concepts.

- **A pipeline of workflows, jobs and steps.** A **workflow** is a YAML file started by an event, such as a pull request. It holds **jobs**, which run side by side unless one waits for another, and each job is a list of **steps**: shell commands or ready-made **actions**. Every job runs on a **runner**, a fresh virtual machine that is thrown away afterwards, so no job can leave anything behind for the next one.
- **CI tests the merge, not the branch.** For a pull request, GitHub prepares a test merge of the branch into the current `main`, the **merge ref**, and the checks run on that. A branch that passes on its own can still break `main` when combined with someone else's newly merged change. That is also why a branch must be **up to date** with `main` before merging: once `main` moves, the tested merge is out of date, and the checks run again on a new one after *Update branch* (or a new push to the branch).
- **Required status checks** are the checks GitHub insists on before the merge button works. A workflow that does not start never reports, so a required check on it would wait forever; Szop's checks workflow therefore always runs, and skips the jobs a change does not need, such as the code checks on a docs-only PR. A skipped job counts as passed, so Szop requires one job, `ci-ok`, that always runs, sums up the others, and fails when the job deciding what to skip has itself failed.
- **Supply-chain security.** An action is someone else's code running inside your pipeline, with your token. Szop limits what a compromised or careless action could do:
  - **Actions are pinned to commit SHAs,** not version tags. A tag can be moved to other code; a commit cannot. In March 2025, attackers moved the version tags of the popular `tj-actions/changed-files` action to code that printed workflows' secrets into their logs. Projects that had pinned it to a SHA kept running the old, safe code.
  - **Tokens are read-only.** Each job gets only the permissions it needs, here only reading the repository.
  - **Untrusted text never reaches a shell through `${{ }}`.** GitHub pastes a `${{ … }}` value into a script before the shell runs it, so a PR title containing shell code would run as code (**template injection**). Such values go through environment variables instead, which the shell treats as plain text.
  - **Tools look for these mistakes:** zizmor checks every workflow change, and CodeQL scans the workflows and the code. Trivy scans the infrastructure code and the image ([section 22](#22-scanning-for-vulnerabilities-and-misconfigurations)).
- **Dependabot keeps the pins and packages current.** Every Monday it proposes updates, with a **cooldown**: a new version is proposed only once it is a week old, since malicious releases are usually found and removed within days.

How a workflow reaches AWS without stored keys (OpenID Connect (OIDC), IAM roles, GitHub environments) is explained in [How CI gets into AWS](#how-ci-gets-into-aws); what uses it is `ci.yml`'s `plan` job, `demo-down` and, from [PH-12b](../roadmap.md#ph-12b-network-and-the-demo-up-button), the real `demo-up`.

## 17. The single-page application: React, React Router and TanStack Query

[PH-05](../roadmap.md#ph-05-spa-skeleton) built the first page of the single-page application (SPA): it asks the API how it is and shows the answer. The decisions are in [ADR 0021](../decisions/0021-spa-skeleton-details.md); this section explains the concepts the page uses, with the page's own code as the example.

- **React: components, hooks and rendering.** A **component** is a function that returns a description of a piece of the screen, written in JSX (HTML-like syntax inside TypeScript). `ApiStatus`, at the bottom of the menu, is one: it returns a `role="status"` element with the API's state. **Rendering** means React calling the function and turning what it returns into the browser's elements; when the data a component depends on changes, React calls it again and updates only what differs. A **hook** is a function whose name starts with `use` that a component calls to attach something to itself, such as `useState` for its own state. `useHealth` is a hook of Szop's own that wraps another hook. Hooks may only be called at the top level of a component, never inside an `if`, which is the rule the ESLint React Hooks plugin enforces.
- **React Router: the data router.** React Router maps the address to the component to show. Szop uses its **data router**: the routes are one array, `routes` in `routes.tsx`, given to `createBrowserRouter` in the app and to `createMemoryRouter` in the tests, so tests run the real route table. The data router lets a route have a `loader`, a function that fetches data before the page renders. Szop leaves that unused: TanStack Query fetches data, and having two owners of it would blur the line drawn in [section 7](#7-kinds-of-state-in-a-frontend). Only `/` and `/design` exist, so any other path shows the router's default error screen for now.
- **Layout routes and `<Outlet />`.** A route can wrap others: Szop's route table has one route without a path, `AppShell`, whose children are the pages (`/` and `/design`). React Router renders the parent and, where the parent puts `<Outlet />`, the child that matches the address, so the header, the menu and the sidebar are written once and every page sits inside them ([PH-14b](../roadmap.md#ph-14b-app-shell)). A route can also carry a `handle`, any value the app wants; Szop's pages put their title there, and the shell reads it with `useMatches()` to show the `h1` and set the tab's title.
- **TanStack Query: queries, keys, caching.** A **query** is a function that fetches server data, which the library runs, caches and tracks as pending, success or error. `useHealth` calls `useQuery` with the function `getHealth` and the **query key** `["health"]`, the name the answer is cached under: two components asking with the same key share one request and one answer, and `queryClient.refetchQueries({ queryKey: ["health"] })` refreshes it by name. A cached answer is shown at once and refreshed in the background, and by default the library fetches again when the tab becomes visible again (TanStack Query listens for the browser's `visibilitychange` event), so returning to the tab refreshes the status. Failed queries are retried three times with growing delays by default, about seven seconds in all; the health query sets `retry: false`, because its whole job is to show a failure, which seven seconds of "Checking the API…" would hide.
- **One origin in development, through a proxy.** `pnpm dev` starts Vite's server, which serves the page, and the API on port 3000. The browser only ever talks to Vite (`http://localhost:5173`). A request for a path starting with `/api` is **proxied**: Vite forwards it to `http://127.0.0.1:3000` and passes the answer back. The browser therefore sees one origin, as in production, and needs no CORS setup. With the API stopped, the proxy itself answers `502` with an empty body, which the client treats as an error.
- **Mock Service Worker (MSW), in one paragraph.** In tests there is no API, so MSW fakes the network: a **handler** such as `http.get("/api/health", …)` says what an address answers, and the request goes out from the real client code and is caught on the way. Nothing in the app is replaced, so the real `getHealth`, hook and schema run; only the answer is made up. A test that needs another state adds a handler for that test with `server.use`. A request with no handler fails the test, naming the request: the setup file records it in a callback that rejects it, and checks the record after each test, because MSW 3's built-in `"error"` strategy would reject the request but leave the test green.
- **The path of one request.** The menu renders `ApiStatus`, which calls `useHealth`. TanStack Query runs `getHealth`, which calls `fetch("/api/health")`. The browser sends it to Vite, whose proxy forwards it to Fastify at `127.0.0.1:3000`. The health route runs one query against PostgreSQL to read the schema version. It answers `200` with the version, or `503` when the query fails, and the body travels back the same way. `getHealth` parses the body with `healthSchema`, TanStack Query caches it under `["health"]`, and React renders the new text: "API: ok", or "API: reachable" with "Database: down". When the request itself fails, the text is "Can't reach the API".

## 18. Tracking the work: issues, milestones and projects

Most teams plan on the same site that holds their code. On GitHub that means three pieces, which Szop uses next to its roadmap ([ADR 0024](../decisions/0024-github-project-tracking.md); the day-to-day guide is [project tracking](../development/project-tracking.md)):

- **An issue** is one piece of work with a number, a title, a body, labels and a state, open or closed. Closing records why: *completed* or *not planned*. A pull request whose description says `Closes #12` closes issue 12 when it is merged, which ties the work to the change that did it.
- **Issues relate to each other.** A **sub-issue** sits under a parent, which shows how many of its children are closed; an issue can be **blocked by** another; and any mention of `#12` leaves a note on issue 12. Szop puts each open point under the phase that settles it, and lets a spike block its phase.
- **A milestone** groups issues towards one goal and shows a progress bar. Szop's milestones are its roadmap stages, plus `Definition` for the decision work before the first phase.
- **A project** collects issues into one table with custom fields, such as a status or a position, and shows them as **views**: a table, a **board** of columns (a kanban board, from the Japanese for "signboard", where cards move from column to column as work progresses) or a **roadmap**, a timeline drawn from date fields. Built-in **workflows** update the fields on events, such as setting the status to done when an issue closes.

## 19. End-to-end tests with Playwright and axe

[PH-07](../roadmap.md#ph-07-first-e2e-journey) added the top layer of the tests. The decisions are in [ADR 0007](../decisions/0007-testing-strategy.md), [ADR 0013](../decisions/0013-visual-design.md) and [ADR 0026](../decisions/0026-first-e2e-journey-details.md); the guide for writing them is the [testing guide](../development/testing.md#writing-an-e2e-journey) and the tool is [Playwright](../development/tools/playwright.md). This section explains the concepts.

- **What an end-to-end (E2E) test is, and where it sits.** The **testing trophy** (see the [glossary](../glossary.md)) puts most tests in the middle, where real components work together, with a few at the top that use the finished app as a person does. An E2E test is one of those: a real browser opens the production build, the build calls the real API, and the API reads the real PostgreSQL. It is the only test that fails when the pieces are each right but disagree: a header the browser refuses, a build that lacks a file. It is also the slowest and the most easily broken, which is why Szop writes one journey per use case and leaves edge cases to the lower layers.
- **How Playwright drives a browser.** Playwright starts the browser as a separate program and sends it commands over a connection, using a protocol the browser understands: *open this address*, *find the element with this role*, *click it*, *tell me its text*. The test code never runs inside the page; it runs in Node and talks to the browser from outside. Because a page appears asynchronously, Playwright's checks (`expect(locator)`) wait and retry until the condition holds or a timeout passes, which is what makes the tests stable without sleeps. Each test gets a fresh **browser context**: like a new private window, with no cookies, storage or sessions from any other test. It is created in milliseconds, so tests run in parallel without sharing state, and every test starts as a first-time guest.
- **Projects and device emulation.** A Playwright **project** is a browser setup every test runs under. Szop has three: desktop Chromium, desktop Firefox and a phone. The phone is *emulated*: Playwright runs Chromium with the Pixel 7's screen size, pixel density, touch input and mobile user-agent string. That tests the layout and the touch behavior of a phone, but not Android itself or its keyboard. Firefox is there because it is the only supported browser with an engine of its own, so the promise that Szop works in it is backed by a test.
- **What axe checks, and what it cannot.** axe takes the rendered page and applies a library of rules, each from the Web Content Accessibility Guidelines (WCAG): every image has a text alternative, every form field a label, the language of the page is set, the headings are in order, text has enough contrast against its background. Contrast needs a real browser, which is part of why this runs in E2E tests and not in the jsdom component tests, which have no layout or colors. Szop runs axe on every page, once in light mode and once in dark: the helper tells the browser to prefer each scheme (`prefers-color-scheme`), which Szop's dark mode follows. But automated checks find only about a third to a half of accessibility problems. They cannot tell whether a text alternative says something useful, whether the tab key moves through the page in a sensible order, or whether a screen reader announces a change. Keyboard and screen-reader use still need people; a passing axe run is a floor.
- **How the CSP guard listens.** When a page tries to do something its Content Security Policy forbids ([section 13](#13-web-security-in-the-browser)), the browser blocks it and also fires a standard event, `securitypolicyviolation`, on the page. The guard adds a small script to every page of the test that listens for that event and sends each one back to the test, which fails if it received any. The guard has caught a real case already: zod, the schema library ([section 8](#8-the-shared-package-and-zod)), tested whether `eval` works by calling `new Function("")`, which the policy, with no `'unsafe-eval'`, blocks and reports. Nothing was visibly wrong with the page, but the policy was broken on every load. Zod has a mode that skips the test (*jitless*, which also skips its compiled fast path), and the web app switches it on before any schema is built.

## 20. Container images

[PH-08](../roadmap.md#ph-08-container-image) packed the app into a container image, the thing AWS's container service will run. The decisions are in [ADR 0008](../decisions/0008-hosting.md), decision 12, and [ADR 0028](../decisions/0028-container-image-details.md); the tool is [Docker](../development/tools/docker.md). This section explains the concepts.

- **What an image and a container are.** An **image** is a read-only package of files: a slimmed-down Linux, Node, the app's code and its libraries, plus a little metadata (which command to run, as which user, with which environment variables). A **container** is that image running: a process on the host's Linux kernel that sees only the image's files and its own network and process list. It is not a virtual machine; nothing boots, so it starts in a moment. The same image runs the same way on the owner's machine, in CI and on AWS, which is the whole point: "it works on my machine" is replaced by "it works in this image".
- **Layers and the build cache.** A Dockerfile is a list of steps, and each step that changes files adds a **layer** on top of the previous ones. Docker caches each layer under the step and its inputs, and reuses it as long as neither changed; once a step's input changes, that step and every step after it run again. That is why Szop's Dockerfile copies the `package.json` files and the lockfile first and installs the dependencies, and only then copies the source code: a change to the code reuses the installed dependencies, and only a change to the dependencies installs them again.
- **Multi-stage builds.** Building needs far more than running: pnpm, the development dependencies, Vite, the web app's source. A **multi-stage** Dockerfile runs several images in a row; the earlier ones build, and the last one copies in only what the app needs at run time. The final image never contains the compiler, the build tools or the source of the web app, so it is smaller and carries fewer libraries an attacker could misuse.
- **Why not root.** By default a container's process runs as `root`. The container's walls make that less dangerous than root on the host, but not harmless: a flaw in the app would then let an attacker change any file in the container, install tools, or, combined with a flaw in the container runtime, reach further. Szop's image runs as the `node` user, and the code belongs to root, so the running app cannot even change its own files. On top of that, Compose and CI run the container with a **read-only root filesystem**: nothing in it can be written at all, which proves the app keeps no state on disk (its logs go to standard output, which Docker collects). On ECS the root filesystem is writable instead, because ECS Exec's agent writes into the container; the files still belong to root, so the app still cannot change its code.
- **Tags and digests.** An image is named like `node:24-trixie-slim`: a repository and a **tag**. A tag is a label the publisher can move to a newer image at any time, which is how security fixes reach you, and also how a build can silently change. A **digest** (`sha256:173f…`) is a hash of the image's content: it names exactly one image, forever. Szop writes both, `node:24-trixie-slim@sha256:…`: the tag tells a reader what it is, the digest guarantees which one, and Dependabot proposes a new digest as a pull request when the tag moves, so every change is reviewed and tested.
- **Build arguments and environment variables.** A **build argument** (`ARG`) is a value handed to `docker build` that exists only while the image is built; an **environment variable** (`ENV`) is stored in the image and is there every time a container runs. Szop's Dockerfile turns one into the other: `ARG GIT_COMMIT=unknown` and `ENV GIT_COMMIT=$GIT_COMMIT`, so the commit the image was built from travels inside it, and `/api/health` reports it on ECS, in CI or on a laptop, wherever the image runs. The lines come after the `COPY` steps, since a changed argument invalidates the cache from the step that uses it on: placed late, it invalidates no earlier layer, and the dependencies are not installed again for every commit. Without the argument (`pnpm dev`, the tests, a plain `docker build`) the value is `unknown`.
- **PID 1 and signals.** Inside a container, the first process gets process identifier (PID) 1, the role an init system plays on a normal machine. When AWS stops a task, it sends that process `SIGTERM`, waits, and then kills it. Szop's API is PID 1 itself and handles `SIGTERM`: it stops accepting requests, finishes the ones in flight and closes the database pool before it exits. An extra init process (`tini`) is only needed when the app starts child processes, which Szop's does not.


## 21. Running several instances

A single copy of an app is simple: whatever it keeps in memory is the whole truth. Running several copies behind a load balancer, which Szop does since PH-37 with two tasks ([ADR 0036](../decisions/0036-scalability-and-isolation.md), [ADR 0040](../decisions/0040-two-tasks-details.md)), is how services survive a crashed process and grow with their load, but every shortcut that relied on being alone has to be replaced. The concepts, in the order they bite:

- **Scaling up and scaling out.** Up means a bigger machine; out means more copies of the same one. Out is what a load balancer and ECS make easy, and what this section is about. The database usually scales up, since it is the one place the copies share.
- **Stateless processes.** A copy that keeps nothing another copy needs can be started, stopped or replaced at any time, and any copy can answer any request. Szop's sessions are in PostgreSQL for this reason: the load balancer sends a user's requests to any task.
- **Shared state lives outside the process.** What must be counted or seen by all copies goes to a store they share: the rate-limit counters and the event bus to Redis, everything else to PostgreSQL. Memory is per copy: two copies counting a limit in memory each allow the full limit, so together they allow twice as much.
- **Locks across processes.** "Only one of us at a time" needs a lock both copies can see. A PostgreSQL **advisory lock** is one: a lock on a number the application picks, which means nothing to PostgreSQL itself, held by a session until it releases it or ends. The copy that holds Szop's migration lock checks and migrates the database while the others wait, then find nothing pending; the cleanup job's try-lock will let one copy clean up while the others skip the round. Without the lock, two copies starting together each run a pending migration, and a data migration runs twice: Szop's test of two migrators shows exactly that against a lock that does nothing. The lock lives on a connection checked out of the pool, so it must be released before the connection goes back, or the next user of that connection would hold it unknowingly.
- **Fan-out.** A change handled by one copy must reach browsers connected to another. Each copy subscribes to a shared channel (Redis publish/subscribe) and forwards what it hears to its own WebSocket clients.
- **Rolling deploys and two versions at once.** ECS starts the new copies, waits until they are healthy, then drains and stops the old ones, so the app stays up. Two numbers on the service set the pace: the **minimum healthy percent** (100: never fewer healthy copies than wanted) and the **maximum percent** (200: up to twice the wanted count may run during the deploy). With 100 and 200, ECS has to start a new copy before it may stop an old one. For that minute, old and new code run on the same database, so a migration may only add what the new code needs and remove what the old code used in a later release: **expand, then contract** ([the rule](../development/tools/drizzle.md#migrations-and-rolling-deploys)). The browser sees two versions as well: while both copies are healthy, the load balancer sends each request on its own, so a page load can get `index.html` from the new copy and ask the old one for an asset only the new build has. Szop accepts that gap, since a reload fixes it ([OP-103](https://github.com/luiki-dev/szop/issues/249); [ADR 0040](../decisions/0040-two-tasks-details.md), decision 1); a public service would keep the previous release's assets reachable or pin a browser to one version. Szop proves a redeploy with a script that asks `/api/health` every second while `demo-up` runs ([runbook](../operations/demo-environment.md#watching-a-redeploy)).
- **The deployment circuit breaker.** A rolling deploy whose new copies never become healthy would otherwise retry for ever, starting copy after copy. The **deployment circuit breaker** counts the failures, copies that fail to start or fail their health checks, and at a threshold marks the deployment `FAILED` and launches no more copies. Szop uses ECS's default threshold, three failures in a row for one wanted copy. It can also **roll back**, return to the previous task definition; Szop leaves that off, because the old code may not work on a database the new version has already migrated, so the fix goes forward as a new deploy. Either way the old copy keeps serving, since it was never stopped.
- **Liveness and readiness.** Liveness asks "is this process alive?", and a dead one is replaced. Readiness asks "can it do its work right now?", the database included. Replacing live copies because the database is down only adds churn, so Szop's load balancer checks liveness (`/api/live`, which touches only the process) and `/api/health` reports readiness for people, the watch script and `demo-up`. The liveness route answers only once the server listens, which is after the migrations, so a new copy is never healthy before it has migrated. A **grace period** (60 seconds) makes ECS ignore the load balancer's verdict while a copy starts, so a slow image pull or a long migration does not get it killed; a process that crashes is replaced at once regardless. ECS also counts a new copy healthy only once the grace period has passed, so it sets how long two versions serve side by side during a deploy.
- **Draining.** Before ECS stops a copy, the load balancer stops sending it new requests and lets open ones finish. The **deregistration delay** is how long it waits, 300 seconds by default and 30 in Szop; ECS then sends `SIGTERM` ([container images](#20-container-images)). AWS ends the wait early: a target with no in-flight requests and no active connections is deregistered at once, so the delay is a limit, not a pause. Requests last milliseconds; a WebSocket lasts until its copy stops, so the browser reconnects to another copy and refetches what it may have missed.
- **Connections are the database's scarcest resource.** Every copy opens a pool; copies times pool size, doubled during a deploy, must stay under the database's `max_connections`. Szop keeps pools at 5 and counts the worst case: two tasks doubled is 20 connections, four doubled 40, and each app logs `max_connections` at startup so the budget can be checked against the real number.
- **Autoscaling.** ECS Service Auto Scaling adds copies when a metric (average CPU, say) stays above its target and removes them when it falls, within a minimum and a maximum: **target tracking**. Scaling in is the harder half, since it stops copies that are serving.
- **Testing for it.** Two copies inside one test process share their module-level state and hide exactly these bugs. Szop tests what goes through a shared store in one process (two migrators on one database, for instance), and runs two real containers behind nginx for the rest: `pnpm check:scale` starts them on a fresh database, checks that requests reach both and that each migration is recorded once. Each process names itself with a random **instance ID** in `/api/health`, which is how the check, and the watch script on the demo, see which copy answered. **Request IDs** must be unique across copies too, so each request gets a random UUID; a counter per process would give two copies the same `req-1`.

## 22. Scanning for vulnerabilities and misconfigurations

Tests show that the code does what it should; scanners look for what is known to go wrong, in the code Szop did not write and in the settings it chose. [PH-35](../roadmap.md#ph-35-security-scanners) added two kinds, both run by one tool, [Trivy](../development/tools/trivy.md), on every pull request that changes code ([ADR 0041](../decisions/0041-security-scanners-details.md); the guide is [CI/CD](../development/ci-cd.md#the-security-scans-and-the-pr-comment)). This section explains the concepts.

- **Known vulnerabilities.** When someone finds a security flaw in a published package, it gets an entry in a public catalog, Common Vulnerabilities and Exposures (CVE), with an ID such as `CVE-2026-33634`, the affected versions and, once one exists, the version that fixes it. An **image scanner** lists every package in the image (the operating system's, from Debian, and the language's, from the Node packages) and looks each one up in a database built from those catalogs. Its answer is only as fresh as the database, which is why Trivy downloads it on every run, and why the same image can be clean today and flagged tomorrow.
- **Severity.** Each vulnerability carries a rating, `CRITICAL`, `HIGH`, `MEDIUM` or `LOW` (or `UNKNOWN` before anyone has rated it), from how easily it is exploited and what it gives an attacker. The rating is about the flaw in general, not about Szop: a `HIGH` in a library the app never calls matters less than a `MEDIUM` in its web server.
- **Fixed and unfixed.** A vulnerability with a fixed version can be closed by updating; one without cannot, yet. Blocking only what can be fixed keeps a pull request from turning red for a flaw nobody can do anything about. For the operating system's packages there is a third case: Debian has shipped the fix, but the official `node` image has not been rebuilt with it, so Szop waits for the new base image, which Dependabot proposes.
- **Misconfiguration scanning.** The same idea, applied to settings instead of versions: a **misconfiguration scanner** reads the Terraform code and the Dockerfile and compares them with a library of rules, such as "a security group should not admit the whole internet" or "a bucket should be encrypted with a key you manage". It reads the code, not the live account, so it runs before anything is applied. **IAM Access Analyzer** does the same for policies, with AWS's own rules ([How CI gets into AWS](#how-ci-gets-into-aws)).
- **Thresholds and exceptions.** A scanner that blocks on everything gets switched off; one that blocks on nothing gets ignored. So a threshold decides what blocks (`CRITICAL` and `HIGH`), and everything below is listed. A rule that does not fit a deliberate choice, such as the demo's public load balancer, gets an **exception**: a comment in the code that names the rule and says why, so the reason is reviewed with the code; the scanner drops the finding, and Szop's scan script lists the exception as accepted.
- **Fewer packages, fewer findings.** Every package in the image is something to scan, update and, if flawed, exploit. Removing what the app never runs is the cheapest fix: dropping npm from the final image removed every fixable finding at once.
- **The scanner is a supply-chain risk too.** A scanner reads everything and runs with the job's rights, which makes it a target: in March 2026, attackers published a malicious Trivy release and moved the tags of its GitHub Actions to code that stole credentials. Szop runs a pinned, checksum-checked binary at least two weeks old, in jobs that hold nothing worth stealing.

## 23. Releases: versions, release PRs and tags

A **release** gives a state of the code a name that people can talk about, `v0.1.0`, and a list of what changed since the last one. Szop's releases are cut by release-please from [PH-13](../roadmap.md#ph-13-releases) on; the decisions are in [ADR 0009](../decisions/0009-git-workflow.md), decision 11 and [ADR 0042](../decisions/0042-releases-details.md), the tool in [release-please](../development/tools/release-please.md).

- **Semantic Versioning (SemVer).** A version is `MAJOR.MINOR.PATCH`: a bug fix raises PATCH, a new feature MINOR, a change that breaks what worked MAJOR. Before `1.0.0` the rules are looser, since nothing is promised yet; Szop raises only MINOR for a breaking change while it is in `0.x`, and declares `1.0.0` when the MVP is done.
- **Versions from commit messages.** Because every commit follows Conventional Commits, a tool can read the history and tell which kind of change happened since the last version: a `feat` means at least MINOR, a `fix` at least PATCH. The highest wins.
- **A release PR instead of a release on every merge.** release-please keeps one open pull request that would raise the version and add the release's notes to `CHANGELOG.md`, and updates it as more work is merged. Nothing is released until someone merges it: the bookkeeping is automatic, the moment is a human choice. Tools such as semantic-release release on every merge instead, which suits libraries more than an app.
- **Tags and GitHub Releases.** Merging the release PR puts a **git tag**, `v0.1.0`, on its commit: a name for that commit that a ruleset keeps from ever moving. A **GitHub Release** is the page for that tag, with its notes. Szop's container image of the same commit gets the version as a second tag, `szop:0.1.0`, so the code and the image share one name.
- **Release notes per pull request.** The notes can list commits or pull requests. Szop merges with merge commits, so every task commit of a phase reaches `main`; listing commits would show each phase several times. Its notes list pull requests, one line each, as GitHub generates them.
- **A bot with its own identity.** The release PR is opened by a GitHub App, `szop-release`, rather than by the workflow's own token, because GitHub does not run other workflows for changes made with that token, and the release PR needs its checks. An App is a separate identity with exactly the permissions it was given, and its token lasts an hour.
