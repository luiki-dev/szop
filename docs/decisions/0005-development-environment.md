# ADR 0005 — Development environment and tooling

- **Status:** ✅ Accepted — extended by [ADR 0008](0008-hosting.md) (production PostgreSQL version and images; Terraform and AWS CLI added to the tooling); completed by [ADR 0007](0007-testing-strategy.md) (the test tooling), [ADR 0009](0009-git-workflow.md) (commitlint) and [ADR 0010](0010-ci-cd.md) (type checks and tests run in CI); decisions 12 and 14 extended by [ADR 0013](0013-visual-design.md) (the Tailwind Prettier plugin and editor extension); its consequences refined by [ADR 0014](0014-roadmap.md), decision 7 (`compose.yaml` and the `.env` files arrive with the database, PH-04); decision 12 refined by [ADR 0016](0016-toolchain-details.md) (Markdown left out of Prettier)
- **Date:** 2026-09-27

## Context

The development environment is the first foundation topic of [ADR 0004](0004-implementation-process.md). As that ADR says, it settles direction and constraints only. The detailed configuration is written, and tried out, in the development environment setup phase of the roadmap.

The starting point:

- **One developer**, working on one Windows machine in **WSL 2** (Windows Subsystem for Linux) with Ubuntu, and editing in VS Code.
- **Node.js** is already managed with nvm. **Docker Desktop** is installed on Windows, with WSL integration enabled.
- The repository holds only documentation. The architecture ([ADR 0002](0002-technical-architecture.md)) fixes a TypeScript monorepo (`apps/web`, `apps/api`, `packages/shared`), a React SPA built by Vite, a Fastify API, PostgreSQL, and one origin for the SPA and the API.

The owner wants an environment with few moving parts while the stack itself is new. The owner also wants the whole setup documented step by step, with every configuration file explained, so the environment can be rebuilt from scratch and so the setup is a learning resource of its own.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|-------|--------------------|------------------------|
| 1 | Where things run | Everything installed directly in WSL; tools in WSL and services in containers; everything in a dev container | **Tools directly in WSL, services in containers.** Node and the tooling run in WSL; PostgreSQL runs in Docker. This is the most common setup and gives the fastest feedback loop. A dev container makes the environment reproducible on any machine, but adds a layer to understand and debug, and pays off mainly for teams. Installing PostgreSQL directly in Ubuntu makes pinning and switching versions awkward and keeps a server running when nobody is working on Szop. |
| 2 | Container runtime | Docker Desktop with WSL integration; Docker Engine installed in Ubuntu | **Docker Desktop with WSL integration.** Already installed and integrated; its graphical view of containers, volumes and logs helps while learning. Its licence is free for personal use. Docker Engine inside Ubuntu is lighter and is what servers run, but has no graphical view and needs manual setup. |
| 3 | Node.js version | nvm; fnm; Volta; mise | **nvm**, with the current long-term-support (LTS) line (Node 24) pinned in `.nvmrc` and in the `engines` field of `package.json`. nvm is the best known and already installed. The alternatives are faster or manage several tools at once, which gains little here. |
| 4 | Local PostgreSQL | Docker Compose; a direct install in Ubuntu | **Docker Compose** (`compose.yaml` at the repository root): one PostgreSQL service with its major version pinned to match production, data in a named volume, listening on `localhost:5432`. `psql` runs inside the container (`docker compose exec`), so no PostgreSQL client is installed in WSL. Where test databases come from is part of the testing strategy topic. |
| 5 | Package manager | npm; pnpm; Yarn | **pnpm**, its version pinned in the `packageManager` field of the root `package.json`. It is strict: a package can import only the dependencies it declares, so code cannot rely by accident on a **phantom dependency** that happens to be installed. It is fast, saves disk space and has first-class workspaces. It is the most common choice for TypeScript monorepos. npm needs no installation and its workspaces are adequate, but it is looser. |
| 6 | Monorepo task running | pnpm workspaces alone; Turborepo; Nx | **pnpm workspaces alone** (`pnpm -r <script>`, `pnpm --filter <package> <script>`). Turborepo and Nx add caching and dependency-aware task ordering, which pays off in large repositories with slow builds. Three packages do not need it. One can be added if builds become slow. |
| 7 | Module system and TypeScript settings | ES modules (ESM); CommonJS | **ESM everywhere, strict TypeScript, one shared base config** that every package extends. ESM is the JavaScript standard and what Vite and current libraries expect. CommonJS is the older Node-only format. |
| 8 | How `packages/shared` is consumed | From source; compiled first, with TypeScript project references | **From source.** Its `package.json` points at `.ts` files. Vite compiles it for the browser and the API's dev runner compiles it on the fly: no build step and no stale builds. Compiling first suits libraries published on their own, but adds a watch step and "did I rebuild?" confusion. Consequence: the production build of the API must include `shared`. How it does that is decided in the setup phase. |
| 9 | Running the API in development | tsx in watch mode; Node's built-in type stripping; compile with `tsc`, then run | **tsx in watch mode.** It restarts the API on every change. Node 24 can run TypeScript itself by stripping the types, but it rejects some TypeScript syntax and has rough edges with path resolution and workspace packages. Compiling before every run is slow. Neither tsx nor Node checks types; that is a separate `tsc --noEmit` script. |
| 10 | Same origin in development | Vite dev server proxying the API; SPA and API on two ports with CORS | **Vite proxies `/api/*`** (and the WebSocket later) to Fastify. `pnpm dev` starts both, and the browser opens only the Vite server, so development matches production: first-party cookies and no CORS setup. Two origins would need CORS and cross-site cookie settings that production does not use. |
| 11 | Local configuration | `.env` files loaded by Node; the `dotenv` package | **`apps/api/.env` loaded with Node's built-in `--env-file`**, validated by the Zod schema already decided in `architecture.md`. The `.env` file is ignored by git; a committed `.env.example` documents every setting. The SPA needs almost no configuration, and Vite exposes only `VITE_`-prefixed variables to the browser, so secrets cannot leak into the bundle by accident. |
| 12 | Linting and formatting | ESLint with Prettier; Biome | **ESLint and Prettier.** ESLint finds bugs and bad patterns: one flat config at the root with typescript-eslint (including type-aware rules, such as one catching a forgotten `await`) and the React Hooks rules for `apps/web`. Prettier only formats; `eslint-config-prettier` turns off the ESLint rules that would conflict with it. Biome does both in one very fast tool, but has a smaller ecosystem. ESLint and Prettier are what most projects and tutorials use, which fits the learning goal. |
| 13 | Git hooks | husky with lint-staged; lefthook; none (CI only) | **A pre-commit hook with husky and lint-staged** running Prettier and `eslint --fix` on the staged files only. Claude Code edits files outside the editor, so "format on save" never runs on its changes; a hook catches every commit, whoever makes it. Type checks and tests are left out of the hook because they are slow and cover the whole project; they belong to CI. lefthook is faster but less common. Without hooks, problems are caught only after a push. |
| 14 | Editor | VS Code with shared settings; no shared settings | **VS Code, connected to WSL through the WSL extension.** The repository holds `.vscode/extensions.json` (recommended: ESLint, Prettier, Container Tools; test tool extensions come with the testing strategy) and `.vscode/settings.json` (format on save with Prettier, ESLint fixes on save, the workspace's TypeScript version). `.gitattributes` forces LF line endings, so Windows-style CRLF endings cannot slip in from the Windows side. No `.editorconfig`: Prettier already covers it. |
| 15 | Documentation of the environment | One large guide; the README only; step-by-step guide plus one page per tool | **`docs/development/setup.md` holds only the setup steps**, from a clean Windows machine to a running app: WSL and Ubuntu, git, nvm and Node, pnpm, Docker Desktop, VS Code, then clone, install, configure, start the database and run the app. **`docs/development/tools/<tool>.md`** has one page per tool: what it is, why it was chosen, the configuration files it owns explained, the recommended starting point and links to the official documentation. `setup.md` links to the tool pages instead of explaining inline. The tool pages cover development tooling; the runtime stack stays in `stack-overview.md`. |
| 16 | Deliberately left out | — | **A dev container** (decision 1), **a monorepo task runner** (decision 6), **a database GUI** (`psql` and Docker Desktop's view are enough for now), **a local mail catcher** such as Mailpit (the console email sender from `architecture.md` prints emails instead). Each can be added when a real need appears. |

## Consequences

- The development environment setup phase creates the configuration files above together with `setup.md` and the tool pages. From then on they are living docs: every phase that adds or changes a tool or a configuration file updates them as part of the definition of done.
- When `docs/development/` exists, `CLAUDE.md` and the README's documentation list point to it, and the README gets a short "Development" section.
- The PostgreSQL major version is chosen in the setup phase and must match production. The hosting topic confirms it.
- The production build of the API must include `packages/shared` compiled from source (decision 8).
- Later foundation topics build on this environment: the testing strategy chooses test tools and test databases, CI/CD runs the same `pnpm` scripts as developers do, and hosting decides production images.
