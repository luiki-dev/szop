# ADR 0020 — Database details

- **Status:** ✅ Accepted
- **Date:** 2026-10-05
- **Refines:** [ADR 0007](0007-testing-strategy.md), decision 12 (in CI, PostgreSQL comes from `compose.yaml`, not a service container; see decision 6); [ADR 0010](0010-ci-cd.md), decision 7 (PostgreSQL in the test job comes from `compose.yaml`, not a service container; see decision 6)
- **Completes:** [ADR 0005](0005-development-environment.md), decision 4 (the version and the Compose service; see decisions 8 and 9); [ADR 0007](0007-testing-strategy.md), decisions 12 and 13 (how test databases are made and emptied; see decisions 7, 10 and 13); [ADR 0008](0008-hosting.md), decisions 14, 15 and 19, and its consequence on the database settings (see decisions 3, 5, 8 and 11)

## Context

[PH-04](../roadmap.md#ph-04-database) brought the database. [ADR 0005](0005-development-environment.md), [ADR 0007](0007-testing-strategy.md), [ADR 0008](0008-hosting.md) and [ADR 0010](0010-ci-cd.md) set its direction; its brainstorm, the [spec](../superpowers/specs/2026-10-05-PH-04-database-design.md) and a prototype of the whole phase settled the details. Decisions 1 to 12 were taken in the brainstorm; decisions 13 to 15 came from the prototype of the whole phase, made while planning (the plan's findings: concurrent `DROP DATABASE`, the pool's error listener, `.prettierignore` and the coverage exclusion). The listener's log shape in decision 14 was refined during implementation, at the owner's request. Each refines an accepted ADR or fills a detail it left open. [OP-006](../open-points.md#op-006) is answered by decision 8: PostgreSQL 18 is the newest major version on RDS (18.6 its newest minor, on 2026-10-05).

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|-------|--------------------|------------------------|
| 1 | Drizzle's release line | 0.45 (stable, `latest`); 1.0 release candidate | **0.45.3.** It is what tutorials and Better Auth's Drizzle adapter target today. Moving to 1.0 later is a deliberate step, like a major update, which Dependabot proposes and which changes the migrations folder's layout ([OP-076](../open-points.md#op-076)). The release candidate has the future API and format, but would put pre-release software, with documentation still moving, at the base of the project. |
| 2 | Driver | node-postgres (`pg`); postgres.js | **node-postgres**, the most widely used PostgreSQL client for Node and the one Better Auth's documentation shows. Its optional native binding is not installed, so it needs no install script. |
| 3 | Shape of the database settings | Separate variables; `DATABASE_URL` without the password plus `DATABASE_PASSWORD`; one `DATABASE_URL` with the password | **Separate variables:** `DATABASE_HOST`, `DATABASE_PORT`, `DATABASE_NAME`, `DATABASE_USER`, `DATABASE_PASSWORD`. On AWS, Terraform sets the first four as plain values and ECS injects the password from one key of the RDS-managed secret ([ADR 0008](0008-hosting.md), decision 22), so nothing is assembled. The pool takes the fields directly, so no password needs URL escaping (a generated one can hold `@`, `/` or `:`), and the tests swap only the name. A URL is the more familiar style, but would need parsing in the tests, and a URL holding the password would have to be assembled at container start. |
| 4 | The first migration | An empty custom migration; a minimal real object (an extension, a small table); no migration yet | **An empty custom migration, `0000_init`**, holding only a comment saying why it exists. It exercises the whole pipeline (journal, the record of applied migrations, startup, the test template, the version in the health check) without deciding now what a later phase should. A table kept only for tests would be dead schema in production; no migration would leave migrations at startup unproven. |
| 5 | The health route's answer | The latest migration's name, 503 when down; the number of applied migrations; reachability only | **The latest migration's name, read from Drizzle's journal; 503 when the database is down.** The version matches the file names in the repository, and a migration the code does not know shows as `"unknown"`. A count needs no journal, but is off by one against the file names (`0000_…` is version 1); reachability alone drops part of the roadmap's goal. The route is public; the name reveals nothing an attacker can use. |
| 6 | PostgreSQL in CI | `docker compose up --wait` with the same `compose.yaml`; a `services:` container in `ci.yml`; a service container whose image is read from `compose.yaml` | **Compose.** One version pin and one configuration, identical locally and in CI, and Dependabot's `docker-compose` updates reach CI too. A service container needs a second pin that Dependabot does not update (its `github-actions` ecosystem ignores service images), so the two would drift apart silently. `services:` is evaluated before any step, so reading the image from the file would need a preparatory job. Refines [ADR 0010](0010-ci-cd.md), decision 7. |
| 7 | How test databases live and are emptied | Creating: upfront by `globalSetup`; one database per test file; lazily per worker. Emptying: one `TRUNCATE` of a fixed list of tables; one statement that reads the table list on every call; emptying after each test instead of before | **Creating, upfront by `globalSetup`:** the template recreated and migrated, then one copy per worker, once per run. The work happens once and in one place, so nothing races, and tests that do not need the database pay nothing. A database per file costs a `CREATE DATABASE` per file and leaves orphans after a crash; lazy creation runs once per file and races on `CREATE DATABASE`. The databases stay after the run, so they can be inspected. <br>**Emptying, one `DO` block before each test:** it reads every table of the `public` schema from `pg_tables` on each call and runs one `TRUNCATE … RESTART IDENTITY CASCADE` over them. Reading the list each time means it never goes stale when a migration adds a table, which a fixed list would, silently, until someone remembered to extend it. One statement is one round trip. `RESTART IDENTITY` resets the sequences, so generated IDs are predictable from test to test, and `CASCADE` spares the helper the foreign-key order. Running it before each test, not after, means a test starts clean even when the previous one crashed; emptying after would leave a crashed test's rows for the next one. Only `public` is emptied: Drizzle's record of applied migrations lives in the `drizzle` schema and is kept, so the migrated template stays valid. |
| 8 | Keeping PostgreSQL running | `restart: unless-stopped`; the tests start the container; manual | **`restart: unless-stopped`.** After one `docker compose up -d`, the container comes back whenever Docker Desktop starts, until it is stopped by hand. The tests still stop with a clear message when it is not running ([ADR 0007](0007-testing-strategy.md), decision 12). Starting it from the tests would hide the database's lifecycle behind `pnpm test`, which ADR 0007 chose against when it rejected Testcontainers. The image is **PostgreSQL 18.6, Debian-based**, matching RDS's newest major version ([OP-006](../open-points.md#op-006)); Debian so that text sorts with glibc's locales, as on RDS, not with Alpine's musl. The port is bound to `127.0.0.1`, so only this machine can connect. |
| 9 | Credentials in `compose.yaml` | Literals; interpolated from `apps/api/.env` | **Literals** (`szop`), matching `apps/api/.env.example`. They guard a throwaway database reachable only from `127.0.0.1`, and are committed in `.env.example` anyway; real secrets exist only on AWS, where neither file is used. Interpolation would need `--env-file apps/api/.env` on every `docker compose` command (or a second `.env`), a `.env` in CI, and would still not change the password of an existing volume, since the image reads them only when it initialises an empty one. |
| 10 | Where tests get the server's address | `apps/api/.env`; constants in the test code | **`apps/api/.env`**, parsed and validated by the same `loadConfig`; only the database name is replaced. The credentials then live in two committed places side by side, `compose.yaml` and `.env.example`, instead of three. CI copies `.env.example` to `.env`, the same step `setup.md` gives. |
| 11 | An unreachable database at startup, and the health route | Fail fast: log and exit; start anyway and retry the migrations in the background. For the route: one combined `/api/health` that includes the database; a process-only `/api/health` plus a separate readiness route, the earlier direction of [OP-043](../open-points.md#op-043) from [audit MAJOR-9](../audits/2026-09-29-design-sanity-check.md#major-9-the-single-instance-guarantee-doesnt-hold-during-a-redeploy-and-branch-redeploys-can-skip-migrations) | **Fail fast.** On ECS, a stopped task is replaced, with an increasing delay for tasks that keep failing, and during a deployment the circuit breaker marks it failed; once the database is back, the next task starts. Starting anyway gives the same loop, slower and less visible (the load balancer fails the health check, then ECS replaces the task), and needs code for a retry and a "migrations pending" state. On the demo the realistic causes are mistakes (a wrong host or password, a missing security group rule), where a clear log line helps most. That a database blip replaces a running task through the combined health check is acceptable with one instance; separate liveness and readiness checks belong to systems with many ([OP-074](../open-points.md#op-074)). A process-only route plus a readiness route would keep a database blip from replacing the only task, but it is a second route and a second ECS check to build and keep right, for a risk the demo accepts; so the earlier direction is dropped. |
| 12 | Who closes the pool | The code that creates it; `buildApp` on `app.close()` | **The code that creates it:** `server.ts` in production, `useTestDatabase()` in tests. If `buildApp` closed it, tests building a fresh app per test would close the worker's shared pool. |
| 13 | Making the test databases fast | One statement at a time; all statements of a step at once, one connection each | **At once.** Each `DROP DATABASE` waits for a checkpoint; concurrent ones share it, so 16 drops take about 0.1 s instead of 2 s, and copies from one template can run together. `globalSetup` makes `os.availableParallelism()` copies when `maxWorkers` is not set: Vitest 5 computes its default internally and never above the number of CPUs. |
| 14 | An idle connection that drops | Let the process crash; a listener on the pool | **A listener.** node-postgres's pool emits `error` when an idle connection is closed by the server, and Node crashes the process when nothing listens. `createDatabase` always attaches one, and `server.ts` adds one that logs the error's code and message at warn; not the error itself, which carries the whole client (about 200 log lines). The pool discards the connection and opens a new one on the next query, so the API answers 503 while the database is down and recovers by itself. |
| 15 | Generated files and test helpers in the tooling | — | **`apps/api/drizzle/meta/` is in `.prettierignore`**, so drizzle-kit's journal and snapshots stay as it writes them; **`apps/*/src/test/**` is excluded from coverage**, as test infrastructure. |

## Consequences

- **PostgreSQL runs locally and in CI from one file**, `compose.yaml`: `docker compose up -d --wait` starts it, and the `test` job does the same, so the version is pinned once and Dependabot's `docker-compose` updates reach CI too.
- **The API migrates at startup and `/api/health` reports the database:** `pnpm dev` logs `migrations applied` with the schema version; the health route answers 200 with the latest migration's name, and 503 within milliseconds when the container is stopped, then 200 again once it is back, without restarting the API. With the container stopped, `pnpm dev` logs `startup failed` after about 1 s and exits.
- **Every test can use a real database** ([OP-012](../open-points.md#op-012)'s PH-04 part): `globalSetup` takes about 0.6 s on 16 CPUs and a whole `pnpm test` about 2 s. A test file that needs the database calls `useTestDatabase()`; the tables are emptied before each test.
- **PH-06 and PH-08 must keep the migrations where the compiled code finds them:** `migrationsFolder` is resolved as `../../drizzle` from the `migrate` module's own location (`apps/api/src/db/migrate.ts`), not from the working directory, so the compiled module must keep that relative position to `drizzle/`; a bundle into a single `dist/server.js` (esbuild or tsup) would resolve to the wrong folder. `meta/_journal.json` must ship too, because `readJournal()` reads it on every `buildApp`. With the journal missing, `buildApp` throws an uncaught exception, outside `server.ts`'s startup `try`, so it is not logged through pino as `startup failed` ([OP-077](../open-points.md#op-077)).
- **Drizzle 0.45 applies only migrations newer than the latest one recorded**, so a migration whose timestamp is older than one already applied is skipped; [`drizzle.md`](../development/tools/drizzle.md) says to regenerate such a migration on top of `main` before merging.
- **Open points:** [OP-005](../open-points.md#op-005), [OP-006](../open-points.md#op-006) and [OP-011](../open-points.md#op-011) are closed; the PH-04 parts of [OP-012](../open-points.md#op-012), [OP-013](../open-points.md#op-013) and [OP-068](../open-points.md#op-068) are done, and the three move to the phases of their next parts (PH-05, PH-06 and PH-08); [OP-067](../open-points.md#op-067) moves to PH-05, since it does not depend on this phase; [OP-043](../open-points.md#op-043) (safe redeploys) is updated with what this phase settled; [OP-073](../open-points.md#op-073) (the database role on RDS), [OP-074](../open-points.md#op-074) (the ECS health check and the circuit breaker), [OP-075](../open-points.md#op-075) (a CI check that the migrations match the schema), [OP-076](../open-points.md#op-076) (Drizzle 1.0) and [OP-077](../open-points.md#op-077) (the migrations folder in the production build) are new.
