# ADR 0028 — Container image details

- **Status:** ✅ Accepted
- **Date:** 2026-10-12
- **Completes:** [ADR 0008](0008-hosting.md), decision 12 (the exact build steps, see decisions 6 to 10); [ADR 0010](0010-ci-cd.md), decision 18 (the `docker` ecosystem)
- **Refines:** [ADR 0008](0008-hosting.md), decision 12 (only the SPA is built, since [ADR 0023](0023-production-build-and-serving-details.md), decision 1, see decision 6); [ADR 0010](0010-ci-cd.md), decision 7 (the startup check is a step of the `docker` job, see decision 4)

## Context

[PH-08](../roadmap.md#ph-08-container-image) builds Szop's container image: one image that holds the API and the built single-page application (SPA), runs as a non-root user and starts next to PostgreSQL, on the owner's machine and in CI. [ADR 0008](0008-hosting.md), decision 12 set the direction (a multi-stage Dockerfile on a slim Node 24 image) and left the exact build steps to the implementation; [ADR 0010](0010-ci-cd.md), decisions 7, 9 and 18 planned the `docker` job, BuildKit's cache and Dependabot's `docker` ecosystem; [ADR 0023](0023-production-build-and-serving-details.md), decision 1 removed the API's build step, so the image runs the API's TypeScript sources through Node's type stripping and must keep pnpm's symlinked workspace. The brainstorm and the [spec](../superpowers/specs/2026-10-12-PH-08-container-image-design.md) settled the details below; the open points [OP-013](https://github.com/luiki-dev/szop/issues/66), [OP-015](https://github.com/luiki-dev/szop/issues/67), [OP-017](https://github.com/luiki-dev/szop/issues/68), [OP-032](https://github.com/luiki-dev/szop/issues/69), [OP-068](https://github.com/luiki-dev/szop/issues/70), [OP-078](https://github.com/luiki-dev/szop/issues/71) and [OP-084](https://github.com/luiki-dev/szop/issues/72) asked for them.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|-------|--------------------|------------------------|
| 1 | Base image | `node:24-trixie-slim`; `node:24-alpine`; distroless (`gcr.io/distroless/nodejs24-debian12`); hardened images (Docker Hardened Images, Chainguard) | **`node:24-trixie-slim`, pinned by digest** (`node:24-trixie-slim@sha256:…`), Debian 13. It is the official image, uses glibc like the PostgreSQL image of `compose.yaml`, has the `node` user, and Dependabot bumps both the tag and the digest. A shell helps when debugging a task. Alpine's musl is the kind of difference the PostgreSQL image avoided; distroless has no shell to debug with and no way for a health check to run anything but Node; hardened images need a vendor account or registry for a learning project. |
| 2 | Where the RDS certificate authority bundle comes from | Committed to the repository; downloaded during the build; downloaded with `ADD --checksum` | **Committed** as `apps/api/certs/rds-global-bundle.pem`, copied by the Dockerfile. It is reviewed once in a PR, the build is reproducible and needs no network for it, and a change shows up in a diff. AWS publishes no checksum, so a download trusts whatever the URL answers that day; a pinned checksum gives the same result as committing, plus a network dependency. The roots it holds last until about 2061; the ADR records the source URL and how to refresh the file. <br>**Settled while building:** the file was downloaded on 2026-10-12 from `https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem`: 111 certificates, every one with `OU=Amazon RDS`, SHA-256 `fe45bbebf92ad3e27a583bbb2ddd1553c521ed4d49af5514dc0a40372ea5395c`. **To refresh it:** download it to the same path, check `git diff --stat`, list the subjects with `openssl crl2pkcs7 -nocrl -certfile apps/api/certs/rds-global-bundle.pem \| openssl pkcs7 -print_certs -noout`, and commit it as `build: refresh the RDS certificate bundle`. |
| 3 | How CI proves the image starts ([OP-032](https://github.com/luiki-dev/szop/issues/69)) | A startup check; the E2E suite against the image; both | **A startup check:** the image starts next to PostgreSQL, the container becomes healthy, its user is not root, and `/` answers with HTML. It covers what the open points ask for in seconds. Running the E2E suite against the image is the stronger proof but changes how PH-07's job starts the app, a second concept for the phase: it is a candidate, [OP-089](https://github.com/luiki-dev/szop/issues/193). <br>**Settled while building:** shown to fail for the right reasons: without `meta/_journal.json` the API exits before it listens and the check reports `the app did not become healthy`, with the `ENOENT` in the logs; with a wrong `WEB_ROOT` it reports `GET / answered 404, not 200`; with `USER root` it reports `the image's user is 'root', not node`. It passes with PostgreSQL stopped beforehand (Compose starts it) and next to a running `pnpm start`. |
| 4 | CI jobs, and how the image runs next to PostgreSQL | One `docker` job that builds, then checks; two jobs, `docker` and a start job; the check as a long `docker run` in the workflow | **One `docker` job:** it builds the image, loads it into the runner's Docker and runs the check on it. The check cannot run without the build, and the image never leaves the runner; a second job needs the image moved as an artifact (about 80 MB) or rebuilt from the cache. **The image runs as an `app` service in `compose.yaml`, under a profile,** so `docker compose up` still starts PostgreSQL only, and the same check runs locally and in CI. **Refines ADR 0010, decision 7:** the roadmap's "job proving the image starts" is a step of `docker`. |
| 5 | Scanning | None in this phase; hadolint; Trivy | **None in this phase.** The phase brings one concept, the image; Dependabot keeps the base current, the final image holds only production dependencies and runs as a non-root user. hadolint adds a pinned tool and its page; Trivy needs a threshold and an ignore list, since Debian slim images almost always carry CVEs without a fix. Both are a candidate, [OP-090](https://github.com/luiki-dev/szop/issues/194). |
| 6 | The Dockerfile's layout ([OP-015](https://github.com/luiki-dev/szop/issues/67)) | Three stages (`build`, `prod-deps`, final); one build stage pruned in place; `pnpm deploy` | **Three stages on one `base`:** `build` builds the SPA, `prod-deps` installs the API's production dependencies with pnpm's symlinks, and the final stage copies those two outputs and the API's runtime files. A web change does not invalidate the dependency layer, and the final image holds only what is copied into it on purpose. Pruning in place copies whatever the build left behind and reinstalls everything on any source change. **`pnpm deploy` is rejected:** it copies `@szop/shared` into `node_modules`, where Node refuses to strip types, so the API would fail to start ([OP-084](https://github.com/luiki-dev/szop/issues/72)). **pnpm comes from Corepack** (`corepack enable`), which reads `packageManager` from `package.json`, so the version stays in one place; `npm i -g pnpm@…` would repeat it. Corepack leaves Node in version 25, and Node's major changes on purpose (audit m13). <br>**Settled while building:** a fourth stage, `manifests`, copies the manifests once and runs `corepack install`, so pnpm is downloaded once for both install stages and the final image carries no pnpm. **No `# syntax=` line:** Docker's built-in Dockerfile frontend supports cache mounts, and the line would pull an unpinned frontend image on every build. The pnpm store is a BuildKit cache mount at `/root/.local/share/pnpm/store`, outside every layer. The image is 394 MB as `docker image ls` shows it, of which the base is 336 MB and `/app` 52 MB. |
| 7 | One pin or two | The final stage `FROM base`; the final stage repeating the pinned image | **One pin: every stage is `FROM base`.** The final image then carries Corepack's shims, a few symlinks inside Node's install, but no pnpm, which is only downloaded when `pnpm` first runs. Dependabot has one digest to bump. |
| 8 | `@szop/shared` in the API | Stays in `devDependencies`; moves to `dependencies` | **Moves to `dependencies`.** The API does not import it at run time yet, but `pnpm install --prod` leaves a development dependency's symlink out, so the image would fail to start the first time it does. <br>**Settled while building:** a probe confirmed the risk: with `@szop/shared` as a development dependency, `pnpm install --prod --filter "@szop/api..."` leaves `apps/api/node_modules/@szop` out entirely. Moved, it links `@szop/shared` to `packages/shared` and installs `packages/shared/node_modules/zod`, which the final stage copies too; `import.meta.resolve("@szop/shared")` in the image gives `file:///app/packages/shared/src/index.ts`. |
| 9 | What the image sets | Everything with a sensible value; nothing; facts of the image only | **Facts of the image only:** `WEB_ROOT=/app/apps/web/dist`, where the image puts the SPA, and `NODE_ENV=production`. `HOST`, `PORT`, `LOG_LEVEL`, the `DATABASE_*` settings and `TRUSTED_PROXIES` come from whoever runs it, Compose now and ECS in PH-12, which keeps [ADR 0019](0019-api-skeleton-details.md), decision 2: no defaults. |
| 10 | Process and file system | `node` as PID 1; `tini` or `--init`; files owned by `node` or by root | **`node` as process 1 (PID 1), without an init process:** `server.ts` handles `SIGTERM` and `SIGINT` itself and starts no child processes that could be left as zombies. **Files owned by root, read-only to `node`,** so the process cannot change its own code. Nothing in the API writes to disk: pino logs to stdout, which Docker collects. Compose runs the container with a read-only root filesystem to prove it, ready for ECS's `readonlyRootFilesystem`. <br>**Settled while building:** the root `package.json` is not needed at run time: `apps/api/package.json` and `packages/shared/package.json` each set `"type": "module"`, so the image has no root manifest. |
| 11 | Health checks | A `HEALTHCHECK` in the Dockerfile; one in `compose.yaml` | **In `compose.yaml` only.** ECS ignores the Dockerfile's `HEALTHCHECK` and uses the task definition's, decided in PH-12. Compose's check runs `node -e` with `fetch`, since the slim image has no `curl`. |
| 12 | The check's language | A bash script; a Node script | **Bash, `scripts/check-image.sh`.** Its steps are Docker commands and `curl` on the host; a Node script would only wrap them. It is not unit-tested: its failure path is shown once instead, with a missing journal and a wrong `WEB_ROOT`. |

## Consequences

- **The base image changes only through Dependabot's PRs** (a new digest or a minor or patch tag of `node:24-trixie-slim`, checked by the `docker` job) **or a deliberate Node major,** which also changes `.nvmrc` and `engines` (audit m13). The digest pinned in this phase was six days old, one short of the cooldown; Dependabot's first `docker` PR replaces it.
- **Every code PR builds the image,** in the `docker` job, required through `ci-ok` without a change to GitHub's settings; its time, with a cold and a warm cache, is measured in the PR. The SPA is built twice per PR, in `build` and in `docker`, in parallel.
- **`pnpm check:image` needs Docker Desktop running.** It uses the development database and port 8080, so it runs next to `pnpm dev` and `pnpm start`.
- **[PH-12](../roadmap.md#ph-12-first-deploy) uses what this phase prepared:** it points the pool's `ssl.ca` at `apps/api/certs/rds-global-bundle.pem` with full certificate verification ([OP-017](https://github.com/luiki-dev/szop/issues/68)), sets the task definition's health check (the Dockerfile has none) and can turn on `readonlyRootFilesystem`, which the Compose service already proves.
- **[PH-10](../roadmap.md#ph-10-domain-and-base-infrastructure)'s registry and the spin-up workflow push this Dockerfile's image** ([ADR 0010](0010-ci-cd.md), decision 10); nothing is pushed until then.
- **A runtime dependency of the API must be in its `dependencies`,** workspace packages included: `pnpm install --prod` leaves development dependencies out of the image (decision 8).
- **Candidates, not planned in any phase yet:** running the E2E suite against the image ([OP-089](https://github.com/luiki-dev/szop/issues/193)) and scanning the image and linting the Dockerfile ([OP-090](https://github.com/luiki-dev/szop/issues/194)).
- **The open points changed:** [OP-015](https://github.com/luiki-dev/szop/issues/67), [OP-032](https://github.com/luiki-dev/szop/issues/69), [OP-078](https://github.com/luiki-dev/szop/issues/71) and [OP-084](https://github.com/luiki-dev/szop/issues/72) are closed by the PR; the PH-08 parts of [OP-013](https://github.com/luiki-dev/szop/issues/66) and [OP-068](https://github.com/luiki-dev/szop/issues/70) are ✅ done and both move to [PH-09](../roadmap.md#ph-09-aws-account-and-terraform-bootstrap); the PH-08 part of [OP-017](https://github.com/luiki-dev/szop/issues/68) is ✅ done and it moves to [PH-12](../roadmap.md#ph-12-first-deploy).
- **The living docs are updated:** the [Docker tool page](../development/tools/docker.md) (new), the [Docker Compose](../development/tools/docker-compose.md) and [Dependabot](../development/tools/dependabot.md) pages, the [testing guide](../development/testing.md), the [CI/CD guide](../development/ci-cd.md), the [setup guide](../development/setup.md), the [architecture](../architecture/architecture.md), the [stack overview](../architecture/stack-overview.md), the [threat model](../architecture/threat-model.md) and the [glossary](../glossary.md).
