# ADR 0059 — Skills for the handoff, finishing a phase and the demo check

- **Status:** ✅ Accepted
- **Date:** 2026-10-31
- **Extends:** [ADR 0052](0052-working-with-claude.md), decision 2 (how a stage hands over to the next session, see decisions 2 to 5)
- **Refines:** [ADR 0054](0054-leaner-documentation.md), decision 2 (the review findings are kept in one list during execution, triaged at once with a recommendation each, and may also become bugs, see decisions 6 and 7)

## Context

The owner asked Claude to look through the earlier Szop sessions for parts of the work that repeat often enough to become skills, next to `/phase-tracking` and `/new-adr` ([ADR 0056](0056-claude-code-tooling.md)). Claude read the owner's messages from about 120 sessions. Three patterns stood out, and the owner named them in this order of pain:

- **Handing over to a new session** (about 30 opening prompts pasted by the owner, each written from scratch on request). The owner never knew whether everything was put away, where, and whether the new session would start where it should. The execution state lives in `.superpowers/sdd/<plan>/progress.md`, which is ignored by git: it exists only on the machine that ran the session.
- **The whole-branch review and its findings** (about 10 times). In PH-16a, about 30 minor findings were deferred across eight tasks, scattered through the ledger's log among dispatch lines, and the triage looked different each time.
- **The demo check** (about 40 messages about `demo-up`, `demo-down`, `infra/base`, Lighthouse and signing in). The owner had to work out each time where to click, what to check and what to report.

The finishing stage ran on `superpowers:finishing-a-development-branch`, whose menu offers a local merge and worktree cleanup that Szop's git workflow forbids ([ADR 0009](0009-git-workflow.md), decision 5), and which has no step for the review findings, tracking or the PR template.

Two other patterns were not taken: starting a phase, which `/phase-tracking` already covers at the brainstorm's start, and "next task" between tasks, which is the deliberate pause of [executing a plan](../superpowers/plans/CLAUDE.md).

## Decisions

| # | Decision | Options considered | Outcome |
|---|---|---|---|
| 1 | Which skills | `/handoff`, `/finish-phase`, `/demo-check`, `/start-phase`; a script for the docs' consistency rules | **`/handoff`, `/finish-phase` and `/demo-check`, in `.claude/skills/`** _(Claude's proposal from the sessions, the owner's choice)_. `/start-phase` would only wrap `/phase-tracking`; the docs' rules are better checked by a script, which is left for later if wanted. |
| 2 | Who starts a handoff | Claude at a threshold; the owner | **The owner runs `/handoff`** _(the owner's choice)_. Claude may suggest it at the end of a stage or at about 150 to 200k of context ([ADR 0052](0052-working-with-claude.md), decision 3), but does not start it. |
| 3 | Where the handoff is kept | Committed on the branch; a local file | **A local file, `.superpowers/handoff/<branch>.md`, one per branch, overwritten by each handoff** _(the owner's choice)_. `.superpowers/` is already ignored by git. The file names the stage, the next step, the documents to read (spec, plan, the ledger in `.superpowers/sdd/`), the decisions from the conversation that no document holds yet, and what waits on the owner. Before writing it, the handoff commits and pushes the finished work and never leaves an edit uncommitted. |
| 4 | A handoff to or from a cloud session | The local file only; the file's content in the prompt | **When the session runs in the cloud, or the owner says the next one will, the file's content goes into the prompt itself** _(Claude's proposal)_. A cloud session starts in a new environment from a fresh clone, so a local file does not survive between cloud sessions or between the machine and the cloud. |
| 5 | How the new session starts | A prompt written each time; a fixed prompt that starts the skill | **The prompt is `/handoff resume <branch>` and one line with the stage and the next step** _(the flow is the owner's, the wording Claude's)_. In resume mode the skill checks `git status -sb` and the branch, reads the file and the documents it names, and confirms in two or three lines where it starts before doing anything. The second line is enough to start if the file is missing. |
| 6 | Where the findings wait | Lines in the ledger's log (today); one list in the ledger | **One findings list in the ledger, kept by every task, one line per finding: a number, the severity, the source task, the file and one sentence** _(Claude's proposal, the owner's choice)_. The whole-branch review adds its own; duplicates are merged, and a finding a later task fixed is dropped after checking the code. |
| 7 | How the findings are decided | Listed as they come; one triage at the end | **One message after the whole-branch review: every finding, grouped by severity, numbered, each with Claude's recommendation (fix now, open point, bug, drop) and a short reason. The owner answers once, naming which are fixed now, which become open points and which become bugs; the rest are dropped** _(the owner's choice)_. Fixes go in one round; open points and bugs are filed through `/phase-tracking` ([ADR 0058](0058-bug-reports.md)); the dropped ones are noted as declined in the phase ADR's "Settled while building", as ADR 0054, decision 2, sets. |
| 8 | Finishing a branch | `superpowers:finishing-a-development-branch`; a skill of Szop's own | **`/finish-phase` replaces it** _(the owner's choice, after Claude compared the two)_. It keeps what applies from the superpowers skill: the full checks on the final head before anything else, no force-push, and a note when the branch is in a worktree, which it does not remove. It drops the menu: the only way out is a PR, and leaving the branch as it is is `/handoff`. It adds the whole-branch review on Opus, the findings of decisions 6 and 7, the token usage report, `/phase-tracking` before the PR and the PR template. It also finishes a branch outside a phase, skipping the steps that only a phase has. It never merges. |
| 9 | How the demo check is run | Step by step, a message per step; all steps in one message | **One message with the whole list for the phase: a table of the step, who does it (the owner or Claude), where (the exact clicks or command, linking the runbook), what to check and what to reply** _(the owner's choice)_. The owner does their steps in a row and replies once when the demo is up; Claude runs its checks while the owner checks the phase's behaviors; the owner replies once more when they are done and `demo-down` has run. At most three exchanges. The owner may take every step; the table then names them for all of them. The list itself stays the one in [the definition of done](../development/definition-of-done.md#the-demo-check). |
| 10 | Who does which demo step | The owner does all; Claude does what needs no owner | **The owner signs in to AWS, applies `infra/base`, starts `demo-up` and `demo-down`, and checks the phase's behaviors; Claude follows the runs and checks the health endpoint and its commit, the redirect to HTTPS, the console and Lighthouse** _(Claude's proposal, the owner's choice)_. Claude never triggers `demo-up` or `demo-down` ([ADR 0010](0010-ci-cd.md), consequences). The owner still ticks `Demo check` in the PR; Claude fills the "Checked at the demo:" line. |
| 11 | Who invokes `/finish-phase` and `/demo-check` | The owner only; Claude and the owner | **Both** _(Claude's call, as in [ADR 0056](0056-claude-code-tooling.md), decision 11)_. The opening prompt of the finishing stage starts `/finish-phase`, and `/finish-phase` ends by offering `/demo-check` for a phase that needs one. |

## Consequences

- **The opening prompts change:** [working with Claude](../development/working-with-claude.md) points to `/handoff` instead of prompts written by hand, and the finishing stage to `/finish-phase`.
- **The execution rules change:** [executing a plan](../superpowers/plans/CLAUDE.md) names the findings list and `/finish-phase` in place of the superpowers skill. `superpowers:subagent-driven-development` calls the superpowers finishing skill at its end, so the rule has to be there for the executing session to see it.
- **The handoff file is local:** a session on another machine starts from the prompt's second line only, unless the handoff was written for the cloud.
- **Lighthouse from Claude's side is new:** the Chrome DevTools MCP's own Lighthouse tool leaves out performance, so Claude runs the Lighthouse command-line tool against the demo, with its default mobile profile. If that cannot run, the owner saves the report from Chrome and Claude reads the file.
