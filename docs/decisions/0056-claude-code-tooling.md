# ADR 0056 — Claude Code tooling: context7, a code-only graphify and two skills

- **Status:** ✅ Accepted
- **Date:** 2026-10-29
- **Revisits:** [ADR 0031](0031-graphify-not-adopted.md), decisions 1 and 2 (graphify is adopted, for code only, see decisions 3 to 7); [ADR 0031](0031-graphify-not-adopted.md), decision 3 (the revisit is done, see decision 8)

## Context

The owner asked Claude to recommend Claude Code automations for Szop. Claude recommended the context7 and Terraform MCP servers, two skills (one for project tracking, one for new ADRs), two hooks (Prettier after every edit, a warning for requirement IDs that aren't links) and a subagent that reviews the docs against the writing rules. The owner chose context7 and the two skills, and added graphify, which they install themselves.

[ADR 0031](0031-graphify-not-adopted.md) did not adopt graphify on 2026-10-17. Building the graph cost about 3.0M weighted tokens, a third of a phase, and keeping the docs in it current needs an LLM call for every changed doc. The owner's new proposal leaves the docs out: graphify maps only the code, which it parses locally, and git hooks keep the map current. Claude measured it on a copy of Szop's code: a first build takes 2.3 s, an update after one changed file 1.4 s, with no LLM call and two lines of output.

While the design was being worked out, Claude ran graphify 0.9.92's install commands in a throwaway repository and read its source. Three findings shaped the decisions:

- **`graphify hook install` already handles husky.** It writes its hooks to `.husky/post-*`, which survive `pnpm install`, not to `.husky/_`, which husky rewrites. Where graphify is missing, the hooks exit 0 but print a warning on every commit.
- **`graphify claude install --project` writes more than a rule.** It adds a section to `CLAUDE.md`, two `PreToolUse` hooks to `.claude/settings.json` (a bare `graphify hook-guard` command, which fails where graphify is missing), the `/graphify` skill in `.claude/skills/graphify/` with a pointer in `.claude/CLAUDE.md`, and a merge driver for a committed `graph.json`. Run again, it rewrites its hooks in `settings.json`.
- **graphify's `PreToolUse` guard nudges on docs too.** Its file list includes `.md`, and it nudges on every `Grep` call while a graph exists, at most 5 times per session or subagent (`GRAPHIFY_HOOK_NUDGE_CAP`), each about 60 to 150 tokens, telling the assistant it "MUST run `graphify query`" first. It does not read `.graphifyignore`, which only the graph's build reads. In a session about the docs, a code-only graph cannot answer the question the nudge points to.

## Decisions

| # | Decision | Options considered | Outcome |
|---|---|---|---|
| 1 | Which automations | context7 and Terraform MCP servers; `/phase-tracking` and `/new-adr` skills; a Prettier hook and an unlinked-ID hook; a docs-conformance subagent; graphify | **context7, the two skills and graphify** _(the owner's choice)_. The Terraform MCP server, both hooks and the subagent are not taken. |
| 2 | Where context7 is configured | Committed in `.mcp.json`; at user scope on the owner's machine | **Committed in `.mcp.json`, over HTTP, without an API key** _(the owner's choice)_. Every session gets it, cloud sessions included. Several libraries are new majors (React Router 8, Vite 8, Tailwind CSS 4, Zod 4, ESLint 10, TypeScript 6), so their current docs matter. Without a key the rate limit is lower, which is enough for lookups. |
| 3 | Adopting graphify | Don't adopt it (ADR 0031); adopt it for code and docs; adopt it for code only | **For code only** _(the owner's choice)_. Code is parsed locally, so keeping the graph current costs no tokens, which removes ADR 0031's objection. The docs stay out of the graph, so nothing ever goes through an LLM. The graph is not committed: `graphify-out/` is in `.gitignore`, and each machine builds its own, for free. A `.graphifyignore` (`docs/`, `*.md`, `*.mdx`, `*.pdf`, `*.txt`) keeps the docs out even if a full build runs. |
| 4 | Installing graphify | The owner runs `graphify hook install` and `graphify claude install --project`; Claude commits their output with guards added | **The owner installs the CLI (`uv tool install graphifyy`) and builds the first graph with `graphify update .`. The branch holds what the two install commands write, with these changes** _(Claude's proposal, the owner's choice)_: the four `.husky/post-*` hooks as written, plus a first line `command -v graphify >/dev/null 2>&1 \|\| exit 0`, so machines without graphify stay silent (a rerun of `graphify hook install` keeps it); the `CLAUDE.md` section with the update rule of decision 7 and without the line about a committed graph; the `PreToolUse` hooks through the wrapper of decision 5. **Not taken:** the merge driver, since the graph is not committed, and the `/graphify` skill with its `.claude/CLAUDE.md` pointer, since its main job is the LLM build of the docs that ADR 0031 rejected _(the owner's choice)_. `graphify claude install` is not run again in the repository: it would put back the bare hooks. |
| 5 | graphify's `PreToolUse` guard | Keep it as graphify writes it; drop it and keep the `CLAUDE.md` rule; wrap it to skip the docs | **Wrapped by `.claude/hooks/graphify-guard.ts`, which skips calls whose paths are all ignored by `.graphifyignore`** _(the owner's choice, against Claude's recommendation to drop it; the owner's idea to reuse `.graphifyignore`)_. The guard's useful part stays: it lists the graph's symbols for the code file about to be read and warns when the graph is stale for it. The wrapper checks the paths with `git -c core.excludesFile=.graphifyignore check-ignore --no-index`, so the matching follows gitignore rules without a new dependency. Calls with no path to check (a `Grep` over the whole repository) go to graphify and get its capped nudge. Where graphify isn't installed, the wrapper does nothing. |
| 6 | Where the guard's filter comes from | Its own list of paths; `.graphifyignore` | **`.graphifyignore`** _(the owner's choice)_. One file says what the graph leaves out, for the build and for the guard. |
| 7 | Keeping the graph current while working | graphify's rule, `graphify update .` after every code change; no rule, the git hooks only; before a query | **"Before a graph query, if you changed code since the last commit, run `graphify update .` first"** _(the owner raised the stale graph; Claude's wording, the owner's choice)_. The git hooks update the graph at every commit, so a new task starts with a current one; the rule covers the changes inside a task, which a stale graph would miss (a function just added, renamed or moved), without an update after every edit. |
| 8 | [OP-095](https://github.com/luiki-dev/szop/issues/211) | Keep it open; settle it | **Settled by this ADR, closed by its PR.** ADR 0031's triggers were about the cost of the full graph; the code-only graph does not have that cost. No measurement with and without the graph was done: graphify is adopted as an experiment, and dropping it is a new ADR. |
| 9 | Project tracking | Keep the "Project tracking" section in `CLAUDE.md`; move it into a skill, with a trigger list in `CLAUDE.md` | **Moved into `/phase-tracking` (`.claude/skills/phase-tracking/`), with the open-point rules. `CLAUDE.md` keeps a list of the moments that run the skill** _(the owner's choice)_. The section loads in every session, including the ones that never touch a phase. A skill only works when it is invoked, so the trigger list names each moment, such as "when a phase's brainstorm starts, before the first question". The skill holds the steps and the exact `gh` commands with the project's field IDs; [project tracking](../development/project-tracking.md) stays the guide with the reasons. |
| 10 | ADR rules | Keep them in `CLAUDE.md`'s "Documentation"; move them into a skill | **Moved into `/new-adr` (`.claude/skills/new-adr/`). `CLAUDE.md` keeps "for a new ADR, run `/new-adr`"** _(the owner's choice)_. The skill holds the numbering (the next free number on `main` and the open branches), the file's shape, the rule against rewriting an accepted ADR, the notes in two places (the header and the `✏️` line in the earlier decision's cell), and for an ADR made outside a phase, its `adr` issue. |
| 11 | Who invokes the skills | The owner only; Claude and the owner | **Both** _(Claude's call)_. The trigger lists only work if Claude can start the skills itself. |

## Consequences

- **`CLAUDE.md` gets shorter** by the tracking and ADR rules, and gains the trigger lists and the graphify section, which applies only where `graphify-out/graph.json` exists.
- **Sessions without graphify are unaffected:** cloud sessions and other machines have no graph, so the `CLAUDE.md` rule does not apply, and the git and Claude hooks exit without output.
- **A graphify upgrade does not change the committed hooks:** `graphify hook install` reports "already installed". Taking a new hook version means `graphify hook uninstall`, then `graphify hook install`, and committing the result, guard line included.
- **The wrapper depends on the `hook-guard` subcommand and its JSON input.** If a graphify release changes them, the wrapper's test catches only our side; the guard's behavior is checked by hand after an upgrade ([the graphify page](../development/tools/graphify.md)).
- **context7 is an outside service.** Only library names and questions are sent to it, never code or secrets.
- **This ADR's [issue](https://github.com/luiki-dev/szop/issues/311) is closed by the PR that merges it**, with [OP-095](https://github.com/luiki-dev/szop/issues/211).

## Settled while building

- **graphify 0.9.97 was used,** not the 0.9.92 the spec names. The hooks it wrote matched the spec's description.
- **Every `graphify hook install` rerun re-adds the merge driver** (the `.gitattributes` line and `merge.graphify.*` in local git config). Both are removed again after each run. This adds to the Consequences line on upgrades (uninstall, install, commit).
- **The post-commit hook leaves `graphify-out/graph.json` untouched when no code-graph topology changed** ("No code-graph topology changes detected; outputs left untouched"). A commit moves the file's modification time only when it changes code structure, so the hook's log (`~/.cache/graphify-rebuild.log`) is the check that the hook ran.
- **The guard wrapper treats an empty relative path as `.`.** A path equal to the project root would otherwise reach `git check-ignore` as an empty string, which makes git fail; `.` is not ignored, so graphify runs.
- **The wrapper reuses `parseSegments` from `guard-git-push.ts`** (now exported) for splitting Bash commands, as the spec allows.
