# ADR 0060 — Workspace from the default data phase details

- **Status:** ✅ Accepted
- **Date:** 2026-11-01
- **Refines:** [ADR 0057](0057-guests-first-list-phase-details.md), decision 8 (the IDs of the default data are UUIDv5 from their names; see decision 2)

## Context

[PH-16b](../roadmap.md#ph-16b-workspace-from-the-default-data) makes a guest's workspace a copy of the default data: the seed catalog's categories and products, and its units. Until now a workspace held only lists, and `GET /api/catalog` served the seed from memory to everyone ([ADR 0050](0050-seed-catalog-phase-details.md), decision 2). The phase also finishes the access layer's first pattern ([OP-054](https://github.com/luiki-dev/szop/issues/102), [OP-118](https://github.com/luiki-dev/szop/issues/321)), and settles how a guest's first change survives the switch from the seed to their copy ([OP-048](https://github.com/luiki-dev/szop/issues/101)).

In this phase the only change a guest can make is creating a list: adding a product to a list comes in [PH-17a](../roadmap.md#ph-17a-list-items), and editing the catalog in [PH-26](../roadmap.md#ph-26-catalog-and-units). So no request yet refers to a default record.

The [spec](../superpowers/specs/2026-11-01-PH-16b-workspace-from-default-data-design.md) holds the design in full; this ADR records the decisions and the alternatives. All were settled in the brainstorm.

## Changes to the roadmap

- **[ACC-1](../requirements/ACC-accounts-and-guest-mode.md#acc-1).5 and the reference part of [NFR-4](../requirements/NFR-non-functional-requirements.md#nfr-4).10 move to [PH-17a](../roadmap.md#ph-17a-list-items)**, the first phase whose requests carry references to default records; a criterion is checked through behavior a user has, not a test-only route.
- **[OP-115](https://github.com/luiki-dev/szop/issues/318), [OP-116](https://github.com/luiki-dev/szop/issues/319) and the bug [#323](https://github.com/luiki-dev/szop/issues/323) move to [PH-16c](../roadmap.md#ph-16c-managing-lists)**, which changes the lists screens and the SPA's writes anyway, so this phase keeps one concept ([ADR 0014](0014-roadmap.md), decision 6).

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|---|---|---|
| 1 | Where the copy comes from | **B:** default tables in the database, loaded from the file by a data migration, copied with one `INSERT … SELECT`. | **A: the API copies from the seed it parsed at startup, inserting the workspace's units, categories and products in the transaction that creates the workspace** _(the owner's choice, on Claude's recommendation)_. The seed file stays the one source of the default data, as [ADR 0050](0050-seed-catalog-phase-details.md), decision 2, has it; B would add a second copy to keep in line with the file. A change to the default data is a change to the file and a deploy, and the copies already made stay as they are ([ACC-1](../requirements/ACC-accounts-and-guest-mode.md#acc-1).9). The copy is three multi-row inserts of about 600 rows, well within PostgreSQL's limit of parameters per statement under the seed's limits. |
| 2 | The default data's IDs | **B:** IDs written in the YAML file by hand. **C:** new IDs in each copy, with the server mapping the seed's IDs at the first change. Keeping the positional IDs (`u1`, `c12`, `p34`). | **Every default record's ID is a UUIDv5 of its name, in lower case as the seed's duplicate check compares names, with one namespace each for units, categories and products. The seed served from memory and every copy use the same IDs** _(the owner's choice, on Claude's recommendation)_. Positional IDs shift when an entry is added to the file, so a guest who loaded the page before a deploy and made their first change after it would point at another product, silently. Name-based IDs do not shift; a renamed entry gets a new ID, so an old reference finds nothing and gets a 404 rather than a wrong record. The file keeps its form ([ADR 0050](0050-seed-catalog-phase-details.md), decision 1). B makes every edit of the file assign an ID by hand; C needs mapping code for a problem A and B do not have. The same ID in many workspaces is safe because every key is `(workspace_id, id)` ([ADR 0057](0057-guests-first-list-phase-details.md), decision 14). This refines ADR 0057, decision 8: records the user creates keep UUIDv7 from the browser. |
| 3 | The workspace's catalog tables | Keys and references by `id` alone; deciding what deleting does in PH-26. | **`units`, `categories` and `products` follow [ADR 0057](0057-guests-first-list-phase-details.md), decision 14: primary key `(workspace_id, id)`, `workspace_id` referencing `workspaces` with `ON DELETE CASCADE`, `created_at` and `updated_at`, names 1 to 100 characters by a `CHECK`. Every reference is a composite foreign key: a category's parent `(workspace_id, parent_id)` and a product's category and unit, `(workspace_id, category_id)` and `(workspace_id, unit_id)`. A category's parent uses `ON DELETE CASCADE`, and a product's references `ON DELETE SET NULL (category_id)` and `SET NULL (unit_id)`** _(Claude's call)_. Composite keys make PostgreSQL refuse a reference into another workspace ([ADR 0012](0012-security-baseline.md), decision 6). These are what [CAT-3](../requirements/CAT-categories.md#cat-3).1, CAT-3.3 and [UNT-1](../requirements/UNT-units.md#unt-1).4 ask for (a deleted category takes its subcategories, and products lose a deleted category or unit), so the phases that delete add no migration for them. Nothing deletes these rows in this phase except a workspace's own deletion. |
| 4 | When the copy is made | In Better Auth's user-creation hook; in a request of its own. | **`ownWorkspace` copies the seed when its insert of the workspace created a row (`INSERT … ON CONFLICT DO NOTHING RETURNING`), in the caller's transaction** _(Claude's call)_. The workspace and its copy commit together or not at all, with the change that caused them. Two tabs' first changes race on the unique `user_id`: the second insert waits for the first transaction, then does nothing, so there is one workspace with one copy ([ACC-1](../requirements/ACC-accounts-and-guest-mode.md#acc-1).6). The hook was ruled out by [ADR 0057](0057-guests-first-list-phase-details.md), decision 13. |
| 5 | What `GET /api/catalog` returns | Always the seed, until PH-26 lets a user change their copy. | **A visitor with a workspace gets their own catalog from its tables; a visitor without one gets the seed from memory. The response's shape does not change** _(Claude's call)_. The catalog page shows the guest's own data from the start, so PH-26 changes nothing in this read path. The SPA needs no change: the copy has the seed's IDs and names, so a catalog cached before the first change is still right. A request that only reads still stores nothing ([ACC-1](../requirements/ACC-accounts-and-guest-mode.md#acc-1).3). |
| 6 | The access layer | Leaving the repositories on a bare `workspaceId`. | **Repositories take the `WorkspaceContext` that `ownWorkspace`, `findOwnWorkspace` and `requireListAccess` return, instead of a bare `workspaceId`; `GET /api/lists/:id` reads the list once. The two-workspace test helper and the schema test over PostgreSQL's catalog come with this phase's references** ([OP-054](https://github.com/luiki-dev/szop/issues/102), [OP-118](https://github.com/luiki-dev/szop/issues/321)) _(Claude's call, as the open points ask)_. Skipping the access layer becomes a type error ([ADR 0012](0012-security-baseline.md), decision 5). The schema test makes every later table follow decision 3's pattern without a reviewer checking it. |

## Settled while building

- **`SET NULL (column)` is a hand edit of the migration** _(Claude's call, as the spec's Risks allow)_. `drizzle-orm` 0.45.4 and `drizzle-kit` 0.31.11 accept only `ON DELETE set null` on a `foreignKey()`, with no column list, so the schema declares `.onDelete("set null")` and `0002_tough_ultron.sql` was edited to `ON DELETE set null ("category_id")` and `("unit_id")` on the two product references. The migration check stays green because `db:generate` compares the schema with the snapshot in `meta/`, not with the SQL, and the snapshot is unchanged by the edit. A later `db:generate` that touches these constraints would write plain `set null` again; [Drizzle](../development/tools/drizzle.md#hand-edited-migrations) says so.
- **`GET /api/catalog` creates no session and sets no cookie of its own**, but a refresh of an existing session is passed on, as on every route with `sessionHook`.
- **[ACC-1](../requirements/ACC-accounts-and-guest-mode.md#acc-1).6 is delivered on the server only:** one user's concurrent first changes make one workspace and one copy, but two fresh tabs have no session yet and each signs in anonymously, so they still make two workspaces. Serializing the sign-in across tabs became [OP-120](https://github.com/luiki-dev/szop/issues/329) for [PH-16c](../roadmap.md#ph-16c-managing-lists), which changes the same `withSession` for [OP-116](https://github.com/luiki-dev/szop/issues/319), and the criterion stays 🚧 there _(the owner's choice, found when checking the criteria before the PR)_.
- **The finishing triage's findings:** the stale texts (the session comment in `lists/routes.ts`, the PH-15a and PH-16a paragraphs of `architecture.md`, the catalog row of `threat-model.md`), a shortcut comment on what `resetDatabase` clears, the persisting test databases in `testing.md`, the delete test in `drizzle.md`, a tighter schema guard in `schema.test.ts`, the type-only `@ts-expect-error` in `lists/repository.test.ts`, the POST status in the two-workspaces test, workspace B's original names in the catalog rename test and the ACC-1.1 calls of `ownWorkspace` inside transactions were fixed in this PR; a working command for running one API test file became [OP-119](https://github.com/luiki-dev/szop/issues/328), a candidate _(the owner's choices)_. Declined: the general statements loop of `resetDatabase`'s `run`; the admin role in `setup-role.test.ts` created only when missing, since its password is fixed; an import out of alphabetical order, which lint does not check; the dense UUID template in `seed.ts`, pinned by the RFC test vector; ACC-1.6's two requests not overlapping for certain, since the assertions catch a double copy either way; the failed-copy test checking only the 500, the rollback being checked separately; and `PATCH /lists/:id` reading the list twice, the spec asking a single read of `GET` only.

## Consequences

- The schema gains `units`, `categories` and `products`, the first tables with references inside a workspace; every later table with references follows decision 3, and the schema test checks it.
- A guest's first change writes about 600 more rows; a workspace costs that much storage from its start.
- The catalog's IDs change from `u1`, `c12`, `p34` to UUIDs. Nothing stores them yet, so nothing migrates.
- Renaming an entry in `seed.yaml` gives it a new ID; references to the old one, from PH-17a on, find nothing in workspaces created later. Older workspaces keep their copy.
- The comment in `seed.ts` that the seed is never put in tables no longer holds and changes with the code.
