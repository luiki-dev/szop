# ADR 0041 — Security scanners details

- **Status:** ✅ Accepted
- **Date:** 2026-10-22
- **Supersedes in part:** [ADR 0010](0010-ci-cd.md), decisions 5 (the PR checks may assume an AWS role, in `ci.yml`'s one `plan` job; `infra-plan.yml` is gone, see decision 4) and 14 (the plan is no longer only informative: a failed plan and Access Analyzer's serious findings block a PR that changes `infra/`, see decisions 4 and 5)
- **Completes:** [ADR 0010](0010-ci-cd.md), decision 19 (the scanners of the code: Trivy scans the Terraform code, the Dockerfile and the container image, and blocks above a severity, see decisions 1 to 3); [ADR 0028](0028-container-image-details.md), decision 5 (the image scanner deferred to OP-090: Trivy, with a threshold and inline exceptions, and no Dockerfile linter, see decisions 2, 3 and 13); [ADR 0029](0029-aws-account-and-terraform-bootstrap-details.md), decision 10 (the misconfiguration scanner deferred to OP-091: Trivy's config scan, see decisions 1 to 3)
- **Refines:** [ADR 0032](0032-ci-access-and-teardown-details.md), decisions 4 (Access Analyzer runs in `ci.yml`'s `plan` job and blocks on `ERROR`, `SECURITY_WARNING` and a policy it could not validate, see decisions 2 and 4) and 8 (the `comment` job lives in `ci.yml` and posts the plan and every scan in one comment, see decisions 4, 6 and 14)

## Context

[ADR 0010](0010-ci-cd.md), decision 19 chose "the baseline plus scanners" for the pipeline and the code. CodeQL and zizmor covered the code and the workflows; nothing scanned the Terraform code for security misconfigurations or the container image for known vulnerabilities, published as Common Vulnerabilities and Exposures (CVEs). [PH-35](../roadmap.md#ph-35-security-scanners) adds both, with one tool, Trivy, and makes the scanners and IAM Access Analyzer block a PR above a set severity. To give all of them one gate and one PR comment, the plan's workflow, `infra-plan.yml`, is folded into `ci.yml`. Three open points reached the phase: [OP-091](https://github.com/luiki-dev/szop/issues/201) (a misconfiguration scanner for `infra/`), [OP-090](https://github.com/luiki-dev/szop/issues/194) (an image scanner and a Dockerfile linter, from [ADR 0028](0028-container-image-details.md), decision 5) and [OP-104](https://github.com/luiki-dev/szop/issues/253) (the deploy role's `rds:ModifyDBInstance` without conditions, from [PH-12d](../roadmap.md#ph-12d-safe-redeploys)), which the phase takes since it touches the IAM code the scanners now read. The spec's builder check also answered [OP-019](https://github.com/luiki-dev/szop/issues/77)'s question (decision 14).

The owner chose what a finding does, the thresholds, the tool, where the scans run, the comment, the handling of npm and of the three blocking findings, and the category for operating-system fixes waiting for a new base image; the rest was Claude's call, argued in the spec. This ADR records the decisions, with what was settled while building them. The [spec](../superpowers/specs/2026-10-22-PH-35-security-scanners-design.md) holds the design in full.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|---|---|---|
| 1 | What a finding does | Every finding blocks; nothing blocks, the PR lists them; block above a severity, list the rest | **Block above a severity, list the rest** _(the owner's choice)_. The owner first asked for listing only, then for a threshold that blocks, and asked for the industry's practice; the thresholds of decision 2 are that practice. |
| 2 | The thresholds | — | _(The owner's choice, from Claude's proposal.)_ **Image:** `CRITICAL` and `HIGH` with a fixed version block when they are in a language package (Trivy's class `lang-pkgs`: the Node packages the lockfile or the Dockerfile controls); vulnerabilities without a fix, fixed ones in the operating system's packages (decision 17) and lower severities are listed. **Terraform and Dockerfile (Trivy's config scan):** `CRITICAL` and `HIGH` block; `MEDIUM` and `LOW` are listed. **Access Analyzer:** `ERROR` and `SECURITY_WARNING` block; `WARNING` and `SUGGESTION` are listed; a policy whose validation failed blocks, since it was not checked, and so does a module whose plan failed. A policy still unknown in the plan ("not checked until applied") does not block: the next PR after the apply checks it. Blocking only fixable vulnerabilities keeps a PR from turning red because a CVE was published overnight against a package nobody can update; AWS's own [tf-policy-validator](https://github.com/awslabs/terraform-iam-policy-validator) fails on `ERROR` and `SECURITY_WARNING` by default. |
| 3 | The tool | Trivy, Grype or Docker Scout for the image; Trivy, Checkov or KICS for Terraform; Trivy, hadolint or Checkov for the Dockerfile | **Trivy for all three; no Dockerfile linter** _(the owner's choice)_. One tool gives one severity scale, one way to record exceptions and one output to read into the comment. Checkov has more Terraform rules but is a second tool on Python; Grype covers only the image; Scout needs a Docker account; hadolint adds style, not security, and Trivy's config scan already holds the Dockerfile's security checks. |
| 4 | Where the scanners run, and `infra-plan.yml` | Keep `infra-plan.yml` and make it a required check that always reports (a `changes` job, an `infra-ok` job, the ruleset changed); keep it and post a second comment; fold it into `ci.yml` | **Fold `infra-plan.yml` into `ci.yml`** _(the owner's choice)_. One workflow gives one comment and one gate, `ci-ok`, with no new required check and no ruleset change. A workflow filtered by `paths:` reports nothing on a PR that does not match, so it cannot be a required check without a stand-in job that always reports; two workflows writing one comment would race. The jobs keep their permissions: `plan` holds `contents: read` and `id-token: write`, `comment` holds `pull-requests: write`, and no job holds both. AWS sees no change: the OpenID Connect (OIDC) token names the repository and the event, not the workflow file. **Supersedes [ADR 0010](0010-ci-cd.md), decision 5 in part** (the PR checks may now assume a role, in the one `plan` job) **and decision 14 in part** (the plan is no longer only informative: Access Analyzer's serious findings and a failed plan block a PR that changes `infra/`). Refines [ADR 0032](0032-ci-access-and-teardown-details.md), decisions 4 and 8. |
| 5 | When AWS is down | — | **A PR that changes `infra/` is blocked** while the plan or Access Analyzer cannot run _(the owner accepted it)_. A gate that could not check does not let the change through. PRs that do not change `infra/` do not plan and are not affected. |
| 6 | The comment | One comment for everything; the plan's comment plus one for the image | **One comment for every scan and the plan** _(the owner's choice)_: a verdict line, the blocking findings of every scanner first, then the plan, Access Analyzer, Trivy's config scan with the accepted exceptions, and Trivy's image scan, each part present only when its job ran. A later push updates it. |
| 7 | Unfixed vulnerabilities in the comment | — | **Listed in their own folded section, with a standing note** that says why they do not block today _(the owner's choice)_: no fix exists yet; they are in the base image's operating-system packages, which the app does not use; the container runs as `node`, not root, and exposes only the app's port behind the load balancer. One note for the section, not one per CVE. What happens once a fix appears is decision 17 (see "Settled while building"). |
| 8 | npm in the image | List its findings as exceptions; remove it from the final stage | **Remove npm, npx and Corepack from the final stage** _(the owner's choice)_. All seven fixable `HIGH` findings of the baseline were in npm's own dependencies (`/usr/local/lib/node_modules/npm`), which the image never runs: the app and `db-setup` start with `node`. Removing it fixes them and shrinks what an attacker in the container could use; exceptions would hide a problem one line removes. |
| 9 | The three blocking config findings | Fix them; accept them with an exception | **Accepted, each with an inline exception and its reason** _(the owner's choice)_: `AWS-0104` (the task's egress on 443 to `0.0.0.0/0`, for ECR, Secrets Manager and CloudWatch without VPC endpoints), `AWS-0053` (the demo's load balancer is public, as it must be), `AWS-0132` (the state bucket uses server-side encryption with S3-managed keys, SSE-S3, not a customer-managed key in the Key Management Service, KMS, which costs about $1 a month and more IAM). The comment lists accepted exceptions, so they stay visible. |
| 10 | Running Trivy safely | The `aquasecurity/trivy-action` or `setup-trivy` action; Trivy's Docker image; the release binary, pinned and checked | **The release binary from GitHub Releases, at a pinned version, checked against a SHA-256 kept in the workflow**, as tflint and actionlint are installed. On 19–20 March 2026 a stolen credential was used to publish a malicious Trivy v0.69.4 and to point almost every tag of both actions at a credential stealer, for about 12 hours; malicious images 0.69.5 and 0.69.6 were pushed to Docker Hub ([CVE-2026-33634](https://cve.circl.lu/cve/CVE-2026-33634)). A pinned checksum stops a swapped download; a version at least two weeks old, outside the attack's range, makes pinning a bad release unlikely. **The version: v0.75.0** (1 October 2026); v0.76.x were under two weeks old on 2026-10-22. A bump follows the same rule: a release at least two weeks old, its release notes and Aqua's security advisories read _(Claude's proposal, accepted)_. |
| 11 | Which jobs run Trivy _(Claude's call)_ | A step in `plan`, `infra` and `docker`; jobs of their own | **Two jobs of their own, `scan-config` and `scan-image`, with `contents: read` only.** Trivy never runs in a job that holds AWS credentials (`plan`), a write token (`comment`) or the Actions cache token (`docker`, which writes the image's layers to GitHub's cache with `cache-to: type=gha`): a compromised Trivy in `docker` could poison `main`'s build cache. `docker` saves the image it built as an artifact, and `scan-image` scans the archive with `trivy image --input`, with no Docker daemon. **The scan jobs run on pull requests only**, not on pushes to `main` _(found by the spec's builder check)_: the artifact steps in a scan job give it the Actions runtime token, and a process Trivy left behind could read it from a later step. On a PR that token is scoped to the PR's merge ref and harmless; on a push to `main` it could write `main`'s cache. Every commit on `main` came through a PR that was scanned, and a red `main` would tell nobody anything, since there is no scheduled scan. |
| 12 | Trivy's rules _(Claude's call)_ | Download the newest checks bundle on every run; use the checks built into the pinned binary | **The built-in checks** (`--skip-check-update`), so the config rules change only when Trivy's version is bumped, in a PR that shows what changed. The vulnerability database is downloaded on every run, as it must be. |
| 13 | Exceptions _(Claude's call)_ | A `.trivyignore` file for everything; inline comments for Terraform and a file for image vulnerabilities | **Inline `trivy:ignore` comments on the line above the Terraform resource**, each with its reason, so the reason sits next to the code. **Image vulnerabilities:** a `.trivyignore.yaml` with a statement and an expiry date for each entry, created only when the first one is needed; none is needed today. |
| 14 | PRs that cannot comment _(Claude's call)_ | Fail them; skip the comment and write the same text to the job summary | **The comment's text is always written to the run's job summary as well; the post is skipped on PRs from forks**, whose `GITHUB_TOKEN` is read-only. The gate does not depend on the comment. A fork's PR also gets no plan (no OIDC token); its config and image scans still block, and the summary says that the plan and Access Analyzer did not run. **Dependabot's PRs keep the comment:** run 39680421083 on PR #256, triggered by `dependabot[bot]`, assumed `szop-ci-plan` and posted its comment with `pull-requests: write` _(found by the spec's builder check)_, which also answers [OP-019](https://github.com/luiki-dev/szop/issues/77)'s question: a Dependabot PR gets the OIDC token and a write token, so it needs no special case. |
| 15 | Running locally _(Claude's call)_ | CI only; a script that CI and the developer both run | **`scripts/scan.sh`, run by CI's two scan jobs and by the developer as `pnpm check:scan`**, as `check-infra.sh` is. Trivy is installed on the developer's machine at the same version, with the same checksum (setup guide). |
| 16 | [OP-104](https://github.com/luiki-dev/szop/issues/253) | — | **As the issue describes:** a `Deny` on `rds:ModifyDBInstance` when `rds:ManageMasterUserPassword` is `false`, checked with the policy simulator; the public-address half named as a residual risk in the threat model, since no condition key exists for it; the misleading comment above `StopDbSetup` fixed. Trivy's `AWS-0342` (`iam:PassRole` filtering) on the same role is assessed and changed only if it is a real gap _(Claude's proposal, accepted)_; it is not (see "Settled while building"). |
| 17 | An operating-system package fixed in Debian before a new base image exists _(found by the spec's builder check)_ | A third, non-blocking category; `apt-get upgrade` in the final stage; block until an entry with an expiry date is added to `.trivyignore.yaml` | **A third category, listed but not blocking: "fixed in Debian, waiting for the base image"** _(the owner's choice)_. Trivy marks an operating-system vulnerability fixed as soon as Debian ships the package, but the official `node:24-trixie-slim` image can take weeks to be rebuilt, and Dependabot looks once a week with a 7-day cooldown; with 43 `HIGH` in the operating system, blocking them once fixed would turn almost every PR red for reasons no PR can fix. The comment's section carries its own note: Debian has a fix, the base image does not have it yet, Dependabot proposes the new image when it does. **Cost:** such a vulnerability can sit in the image for weeks. `apt-get upgrade` would close it sooner, but the build would no longer follow from the Dockerfile and its pinned digest, and GitHub's layer cache would keep serving the old layer; a blocking routine of ignore entries is manual work and red PRs in the meantime. |

## Settled while building

Facts the plan did not have, found while building, and kept here because they explain code that looks odd or record what was proven:

- **The exception syntax is one line**, `# trivy:ignore:<ID> -- <reason>`, on the line directly above the resource, with the ID as Trivy v0.75.0 prints it (`AWS-0104`). Trivy ignores the text after the ID, so the reason sits on the same line instead of a comment of its own; an exception with a wrong ID suppresses nothing.
- **Trivy's JSON does not report suppressed findings**, so `scripts/scan.sh` reads the exceptions from the code itself: every `trivy:ignore` line under `infra/` and in the `Dockerfile`, with its file, line and reason. The comment lists them under "Accepted exceptions".
- **Every other way to suppress a finding is refused**, so none escapes that list. Trivy v0.75.0 also honours a `.trivyignore` and a `trivy.yaml` at the repository root, `// trivy:ignore:…`, `# trivy:ignore:*`, a `trivy:ignore` at the end of a code line, the long IDs (`aws-rds-enable-deletion-protection`) and the older `tfsec:ignore`. `scripts/scan.sh` runs Trivy with `--ignorefile "" --config ""` (Trivy's way to load neither default file, for the config and the image scan alike), and fails with `FAIL: non-standard trivy:ignore at <file>:<line>` on any line under `infra/` or in the `Dockerfile` that names `trivy:ignore` or `tfsec:ignore` and is not exactly `# trivy:ignore:<ID> -- <reason>`, with a short ID and a reason. **The first image-vulnerability exception** (decision 13) therefore has to be passed by `scripts/scan.sh` explicitly (`--ignorefile .trivyignore.yaml`), and listed by it as an accepted exception in the comment; the file is still created only when it is needed.
- **The config baseline** on `main`, run locally with v0.75.0: 3 blocking (`AWS-0104` CRITICAL, `AWS-0053` and `AWS-0132` HIGH) and 11 listed. With the three exceptions: 0 blocking, 11 listed, 3 exceptions.
- **`trivy image --input` on a `docker save` archive** finds the same as scanning the loaded `szop:local`: the two JSON outputs differ only in `target` (the archive's path or `szop:local`). The archive is about 89 MB and is kept one day.
- **The image after npm's removal:** before, 7 blocking (CVE-2026-102276, CVE-2026-102278, CVE-2026-14257 and CVE-2026-69152 in `brace-expansion`, CVE-2026-19534 in `undici`, CVE-2026-69192 in `ip-address`, CVE-2026-73566 in `tar`, all inside npm). After: **0 blocking, 2 waiting for the base image** (both `UNKNOWN`, in `liblzma5`), **162 unfixed** (43 `HIGH`, 58 `MEDIUM`, 60 `LOW`, 1 `UNKNOWN`) and 0 listed: no finding is left in a Node package at all. `/usr/local/bin` holds `docker-entrypoint.sh`, `node` and `nodejs`; the final stage also removes the `yarn` and `yarnpkg` shims Corepack had added. `pnpm check:image` and `pnpm check:scale` pass, so the app and two migrators start without npm.
- **No cache for Trivy's vulnerability database.** The spec left it to the builder: `scan-image` took 17 seconds in all on run 39794712117, database download included, so a cache would hand the job the cache token for a saving that does not matter. Trivy's default mirror works from GitHub's runners without a token. A failed download fails the scan, never passes it.
- **When a fix appears for an unfixed vulnerability**, it moves to "fixed in Debian, waiting for the base image" if it is in the operating system (decision 17), and blocks only if it is a `CRITICAL` or `HIGH` in a Node package. The brainstorm's wording of decision 7 ("the scan starts blocking until it is merged") predates decision 17; the comment's note says what the code does. The note also says **most** unfixed vulnerabilities are in the operating system's packages, where decision 7 says all are: an unfixed one in a Node package lands in the same section, and once fixed it blocks if it is `CRITICAL` or `HIGH`.
- **Access Analyzer's baseline is five findings, not three:** 3 `SUGGESTION` `CONFIRM_AUDIENCE_CLAIM_TYPE` (two on `szop-ci-deploy`'s trust policy, one on `szop-ci-plan`'s) and 2 `WARNING` `SPECIFIC_GITHUB_REPO_AND_BRANCH_RECOMMENDED` (one on each trust policy), as [ADR 0034](0034-network-and-demo-up-details.md) had already found the warning back on the deploy role. None blocks.
- **The `plan` job's artifact** holds one folder per module under `plan/`; the policy documents the validation read are left out, since they are only its inputs and are already in the log.
- **The `comment` job checks out one file**, `scripts/write-ci-comment.sh`, from the PR's merge commit (a sparse checkout without credentials), where the spec said "no checkout": the comment's shell and `jq` moved out of the workflow into a script that can be tested with fixtures. The trust boundary is unchanged. On a same-repository PR the author can already change `ci.yml`, the job's own definition, so running their copy of the writer gives them nothing new; on a fork's PR the token is read-only and the post is skipped. The writer still filters every text that came from the PR or from Trivy's database, and the comment travels only as a file. The filter leaves no HTML and no Markdown link but the one to Aqua's page for a rule; GitHub may still turn a bare URL in a title or a message into a link of its own, so the boundary is the job's permissions, not the filter.
- **The `comment` job runs for a fork's PR too**, to write the job summary; only its post step is skipped.
- **The marker is `<!-- ci-scans -->`.** The old `<!-- infra-plan -->` comment on PR #260 is left as it was, a record of the old workflow.
- **The comment's size:** about 37,000 characters of GitHub's limit of 65,536 characters, most of it the folded list of 162 unfixed vulnerabilities. A post over the limit fails and leaves the old comment, with a verdict that may no longer hold, so the `comment` job counts the full text's characters (`LC_ALL=C.UTF-8 wc -m`) and, past 60,000, posts the writer's short text (`write-ci-comment.sh --short`): the folded listed, waiting and unfixed sections keep their counts by severity and their notes but lose their lines, and one line says the full report is in the run's summary. The marker, the verdict, Blocking, the plan and Access Analyzer are always posted in full. The job summary always gets the full text. A fixture with three times today's unfixed list gave 97,755 characters in full and 5,513 short.
- **The deliberate failure:** a throwaway commit opened a security group to `0.0.0.0/0` on port 22. Run 39809859036 failed `scan-config` and `ci-ok`, and [the comment](https://github.com/luiki-dev/szop/pull/260#issuecomment-6344846201) read "❌ 1 blocking finding(s)" with `AWS-0107` (`HIGH`, "Security groups should not allow unrestricted ingress to SSH or RDP from any IP address.") at `infra/demo/service.tf:285`. The revert is typed `test:`, not `revert:`, because commitlint's type list has no `revert`; run 39810445732 was green again and the same comment was updated back to "✅ nothing blocking".
- **The `Deny` of OP-104** is the statement `DenyUnmanagedMasterPassword` in `szop-ci-deploy-demo-database`: `rds:ModifyDBInstance` on `arn:aws:rds:*:*:db:*`, with the condition `Bool` `rds:ManageMasterUserPassword` = `false`. It names every instance, with no region or tag condition: the allow (`DemoDatabases`) reaches only the demo's tagged instance in `eu-central-1`, so a deny on every instance covers it and can only narrow it. A modify that leaves the key out, as Terraform's ordinary changes do, does not match.
- **The simulator** ran on the whole rendered policy, taken from the branch's plan (`terraform plan -refresh=false -lock=false`, then `terraform show -json`), with `aws iam simulate-custom-policy --cli-input-json`, the demo instance's ARN as the resource and the allow's own conditions as context (`aws:RequestedRegion` = `eu-central-1`, `aws:ResourceTag/project` = `szop`, `aws:ResourceTag/group` = `demo`). `--policy-input-list file://policy.json` is refused, since the CLI limits that form to 2,000 characters and the document has 2,493; the same document inside `--cli-input-json` is accepted unsplit. Results: the key `false` gives `explicitDeny` (matched by `DenyUnmanagedMasterPassword`), `true` gives `allowed` and no key gives `allowed` (both matched by `DemoDatabases`). The controls: without the tags `implicitDeny`, with `group` = `other` `implicitDeny`, and without the tags but with `false` `explicitDeny`, so the simulator does evaluate the tag conditions for this action. The raw responses are summarised here, with the account replaced; none is kept. Terraform's AWS provider could not refresh the owner's single sign-on token while the CLI could, so the plan and the simulator ran with credentials exported by `aws configure export-credentials`. The simulator cannot show what the provider sends on a real modify; the apply and the demo do.
- **The `StopDbSetup` comment** now says what holds: the statement requires the tag `Name` = `szop-demo-db-setup`, which `db-setup`'s task gets from its task definition (`demo-up` runs it with `--propagate-tags TASK_DEFINITION`), and the app's tasks carry no `Name` tag at all, since the service sets no `propagate_tags`.
- **`AWS-0342` is a false positive and stays listed** (`MEDIUM`). The check built into v0.75.0 flags any policy with an `Allow` on `iam:PassRole` and no `Deny` on `iam:PassRole` in the same policy; it reads neither `Resource` nor `Condition`, so no scoping clears it. `PassAppRoles` already does what AWS recommends: it names the two app roles and requires `iam:PassedToService` = `ecs-tasks.amazonaws.com`.
- **The demo:** the owner applied `infra/base` from the branch on 2026-10-22, the plan showing the one change to `szop-ci-deploy-demo-database`. `demo-up` [run 39834111977](https://github.com/luiki-dev/szop/actions/runs/39834111977) on `86270e0` passed: the image without npm built and started, `db-setup` migrated the new database, and Terraform created and configured the RDS instance with the `Deny` in force, so the AWS provider does not send `ManageMasterUserPassword = false` on its own changes. `/api/health` answered `200` with `"commit":"86270e0…"` and the database `up`. `demo-down` [run 39838055226](https://github.com/luiki-dev/szop/actions/runs/39838055226) reported `Destroy complete! Resources: 33 destroyed.`

## Consequences

- Every PR that changes code gets Trivy's config scan, and every PR whose `docker` job succeeds gets the image scan; a PR that changes `infra/` gets the plan and Access Analyzer as before, but now they can block it. One comment shows all of them, and the run's summary holds the same text.
- A PR that changes `infra/` cannot be merged while AWS or Access Analyzer is unreachable (decision 5); rerunning the `plan` job once AWS answers again unblocks it.
- A new CVE against a Node package with a fix turns the next PR that rebuilds the image red until the dependency is updated, even when the PR did not touch it. That is the point of blocking only what can be fixed.
- Nothing scans `main` after a merge (decision 11): a vulnerability published later shows up in the next PR that rebuilds the image.
- Trivy is updated by hand, in both scan jobs and the setup guide, under the two-week rule (decision 10); Dependabot cannot see it.
- Accepted exceptions live in the code with their reasons and are listed in every comment; a new one is reviewed like any other line of the PR.
- The deploy role can no longer give the demo database a password of its own; it can still make the running instance publicly accessible with `rds:ModifyDBInstance`, which no condition key can stop. The security group and the private subnet group, which the same role manages, keep it off the internet; the threat model names it as a residual risk.
- Once the full comment passes 60,000 characters, the posted one shows only the counts of the long sections, and their lines are read in the run's summary; the gate does not depend on the comment.
- No Dockerfile style linter and no smaller base image are planned (the owner's choices); the unfixed vulnerabilities are explained in the comment instead.
