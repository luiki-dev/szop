# ADR 0008 — Hosting: an on-demand demo environment on AWS

- **Status:** Accepted — the versioning scheme left open by decision 13 is decided in [ADR 0009](0009-git-workflow.md) (SemVer, cut by release-please)
- **Date:** 2026-09-28
- **Refines:** decisions 5 and 7 of [ADR 0004](0004-implementation-process.md) (what "deployed" means); completes open points of [ADR 0003](0003-abuse-protection.md) (infrastructure-level protection), [ADR 0005](0005-development-environment.md) (production PostgreSQL version, production images, tooling) and [ADR 0007](0007-testing-strategy.md) (how the E2E environment shares one origin, load testing)

## Context

Hosting is the third foundation topic of [ADR 0004](0004-implementation-process.md), after the development environment and the testing strategy. Like every foundation topic, it settles direction and constraints only. The Terraform code, the Dockerfile and the first deployment are written in the walking skeleton phase.

Earlier decisions left these points to this topic:

- **Runtime shape.** One long-running Node.js process (the Fastify API), which later also holds WebSocket connections, and runs the guest cleanup task and the event bus in-process ([architecture.md](../architecture/architecture.md)).
- **One origin** for the SPA and the API, by a reverse proxy or by the API serving the static files ([ADR 0002](0002-technical-architecture.md)). The E2E environment follows the choice ([ADR 0007](0007-testing-strategy.md), decision 15).
- **The PostgreSQL major version** in production, matching local development ([ADR 0005](0005-development-environment.md)), and how production images are built.
- **Email provider, secrets, database backups and monitoring** ([ADR 0004](0004-implementation-process.md), decision 2).
- **Infrastructure-level protection** against volumetric denial of service ([ADR 0003](0003-abuse-protection.md)).
- **Load testing** ([ADR 0007](0007-testing-strategy.md), decision 6).

The brainstorm established what production Szop is for:

- **A demo and portfolio piece**, not a service people depend on. Data loss is acceptable; downtime is the normal state.
- **Used in short sessions the owner runs**: brought up to show someone or to try a deployment, for hours at most, then taken down. Nobody expects the link to work in between.
- **Near-zero cost**, yet on a **major cloud provider**, because learning the platforms and patterns used in commercial work is the point of the project.

That combination is an **ephemeral environment**: the whole setup is described as code (infrastructure as code, IaC), created with one command and destroyed with another, and paid for by the hour only while it exists. Commercial teams use the same technique for preview and test environments.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|-------|--------------------|------------------------|
| 1 | Availability | Always on; a link that always works (wake on request); up for days at a time; up for short sessions | **Short sessions, on demand.** The environment exists only while the owner is using it and is destroyed afterwards. It matches how a demo is used and keeps costs near zero without depending on free tiers. The cost of an always-on setup (roughly €30–50 a month on AWS) buys nothing a demo needs. |
| 2 | Kind of hosting | A hyperscaler (AWS, Azure, Google Cloud); a platform as a service (PaaS: Render, Railway, Fly.io, Vercel, Heroku); a virtual private server (VPS: Hetzner, DigitalOcean) | **A hyperscaler.** It is where most commercial systems run, and its building blocks (networks, identity and access management, managed databases, containers, IaC) are the skills the project wants to learn. A PaaS is widely used by startups, but it deliberately hides the infrastructure, so less of what is learned transfers. A VPS teaches Linux administration and running PostgreSQL yourself, but not cloud platforms. |
| 3 | Cloud provider | AWS; Google Cloud; Azure | **AWS.** The market leader and the most requested cloud skill. The pattern Szop uses (containers on ECS behind a load balancer, PostgreSQL on RDS) is the classic commercial AWS setup. It has the steepest learning curve of the three: networking, security groups and IAM must be understood before anything runs. Google Cloud fits Szop's single container most simply (Cloud Run scales to zero and has a permanent free allowance), and Azure is strong in enterprises, but both are less widespread. AWS's simplest container service, App Runner, closed to new customers on 30 April 2026, so it was not an option. |
| 4 | How infrastructure is defined | Terraform with every resource written out; Terraform with ECS Express Mode; AWS Cloud Development Kit (CDK) in TypeScript; clicking in the AWS console | **Terraform, with every resource written out explicitly:** network, security groups, load balancer, ECS service, database. It is the most widely used IaC tool and works across clouds. Writing each resource teaches what it is for, which is the goal. ECS Express Mode (new in late 2025, AWS's successor to App Runner) creates the load balancer, certificate and scaling from a few lines, and hides exactly the parts that teach the most. The CDK would keep one language across the project, but works only on AWS, is less common in job ads and its high-level building blocks hide as much as Express Mode. Clicking in the console cannot be repeated reliably, which rules out creating and destroying the environment on demand. |
| 5 | Terraform or OpenTofu | Terraform; OpenTofu | **Terraform.** OpenTofu is the open-source fork created after Terraform's 2023 licence change; the two are nearly identical and the licence does not affect Szop. Terraform is the name in job ads and most documentation. |
| 6 | Layout of the infrastructure code | One configuration for everything; configurations grouped by how long their resources live | **Three Terraform root modules** (each a folder with its own state, applied separately) under `infra/` in the monorepo. **`infra/bootstrap`**: the S3 bucket for Terraform state and the budget alerts, created once. **`infra/base`**: permanent resources that are slow to create or tied to an identity: the image registry, the DNS zone, the certificate, the email sender identity, the secrets and the log group (together roughly €0.50–1 a month). **`infra/demo`**: everything created for a session and destroyed after it: network, load balancer, ECS cluster and service, database. Dependencies point one way only, **demo → base → bootstrap**, and teardown runs in the reverse order. Keeping them apart means destroying the demo can never touch the registry or the domain. Whether demo finds base's resources by name (data sources) or by reading base's outputs (`terraform_remote_state`) is decided in the implementation phase. Every group can be destroyed; a domain bought through AWS stays registered until it expires or its auto-renewal is cancelled. |
| 7 | Terraform state | A local file; an S3 bucket with S3's native locking; S3 with a DynamoDB lock table; HCP Terraform (HashiCorp's hosted service) | **An S3 bucket created by bootstrap, with Terraform's S3-native lock file.** State is shared by the owner's machine and, later, CI. The lock file prevents two runs from clashing without the DynamoDB table older setups needed. Bootstrap cannot keep its own state in a bucket it has not created yet: it starts with local state (ignored by git) and may move it into the bucket afterwards. Destroying bootstrap means moving its state back first. This is a documented, one-off step. |
| 8 | Region | Frankfurt (`eu-central-1`); Stockholm (`eu-north-1`) | **Frankfurt.** The closest full-featured region to the owner. Stockholm is slightly cheaper, which matters little at these amounts. |
| 9 | Data between sessions | A fresh database every session; a final snapshot on teardown, restored on the next spin-up | **Fresh every session.** Each spin-up starts with an empty, migrated database; seed data is copied per workspace anyway. Restoring snapshots adds minutes to every spin-up, Terraform complexity and a small permanent cost, for data a demo does not need. |
| 10 | Compute | ECS on Fargate; ECS on EC2 instances; Kubernetes (EKS); Lambda functions | **ECS on Fargate:** AWS runs the containers, with no servers to manage or patch. **One task (instance) with 0.25 vCPU and 0.5 GB of memory, never more, on x86_64.** A single instance keeps the in-process event bus and cleanup task of `architecture.md` valid unchanged. ARM (Graviton) is about 20% cheaper, but the owner's machine builds x86_64 images natively, and emulated ARM builds are slow. EC2 means managing servers; EKS's control plane alone costs about $73 a month and Kubernetes is far more than one container needs. Lambda does not fit a long-running process with WebSockets and in-process timers. |
| 11 | One origin in production | The API serves the SPA's files; the SPA in S3 behind CloudFront, with `/api/*` routed to the load balancer; the load balancer routing paths to two services | **The API serves the built SPA** with `@fastify/static`, falling back to `index.html` for any non-API path so React Router's URLs survive a reload. One container, one origin, no extra infrastructure. The E2E environment of ADR 0007 therefore runs one process too. S3 and CloudFront is the textbook setup for SPAs and faster for users far away, but adds a content delivery network (CDN) that takes 5–15 minutes to create or delete, which does not pay off for a demo. |
| 12 | Container image | — | **A multi-stage Dockerfile:** a build stage with the full toolchain compiles the SPA and the API, including `packages/shared` (ADR 0005, decision 8); the final stage copies only the build output and production dependencies onto a slim Node 24 image. The exact build steps are decided in the implementation phase. Images live in **ECR** (Elastic Container Registry), whose lifecycle policy keeps only the most recent few. |
| 13 | Image tags | The git commit hash; a version from a git tag; both | **Both.** Every image is tagged with the **commit hash** it was built from: automatic, unique and pointing at the exact code, so any commit (including an unfinished branch) can be deployed and identified. An image built from a **git version tag** also gets the version, pointing at the same image. Tags in ECR are **immutable**, so a published version can never be overwritten, and the `latest` tag is never used, because it hides what is running. The versioning scheme and when versions are cut belong to the git workflow topic ([ADR 0006](0006-git-workflow-topic.md)). |
| 14 | Database migrations | When the container starts; in a separate one-off task per deployment | **When the container starts**, before it accepts requests. With exactly one instance nothing can race. A separate task matters once several instances start at the same time. |
| 15 | Health check | — | **`GET /api/health`**, which also checks the database connection. The load balancer sends traffic only to a healthy task, and ECS replaces a task that keeps failing. |
| 16 | Network | Public and private subnets with no NAT gateway; private subnets with a NAT gateway; private subnets with VPC endpoints | **A virtual private cloud (VPC) across two availability zones**, since the load balancer and RDS both require two. **Public subnets** hold the load balancer and the Fargate task. The task has a public IP address so it can reach ECR, CloudWatch, SES and the secret stores directly. **Private subnets** hold only RDS, with no route to or from the internet. **Security groups** do the locking down, each layer accepting traffic only from the one in front of it: the load balancer accepts 443 and 80 (redirected to HTTPS) from anyone; the task accepts the app port only from the load balancer; RDS accepts 5432 only from the task. A NAT gateway (about $32 a month) or the five or so VPC endpoints (more per hour than the rest of the environment) would let the task live in a private subnet, which is not worth their cost for a demo. |
| 17 | HTTPS and domain | A domain registered through Route 53; a domain from another registrar; a subdomain of an existing domain; CloudFront's default `…cloudfront.net` address | **A domain registered through Route 53**, AWS's DNS service. HTTPS is required because the session cookie is `Secure` (ADR 0002), and AWS Certificate Manager (ACM) issues free certificates only for domains you control, not for the load balancer's `…elb.amazonaws.com` name. A domain also gives **a stable URL across spin-ups** (the load balancer's name changes every time) and a proper sender identity for email. **Base** holds the DNS zone (about $0.50 a month) and a certificate for `demo.<domain>`. **Demo** only adds the DNS record pointing that name at the new load balancer. Registration through Route 53 keeps registration, DNS and certificates in one place, at a slightly higher price than the cheapest registrars. CloudFront would bring back the CDN rejected in decision 11, and its address changes with every spin-up. The domain name itself is chosen when it is bought. |
| 18 | Infrastructure-level protection | AWS Shield Standard; CloudFront with AWS WAF (web application firewall) | **Shield Standard**, which protects every load balancer at no cost against common network-level floods. Together with the application's rate limits and quotas (ADR 0003) and an environment that exists for hours at a time, it is enough. CloudFront with WAF is the step up for a public, always-on service. This answers the open point of ADR 0003. |
| 19 | Database | RDS for PostgreSQL; Aurora Serverless v2; PostgreSQL in a container | **RDS for PostgreSQL**, the smallest sensible configuration: `db.t4g.micro` (burstable, 1 GB of memory), 20 GB of storage, one availability zone, encrypted at rest, not publicly accessible. **No automated backups, no final snapshot, no deletion protection**, since the data is disposable (decision 9); a real production system would turn all three on. **Version:** the newest PostgreSQL major version RDS offers when the walking skeleton is built, pinned to the same major version in `compose.yaml` (the open point of ADR 0005). Aurora Serverless v2 can scale to zero, but it is AWS-specific and costs more per hour while running, and scaling to zero does not matter when the database is destroyed anyway. PostgreSQL in a container on Fargate would need persistent storage and hand-made administration, which RDS exists to avoid. |
| 20 | Database access for debugging | ECS Exec; a bastion host; a publicly reachable database | **ECS Exec:** `aws ecs execute-command` opens a shell inside the running task, and `psql` runs from there. No server kept only for access (a bastion host) and no public database port. |
| 21 | How secrets reach the app | Plain values in the ECS task definition; ECS `secrets` references; the app fetching them with the AWS SDK | **ECS `secrets` references.** The task definition holds only a reference (an ARN, the identifier of an AWS resource) to each secret; ECS reads the value when the task starts and sets it as an environment variable in the container. The app stays unaware of AWS: locally it reads `.env`, in AWS the same variables, validated by the same Zod schema. Plain values are readable by anyone who can view the task definition and end up in Terraform state. Fetching with the SDK puts AWS code and a second configuration path into the app, and the value still sits in the process's memory. The remaining risk, a secret in the process environment, is handled by two rules: **the configuration is never logged**, and pino's `redact` option hides secret fields. Code running inside the process can read secrets under every option. |
| 22 | Where secrets live | SSM Parameter Store; Secrets Manager; both | **Both, each where it fits.** App secrets (the Better Auth signing secret) are `SecureString` parameters in **SSM Parameter Store** (the Parameter Store of AWS Systems Manager): free and encrypted. The **database password is generated and kept by RDS itself** in Secrets Manager (a few cents while the demo exists), so no person or file ever holds it. **Secret values never appear in git, the image, the task definition or Terraform state**; Terraform's write-only arguments keep generated values out of state where the provider supports them, which the implementation phase confirms for each resource. |
| 23 | IAM roles of the app | — | **Two roles, with the least privilege each needs.** The **task execution role** is what ECS uses to pull the image, write logs and read the task's secrets. The **task role** is what the app itself runs as: it may send email through SES, plus what ECS Exec needs, and nothing else. |
| 24 | Email | Amazon SES; a third-party provider (Resend, Postmark) | **Amazon SES.** Base registers the domain as a sender identity and Terraform writes its DKIM records (signatures proving mail really comes from the domain) into Route 53. The app's SES implementation of `EmailSender` sends through the AWS SDK as the task role, so there is **no email API key** at all. **SES stays in its sandbox**, where mail reaches only addresses verified in advance (up to 200 a day). That is enough for sessions the owner runs: the owner verifies the addresses they register with. Leaving the sandbox is a manual request to AWS, made only if visitors should register on their own. Resend or Postmark are simpler to start with, but add a vendor and an API key to protect. |
| 25 | People's access to AWS | The root user; an IAM user with access keys; IAM Identity Center | **The root user gets multi-factor authentication (MFA) and no access keys, and is then not used.** Everyday work uses a user in **IAM Identity Center**, AWS's single sign-on (SSO) service, with administrator rights: `aws sso login` gives the CLI and Terraform short-lived credentials that expire after a few hours. **No long-lived access keys** exist on the owner's machine; a leaked key is the most common way AWS accounts are compromised. The root user and the Identity Center user are set up by hand in the console, since Terraform needs an identity before it can run. How CI authenticates is left to the CI/CD topic. |
| 26 | Cost guards | — | **AWS Budgets** alerts by email at low thresholds (for example a forecast above $5 and actual spending above $10 in a month), created by bootstrap. **Every resource carries tags** `project=szop` and its group (`bootstrap`, `base`, `demo`), set once as the Terraform provider's default tags, so Cost Explorer shows what the demo costs. **An automatic teardown safety net is required:** a demo still running after a set time is destroyed. A nightly scheduled CI job running `terraform destroy` is the natural mechanism, so the CI/CD topic implements it. Both come before the walking skeleton, so no demo runs without it. |
| 27 | Logs and monitoring | — | **pino's JSON lines on standard output go to CloudWatch Logs.** The log group lives in **base**, with 7-day retention, so logs survive teardown and a session can be examined afterwards. Monitoring is the load balancer's health checks, ECS replacing failed tasks and CloudWatch's free default metrics. No alarms, dashboards, uptime monitor or error tracking (such as Sentry): a demo is watched live by the person running it. |
| 28 | Environments | A demo only; staging and production | **One environment: the demo.** Local development and the test suites cover everything before it. A second environment would double the infrastructure for no audience. |
| 29 | Definition of done | — | **"The change is deployed" (ADR 0004, decision 7) means:** the phase's image is built and pushed, a demo environment is created from it, the app is checked there (the health check passes and the phase's behavior works in a browser), and the environment is destroyed. The walking skeleton's "deployed to production" (ADR 0004, decision 5) means the same. |
| 30 | Tooling | — | Added to the development environment of ADR 0005: the **Terraform CLI**, its version constrained in the code (`required_version`) and the AWS provider locked by the committed `.terraform.lock.hcl`; **AWS CLI v2** and the **Session Manager plugin** that ECS Exec needs. `terraform fmt` and `terraform validate` run as scripts; further checks (such as tflint) belong to the CI/CD topic. |
| 31 | Documentation | — | **`docs/operations/demo-environment.md`**: a runbook for the one-time AWS account setup, spinning up, tearing down, debugging with ECS Exec and logs, costs, and destroying everything including base and bootstrap. Following ADR 0005, decision 15, tool pages **`docs/development/tools/terraform.md`** and **`aws-cli.md`**. The [stack overview](../architecture/stack-overview.md) explains the AWS concepts in a section of its own. |
| 32 | Deliberately left out | — | **A CDN and AWS WAF** (decisions 11, 18), **a NAT gateway and VPC endpoints** (decision 16), **more than one instance and autoscaling** (decision 10), **backups** (decision 19), **Aurora** (decision 19), **Kubernetes** (decision 10), **alarms and error tracking** (decision 27), **SES production access** (decision 24), **ARM/Graviton** (decision 10), **a staging environment** (decision 28) and **load testing** (ADR 0007, decision 6): a deliberately tiny demo has no load targets worth measuring. Load testing could return as an optional learning phase with k6 against the demo environment. Each can be added when a real need appears. |

## Consequences

- **Costs.** Roughly $0.07 an hour while the demo runs (load balancer, one small Fargate task, `db.t4g.micro`, public IP addresses), so a three-hour session costs about $0.20. Between sessions: the domain (about $13–15 a year for a `.com`), the DNS zone and a few cents for images, state and logs, together around €1.50 a month. A forgotten demo would cost about $50 a month, which is why decision 26 requires the automatic teardown. A new AWS account's credits ($100–200 for six months) cover the first months.
- **Spinning up takes 10–15 minutes**, mostly waiting for RDS; tearing down takes a few. Sessions are planned, not instant.
- **The walking skeleton phase** writes the Terraform code for all three groups, the Dockerfile, the `@fastify/static` setup, `/api/health`, migrations at startup and the SES `EmailSender`, and creates the runbook and tool pages. The owner creates the AWS account, secures the root user, sets up IAM Identity Center and buys the domain, following the runbook.
- **The configuration schema** receives the database password as its own variable, injected from the RDS-managed secret. How it assembles the connection string is decided in that phase.
- **`architecture.md`** records the deployment and resolves its open points: the API serves the SPA, exactly one instance runs (so the in-process event bus and cleanup stay as designed), Amazon SES is the email provider and Shield Standard is the infrastructure-level protection.
- **The git workflow topic** decides the versioning scheme behind the version tags of decision 13.
- **The CI/CD topic** must provide: how CI authenticates to AWS (expected: OpenID Connect (OIDC), with no stored keys); building and pushing images; where `terraform apply` and `destroy` run (the owner's machine, a manual CI workflow, or both); the scheduled teardown safety net of decision 26; and Terraform checks such as tflint.
- When `docs/operations/` exists, `CLAUDE.md` and the README's documentation list point to it.
