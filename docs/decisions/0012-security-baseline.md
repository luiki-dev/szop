# ADR 0012 — Security baseline: threat model, access control, web baseline, rate limits and delivery

- **Status:** ✅ Accepted — decision 19 refined by [ADR 0015](0015-git-push-guard-hook.md) (a hook catches the pushes the deny rules miss; the broken `:branch` rule removed)
- **Date:** 2026-10-01
- **Refines:** [ADR 0002](0002-technical-architecture.md), decisions 7 (the cookie's attributes, protection against cross-site request forgery) and 16 (every referenced ID resolved within the workspace, through an access layer, backed by the database); [ADR 0003](0003-abuse-protection.md), decision 2 (the client IP behind the load balancer, new limits, a daily email cap); [ADR 0010](0010-ci-cd.md), decisions 12 (a required reviewer on `demo`, a `demo-teardown` environment) and 16 (the deploy role trusts both environments; the plan role cannot read log contents)
- **Extends:** the document roles table of [ADR 0011](0011-design-sanity-check-follow-ups.md), decision 4 (the threat model)

## Context

The security baseline is the sixth foundation topic of [ADR 0004](0004-implementation-process.md), added by [ADR 0011](0011-design-sanity-check-follow-ups.md), decision 6, after CI/CD and before visual design. Like every foundation topic, it settles direction and constraints only; the code, configuration and settings are written by the phases that introduce them. It has to come before the walking skeleton, which builds the first endpoint and the first deploy role.

The starting point is six open points, each from the [2026-09-29 design sanity check](../audits/2026-09-29-design-sanity-check.md):

- **OP-050** (finding C1): start from a threat model.
- **OP-034** (CRITICAL-1): the access-control rule protects the record being written, not the records it points to. An item saved in one workspace with another workspace's `category_id` passes the scoped update.
- **OP-042** (MAJOR-8): with sharing, lists are reached through the list owner's workspace, not the session's, so an MVP where every query takes the session's workspace would be rewritten.
- **OP-035** (MAJOR-4): the per-IP rate limits depend on how the client IP is read behind the load balancer, which no document mentions; the email-sending endpoints have no limit.
- **OP-036** (MAJOR-5, C7): no document mentions cross-site request forgery (CSRF), security headers, session revocation, tokens in URLs, account enumeration or a password policy.
- **OP-037** (MAJOR-11, C8): any job on any branch that declares the `demo` environment gets the deploy role, without the button being pressed; ADR 0010's wording says otherwise.

Szop runs only as an on-demand demo ([ADR 0008](0008-hosting.md)), but its application code is the code an always-on service would run. Most of it is written by Claude Code, acting with the owner's credentials.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|-------|--------------------|------------------------|
| 1 | How far the baseline goes | Proportionate to the demo (fix the audit's findings only); production grade throughout (as if always-on, measured against a checklist such as OWASP ASVS); split by layer | **Split by layer.** **Application rules are production grade**: they cost the same whether the app runs as a demo or always-on, and they are where most of the learning is. **Infrastructure stays proportionate to the demo**: what an always-on service would add (backups, a web application firewall (WAF), alarms) stays in [OP-033](../open-points.md#op-033). Production grade throughout would decide things the demo never exercises; fixing only the findings would leave the next hole to the next audit. |
| 2 | The threat model | A section of this ADR; a section of `architecture.md`; a living page of its own. As a method: an actor table only; a full STRIDE analysis per component and data flow; an actor table with one STRIDE check per entry point | **A living page, [`docs/architecture/threat-model.md`](../architecture/threat-model.md), built from an actor table and one STRIDE check per entry point.** The actor table answers OP-050's question directly: who can act, through which path, what they can reach, and what guards it. Checking each entry point once against **STRIDE** (spoofing, tampering, repudiation, information disclosure, denial of service, elevation of privilege) makes sure no category of threat is forgotten, and teaches the industry's vocabulary. A full per-component STRIDE analysis is the thorough form, but too heavy for a page every phase is meant to update. Inside this ADR the model would be frozen today and stale once sharing and live updates arrive; inside `architecture.md` it would mix GitHub, CI and Claude Code into the application's architecture. **Every phase that adds an actor or an entry point updates the page** (the definition of done's "living docs" item). |
| 3 | The access-control rule (CRITICAL-1) | Scope the record being written (as before); resolve every ID | **Every ID in a request is resolved within the workspace the request acts in**: the record itself and every record it points to, in the path, the query and the body (`category_id`, the new parent in a category move, product IDs in a multi-add, the template ID, a unit, IDs the browser generates for new rows). A reference that does not resolve gets the same **404** as a missing record. Scoping only the written record leaves the classic "insecure direct object reference" (IDOR) hole one level removed: the item is saved in my workspace, but it points into yours, shows your category's name through a join, and [CAT-3](../requirements/functional-requirements.md#cat-3)'s cascade reaches across workspaces. |
| 4 | Where the workspace comes from (MAJOR-8) | Services read the session's workspace (as before); an access layer gives services the workspace they act in | **An access layer, not the session.** Services never read the session. They receive a context `{ user, workspaceId, role }` from one of two functions: **`ownWorkspace(user)`**, the session's own workspace, for one's own data (categories, catalog, units, templates, settings, the list overview); and **`requireListAccess(user, listId, minRole)`**, for anything reached through a list, which returns **the list owner's workspace** and the caller's role. In the MVP the only role is *owner*, so it amounts to "the list is in my workspace, otherwise 404"; sharing adds *shopper* and *editor* to this function, and the services and their queries do not change. **Item routes nest under their list** (`/api/lists/:listId/items/:itemId`), and an item is looked up within that list, never by its ID alone. Editors reach the owner's category tree through the list ([SHR-5](../requirements/functional-requirements.md#shr-5)); the route is the sharing phase's choice. Reading the session in every service would be rewritten when sharing arrives, because an editor acts in someone else's workspace. |
| 5 | Repositories | Lookups by ID alone allowed; the workspace required in every query | **Every repository function takes `workspaceId` as a required parameter**, and there is no unscoped lookup such as `findById(id)`. Forgetting the scope is then a TypeScript error, not something code review has to catch. |
| 6 | How the database backs the rule | Checks in the services only; services backed by composite foreign keys; PostgreSQL row-level security (RLS) | **Services, backed by composite foreign keys.** Every workspace-owned table has `workspace_id NOT NULL` and `UNIQUE (workspace_id, id)`; every reference to such a table is a composite foreign key, such as `items (workspace_id, category_id) → categories (workspace_id, id)`, so **PostgreSQL refuses a cross-workspace reference** even when a service forgets the check. A nullable reference that becomes null when its target is deleted ([CAT-3](../requirements/functional-requirements.md#cat-3)) uses **`ON DELETE SET NULL (category_id)`**, which nulls only that column; this needs **PostgreSQL 15 or newer**. A write that reaches the database anyway fails with a foreign-key error, answered as 500 and logged: a visible bug, not a leak. Checks in the services alone are simplest, but one forgotten check is a hole with nothing beneath it, which is how CRITICAL-1 arose. RLS is the strongest guarantee (even an unfiltered query sees only one workspace), but sharing makes its policies complex, every transaction must set the workspace, and an empty result is hard to debug; it is too much for a first project. **Tested by** an API test pattern, "a reference into another workspace returns 404", for every field that references another record, using a helper that sets up two workspaces; and **a schema test** that reads PostgreSQL's catalog and fails if a workspace-owned table lacks the composite unique key or a foreign key into one is not composite, which guards every table added later. |
| 7 | Cookies and cross-site request forgery | `SameSite=Strict`; `SameSite=Lax`; CSRF tokens; Origin checks | **The session cookie is `HttpOnly`, `Secure`, `SameSite=Lax`, has no `Domain` attribute, and uses the `__Host-` prefix** if Better Auth allows it (otherwise `__Secure-`); the prefix stops a sibling subdomain from planting a cookie. `Strict` would make the user look logged out whenever they arrive through a link in an email or on another site; `Lax` is safe because **GET never changes anything**. **Every unsafe request (POST, PUT, PATCH, DELETE) on every route**, not only Better Auth's, must come from the app itself (`Sec-Fetch-Site: same-origin`, a header the browser sets and scripts cannot forge, with an `Origin` check as the fallback), otherwise **403**; and its body must be JSON (`Content-Type: application/json`), which an HTML form on another site cannot send. Better Auth's `trustedOrigins` lists exactly the app's origin. The WebSocket (later) checks `Origin` when the connection opens. Better Auth's own check covers only `/api/auth/*`. With the SPA and the API on one origin, these checks replace CSRF tokens, which would add state for no extra protection. |
| 8 | Security headers | None; `@fastify/helmet` with its defaults; helmet with a strict Content Security Policy | **`@fastify/helmet`, with a strict Content Security Policy (CSP).** The policy allows only the app's own files: `default-src 'self'`, `object-src 'none'`, `base-uri 'none'`, `form-action 'self'` and **`frame-ancestors 'none'`** against clickjacking. **No inline scripts and no `<style>` elements**: this is a constraint for the visual design topic, which chooses build-time CSS (CSS modules, Tailwind and the like) over a CSS-in-JS library that injects styles at run time ([OP-001](../open-points.md#op-001)). **HTTP Strict Transport Security (HSTS) for one year, without `preload`**, since the demo's domain may change. **`Referrer-Policy: no-referrer`**, plus helmet's other defaults (`X-Content-Type-Options: nosniff` and the like). The API serves the SPA itself, so these headers protect the whole app. |
| 9 | Tokens in URLs | — | Verification, password-reset and (later) share-link tokens travel in URLs. **They are single-use and expire** (Better Auth's defaults); **the request log's URL serializer strips them** before anything reaches CloudWatch Logs, which keeps logs for 7 days; **`no-referrer`** keeps them out of other sites' logs; and **the SPA removes the token from the address bar** once it has been used. Otherwise a log reader would hold working links, undoing the reason tokens are stored hashed. |
| 10 | Sessions and account actions | — | **Better Auth's session cookie cache stays off**: while it is on, a revoked session keeps working until the cache expires. **A password change or reset revokes every other session**, through Better Auth's options for both. **Deleting an account ([ACC-6](../requirements/functional-requirements.md#acc-6)) requires the current password**, not only a confirmation dialog, so a session left open on a shared computer cannot delete the account. |
| 11 | Password policy (C7) | 8 or more characters with a breach check; 12 or more with a local list of common passwords; 15 or more with a breach check | **15 to 128 characters, no composition rules, checked against breached passwords.** This follows NIST's SP 800-63B, revision 4: 15 characters is its minimum for a password that is the only factor, and it advises against rules like "one digit, one symbol". Pasting and password managers work. **Better Auth's Have I Been Pwned plugin** checks the password on registration, change and reset; it sends only the first 5 characters of the password's SHA-1 hash, so the service never learns the password (k-anonymity). **If the service cannot be reached, the check fails open**: the password is accepted and a warning is logged, so an outside outage never blocks registration. Better Auth's default hashing (scrypt) stays. 8 characters is Better Auth's default, but below NIST's minimum for a single factor; a local list is far smaller than Have I Been Pwned's and has to be kept up to date. |
| 12 | Account enumeration | Reveal it everywhere; reveal it at registration only; never reveal it | **Never reveal whether an email address has an account.** Login answers the same for an unknown email and for a wrong password, with no noticeable difference in timing. **Registration always says "check your inbox"**; an address that already has an account gets an email saying so, with links to log in or reset the password. Password reset and verification resend always answer with the same generic success. Invitations ([SHR-1](../requirements/functional-requirements.md#shr-1), later) behave the same whether or not the invitee has an account. The design already hides which lists exist; this does the same for accounts. Revealing it at registration only is the common compromise, and simpler with Better Auth's defaults, but it lets anyone check an address in one request. **Cost:** registration needs custom handling around Better Auth (the exact hooks are the account phase's choice), and it sends an email even for existing accounts, which decision 14 limits. |
| 13 | Which IP address counts (MAJOR-4) | `trustProxy: true`; no trusted proxy; a fixed number of trusted hops | **Exactly one proxy hop is trusted in AWS, and none locally**, set from a configuration value (`TRUSTED_PROXY_HOPS`), validated at startup like every setting. The load balancer appends the address it saw to the end of `X-Forwarded-For`; everything before it was written by the client. With one trusted hop, Fastify's `request.ip` is the address the load balancer saw. **`trustProxy: true`**, the usual copy-paste, takes the leftmost entry, which the client controls, so a script bypasses every per-IP limit by sending a random value. **No trusted proxy** puts every client behind the load balancer's address, so the 11th guest of the hour is refused for everyone. **Better Auth must use the same address**: its own lookup takes the first entry of a configurable header, so the app hands it the address Fastify computed (for example, by overwriting the header Better Auth reads); the mechanism is the walking skeleton's choice. **Tested by** an API test that sends a forged `X-Forwarded-For` through `inject()`, simulating the load balancer, and expects the real address in both limiters; and **a one-time manual check on the demo** in the walking skeleton, sending a forged header and reading the address in the log, which proves AWS really has one hop. |
| 14 | Rate limits (MAJOR-4) | — | **[LIM-4](../requirements/functional-requirements.md#lim-4) gains rows** in the [functional requirements](../requirements/functional-requirements.md): registrations are limited **per target email too** (3 an hour), since registration now sends an email even for existing accounts; **password reset and verification resend**: 5 an hour per IP and 3 an hour per target email; **requests without a session**: 300 a minute per IP, a stated choice rather than an omission; and **a daily cap on outgoing emails in total**, configured below SES's quota (for example 150 a day in the SES sandbox, which allows 200), so an attack spread over many addresses cannot use up the quota. **When a per-email limit or the cap is hit**, registration, reset and resend still give their usual answer and send no email, so a limit never reveals anything about an address (decision 12); hitting the cap also logs a warning. **The per-email login limit** (10 failed attempts in 15 minutes) is custom code, since Better Auth's limiter works per IP only; it counts failed attempts, and someone could still lock a victim out for 15 minutes at a time, which is accepted at these values because the victim can still reset the password. |
| 15 | Where rate-limit counters live | In memory; in PostgreSQL; in Redis | **In memory**, for both `@fastify/rate-limit` and Better Auth. That is valid only because exactly one instance runs ([ADR 0008](0008-hosting.md)); counters reset when the container restarts, which is acceptable for a demo. Several instances would need a shared store, added to [OP-033](../open-points.md#op-033). |
| 16 | Who can use the deploy role (MAJOR-11) | No reviewer, the wording corrected (accept the risk); only `main` may deploy; a required reviewer on `demo`; customise the OIDC subject to name the workflow file | **The owner is a required reviewer on `demo`, and the teardown moves to a second environment, `demo-teardown`, which only `main` may use.** The OIDC token certifies the environment, not the workflow file or the button: today any job in any workflow on any branch that declares `environment: demo` gets the deploy role, including a new file pushed by Claude Code, a compromised dependency on the owner's machine or a prompt-injected session. **With the reviewer**, every job in `demo` pauses at "Waiting for review" until the owner approves, so a run the owner did not start is rejected before it receives a token. The `demo-up` button stays in GitHub Actions; its image and deploy jobs wait together, and one approval starts them. "Prevent self-review" stays off, since the owner both presses and approves. **The scheduled teardown cannot wait for an approval at night**, so `demo-down` (nightly and by hand) runs in **`demo-teardown`: no reviewer, `main` only**. Without the branch restriction a branch would simply declare `demo-teardown`, which unlocks the same role; with it, only workflows already on `main`, merged by the owner, can use it. `demo-down` still destroys with the deployed commit's Terraform code ([ADR 0011](0011-design-sanity-check-follow-ups.md), decision 7). **The deploy role trusts both environments.** Only `main` deploying is impossible: the definition of done checks a branch on the demo before its PR is merged. Accepting the risk leaves the hole open to anything that can push a branch. A custom subject naming the workflow file adds nothing once the reviewer sees which workflow asks. **Cost:** one click per deploy, and one more environment. This reverses ADR 0010, decision 12's "no required reviewer": the approval is the only real proof that the owner pressed the button. |
| 17 | The plan role's reach | — | **`szop-ci-plan` is denied reading log contents** (`logs:GetLogEvents`, `logs:FilterLogEvents`, `logs:StartQuery`, `logs:StartLiveTail`), on top of ADR 0010, decision 16's denies on secret values. It trusts every same-repository PR, and an edited workflow could otherwise copy the app's logs into a public job log. `terraform plan` can run arbitrary programs (`data "external"`); with a role that is read-only, without secrets and without logs, that is accepted. |
| 18 | Code that runs next to AWS credentials (C8) | — | **`id-token: write` is granted per job, never per workflow**, so only the jobs that need AWS can ask for a token. **Those jobs never run `pnpm install` or project scripts on the runner**: they run Terraform and the AWS CLI only, and the app's dependencies are installed inside the Docker build, which does not see the runner's credentials. **pnpm's default stays**: dependencies' install scripts run only for packages on an allowlist (`onlyBuiltDependencies`), kept as short as possible, which also protects the owner's machine. A compromised dependency then runs, at worst, where no AWS credentials are. |
| 19 | Guardrails for Claude Code | `CLAUDE.md` alone; `CLAUDE.md` backed by permission `deny` rules | **Deny rules in `.claude/settings.json`**, committed so they apply in every session and win over any `allow`: merging PRs (`gh pr merge`), running workflows (`gh workflow run`), force pushes (`--force`, `-f`, `--force-with-lease`, a `+branch` refspec), deleting remote branches (`--delete`, `-d`, a `:branch` refspec) and pushing tags (`--tags`). They back the `CLAUDE.md` rules that Claude never merges a PR and never triggers `demo-up` or `demo-down` unless asked. **They guard against mistakes, not against a determined attacker**: a shell command can be written in a form a pattern does not match. The real boundaries are GitHub's: the rulesets ([ADR 0009](0009-git-workflow.md)) and the reviewer on `demo` (decision 16). |

## Consequences

- **Costs:** nothing extra. Required reviewers are free on a public repository; the breach check's service is free; helmet and the rate limiter are open-source plugins.
- **The living docs are updated:** `architecture.md` (access control, data model, abuse protection, web security, a link to the threat model), the stack overview (cookies and CSRF, security headers, composite foreign keys, the nested route example), the functional requirements ([ACC-2](../requirements/functional-requirements.md#acc-2)'s password policy and registration, [ACC-6](../requirements/functional-requirements.md#acc-6)'s password, [LIM-4](../requirements/functional-requirements.md#lim-4)'s new rows), the glossary, the definition of done and the PR template (the threat model in the living docs item), `git-workflow.md` (what enforces the deploy approval and Claude's guardrails), the phase walkthrough (the approval in `demo-up`, the teardown's environment), and the documentation lists of `CLAUDE.md` and the README.
- **ADR 0002 and ADR 0003 are refined** by decisions 3–7 and 13–15; **ADR 0010 is refined** by decisions 16 and 17, which correct its wording ("no other workflow can assume it, even if edited") and the glossary's ("only OIDC tokens from specific workflows").
- **`.claude/settings.json` is added** with the deny rules of decision 19.
- **The open points of this topic are closed** (OP-034, OP-035, OP-036, OP-037, OP-042, OP-050). The work they leave is tracked as new points for the phases that build it: the app-wide web baseline in the walking skeleton (**OP-053**), the access layer and the composite keys in the first data phase (**OP-054**), and the session, password and account rules in the account phases (**OP-055**). Existing points gain what this ADR adds to them: the CSP constraint on styling (OP-001), the owner's steps (OP-003: create `demo-teardown`, add the reviewer on `demo`), pnpm's allowlist (OP-005), PostgreSQL 15 or newer (OP-006), the workflows' token and install rules (OP-019), the deploy role's trust and the plan role's denies (OP-020), a shared store for rate-limit counters (OP-033), and remapping references when a guest's lists are imported (OP-038), which the composite keys enforce.
- **The next foundation topic is visual design** (OP-001), the last one before the roadmap.
