# ADR 0010 — CI/CD: GitHub Actions checks and push-button demo environments

- **Status:** Accepted — decision 23 refined by [ADR 0011](0011-design-sanity-check-follow-ups.md), decision 2 (the nightly `demo-down` and a placeholder `demo-up` are merged before any demo, not together with the first `demo-up`); decisions 11 and 13 refined by ADR 0011, decision 7 (both workflows run the Terraform code of the deployed commit; one concurrency group per workflow and the state lock instead of one shared group)
- **Date:** 2026-09-29
- **Completes:** the CI/CD obligations left by [ADR 0005](0005-development-environment.md) (type checks and tests run in CI), [ADR 0007](0007-testing-strategy.md) (PostgreSQL service, Playwright browsers, traces and reports), [ADR 0008](0008-hosting.md) (CI's access to AWS, image builds, where Terraform runs, the teardown safety net, Terraform checks) and [ADR 0009](0009-git-workflow.md) (required status checks, the PR title check, release-please, versioned images, Dependabot)
- **Extends:** [ADR 0008](0008-hosting.md), decisions 6 and 23 (the app's IAM roles, the CI roles and the GitHub OpenID Connect (OIDC) provider live in `infra/base`)
- **Confirms:** [ADR 0009](0009-git-workflow.md), decision 1 (the repository stays public), after revisiting it with the paid plans in view

## Context

CI/CD is the fifth foundation topic of [ADR 0004](0004-implementation-process.md), after the git workflow ([ADR 0006](0006-git-workflow-topic.md)). Like every foundation topic, it settles direction and constraints only. The workflow files, IAM policies and settings are written in the roadmap phases that introduce them.

The starting point:

- **A public GitHub repository** owned by the personal account `luiki-dev`, on the Free plan ([ADR 0009](0009-git-workflow.md), decision 1). GitHub Actions is free and unlimited for public repositories on GitHub-hosted runners.
- **GitHub flow**, one branch and PR per roadmap phase, merge commits, the owner's merge as the approval; commits and PR titles follow Conventional Commits; releases are cut by release-please ([ADR 0009](0009-git-workflow.md)).
- **The test suites and their scripts**: Vitest unit, API and component tests against a real PostgreSQL, Playwright E2E journeys on two viewports, mutation testing on demand ([ADR 0007](0007-testing-strategy.md)). CI runs the same `pnpm` scripts as developers ([ADR 0005](0005-development-environment.md)).
- **One on-demand demo environment on AWS**, built with Terraform in three root modules (`bootstrap`, `base`, `demo`), created from any image identified by its commit hash, and destroyed after each session ([ADR 0008](0008-hosting.md)). "Deployed" means: the phase's image is built and pushed, a demo is created from it and checked, and the demo is destroyed (ADR 0008, decision 29).
- **Most code is written by Claude Code**, and a public repository whose CI can reach an AWS account is a real target. Attacks on CI pipelines are a common way into companies; the best-known recent one is the compromise of the `tj-actions/changed-files` action in March 2025.

Before deciding pipeline security, the owner asked to revisit the repository's visibility: would a paid plan with a private repository be better? The comparison is in decision 1.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|-------|--------------------|------------------------|
| 1 | Repository visibility, revisited | Stay public on the Free plan; private with GitHub Pro (personal accounts, about $4 a month); private with GitHub Team (organizations only, $4 per user a month "for the first 12 months") plus the Advanced Security add-ons | **Stay public; ADR 0009, decision 1 holds.** A paid plan gives a private repository rulesets, code owners, draft PRs and environments with secrets, and 3,000 Actions minutes a month instead of unlimited. It does **not** give a private repository what a public one gets for free: **code scanning (CodeQL), secret scanning, push protection and dependency review** need the add-ons GitHub Code Security ($30) and GitHub Secret Protection ($19) per active committer a month, sold only on Team or Enterprise, and **required reviewers, wait timers and custom protection rules on environments** need Enterprise. Matching today's public setup would take an organization on Team with both add-ons, about $53 a month, to end up where the free public repository already is. Going private hides the code, the workflows and the Terraform code, none of which should hold anything secret: secret values never reach git, images or Terraform state (ADR 0008, decision 22). The risks that come with public (PRs from forks, visible logs) are handled by decisions 13 and 21. A private repository would make sense only for a reason other than security, such as not wanting the code seen at all. |
| 2 | How much delivery is automated | CI and image builds only, with the demo run from the owner's machine; push-button environments, with Terraform run by manual CI workflows; an automatic preview environment per PR | **Push-button environments.** Manual workflows create a demo from any commit and destroy it; the owner's machine can still run Terraform directly as a fallback. The definition-of-done check (ADR 0008, decision 29) becomes one click on the phase's branch. It teaches the transferable parts of CD: OIDC-scoped IAM roles, Terraform in a pipeline, GitHub environments. And the nightly teardown safety net (ADR 0008, decision 26) needs Terraform in CI anyway. CI with image builds only leaves half of "CD" untaught. A preview per PR is common in commercial teams, but here it would mean 10–15 minutes of RDS per PR, clashes over the single `demo.<domain>` name, and costs whenever a PR sits open. |
| 3 | CI platform | GitHub Actions; GitLab CI; CircleCI or Buildkite; AWS CodeBuild and CodePipeline | **GitHub Actions.** It is built into the repository, free and unlimited for public repositories, and release-please, Dependabot and CodeQL are native to it. It is also the most common CI in job ads. GitLab CI would need the repository mirrored to a second platform. CircleCI and Buildkite are external services with their own accounts and secrets. CodeBuild keeps CI inside AWS, but integrates poorly with PRs and is paid per minute. |
| 4 | Runners | GitHub-hosted, `ubuntu-latest`; GitHub-hosted, pinned image; self-hosted | **GitHub-hosted runners pinned to `ubuntu-24.04`**, so a runner image upgrade never changes CI without a commit saying so. **No self-hosted runners:** on a public repository, a PR from a fork could run arbitrary code on the machine hosting the runner. |
| 5 | Workflow layout | One workflow for everything; one workflow per trigger and permission set | **One workflow per trigger and permission set**, in `.github/workflows/`: `ci.yml` (all quality checks, on every PR and every push to `main`); `pr-title.yml` (the PR title against Conventional Commits, on PRs opened, edited or updated); `infra-plan.yml` (`terraform plan` on PRs touching `infra/`, decision 14); `demo-up.yml` and `demo-down.yml` (decisions 11 and 13); `release-please.yml` (decision 17); `mutation.yml` (StrykerJS on demand, as ADR 0007, decision 19 asks: not on every commit). CodeQL uses GitHub's **default setup**, switched on in the repository settings with no YAML to maintain. A **composite action** in `.github/actions/setup/` holds the shared steps (check out, set up Node from `.nvmrc`, set up pnpm, restore the cache, install). Separate files keep each workflow's powers small and visible: a deploy workflow may assume an AWS role, the PR checks never can. |
| 6 | When CI runs | — | **On every push to a branch with an open PR, and on every push to `main`.** A branch without a PR runs nothing, so work in progress can be pushed freely. A run is per push, not per commit: it checks the newest commit, and `concurrency` cancels a PR's older run when a newer push arrives. For PRs, GitHub checks out the **merge of the branch into `main`** (`refs/pull/N/merge`), so CI tests what `main` would look like after the merge. The run on `main` after each merge is a cheap safety net and keeps `main`'s own status visible. |
| 7 | Checks in `ci.yml` | — | **Parallel jobs, each skipped when its area did not change:** `lint` (ESLint and Prettier in check mode); `typecheck` (`tsc --noEmit` for every package); `test` (`pnpm test` against a **PostgreSQL service container** of the same version as `compose.yaml`, coverage shown in the job summary and never gated, ADR 0007, decision 19); `e2e` (a production build, then `pnpm test:e2e` on both viewports with its own PostgreSQL service); `docker` (builds the Dockerfile without pushing, so a broken image shows up in the PR rather than at spin-up); `commits` (commitlint over **every commit in the PR**, because the local hook can be skipped with `--no-verify` and release-please reads the branch commits that merge commits bring into `main`); `infra` (`terraform fmt -check`, `terraform validate` and tflint, with no AWS credentials); `workflows` (actionlint and zizmor, decision 21). Target: a code PR fully checked in about 10 minutes. |
| 8 | Required checks and change detection | A `paths:` filter per workflow; one always-running workflow with an aggregating job | **`ci.yml` always runs; a first step detects which areas changed, jobs are skipped by their `if:` conditions, and a final job `ci-ok`** (`needs:` every job, `if: always()`) succeeds only when every job succeeded or was skipped on purpose. **The required status checks are `ci-ok` and the PR title check**, with branches required to be up to date with `main` (ADR 0009, decision 13), plus the code scanning rule of decision 21. A workflow skipped by a `paths:` filter never reports, so a required check on it would leave the PR waiting forever. With the aggregating job, a docs-only PR finishes in about a minute, and adding a job later never means editing the ruleset. |
| 9 | Caches and artifacts | — | **Cached:** the pnpm store, the Playwright browsers (keyed by Playwright's version) and Docker layers (the GitHub Actions cache backend of BuildKit). **Kept:** the Playwright HTML report and traces are uploaded as an artifact **when the E2E job fails**, for 14 days, which answers ADR 0007's question of where traces from failed runs live. |
| 10 | When images are built | On demand, when a demo is created; on every push to a PR and to `main`; on `main` and version tags only | **On demand.** The spin-up workflow builds and pushes `szop:<commit hash>` only if ECR does not have it yet, and the release workflow builds the versioned image (decision 17). The `docker` job checks every PR's Dockerfile without pushing. Only images that are deployed or released are stored. Building on every push ("build once, deploy many") is what most commercial pipelines do, and pays off when every commit is deployed automatically, which Szop does not do. Building on `main` only would break the definition of done, which checks the branch's image before merging. |
| 11 | Spinning up a demo | — | **`demo-up.yml`, run by hand** with a branch, tag or commit hash, resolved to the full commit hash. The `image` job builds and pushes the image if it is missing (decision 10). The `deploy` job runs `terraform apply` on `infra/demo` with that image tag; migrations run when the container starts (ADR 0008, decision 14). The workflow then waits for `https://demo.<domain>/api/health` to answer and writes a summary: the URL, the commit and image, and when the nightly teardown will run. The image build is expected to run in parallel with Terraform, because the ECS service starts only after RDS exists, which takes longer; the phase confirms the ordering holds, and otherwise the jobs run one after the other. **Running it again with the demo up redeploys** another commit: only the ECS service's image changes, which takes a few minutes. |
| 12 | The `demo` environment | Required reviewers on the environment; no reviewers | **A GitHub environment `demo`** holds the deploy jobs. The deploy role trusts only OIDC tokens from jobs in this environment (decision 15), so no other workflow can assume it, even if edited. The repository page shows the deployed commit and URL. **Any branch may deploy**, because the definition of done checks branch images. **No required reviewer:** the owner is the one pressing the button, so approving their own deploy would be ceremony. One can be added later, free on a public repository. |
| 13 | Tearing down, and the safety net | A nightly scheduled destroy; an AWS-side timer (EventBridge Scheduler with a Lambda function) | **`demo-down.yml` runs `terraform destroy` on `infra/demo`, by hand or every night** (cron `17 1 * * *` in UTC, about 02:17–03:17 in Poland; off the full hour, when GitHub delays scheduled runs). With nothing to destroy it finishes in seconds. A forgotten demo therefore costs at most about a day (roughly $1.70), and a failed scheduled run is emailed to the owner. **`demo-up` and `demo-down` share one `concurrency` group that never cancels:** runs queue, because a Terraform run killed halfway leaves a lock and half-created resources. **GitHub disables scheduled workflows in a public repository after 60 days without activity**, so a demo started after a quiet spell could outlive a disabled safety net: **`demo-up` re-enables `demo-down` through the GitHub API every time it runs.** The AWS Budgets alerts (ADR 0008, decision 26) stay the second net. An AWS-side timer would not depend on GitHub, but adds a Lambda function and its own IAM role for a risk the two nets already cover. This answers ADR 0008, decision 26. |
| 14 | Where Terraform runs | CI runs only the demo module, with static checks on PRs; the same plus `terraform plan` on infrastructure PRs; the same plus a push-button for base; base applied on every merge to `main` | **`infra/demo` is applied and destroyed by CI** (decisions 11 and 13); **`infra/base` and `infra/bootstrap` are applied from the owner's machine**; and **`infra-plan.yml` runs `terraform plan -lock=false` for base and demo on every PR touching `infra/`**, with the read-only role of decision 16. It posts a summary as one PR comment that updates itself (the changed resources, "2 to add, 1 to change, 0 to destroy"), with the full plan in the job log. The plan is informative, not a required check: it depends on AWS being reachable, and `terraform validate` in `ci.yml` already blocks broken code. **Everything it prints is public**, since logs and comments of a public repository are world-readable. That is acceptable only because secret values never enter Terraform state (ADR 0008, decision 22). PRs from forks get no OIDC token, so the job is skipped for them. Seeing a plan before merging is the most valuable review practice for infrastructure as code. Base changes are rare and need broad permissions, so applying them with the owner's short-lived SSO credentials is fine; a push-button for base would add a broadly privileged role to save a few applies a year. Applying base on merge (GitOps) clashes with the definition of done, which checks a phase on the demo before its PR is merged, so base changes must be applied from the branch. **Bootstrap** stays on the owner's machine in every option: it creates the state bucket that CI's Terraform runs depend on. |
| 15 | How CI authenticates to AWS | OIDC with IAM roles; access keys stored as GitHub secrets | **OIDC.** Each job asks GitHub for a signed token stating who it is (the repository, and the environment, branch or PR event); AWS checks it against an IAM role's **trust policy** and returns credentials that expire within an hour. **No AWS key exists in GitHub**, so none can leak; role ARNs are identifiers, not secrets, and are stored as GitHub **variables**. Session names carry the workflow run ID (`gh-<run_id>`), so CloudTrail's free 90-day event history shows which run did what. **The OIDC provider and the CI roles live in `infra/base`**: permanent, applied from the owner's machine, and it already holds the registry the roles refer to. Stored access keys are the most common way AWS accounts are compromised (ADR 0008, decision 25). |
| 16 | CI roles | — | **Three roles, each with the least privilege its jobs need.** **`szop-ci-plan`**, trusted only for pull requests (`repo:luiki-dev/szop:pull_request`): AWS's `ReadOnlyAccess`, with explicit denies on reading secret values (SSM parameters, Secrets Manager) and on S3 objects other than the Terraform state. **`szop-ci-deploy`**, trusted only for the `demo` environment (`repo:luiki-dev/szop:environment:demo`): push to the one ECR repository; read and write the demo's state and lock file; create and destroy the demo's resources; change the one DNS record `demo.<domain>`; and `iam:PassRole` for the app's two roles, nothing else in IAM. The nightly destroy uses it too: a destroy-only role would need nearly the same permissions, since destroying reads everything it deletes. **`szop-ci-release`**, trusted only for the `release` environment, which only `main` may use (decision 17): push and tag images in the ECR repository, nothing else. **CI never creates or edits IAM:** the app's task execution role and task role (ADR 0008, decision 23) move to `infra/base`, because a role that may create roles can create an administrator role for itself, the most common privilege escalation in AWS. **The deploy role cannot delete or change base's resources** (the registry, DNS zone, certificate, secrets, log group), so a bug in the demo's Terraform or a compromised deploy cannot reach them, which enforces ADR 0008, decision 6 in IAM and not only by folder layout. Permissions are scoped by the `szop-` name prefix and the `project=szop` tag where AWS supports it; some create actions cannot be scoped and are allowed more broadly. The phase writes the policies and checks them with **IAM Access Analyzer's policy validation**. |
| 17 | Releases | release-please with a GitHub App token; with a fine-grained personal access token (PAT) | **release-please runs on every push to `main`** with the settings of ADR 0009: one version for the repository, `bump-minor-pre-major`. **It authenticates as a GitHub App**, because a PR created with the workflow's default `GITHUB_TOKEN` triggers no other workflows, so the release PR would never get its required checks. The owner creates a small private App ("szop-release"), installed only on this repository, with *contents* and *pull requests* write permissions; each run exchanges the App's private key for a token that expires within an hour (`actions/create-github-app-token`). The release PR is then authored by `szop-release[bot]`, clearly not the owner, and can do nothing beyond those two permissions. **The App's private key is the only long-lived secret of the whole setup**, and it is stored in the **`release` environment**, which only `main` may use, so no PR or branch workflow can read it. **When the release PR is merged**, a follow-up job in the `release` environment gives the release commit's image its version tag: it re-tags the image if ECR already has it, and otherwise builds and pushes it with both tags. This is ADR 0008, decision 13's image built from a version tag. A fine-grained PAT is simpler to set up, but it acts as the owner, makes every release PR look like the owner's, and is a long-lived credential tied to a personal account. |
| 18 | Dependency updates | Dependabot; Renovate | **Dependabot version updates**, in `.github/dependabot.yml`, for the `npm` (all workspaces), `github-actions` (it updates the pinned commit SHAs, the hashes that name exact commits of an action, and keeps the version comment next to them), `docker` (the Node base image), `docker-compose` (PostgreSQL in `compose.yaml`) and `terraform` (the AWS provider) ecosystems. **Weekly on Monday, grouped:** one PR per ecosystem for minor and patch updates, a separate PR for each major version, about 3–5 PRs a week. Commit messages are Conventional (`build(deps): …`, `ci(deps): …`). **A 7-day cooldown:** a new version is not proposed until it is a week old (Dependabot's default is 3 days). Malicious releases, such as those of the September 2025 "Shai-Hulud" npm worm, have typically been found and removed within days. **Dependabot security updates** are on and skip the cooldown. Dependabot PRs are merged by the owner like any other; no auto-merge (ADR 0009, decision 7). Since branches must be up to date with `main`, merging one Dependabot PR makes the others out of date, and each needs an *Update branch* and a new CI run; grouping keeps this manageable. Renovate is more capable (a dependency dashboard, finer grouping, auto-merge rules), but it is an extra app to install and configure; it becomes worth it if Dependabot proves too noisy. |
| 19 | How much pipeline security | A baseline of good practice; the baseline plus scanners of the pipeline and the code; the same plus supply-chain provenance (signed attestations, a software bill of materials (SBOM), an OpenSSF Scorecard) | **The baseline plus scanners** (decisions 20 and 21). The scanners are free, automatic, and aimed at exactly the mistakes an AI author is likely to make in workflow files, such as interpolating `${{ github.event… }}` into a shell script. Provenance is valuable when others consume the images; nobody pulls Szop's, so it can come later as a learning phase. |
| 20 | Rules for every workflow | — | **`permissions: {}` at the top of every workflow, and each job grants only what it needs:** `contents: read` by default, `id-token: write` only in jobs that assume an AWS role, `pull-requests: write` only for the plan comment, `actions: write` only for re-enabling the teardown schedule. **Every action, GitHub's own included, is pinned to a full commit SHA** with its version in a comment; Dependabot keeps the pins current. **`persist-credentials: false`** on checkout, so the token is not left in `.git/config` for later steps. **No untrusted `${{ … }}` inside `run:` scripts:** PR titles, branch names and similar values are passed through `env:`. **No `pull_request_target`**, and no `workflow_run` that consumes artifacts of untrusted runs: these triggers run with the repository's secrets on code or data from a fork, and are behind most published CI exploits. |
| 21 | Settings and scanners | — | **Enforced by repository settings,** recorded in `github-settings.md` by the phase: **require actions to be pinned to a full-length commit SHA** (a GitHub Actions policy since August 2025; any unpinned action makes its workflow fail); **default `GITHUB_TOKEN` permissions read-only**, with *Allow GitHub Actions to create and approve pull requests* off; **approval required for workflow runs from all outside contributors**, not only first-time ones; and a **ruleset rule *Require code scanning results*** for `main`: CodeQL must have run, and a PR introducing a *high* or *critical* security alert cannot be merged. **Checked by tools:** **actionlint** (workflow correctness) and **zizmor** (a security linter for GitHub Actions: template injection, excessive permissions, unpinned actions) in the `workflows` job; **CodeQL** for the TypeScript code and the workflows; secret scanning with push protection (already on, ADR 0009, decision 14). |
| 22 | Documentation | — | **This ADR** explains *why*. **`docs/development/ci-cd.md`**, written by the phase, is the living guide to *how*: what runs when, how to spin a demo up and down with the buttons, how to read a failed run and its Playwright trace, and the inventory of environments, variables and the one secret. Following [ADR 0005](0005-development-environment.md), decision 15, tool pages in `docs/development/tools/` for GitHub Actions, release-please, Dependabot, tflint, actionlint and zizmor. The **runbook** `docs/operations/demo-environment.md` makes the buttons the primary way to run the demo and local Terraform the fallback. The [stack overview](../architecture/stack-overview.md) gains a section on CI/CD concepts (pipelines, OIDC, environments, supply-chain security). |
| 23 | Rollout | — | **The roadmap decides the phases, with one hard constraint: the nightly `demo-down` is merged before or together with the first `demo-up`, never after** (ADR 0008, decision 26). Each check joins `ci.yml` in the phase that creates what it checks; for example, `e2e` arrives with the first Playwright journey. The **owner's manual steps**, documented by the phase: create and install the GitHub App, create the `demo` and `release` environments, apply the Actions settings, turn on CodeQL's default setup, and update the `main` ruleset. |
| 24 | Deliberately left out | — | **Preview environments per PR** (decision 2), **building an image on every push** (decision 10), **a push-button for base and applying on merge** (decision 14), **a private repository and paid plans** (decision 1), **signed attestations, an SBOM and an OpenSSF Scorecard** (decision 19), **self-hosted runners** (decision 4), **Renovate** (decision 18), **auto-merge** (ADR 0009, decision 7), **a required reviewer on the `demo` environment** (decision 12), **skipping heavy jobs on draft PRs** (the full run costs nothing on a public repository), **running workflows locally with `act`**, **an AWS-side teardown timer** and **a destroy-only role** (decisions 13 and 16), **hosted Terraform runners** such as HCP Terraform or Atlantis, and **a merge queue**, which would remove the *Update branch* churn but is available only to repositories owned by an organization. Each can be added when a real need appears. |

## Consequences

- **Costs:** nothing extra. Actions minutes, caches and artifacts are free for a public repository, the GitHub App is free, and AWS costs stay as in ADR 0008. The nightly teardown caps a forgotten demo at about a day.
- **ADR 0008 is extended:** `infra/base` also holds the GitHub OIDC provider, the three CI roles and the app's task execution role and task role (decisions 15 and 16). Where Terraform runs, CI's access to AWS, the teardown safety net and the Terraform checks are answered by decisions 13–16 and 7.
- **ADR 0009's CI/CD items are answered:** the required status checks (decision 8), the PR title check (decisions 5 and 8), release-please with a GitHub App token (decision 17), the versioned image (decision 17) and Dependabot version updates (decision 18). CI also lints every commit of a PR, not only the title (decision 7).
- **ADR 0007's items are answered:** the PostgreSQL service container and cached Playwright browsers (decision 7), and the Playwright report and traces of failed runs (decision 9).
- **The CI/CD phase** writes the workflows, the composite action, `dependabot.yml`, the release-please configuration, the IAM roles in `infra/base`, `ci-cd.md` and the tool pages; updates `github-settings.md` with the environments, the Actions settings, CodeQL and the `main` ruleset's required checks; and adds the pnpm scripts CI calls (`lint`, `typecheck`) if earlier phases have not.
- **The roadmap turns the owner's manual steps of decision 23 into tasks of the phases that introduce them**, so none is left only in this ADR.
- **`CLAUDE.md`** points to `ci-cd.md` once it exists, and gains a rule that **Claude never triggers `demo-up` or `demo-down` unless the owner asks**, since they create resources that cost money.
