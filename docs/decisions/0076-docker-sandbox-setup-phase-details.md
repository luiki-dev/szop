# ADR 0076 — Reproducible Docker Sandbox setup phase details

- **Status:** ✅ Accepted
- **Date:** 2026-11-12
- **Completes:** [ADR 0075](0075-docker-sandbox-poc-phase-details.md), decision 2 (the setup phase after the GO)

## Context

[PH-48](../roadmap.md#ph-48-docker-sandbox-proof-of-concept) ended in a ✅ GO ([ADR 0075](0075-docker-sandbox-poc-phase-details.md), "Settled while building"): Claude Code can work on Szop in a Docker Sandbox (`sbx`) that sees neither Windows nor the owner's cloud files, with only `claude-readonly` on AWS and a machine account on GitHub. Everything in the proof of concept was set up by hand, and its [record](../audits/2026-11-08-docker-sandbox-poc.md#task-6-the-decision) lists about 25 things the setup phase must bring. `sbx` is at `0.x` and some releases require sandboxes to be recreated, so rebuilding must be routine, not a disaster drill.

[PH-49](../roadmap.md#ph-49-reproducible-docker-sandbox-setup) builds the environment from source. It also settles the two open points the proof of concept left: the machine account's last question ([OP-143](https://github.com/luiki-dev/szop/issues/428)) and a backup of Claude Code's own setup and memory ([OP-145](https://github.com/luiki-dev/szop/issues/435)), which the owner wants here as the setup's rollback.

`sbx` builds a sandbox from two kinds of source, both layered by design ([Kits](https://docs.docker.com/ai/sandboxes/customize), [Environment files](https://docs.docker.com/ai/sandboxes/configuration/environment-files/)):

- **Kits** (format v3): a YAML descriptor and a Dockerfile. A *workload* gives the base and the agent; *mixins* add tools, files, lifecycle hooks and the network hosts they need. Several mixins combine with `--kit`, and a local directory is built when the sandbox is created.
- **Environment files** (`sbxenv.yaml`): the kits, the size, the secrets (a `command` run on the host prints each one), ports and lifecycle commands, which **run on the host with the owner's rights**. Several files merge in order: `sbx env run base.sbxenv.yaml szop.sbxenv.yaml`.

## Changes to the roadmap

- **PH-49's owner steps** name what the design gives the owner: the machine account's settings on Szop's repository, the private configuration repository, the host's `sbx` settings and the network policy's groups, the logins, the rebuild and reading the lost machine runbook.

## Decisions

| # | Decision | Options considered | Outcome |
|---|---|---|---|
| 1 | The phase's approach | Full or bounded path; one phase or a split | **Full path; one new concept, an environment defined in source (`sbx` kits and environment files); about 8 tasks, at most 10; a stop after the tasks where the owner acts: the host settings and network policy, the configuration repository, the machine account and the rebuild from nothing.** The phase brings scripts and files that are kept and rebuilt from, not a one-off experiment. The backup stays in the phase, though it is a second, smaller topic, since without it the rebuild would lose the memory. Claude's recommendation; the owner chose it. |
| 2 | Who runs `sbx` | The owner runs everything, as in PH-48; Claude drives `sbx.exe` from WSL; a hybrid | **A hybrid. Claude runs from WSL only the `sbx` commands that read (`sbx ls`, `sbx policy ls`, `sbx policy log`) and the provisioning scripts inside the sandbox; the owner runs everything that changes a boundary (creating and removing sandboxes, the network policy, `sbx` settings, the logins) and the final rebuild.** With Claude driving it all, Claude would set the walls of its own cage, which is what the sandbox exists to avoid; inside the sandbox most of the iterations happen, and nothing there can hurt the host. Claude's recommendation; the owner chose it. |
| 3 | The owner's view of what Claude runs | An announcement in chat only; a permission rule; a log of every `sbx` call | **An `ask` rule in `.claude/settings.json` for every call of `sbx.exe`, `deny` rules for the calls that change a boundary (`policy allow`, `policy approval respond`, `create`, `rm`, `secret`, `settings set`), and an announcement in chat before each batch. Claude runs only scripts committed on the branch, and the plan says in each task who runs which `sbx` command.** An `ask` rule prompts even in auto mode ([Permissions](https://code.claude.com/docs/en/permissions)), so the view does not depend on Claude's behaviour. The owner chose it. |
| 4 | Layers | One kit for Szop; a generic layer and Szop's, in Szop's repository; the generic layer in a repository of its own now | **Two layers in Szop's repository: `sandbox/base`, which names nothing of Szop, and `sandbox/szop`, each a mixin on Docker's Claude Code workload, with an environment file each, merged in that order.** A tool added later (such as lazydocker) is a line in a layer's Dockerfile through a PR, taken by the next rebuild. A repository of its own now would add two to three tasks and a second new concept (versions across repositories, publishing kit images); moving the base layer waits for a second project ([OP-146](https://github.com/luiki-dev/szop/issues/437)). Claude's recommendation; the owner chose it. |
| 5 | Where the backup lives | Claude's memory in Szop's repository; a private repository for Claude's configuration; a copy the owner pulls to the host | **A private repository for Claude's configuration: the memory of each project, the global `CLAUDE.md`, the user `settings.json`, the status line and usage log. `autoMemoryDirectory` points into its clone, on WSL and in the sandbox, and a hook commits and pushes on its own.** Szop's repository is public, and the memory holds the owner's preferences; a copy pulled by hand is one-way and easy to forget. Pointing the memory at the clone also removes the two project paths (`-home-lemekk-…` on WSL, `-home-agent-…` in the sandbox). The owner chose the repository and the hook. |
| 6 | The configuration repository and the base kit | One repository for both; separate | **Separate.** The sandbox pushes to the configuration repository without review, while the kit and the environment files run on the host or as root when the image is built; a sandbox able to change them could escape at the next rebuild. The base kit stays in Szop and, at [OP-146](https://github.com/luiki-dev/szop/issues/437), moves to a protected repository of its own. Claude's recommendation; the owner chose it. |
| 7 | The machine account and `szop-ci-plan` ([OP-143](https://github.com/luiki-dev/szop/issues/428)) | Accept it; take the role away from the account through the OIDC subject claim | **Accepted and recorded in the threat model.** A workflow the account pushes in a PR can assume `szop-ci-plan`, which reads the infrastructure and the two Terraform states. Neither holds a secret value, and `claude-readonly` already reads most of the infrastructure; cutting the account off would change CI's trust policy, a new concept for a small gain. Claude's recommendation; the owner chose it. |
| 8 | Network and `sbx` settings | — | **context7 allowed and signed into at each rebuild; telemetry turned off at the source (`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, the VS Code server's `telemetry.telemetryLevel` `off`), with explicit deny rules behind it; the six groups of `balanced` reviewed one by one with the owner, deeper narrowing left to [OP-144](https://github.com/luiki-dev/szop/issues/430) with its data; the host settings `model.server.enabled false`, `env.rememberHostCommands false`, `ssh.agentForwardingEnabled false`, `telemetry.disabled true`, `kit.requireSignature false`, in a script the owner runs.** The project's instructions rely on context7; a deny rule alone did not stop the telemetry's attempts in PH-48; Szop's kits are local and unsigned. The spec and the `sbx` tool page explain each setting. Claude's recommendation; the owner agreed. |
| 9 | What the rebuild proves | A lost sandbox; a lost machine, carried out | **A lost sandbox rebuilt for real and timed; a lost machine as a runbook in `docs/operations/`, read through with the owner and not carried out.** The first covers everything inside the sandbox; the second adds only installs and logins on the host, and carrying it out needs a clean Windows machine. Claude's recommendation; the owner chose it. |
| 10 | Transcripts | In the configuration repository whole; a stripped copy; a compressed archive outside git | **A stripped copy: the same `.jsonl` lines with only the fields `scripts/token-usage.py` reads, written by the backup hook into the configuration repository, one folder per environment. The transcripts themselves stay where Claude Code keeps them, and the first run takes the whole WSL history since 2026-09-27.** The whole set is 865 MB on WSL, grows while a session runs, and holds every file and command output seen, secrets included if one was ever printed. Claude's recommendation; the owner chose it. |
| 11 | Which way trust flows | Every copy restored automatically; data only from the sandbox; the sandbox owns the owner's settings, WSL takes them reviewed | **The sandbox writes everything to the configuration repository: the memory, the stripped transcripts, the usage log and `user/` (the owner's user settings, global `CLAUDE.md` and status line). WSL writes the memory, the stripped transcripts and the usage log, never `user/`. A new sandbox takes `user/` at creation; WSL takes the memory at every session start and `user/` only by the owner's copy after reading the diff. Hook scripts never come from the repository.** The sandbox is where Claude's configuration changes (decision 13), so it owns `user/`; WSL writing it too would put an older version back after every session there. Nothing from the repository runs on WSL unreviewed except the memory, and losing the sandbox is acceptable ([ADR 0075](0075-docker-sandbox-poc-phase-details.md), decision 3). Claude's first call kept `user/` from the sandbox; the owner moved the configuration's changes into the sandbox, and the owner chose this. |
| 12 | What is public | Everything in `sandbox/`; the mechanism public, the owner's own files private | **`sandbox/` in the public repository holds only the mechanism: the Dockerfiles, the descriptors, the scripts, the environment files and generic defaults. The owner's own files (the user `settings.json` with its `autoMode` text, the global `CLAUDE.md`, the memory) live only in the private repository.** The user settings describe the owner's AWS and GitHub setup in detail. Claude's call. |
| 13 | Where Claude works | WSL with the sandbox beside it; the sandbox only; the sandbox, with WSL kept as the fallback and the way back | **The sandbox is where Claude Code works, and where its configuration changes. WSL's setup stays as it is, with the backup hook, but Claude is not started there; it is the fallback when `sbx` breaks (a faulty update) and the way back if the sandbox is given up. Going back takes the last state through the configuration repository: the memory by itself, `user/` by the owner's reviewed copy, the usage log and the stripped transcripts for statistics. A sandbox's session cannot be resumed on WSL, since its whole transcript stays in the sandbox (decision 10).** Claude in isolation is the reason for the move; a way back costs only the hook on WSL. The owner chose it. |
| 14 | The host's copy of Szop | A clone of its own on WSL; the existing WSL checkout, kept on `main`; the mixins by `git+https://` | **The existing checkout, `~/workspace/szop`, kept on `main` and updated by the owner with `git pull`; `sbx.exe` gets its paths through `wslpath -w`. While this phase is built, it is on the phase branch.** `sbx env` reads the environment files and the kits on the host, and their host commands run there, so it reads only reviewed `main`. With no work done on WSL (decision 13), a second clone would add nothing. Claude's recommendation; the owner agreed. |
| 15 | Working in the sandbox from Windows | A terminal through `sbx`; VS Code's Remote-SSH | **VS Code's Remote-SSH: the OpenSSH client and the Remote-SSH extension on Windows, `sbx setup ssh` with its `Include` line in `~/.ssh/config` checked and fixed by hand, `remote.downloadExtensionsLocally` `true`. It is in the runbook and in the rebuild's checks.** It is how PH-48 worked in the sandbox; `sbx setup ssh` wrote a broken `Include` there, and VS Code needed no host allowed. The owner asked for it. |
| 16 | Updating `sbx` | Update when one comes; a procedure in the runbook | **A procedure in the runbook: Claude in the sandbox reads Docker's release notes between the installed and the new version and says what touches Szop's setup (the kit format, the environment files' schema, the settings, the network policy, security), with a verdict; before the update every branch is pushed, the backup is pushed and the installed version and the way back to it are written down; the owner updates; after it, the owner runs the host settings script again and compares `sbx policy ls`, and Claude runs the sandbox's check script (the isolation of PH-48, the push hook, `pnpm check`); the runbook records the last version proven.** `sbx` is at `0.x`, and a release can reset settings or change formats. Where the release notes are published and whether an older version can be installed again are checked by the plan's first `sbx` task. The owner asked for it. |

## Settled while building

- **`sbx` is installed with winget, and an update can be undone** (Task 1). `sbx.exe` 0.51.0 came from winget's `Docker.sbx`; winget keeps the older versions, so `winget install --id Docker.sbx --exact --version <v> --force` goes back. The release notes are on GitHub, [docker/sbx-releases](https://github.com/docker/sbx-releases/releases), whose host `github.com` is already in `balanced`.
- **All six groups of `balanced` are kept** (Task 1). Each holds something Szop uses, and the broad entries are in groups Szop cannot drop; `REMOVED_GROUPS` stays empty. Narrowing waits for [OP-144](https://github.com/luiki-dev/szop/issues/430). The owner chose it.
- **`sbx.exe` reads the environment files and builds a local kit from a WSL path** (Task 1). The probe, `sbx.exe env create` of `\\wsl.localhost\…\sandbox\base\base.sbxenv.yaml`, built the base layer's overlay in 7 seconds and copied its files. So the host's copy stays the WSL checkout (decision 14); neither a clone on the Windows disk nor `git+https://` kits are needed.
- **A kit's `network-policy@1` hosts add to `balanced` for its own sandbox** (Task 1). `sbx policy ls` showed the probe's kit hosts as a separate policy, `source: kit`, applied to `sandbox:szop-probe` only, beside the global `local-policy`, and `mcp.context7.com` was reached. Each layer's hosts stay in its descriptor, not in `settings.sh`.
- **apt packages go in a `lifecycle@1` install hook, and the start command in the environment file** (Task 1). A mixin's overlay is laid over a workload it has never seen, so it cannot carry apt packages, and it cannot set `ENTRYPOINT` or `CMD` (kit format v3). The probe's hook ran `apt-get update` at create; `less` was already in the workload `docker/sbx-kit-claude:2.1.316`, so installing a new package is first proven by Task 6. The workload's version is pinned at `2.1.316`, the highest tag on 2026-11-13.

## Consequences

- Rebuilding a sandbox is a few commands and the owner's logins, so a release of `sbx` that requires a new sandbox costs minutes, and [OP-144](https://github.com/luiki-dev/szop/issues/430) can start on a sandbox built this way.
- WSL changes in one way only: the memory moves into the configuration repository's clone, and the backup hook runs there too. Everything else lives in `sandbox/` and does not touch the WSL workflow, which stays the fallback (the condition of PH-48's GO).
- Memory written in the sandbox is loaded into Claude's context on WSL, which has no isolation; a compromised sandbox could plant instructions there. The threat model records it; it is accepted while WSL is only the fallback.
- A compromised sandbox can change `user/`, and a rebuilt sandbox takes it: a planted hook or setting survives the rebuild, inside the VM. The repository's history shows every change, and the project's deny rules and push hook stay in Szop behind review. The threat model records it.
- Work not pushed from a sandbox is lost with it: every branch is pushed before an update or any other step that could break the sandbox.
- The `sbx.exe` permission rules matter only while Claude runs on WSL, which is this phase's build; Claude in the sandbox cannot reach `sbx.exe`.
- A pull request that changes `sandbox/*/*.sbxenv.yaml` or a kit's lifecycle hooks changes what runs on the owner's host: the owner's review of that diff is a security boundary.
- A second project reuses `sandbox/base` by copying it until [OP-146](https://github.com/luiki-dev/szop/issues/437) moves it to its own repository.
