# ADR 0055 — Mutation testing phase details

- **Status:** ✅ Accepted
- **Date:** 2026-10-28
- **Refines:** [ADR 0007](0007-testing-strategy.md), decision 19 (what is mutated and where an accepted survivor's reason lives, see decisions 1 and 3)
- **Revisits:** [ADR 0010](0010-ci-cd.md), decision 5 (no `mutation.yml`, see decision 2)

## Context

[PH-15b](../roadmap.md#ph-15b-mutation-testing) brings mutation testing with StrykerJS, which [ADR 0007](0007-testing-strategy.md), decision 19, chose to judge whether tests check anything, tests Claude wrote above all. The score is measured, not gated. The owner wants the result reviewed and the weak tests it reveals improved: good tests are what test-driven development (TDD) relies on. The [spec](../superpowers/specs/2026-10-28-PH-15b-mutation-testing-design.md) holds the design. Decisions 1 to 4 were settled in the brainstorm.

## Changes to the roadmap

PH-15b no longer delivers `mutation.yml` (decision 2): its goal drops "and in a workflow run on demand", and its **Delivers** drops `mutation.yml`. The PH-15b part of [OP-019](https://github.com/luiki-dev/szop/issues/77) is dropped, which closes that open point.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|---|---|---|
| 1 | What is mutated | `packages/shared` only, as ADR 0007, decision 19, put it; a list of files in Stryker's configuration; a naming convention for logic files that a glob picks up. | **Every application source file under `apps/api/src`, `apps/web/src` and `packages/shared/src` is mutated by default, except the tests, the test infrastructure and the vendored shadcn/ui components. A file that holds no logic a test should check (wiring, configuration, plain rendering) opts out with a `// Stryker disable all` comment at its top, giving the reason** _(the owner's choice, on Claude's recommendation)_. The criterion is pure logic wherever it lives: `packages/shared` is not the only place, the catalog search in `apps/web` and the URL redaction in `apps/api` are logic too. A list in the configuration would age, and a logic file nobody added would silently go unmeasured. A naming convention would bend the code's structure to the tool. With an opt-out, the choice is made in the file, when it is written, and forgetting it adds visible noise to the report instead of hiding logic. The E2E journeys, `apps/landing`, the Claude Code hooks and `infra/` are out _(Claude's call)_: they are not application code, and E2E tests would need a build per mutant. |
| 2 | Where mutation testing runs | `mutation.yml`, run on demand, as ADR 0010, decision 5, planned. | **Only locally, with `pnpm test:mutation`; there is no `mutation.yml`** _(the owner's choice, on Claude's recommendation)_. The owner could name no situation in which they would start a workflow instead of running the script. The review at the end of a phase runs locally, a cloud session has Docker and PostgreSQL too, and a workflow would still need its documentation, permissions and Dependabot updates. If runs grow long enough to be a nuisance, a workflow can come back as a candidate. |
| 3 | Where an accepted survivor's reason lives | In the PR description, as the definition of done said. | **In the code, as a comment above the line: `// Stryker disable next-line <Mutator>: <reason>`, one mutator on one line, never `all`** _(the owner's choice, on Claude's recommendation)_. A reason in the PR is lost to the next run, which shows the same survivor again, so every phase would review it anew. In the code, the next report shows only new survivors, and the reason stays next to the code and goes with it. Naming one mutator keeps a stale comment from hiding a new, real survivor on the same line. |
| 4 | What happens to the survivors of the first run | Fixing them all here; recording them all as open points. | **Each survivor is killed by a better test, accepted with a reason in the code (decision 3), or, when the fix is larger, recorded as an open point; small fixes are done in this phase** _(the owner's choice)_. The phase is small, so most fixes are expected to fit. |

## Settled while building

Facts the plan did not have, found while building and kept here because they explain code that looks odd:

- **The runner's plugin is named by path.** With pnpm, `@stryker-mutator/vitest-runner` is a dependency of the root, not of Stryker's own package, so Stryker's default search (`@stryker-mutator/*` from its own directory) loads no test runner and stops with "Cannot find TestRunner plugin". `stryker.config.mjs` sets `plugins` to the runner's resolved path.
- **`@szop/shared` is aliased to its source in the api and web Vitest projects.** The spec's risk came true: Stryker links each `node_modules` into its sandbox, and the link to `@szop/shared` resolves to the original `packages/shared`, so a mutant there was "no coverage" for the apps' tests (the first check showed `api-error.ts` at 0%, with 2 of 2 mutants uncovered). A `resolve.alias` to `../../packages/shared/src/index.ts`, relative to each config file, makes the tests load the sandbox copy; the same check then killed both mutants. Under `pnpm test` the alias points at the file the package's `exports` names already, so nothing changes there.
- **`stryker.config.mjs` has no type annotation.** The root `tsconfig.json` includes `*.mjs` so that ESLint's type-aware rules can parse the file. `PartialStrykerOptions` is not exported by `@stryker-mutator/core`, only by `@stryker-mutator/api`, which is not a direct dependency, so the file has no `@type`; Stryker warns on an unknown option at the start of a run.
- **Class-name strings are accepted line by line, not file-wide.** The owner's decision allowed `// Stryker disable StringLiteral` for a whole file in `catalog-tree.tsx`, `menu.tsx`, `api-status.tsx` and `app-shell.tsx`, as an exception to decision 3's "one line", with `// Stryker restore StringLiteral` around the strings that carry behaviour. A run of the four files without any comment showed that only seven class-name literals survive (Stryker does not mutate JSX attribute strings, and tests already kill the class names in `cn()` conditions): `catalog-tree.tsx` lines 63 and 101, `api-status.tsx` line 11, `menu.tsx` line 26 and `app-shell.tsx` lines 84, 97 and 98. Seven `disable next-line StringLiteral` comments are a smaller diff than a file-wide disable with a restore around each behaviour string (the `Szop` title, `Can't reach the API`, the labels), keep decision 3 as it is, and leave the class names that tests do kill covered. `testing.md#mutation-testing` has a line for class names.
- **Equivalent mutants accepted, each checked against the code and the run.** All with `disable next-line <Mutator>`, listing the mutators that survive on the line: unreachable fallbacks and optional chaining (`setup-role.ts`, `web/routes.ts`, `config.ts`, `seed.ts` lines 45, 65, 71, 73, 77, `catalog-page.tsx`, `tree.ts`, `search.ts`, `catalog-tree.tsx` line 94); the options that only state a library default (`seed.ts` line 62 for the YAML parser, `headers.ts` lines 23 and 28 for helmet); the Fastify plugin `name` options in `cross-site.ts`, `headers.ts` and `json-only.ts` (they only label the plugin in errors and logs); `client.ts` (`.catch(() => null)`: `null` and `undefined` are the same unreadable body); `errors.ts` (the `+` of the separator regex, the redundant `undefined` check) and `migration-check.ts` line 48 (`<` against `<=`: a migration at the newest time is recorded already). Two lines needed a different form because Stryker attaches a directive to the next syntax node, not the next line: in `errors.ts` the regex moved to a `separators` constant so the comment sits on its own statement, and in `cross-site.ts` the empty `catch` block is covered by a `disable BlockStatement` before the `try`'s first statement and a `restore BlockStatement` at the start of the `catch`, which leaves the `try` block's own mutant covered.
- **The migration check's test databases go through `testDatabaseName`.** `migration-check.test.ts` named its databases `szop_test_migrations_<VITEST_POOL_ID>` itself, so two Stryker processes, each running the whole suite with the same pool IDs, dropped each other's database. It now calls `testDatabaseName("migrations_<pool id>")`, which gives `szop_test_migrations_<n>` under `pnpm test` and `szop_test_s<process>_migrations_<n>` under Stryker.
