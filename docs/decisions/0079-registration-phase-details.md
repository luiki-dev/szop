# ADR 0079 — Registration phase details

- **Status:** ✅ Accepted
- **Date:** 2026-11-20
- **Refines:** [ADR 0012](0012-security-baseline.md), decision 11 (the breach check is our own, not Better Auth's plugin, see decision 15)
- **Completes:** [ADR 0012](0012-security-baseline.md), decisions 9 and 12 (the verification link single-use and removed from the address bar; no enumeration on registration and resend, see decisions 13, 14 and 16); [ADR 0025](0025-web-security-baseline-details.md), decision 6 (the link built by the app with the token in the query string, see decision 13)
- **Settles:** [OP-038](https://github.com/luiki-dev/szop/issues/97), how a guest's workspace moves into an account (decisions 6 and 17)

## Context

[PH-18a](../roadmap.md#ph-18a-sending-email) gave the API a proven `EmailSender` ([ADR 0078](0078-sending-email-phase-details.md)). PH-18b was Registration and login: email-and-password accounts with verification, the guest's workspace becoming the account's, logging in and out. Better Auth 1.7.21 runs with the anonymous plugin only. [OP-038](https://github.com/luiki-dev/szop/issues/97)'s spike showed that with `requireEmailVerification` a sign-up returns no session, that opening the link signs in and links **the opening browser's** guest, and that linking is not atomic.

The brainstorm drew every screen and transition of registration and login on one mockup ([`journey-v5.html`](../architecture/visual-design/ph-18b-journey-v5.html)) so the login phase builds from it with no rework, and checked Better Auth's code for each technical choice.

## Changes to the roadmap

- **PH-18b is split** into PH-18b Registration and PH-18c Login and logout. PH-18c gets the login screen, logging out, the unverified sign-in, [ACC-2](../requirements/ACC-accounts-and-guest-mode.md#acc-2).8 and SEC-04 ([#344](https://github.com/luiki-dev/szop/issues/344)); it builds from this phase's mockup.
- [UC-8](../requirements/UC-use-cases.md#uc-8-guest-becomes-a-user) is completed by PH-18c, since "available on their laptop" needs logging in.

## Decisions

| # | Decision | Options considered | Outcome |
|---|---|---|---|
| 1 | The phase's approach | — | **Full path; one new concept, email-and-password authentication with verification; about 9 tasks; stops after the Better Auth configuration task, after the workspace takeover task, and before the first screen task**, where the owner supplies the illustrations. Claude's recommendation; the owner chose it. |
| 2 | How PH-18b is split | One phase of about 13 tasks; registration, then login. | **PH-18b Registration and PH-18c Login and logout.** One phase passed the size [ADR 0072](0072-phase-approach-per-phase.md), decision 1, aims for. Resending the link stays in PH-18b (decision 14), so PH-18c has about 4 tasks. Claude's recommendation; the owner chose it, and moved the resend into PH-18b. |
| 3 | Where the screens of both phases are designed | Each phase designs its own; this brainstorm designs both. | **This brainstorm designs every screen and transition of registration and login**, so shared screens stay consistent and PH-18c reworks nothing. The owner's call. |
| 4 | How the screens are laid out | Separate pages in the app shell; a dialog over the current page; one page with tabs. | **Separate pages in the app shell**: `/register`, `/register/sent`, `/register/resend`, `/verify`, `/login`, and `/import` for [PH-19](../roadmap.md#ph-19-guest-data-on-login). Each state has an address an email can link to, and the menu stays beside them. Claude's recommendation; the owner chose it. |
| 5 | What the registration form asks | Email and password; with the password twice; with a display name too. | **A display name, the email, and the password twice.** No password reset exists until [PH-29](../roadmap.md#ph-29-password-reset-and-change), so a typo would lock the user out. Better Auth's `users.name` is required anyway. The name is a display name, not unique, 1 to 50 characters after trimming, with no control characters, the list name's rules. The owner's call; the rules are Claude's. |
| 6 | A verification link opened in another browser | It signs that browser in and moves that browser's guest; it moves the registering browser's guest and signs in the opening browser; it only verifies, with no sign-in. | **It signs in the browser that opens it and moves the registering browser's guest workspace.** The registering browser's guest stops working; at its next request it shows "Your address was confirmed in another browser" with the login page. No polling. The guest of the opening browser is not touched. Until PH-18c, the login page has no working form, a gap accepted. Claude's recommendation; the owner chose it. |
| 7 | A sign-up for an address with an unverified account | Answer as for any existing account and send nothing, so the address stays blocked until [ACC-8](../requirements/ACC-accounts-and-guest-mode.md#acc-8)'s cleanup; replace the unverified account. | **Replace it:** the unverified account is deleted and the sign-up registers afresh. A stranger cannot block an address, nor prepare an account in advance for its owner to verify by mistake (account pre-hijacking). Two abuses stay open and are accepted: anyone can cancel a pending registration by signing up the same address, and a stranger who replaces it sends the owner a genuine link to the stranger's account; the spec's Risks hold both. Claude's recommendation; the owner chose it; the open abuses found in the spec's review, the owner accepted them. |
| 8 | The menu's account box | A box with two equal buttons; "Log in" as the main button. | **An account box at the bottom of the menu, above the API status: "Log in" as the main button and "Create account" as a link set further below.** On `/login` or `/register` the current page's entry takes the menu's current-page look (`aria-current="page"`), not a disabled button. Logged in: the name, the email under it, and, from PH-18c, "Log out". The owner's call from the mockup; the current-page look Claude's. |
| 9 | Leaving a form | A Cancel button on the form only; on every state. | **Cancel on every state of `/register` and `/login`**, errors and notices included: back to the page the user came from, Lists if none. The owner's call. |
| 10 | Keeping the guest's lists | Always kept on registration and asked after login; a choice on both forms; a choice on registration, and a question after login. | **On registration, a "Keep this browser's lists" checkbox, ticked by default, shown only when the guest has a workspace. After a login, a page asks only when the guest has lists or templates (PH-19).** With no checkbox shown, the sign-up keeps the guest's data, so lists added before verification move with it; a guest's workspace is created at its first write. Unticked, the account starts from the default data and the guest's data is left to [ACC-7](../requirements/ACC-accounts-and-guest-mode.md#acc-7)'s expiry. Login asks afterwards because only then are both sides known, with any quota they would pass ([ACC-4](../requirements/ACC-accounts-and-guest-mode.md#acc-4).5). The owner's call; the login page and its counts are Claude's recommendation. |
| 11 | When the login question is asked | On every login of a browser with a guest workspace; only when there is something to import. | **Only when the guest workspace holds at least one list or template, even an empty one**, and the guest's data is gone after either choice, so the question does not come back. Without it, a user would be asked at every login. The owner's call. |
| 12 | What a failed link shows | One screen per failure; one screen for all. | **One "Link not valid" screen** for a used, expired or replaced link: "It may have expired, or you may have used it already.", with "Send a new link" as the main action and "Already confirmed your address? Log in" as a link. It reveals nothing about the account. Claude's proposal; the owner approved it. |
| 13 | How a verification link works once and expires | Better Auth's stateless JWT; a token table of our own. | **Better Auth's JWT, with `expiresIn` of 24 hours, and the link built by the app as `/verify?token=…`.** A verified account ignores every later link (no session), and a replaced account has a new ID (`INVALID_TOKEN`), so a link works once without a table. Better Auth answers `user: null` both to a verification and to a used link, so an after hook answers `{ verified }`, true when Better Auth set a new session. Until any one is used, the links of several resends all work. The SPA removes the token from the address bar before it calls `GET /api/auth/verify-email`. Claude's recommendation; the owner chose it. |
| 14 | Resending the link | Better Auth's `/send-verification-email`; a route of our own. | **`POST /api/registration/resend`, calling Better Auth's endpoint without the session.** With a session, Better Auth compares the address with the session's own and answers `EMAIL_MISMATCH`, which a guest always gets. Without one, it answers the same for every address with a 500 ms floor. Its own path stays closed ([NFR-4](../requirements/NFR-non-functional-requirements.md#nfr-4).12). Called from the app, Better Auth's rate limiter does not apply, so the route limits itself to 3 requests in 60 seconds per IP. Resending moved into this phase, with `/register/resend`, so no button of this phase's screens is dead. Claude's recommendation; the owner chose it. |
| 15 | Checking breached passwords | Better Auth's `haveIBeenPwned` plugin; a check of our own. | **A check of our own**, in the sign-up's before hook: the Have I Been Pwned range API with `Add-Padding`, a time limit of about 3 seconds, and on any failure a `warn` line and the password accepted. The plugin answers 500 when the service fails, against [ACC-2](../requirements/ACC-accounts-and-guest-mode.md#acc-2).4. PH-29 reuses the check. Claude's recommendation; the owner chose it. |
| 16 | Replacing an unverified account safely | — | **A before hook on `/sign-up/email` checks the body first, then deletes the unverified account (never a guest) in a transaction**, and an after hook turns the error of two sign-ups at once into the same "check your inbox". The hook runs ahead of Better Auth's own checks, so without its own a sign-up with a 1-character password would delete the pending account. Better Auth's `onExistingUserSignUp` then sees only verified accounts and sends the "already have an account" email. Claude's call. |
| 17 | Moving the workspace | Better Auth's `onLinkAccount`; our own move at verification. | **Our own move, in `beforeEmailVerification`.** Sign-up stores the registering guest (through `databaseHooks.user.create.before`) and the checkbox on the new user, both kept out of every answer so they do not tell a new address from an existing one; verification moves `workspaces.user_id` from the guest to the account when kept, and marks the guest converted, in one transaction that can run twice with the same result. A failure leaves the account unverified, and opening the link again finishes it. `onLinkAccount` would link the opening browser's guest, and `disableDeleteAnonymousUser` keeps every guest. The session hook answers a converted guest's request with 401 `guest_converted`. Claude's recommendation; the owner chose it. |
| 18 | What the emails say | The mockup's "Hi Ania"; "Hi," alone. | **"Hi," alone, with no display name.** The name is free text sent to any address, so it would carry a stranger's message from Szop's domain. Claude's recommendation; the owner chose it. |
| 19 | How emails are written | A template engine; a function per email. | **One function per email returning its subject, text and HTML**, with no engine. Claude's call. |

## Settled while building

- **`AppDeps.email` is optional** (Task 1). `buildApp` builds the sender from `config.email` when it is left out, so `server.ts` and the tests that send nothing stay as they are; the tests that read emails pass a fake that records them.
- **Better Auth's logger is set to `warn`** (Task 1). Its sign-up line for an existing address, at `info`, holds the address in its message, so passing messages only is not enough; `info` is off.
- **A UUIDv7 in every synthetic answer** (Task 1). A real user's ID is a UUIDv7 made by the database, Better Auth's synthetic one a v4, which told an existing address from a new one; `customSyntheticUser` and the after hook both use `uuidv7()`.
- **`GET /api/lists` answers `{ lists, hasWorkspace }`** (Task 4). The registration form needs to know whether to show the checkbox and how many lists its hint names; `hasWorkspace` is false until the guest's first write. The web client's `getLists` reads only `lists`.
- **`sessionHook(auth, db)` reads `users.converted_at` with a query** (Task 4), only for an anonymous session's user, since Better Auth does not return the column. A converted guest's session is kept, so every request with it, including a second tab's or a parallel write, answers 401 `guest_converted`; deleting it would give only the first request the code (the owner's ruling at the Task 4 stop).
- **The resend's limit is a `Map` in the route** (Task 5, decision 4). `registrationRoutes` keeps a `Map<string, number[]>` of request times per `request.ip`, created per app, so per task and lost on restart. A request counts when it arrives, answered or refused; those older than 60 seconds drop out, and the fourth within 60 seconds answers 429.
- **The illustrations were traced, not drawn** (before Task 6). The owner's PNGs, kept in the [spec's folder](../superpowers/specs/2026-11-20-PH-18b-registration-design/), went through `trash-can.svg`'s recipe ([ADR 0066](0066-managing-lists-phase-details.md), "Settled while building"): cropped, 512 px wide, quantized to the raccoon's five colours, a mode filter (7 px for the hourglass, 3 px for the others) turning the shading into flat shapes, traced with vtracer, fills snapped and coordinates rounded, no hand edits. The mailbox's red flag became `sage-500` (`#5F9273`), since the palette has no red and grey would merge with the box; the chain was lifted one tone, as it came out nearly black. The envelope became `mailbox.svg`: the owner's picture is the raccoon diving into a mailbox. The owner approved them.
- **The verify page learns whether the lists were kept from the account's workspace** (Task 7). `{ verified }` carries nothing else and the page may open in another browser, so after a verification it asks `GET /api/lists`: a workspace means the guest's was moved ("Welcome! Your lists are in your account now."), none (or a failed call) gives "Welcome!". The route's title is "Confirm your address" and "Link not valid" is the card's heading, since the shell's title comes from the route and a route cannot change it with its state. A converted guest is sent with `window.location.assign("/login?confirmed")` from `failure()`, which every read and write passes through; `withSession` returns the 401 as it is instead of signing in a guest.
- **Zod and its config share a chunk** (Task 9). The branch's shared imports put the schemas in a chunk that the browser evaluated before `zod-config.ts`, so zod's `new Function` probe hit the CSP on every page and failed every E2E journey. `build.rolldownOptions.output.codeSplitting` groups zod and `zod-config.ts` into one chunk, so `jitless` is set first; the first screen measures 173.8 KB Brotli of 200.
- **A sign-up replaces every pending registration of the same guest** (finishing fixes). Two sign-ups from one guest left two links that both moved its workspace, the earlier one still working. `signUpBefore` now deletes the guest's other unverified accounts in the replacement's transaction, so the earlier link answers 401 (Better Auth finds no user) and moves nothing, consistent with decision 7.
- **The verification hook sets `email_verified` itself** (finishing fixes). Better Auth marks the address verified after the hook, so a replacing sign-up landing between the move and that mark could cascade-delete the moved workspace. The hook now writes the flag in the move's transaction; Better Auth checks the token before calling it, and its own later write is a harmless repeat. This closes the replacement race the spec had accepted.
- **`signUp` makes sure a guest session exists first** (finishing fixes). A browser with no session registered with no guest to link, so lists it added before opening the link stayed with a later guest. The web client's `signUp` calls the same `guestSignIn` that writes use, before the POST.

## Consequences

- The `users` table gains the registering guest, the checkbox and the guest's conversion. A guest's session stops working once its registration is verified, in any browser.
- Every guest stays in the database after a registration or login; [ACC-7](../requirements/ACC-accounts-and-guest-mode.md#acc-7)'s cleanup deletes them.
- The API calls the Have I Been Pwned range API on every sign-up; a failure accepts the password.
- Between this phase's merge and PH-18c's, a verified user cannot log in again in another browser.
