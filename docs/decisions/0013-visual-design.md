# ADR 0013 — Visual design: look, components, styling, tokens and non-functional requirements

- **Status:** ✅ Accepted — its consequences refined by [ADR 0014](0014-roadmap.md), decision 9 (the UI foundation comes with the first MVP phase, PH-14, rather than the first phase that builds UI)
- **Date:** 2026-10-01
- **Extends:** [ADR 0007](0007-testing-strategy.md), decisions 5 and 6 (a Firefox E2E project; axe's rule sets, both color schemes, and journeys that fail on a CSP violation); [ADR 0005](0005-development-environment.md), decisions 12 and 14 (the Tailwind Prettier plugin and editor extension); the document roles table of [ADR 0011](0011-design-sanity-check-follow-ups.md), decision 4 (the visual design doc); the definition of done of [ADR 0004](0004-implementation-process.md), decision 7 (UI screenshots, a Lighthouse run at the demo check)

## Context

Visual design is the last foundation topic of [ADR 0004](0004-implementation-process.md). Decision 4 of that ADR sets its scope: **a foundation up front, screens per phase**. This topic settles the overall look, the styling approach, the component library and the design tokens; each phase designs the screens it builds. Like every foundation topic, it settles direction and constraints; the code and configuration are written by the phases.

Its open point, [OP-001](../open-points.md#op-001), adds two things:

- **The non-functional requirements Szop has none of yet** (audit finding m20): which browsers are supported, the accessibility target axe checks against, and a performance budget for a phone on a weak signal.
- **The constraint of [ADR 0012](0012-security-baseline.md), decision 8:** the Content Security Policy (CSP) allows no inline scripts and no `<style>` elements, so styles must be built ahead of time, not injected at run time.

Other facts that shaped the choices:

- **The owner's goal for this topic** is to learn the frontend styling technology. The look itself should be good and mainstream, reached quickly, not a long design exercise.
- **The references** the owner picked are Todoist and Things (calm, airy, one accent color, list-centric) and Bring! and AnyList (shopping apps with large tap targets).
- **The app is used on phones in stores and on desktops for planning** ([functional requirements](../requirements/functional-requirements.md#assumptions)), served without a CDN from one container in Frankfurt ([ADR 0008](0008-hosting.md), decision 11).
- **The stack is fixed:** a React SPA built by Vite ([ADR 0002](0002-technical-architecture.md)).

The options were explored in mockups during the brainstorm. The approved ones are kept in [`docs/architecture/visual-design/`](../architecture/visual-design/) and described in the living [visual design](../architecture/visual-design.md) doc.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|-------|--------------------|------------------------|
| 1 | Supported browsers | "Baseline widely available" including Safari, with a WebKit E2E project; the same, with Safari checked by hand; Chromium only | **Chrome, Edge, Firefox and Chrome on Android ([NFR-1](../requirements/functional-requirements.md#nfr-1)). Safari and iOS are explicitly unsupported**, a choice rather than an oversight: the owner does not target Apple's ecosystem, for now at least, and a third engine would add an E2E project to every run. Szop will probably work there, untested. **The build keeps Vite's default target, `baseline-widely-available`** (Chrome and Edge 111, Firefox 114, Safari 16.4 for Vite's current major): it is the mainstream setting, and narrowing it to drop Safari would gain nothing measurable. |
| 2 | E2E browsers | Desktop Firefox on every journey; Firefox on a few smoke journeys; Firefox by hand | **A Playwright Firefox project at the desktop viewport runs every journey**, next to desktop Chromium and the emulated Pixel ([ADR 0007](0007-testing-strategy.md), decision 5). Firefox is the only supported browser with its own engine (Gecko), so the support promise is backed by tests. Edge runs on Chromium and Android is the Pixel, both already covered. A smoke subset adds a rule about which journeys count; by hand leaves the promise untested. The suite is small at first; revisit if CI gets slow. |
| 3 | Accessibility target | WCAG 2.2 AA; WCAG 2.1 AA; axe's defaults with no stated level | **WCAG 2.2 AA ([NFR-2](../requirements/functional-requirements.md#nfr-2)).** axe runs with the `wcag2a`, `wcag2aa`, `wcag21aa` and `wcag22aa` rule sets. AA is the level products and laws aim for; 2.2 is the current version and adds criteria that matter here (a minimum target size, focus not hidden behind sticky bars), which Szop meets anyway. 2.1 AA, which the European Accessibility Act references, is practically the same work. No stated level would leave "accessible" undefined. axe finds only part of the real problems automatically; keyboard use and the component library (decision 7) cover much of the rest. |
| 4 | Performance budget and how it is enforced | A size gate in CI with Core Web Vitals measured by hand; Lighthouse CI as a gate; targets measured only | **Targets ([NFR-3](../requirements/functional-requirements.md#nfr-3)): Core Web Vitals in Google's "good" range, Largest Contentful Paint (LCP) ≤ 2.5 s, Interaction to Next Paint (INP) ≤ 200 ms and Cumulative Layout Shift (CLS) ≤ 0.1, on Lighthouse's default mobile profile (a slow 4G phone); initial JavaScript ≤ 200 KB compressed.** **The bundle size is a CI gate**: the number is the same on every build, so the gate is reliable. **Core Web Vitals are checked with a Lighthouse run during the demo check**, where the app is deployed anyway. Lighthouse in CI needs a running deployment and its scores vary between runs, which makes a gate flaky. Measuring only lets a heavy library slip in between checks. React, React Router, TanStack Query, React Hook Form and Zod take roughly half of the 200 KB, so the budget also guards the component library. The numbers are a starting point, adjusted with a reason when real measurements exist. |
| 5 | Serving the static files | — | **The build writes Brotli and gzip copies of every file, and `@fastify/static` serves them with `preCompressed`.** **Fingerprinted assets** (Vite puts a content hash in their names) **are cached for a year as `immutable`; `index.html` is never cached**, so a new deploy reaches the browser at once. Without a CDN, every byte travels from Frankfurt, so compression and caching are the cheapest speed there is. |
| 6 | Overall look | A calm list (Todoist-like: compact rows, small checkboxes); friendly tiles (Bring!-like: a colored tile with a picture per product); calm and roomy (a blend) | **Calm and roomy.** Category sections are soft white cards on a light gray page, rows are 56 px high with large checkboxes, and color is used sparingly. It matches both references and suits one hand on a phone in a store. Compact rows fit more on screen but are harder to hit. Tiles look great, but they need a picture for every product in a catalog users edit themselves, and fit notes and prices badly. |
| 7 | Component library | shadcn/ui on Base UI; shadcn/ui on Radix; React Aria Components; Mantine; Material UI or Chakra | **shadcn/ui on Base UI.** shadcn/ui is not a dependency: its command-line tool copies styled component source into the repository, built on a **headless** library (behavior and accessibility, no looks) and Tailwind, and the code is then ours to read and change. It is the most widespread React setup, which serves the learning goal, and its defaults are polished and easy to restyle. Since July 2026 its default headless library is **Base UI**, which works under our CSP (decision 9). **Radix**, the older default, injects `<style>` elements for dialogs' scroll lock through `react-remove-scroll`, with only a nonce as the fix. **React Aria Components** (Adobe) is CSP-safe and has the strongest accessibility, but more styling is written by hand and it is less mainstream. **Mantine** is the fastest to a good look, but injects `<style>` elements, so it needs a nonce: `index.html` templated per request and ADR 0012's policy loosened; it also teaches theme configuration more than styling. **Material UI and Chakra** use CSS-in-JS, which injects styles at run time. |
| 8 | Styling approach | Tailwind CSS; CSS Modules; both | **Tailwind CSS v4, through its Vite plugin (`@tailwindcss/vite`).** Utility classes in the markup (`px-4 min-h-14 border-t`) are compiled at build time into one small stylesheet holding only the classes used, served from our origin, which the CSP allows. v4 is configured in CSS, without a `tailwind.config.js`. shadcn/ui is built on Tailwind. **CSS Modules** (scoped plain CSS files per component, also CSP-safe and easier to read at first) are rejected: mixing them with shadcn's Tailwind would give every styling question two answers. The trade-off is long class lists; components keep them in one place. |
| 9 | Living with the CSP | A nonce per response; build-time styles only, with a guard | **Build-time styles only, guarded by the tests.** Base UI's `CSPProvider` is set with **`disableStyleElements`**, and the small CSS it would otherwise inject (hiding native scrollbars in scroll areas and selects) goes into our stylesheet. **Toasts use Base UI's Toast**, not shadcn's default Sonner, which injects a `<style>` element and has no option to stop it. **Every E2E journey fails on a CSP violation** the browser reports, so a component that injects styles is caught the first time a test opens it. Setting styles from JavaScript through the DOM (`element.style`), which React's `style` prop does, is allowed by the CSP and stays usable. A nonce would mean templating `index.html` for every response and loosening ADR 0012, decision 8. |
| 10 | Design tokens | Raw values in components; one tier of named values; two tiers | **Two tiers, as CSS custom properties, the way shadcn/ui is built.** **The palette** is Tailwind's built-in colors (`teal-700`); **semantic roles** (`--primary`, `--background`, `--muted`, `--border`, `--destructive`, …) point into it, and components use only the roles. Changing the brand color, or adding dark mode or themes later, then changes the tokens and nothing else. **Everything lives in `apps/web`**; there is no `packages/ui`, since there is one web app and the future Android app would not share React components. shadcn's components go to `apps/web/src/components/ui/`, added one by one as phases need them, never all up front. |
| 11 | Color | Green, blue, teal or orange as the accent | **Teal**: `teal-700` in light mode, `teal-400` in dark mode, with a soft teal tint for highlights. Calm and a little distinctive, it fits the chosen look, and it does not collide with green for success or orange for warnings. Blue is safe but generic; green is the expected shopping-list color; orange has the most personality but sits next to warning and delete colors. **Neutrals come from Tailwind's `gray`.** **The roles are shadcn's set plus `warning`** (amber, for the [NET-1](../requirements/functional-requirements.md#net-1) offline banner); phases add a role when they need one. **Every pair of tokens meets AA contrast in both schemes**: 4.5:1 for text, 3:1 for UI parts such as checkbox borders. **axe scans every page in light and dark**, one extra scan per page rather than an extra E2E project, so a dark-mode mistake in a component is caught too. |
| 12 | Dark mode | Follow the system; light only, structured for dark later; system plus a manual toggle | **Dark mode follows the system setting** (`prefers-color-scheme`), with light and dark token sets. It needs no JavaScript: Tailwind's `dark:` variant works that way by default. **A manual toggle** (light, dark or system) **is recorded as a 💡 future extension.** It would be one small task: one line switching `dark:` to a class, a theme script, a menu and two tests. The script must run before the page paints, and our CSP forbids the usual inline script, so it would be a separate file that the page waits for; Vite does not fingerprint it, so it cannot be cached forever, and every load would wait for the browser's revalidation request. Adding it later costs the same as now, since components' `dark:` classes do not change. Light only would halve the color work, but dark mode is nearly free with shadcn's token sets. |
| 13 | Typography | The system font stack; a self-hosted web font (Inter, Figtree, Nunito) | **Figtree, self-hosted from npm (`@fontsource-variable/figtree`).** One variable file covers every weight: 20 KB for Latin and 10 KB for Latin Extended, which the browser downloads only when a character needs it, such as the Polish product names users type (*śmietana*, *żurek*) while the UI stays English. Vite bundles the files with a hash, so they come from our origin (allowed by the CSP, no Google Fonts) and are cached for good. `font-display: swap` shows text at once in the fallback font. Figtree is clean and a little warmer than Inter, and it has **tabular figures**, so prices and quantities line up. Inter, the mainstream choice, was the close alternative; the system font downloads nothing but looks different on every device; Nunito's rounded letters are more playful than a tool should be. **Tailwind's default type scale**; item names and inputs are 16 px, nothing is below 12 px, and the weights are 400, 600 and 700. |
| 14 | Spacing, size, shape and motion | — | **Tailwind's 4 px spacing grid. At least 48 px for anything tappable** (Android's guideline, well above WCAG 2.2's 24 px minimum); list rows are 56 px. **One `--radius` token of 12 px** for cards, buttons and inputs; checkboxes and pills are fully round. **Flat**: sections stand out by color, and one shadow level is used only for floating elements (dialogs, menus, toasts). **Motion** is short, 150 to 200 ms, for checking items off and opening dialogs, and **off entirely when the system asks for reduced motion** (Tailwind's `motion-safe:` variant). |
| 15 | Icons | Lucide; another icon set | **Lucide**, shadcn/ui's default: about 1,500 consistent line icons as React components. Only the icons imported reach the bundle, and they render as inline SVG elements, which the CSP allows. |
| 16 | Brand mark | A monogram; a raccoon (flat, cartoon or line style); a shopping basket | **A flat raccoon on a teal rounded square, with a lowercase "szop" wordmark in Figtree Bold** (teal, lighter teal in dark mode). "Szop" is Polish for raccoon, so the mark explains the name and makes the app recognizable. The raccoon is drawn around what makes it one: a solid eye mask with white brows, a white muzzle, rounded ears and cheek ruffs. Flat shapes stay clearest at favicon and header sizes; the cartoon style has more charm but its details clump at 16 px, and the line style read as a cat until its mask was made solid, and stayed the busiest. A monogram has no character; a basket is generic. **The approved draft is [`raccoon.svg`](../architecture/visual-design/raccoon.svg)**; the first UI phase polishes it into the favicon and header logo. |
| 17 | Navigation | A bottom tab bar; the lists as the home screen with a menu drawer; Todoist-style, with every list in the drawer | **The lists are the home screen, and everything else is in one menu: a drawer on phones, a permanent sidebar from Tailwind's `lg` breakpoint (1024 px).** Szop's destinations are not equally important: lists are used constantly, templates sometimes, and the catalog, categories, units and settings are setup. A tab bar suits a few destinations of equal weight, which is Material Design's own guidance; it would spend tabs on setup and still need a second level. The drawer keeps every destination on one level and gives the list screens all the room. Todoist's pattern, which opens straight into the last list, loses the overview the reuse, archive and duplicate actions need. **Inside a list, the menu gives way to a back arrow, and the add bar sits at the bottom.** |
| 18 | Layout and interaction principles | — | Every phase follows these; screens are designed in the phase. **Mobile first**: styles are written for the phone and wider screens add to them. **Desktop content is capped at about 720 px.** **On phones, the screen's main action is pinned at the bottom**, within thumb reach, and sticky bars never cover the focused element. **Changes are optimistic** ([architecture](../architecture/architecture.md#optimistic-updates)), with no spinner. **Messages are Base UI toasts** that say what happened and what to do, never a generic "Something went wrong" ([LIM-3](../requirements/functional-requirements.md#lim-3), [LIM-4](../requirements/functional-requirements.md#lim-4) included). **Undo is preferred over "Are you sure?"** for reversible actions, and a confirmation dialog is kept for what cannot be undone, such as deleting an account; which actions get undo stays with their phases ([OP-051](../open-points.md#op-051)). **First loads show skeleton placeholders**, never a full-screen spinner. **Every empty page says what it is for and offers the next action.** **Offline ([NET-1](../requirements/functional-requirements.md#net-1))**: an amber banner stays at the top, and controls that change data are disabled with a visible reason. **Labels are always visible**, never placeholder-only; errors appear under the field, checked when leaving it and on submit. **A visible teal focus ring** (the `--ring` token) marks the focused element; dialogs and drawers trap focus and return it, which Base UI handles. **Text is plain, friendly English in sentence case** ("New list", not "Create New List"). |
| 19 | Tooling | — | **`prettier-plugin-tailwindcss`** sorts class lists the same way on every save ([ADR 0005](0005-development-environment.md), decision 12). **The Tailwind CSS IntelliSense extension** joins `.vscode/extensions.json` (ADR 0005, decision 14): it completes class names and shows the CSS behind them. **shadcn's `cn()` helper** merges class lists without conflicts. Tailwind and shadcn/ui each get a tool page in `docs/development/tools/` (ADR 0005, decision 15). |
| 20 | Storybook | Not now, revisited later; a workshop only; a workshop with its test integration | **Not now.** Storybook shows each component on its own, in every state, outside the app. Its cost is setup, a story file per component and one more build in CI, and its test integration runs in a real browser (Vitest Browser Mode), which [ADR 0007](0007-testing-strategy.md), decision 9 left out. For now, components are built in the running app and checked by component tests. [OP-060](../open-points.md#op-060) revisits it once the component set grows or reviewing states by hand gets tedious. |
| 21 | How a phase designs its screens | — | **The phase brainstorm designs its screens as mockups in the visual companion**, using the real tokens. **The approved mockups are committed as screenshots**, phone and desktop, in a folder next to the phase's spec, which links them; mockups left in `.superpowers/` are not kept (it is ignored by git). **The spec lists each screen's states**: empty, loading, error, offline, long content (a 40-character product name) and dark. **A PR that changes the UI shows screenshots** of what was built: phone in light and dark, desktop in light (definition of done, item 11). |
| 22 | Where it is written down | The ADR only; a living doc; the non-functional requirements in that doc, in the functional requirements or in a file of their own | **A living doc, [`docs/architecture/visual-design.md`](../architecture/visual-design.md)**, says what the design system is *now*: the look, tokens, typography, brand, layout and interaction principles, and how screens are designed. This ADR says *why*. Each phase that changes the design system updates it. **The non-functional requirements get their own linkable section in the [functional requirements](../requirements/functional-requirements.md#3-non-functional-requirements)** ([NFR-1](../requirements/functional-requirements.md#nfr-1) to [NFR-3](../requirements/functional-requirements.md#nfr-3)), so there is one requirements document and every requirement is linked the same way. A file of their own would split the requirements; keeping them in the visual design doc would hide them where nobody looks for requirements. |
| 23 | Deliberately left out | — | **Safari and iOS, and a WebKit E2E project** (decision 1); **a manual theme toggle** (decision 12, a 💡 future extension); **Storybook** (decision 20, [OP-060](../open-points.md#op-060)); **Lighthouse CI** (decision 4); **visual regression testing**, as [ADR 0007](0007-testing-strategy.md) decided; **CSS Modules, Radix, React Aria Components, Mantine, Material UI and Chakra, and Sonner** (decisions 7–9); **an installable app** (a web app manifest and home-screen icon), which belongs with the offline extensions ([OP-061](../open-points.md#op-061)). |

## Consequences

- **Costs:** nothing. Tailwind, shadcn/ui, Base UI, Lucide and Figtree are free and open source; the font is served from our own origin.
- **The living docs are updated:** the new [visual design](../architecture/visual-design.md) doc with the approved mockups and the raccoon; the [functional requirements](../requirements/functional-requirements.md) (a new section 3 for [NFR-1](../requirements/functional-requirements.md#nfr-1) to [NFR-3](../requirements/functional-requirements.md#nfr-3), which renumbers use cases and release slicing to 4 and 5, and the theme toggle among the future extensions); `architecture.md` (visual design is no longer out of scope; styling, components and the serving rules); the stack overview (styling with Tailwind, headless components, design tokens, performance); the glossary; the definition of done and the PR template (UI screenshots, Lighthouse at the demo check); and the documentation lists of `CLAUDE.md` and the README.
- **ADR 0005 and ADR 0007 are extended** by decisions 2, 3, 9, 11 and 19, noted in their status lines.
- **`.gitignore` ignores `.superpowers/`**, where the visual companion keeps its mockups.
- **OP-001 is closed.** The work this ADR leaves is tracked as new points: the UI foundation in the first phase that builds UI (**OP-056**); the E2E additions (**OP-057**); serving the SPA's files (**OP-058**); the bundle-size gate in CI (**OP-059**); revisiting Storybook (**OP-060**); and an installable app (**OP-061**).
- **Every foundation topic is now decided.** The next step is the roadmap ([OP-002](../open-points.md#op-002)).
