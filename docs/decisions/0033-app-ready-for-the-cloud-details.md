# ADR 0033 — App ready for the cloud details

- **Status:** ✅ Accepted
- **Date:** 2026-10-18
- **Refines:** [ADR 0008](0008-hosting.md), decision 14 (the app checks the recorded migrations against its own before migrating, and refuses to start on a mismatch; see decision 3); [ADR 0019](0019-api-skeleton-details.md), decision 8 (the graceful shutdown has a 10-second deadline; see decision 6)

## Context

PH-12 First deploy was the largest phase of Stage 3, with about twenty tasks and two concepts new to the project. Its brainstorm split it in three ([ADR 0014](0014-roadmap.md), decision 6), and the first part, [PH-12a](../roadmap.md#ph-12a-app-ready-for-the-cloud), gets the app ready for Elastic Container Service (ECS) and RDS before it gets there, so that the first real deploy in [PH-12c](../roadmap.md#ph-12c-app-on-ecs-and-rds) meets no app-side surprise. Everything in it runs and is tested locally; no AWS resource changes.

Four open points reached the phase from earlier ones: what the app does when the demo's database holds migrations of another branch ([OP-043](https://github.com/luiki-dev/szop/issues/84)), TLS to RDS ([OP-017](https://github.com/luiki-dev/szop/issues/68)), a shutdown that hung for 145 seconds in [PH-06a](../roadmap.md#ph-06a-production-build-and-serving)'s browser check ([OP-085](https://github.com/luiki-dev/szop/issues/88)), and the load balancer's health checks filling the log ([OP-072](https://github.com/luiki-dev/szop/issues/85)). The brainstorm also asked whether the demo's data should ever survive a session.

This ADR records the decisions, with what was settled while building them. The [spec](../superpowers/specs/2026-10-18-PH-12a-app-ready-for-the-cloud-design.md) holds the design in full.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|-------|--------------------|------------------------|
| 1 | The phase's scope | Keep PH-12 whole; split it in two (the app's preparation, then all the infrastructure); split it in three | **PH-12 First deploy is retired and split into three phases:** PH-12a App ready for the cloud (the app-side changes, no AWS), [PH-12b](../roadmap.md#ph-12b-network-and-the-demo-up-button) Network and the demo-up button (the network, the load balancer with a placeholder page, the certificate, the DNS record and the real `demo-up`) and PH-12c App on ECS and RDS. PH-12 held about twenty tasks and two new concepts, the network with the push-button deploy, and the app on ECS with a managed database. Two phases would have left one of about twelve tasks with both concepts. ECS and RDS stay together: the app does not start without a database, so either alone ends with nothing working. |
| 2 | Data that survives | Data disposable for good; keep it from now; keep the door open | **Data stays disposable today, and the door stays open for data that survives.** The owner does not want to rule out real data. Keeping it does not grow harder as the app grows, since every demo database until then is empty and thrown away; what could grow is an assumption of an empty database baked into the code. So the migration check's remedy lives in its message and the docs, not in its logic; a seed, if one comes, is an explicit command and never runs at startup; and the check catches edited migrations, harmless on a throwaway database but not on a kept one. The options for keeping data (a snapshot between sessions, a stopped database in base, a dump to S3, Aurora scaling to zero) are candidate [OP-097](https://github.com/luiki-dev/szop/issues/224); a seed that shows the system in the middle of use is candidate [OP-098](https://github.com/luiki-dev/szop/issues/225). |
| 3 | The migration check ([OP-043](https://github.com/luiki-dev/szop/issues/84)) | Rely on Drizzle; check unknown and skipped migrations; check those and edited ones | **Before migrating, the app compares the migrations recorded in `drizzle.__drizzle_migrations` with its own, matched by timestamp, and refuses to start on any of three cases.** **Unknown:** a recorded migration this code does not have (an older commit on a newer database). **Skipped:** a migration of this code, not recorded, older than the newest recorded one, which Drizzle 0.45 would skip without a word ([ADR 0020](0020-database-details.md), consequences). **Edited:** a recorded migration whose SQL differs from this code's file with the same timestamp. Each comes from switching branches against one database, on the demo or locally, and each would otherwise fail later and far from its cause, or not at all. The error names each migration, its case and the remedy, and the process exits with code 1. A new, empty database and migrations newer than every recorded one (a normal upgrade) pass. Matching by timestamp, not hash, keeps two migrations with the same SQL apart. Refines ADR 0008, decision 14. |
| 4 | The remedy, locally *(Claude's call)* | Document the Docker commands; a script | **`pnpm db:reset`** removes PostgreSQL's container and its volume and starts it again, empty; the next start migrates it. On the demo the remedy is `demo-down`, then `demo-up` (PH-12c's runbook). The check's message names both: ``Reset the database: `pnpm db:reset` locally; on the demo, `demo-down` then `demo-up`.`` |
| 5 | TLS to the database ([OP-017](https://github.com/luiki-dev/szop/issues/68)) *(Claude's call)* | A flag; a path to a certificate bundle; a mode named after libpq's `sslmode` | **A required setting `DATABASE_TLS`, `none` or `verify-full`**, written like `TRUSTED_PROXIES=none` and with no default ([ADR 0019](0019-api-skeleton-details.md), decision 2). `verify-full` gives the pool `ssl: { ca, rejectUnauthorized: true }` with the RDS certificate authority (CA) bundle committed in PH-08 ([ADR 0028](0028-container-image-details.md), decision 2), read when the pool is created, so a missing bundle stops startup. node-postgres then rejects a certificate the bundle does not vouch for or one issued for another host. Local development, Compose and the tests use `none`. Unit tests prove the pool's options for each value; the handshake itself is proven on the demo in PH-12c, since a local PostgreSQL with TLS would take a test CA, a server certificate and a second Compose service to prove what the demo proves anyway. |
| 6 | The shutdown deadline ([OP-085](https://github.com/luiki-dev/szop/issues/88)) | Leave shutdown as it is; Fastify's `forceCloseConnections: true`; a deadline | **A 10-second deadline, kept even though the 145-second hang turned out to be gone.** The check came first: with the Linux Chrome inside WSL2's NAT networking, the page loaded and closed, SIGTERM ended the API in 0.029 s (Node 24.21.0, Fastify 5.12.5). The hang was WSL's mirrored networking, since dropped, which held connections to closed ports open. A slow client or a long request can still hold a shutdown past ECS's 30-second kill, which cuts off requests and skips closing the pool. So at 10 seconds the API logs a warning with the number of connections still open and closes them all (`closeAllConnections()`), and the usual path finishes with exit code 0; if it still has not exited 5 seconds later, it exits with code 1. Both timers are `unref`'d. `forceCloseConnections: true` would cut every request in flight at once. Refines ADR 0019, decision 8. |
| 7 | Quieter health checks ([OP-072](https://github.com/luiki-dev/szop/issues/85)) *(Claude's call)* | Raise the route's `logLevel` to `warn`; turn request logging off for the route | **Request logging is off for `/api/health` only: Fastify's `disableRequestLogging` gets a function that is true when the matched route is `/api/health`.** Its two request lines per check go; its own `database check failed` warning stays, so an outage still shows; look-alike paths such as `/api/healthz` keep their lines; and `LOG_LEVEL` still governs everything. A route `logLevel` was the first idea, but the spec's builder check found that Fastify 5.12 gives such a route a logger fixed at that level: the route would log warnings even with `LOG_LEVEL=silent`, including in the tests. |

## Settled while building

Facts the plan did not have, kept here because they explain code or record what was proven:

- **Drizzle's reader gives the recorded hashes.** `readMigrationFiles` is exported from `drizzle-orm/migrator` in 0.45, and its hash for `0000_init` is the SHA-256 of the SQL file and equals the hash the migrator recorded, as the check's tests prove against a freshly migrated database.
- **node-postgres checks the host name.** For a host that is not an IP address, node-postgres 8.23.1 passes it to Node's TLS as `servername`, so `rejectUnauthorized: true` checks the certificate's name as well as its chain; RDS endpoints are DNS names.
- **`closeAllConnections()` lets a pending `app.close()` resolve** in Fastify 5.12: with half a request held open, the warning came 10.01 seconds after `shutting down`, with `openConnections: 1`, and the API exited with code 0.
- **Holding half a request open needs stdin kept open.** `printf 'GET / HTTP/1.1\r\nHost: x\r\n' | nc 127.0.0.1 3000` half-closes the socket when `printf` ends, and Node answers the incomplete request with 400 at once; `(printf 'GET / HTTP/1.1\r\nHost: x\r\n'; sleep 30) | nc 127.0.0.1 3000` holds it.
- **`disableRequestLogging`'s function sees the matched route** for both request lines, so `request.routeOptions.url` matches `/api/health` with or without a query string.
- **The client-address tests moved off `/api/health`.** They read the address from the `incoming request` line, which the health route no longer writes; they now request an unknown API path, which logs the same way.

## Consequences

- Every `apps/api/.env` needs the line `DATABASE_TLS=none`; without it the API and the API tests stop with `DATABASE_TLS: missing` ([setup guide](../development/setup.md)). CI copies `.env.example` and needs nothing.
- [PH-12c](../roadmap.md#ph-12c-app-on-ecs-and-rds) sets `DATABASE_TLS=verify-full` on ECS and proves the handshake with RDS (decision 5); sets ECS's deployment to a minimum of 0% and a maximum of 100% healthy tasks; tunes the health check, the stop timeout and the load balancer's deregistration delay with the 15-second bound of decision 6 in mind; and writes the runbook's explanation of the migration check's message and of switching branches on the demo ([OP-043](https://github.com/luiki-dev/szop/issues/84)). The TLS part of [OP-017](https://github.com/luiki-dev/szop/issues/68) moves there too.
- A database that ever needs to keep its data needs a remedy other than a reset, without any change to the check (decision 2, [OP-097](https://github.com/luiki-dev/szop/issues/224)). A representative seed stays a candidate ([OP-098](https://github.com/luiki-dev/szop/issues/225)).
- A successful health check leaves no trace in the log; a failing one still logs its warning, and the load balancer's target health shows the checks' results.
- Costs: none; nothing in the phase touches AWS.
