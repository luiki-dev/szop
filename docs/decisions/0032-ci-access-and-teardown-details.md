# ADR 0032 — CI access to AWS and teardown details

- **Status:** ✅ Accepted
- **Date:** 2026-10-17
- **Refines:** [ADR 0010](0010-ci-cd.md), decisions 14 (base is planned without refreshing; see decision 11) and 16 (the deploy role grows phase by phase, lists the whole state bucket and trusts only `demo-teardown` for now; see decisions 3, 10 and 12); [ADR 0012](0012-security-baseline.md), decision 16 (the deploy role does not trust `demo` before that environment exists, see decision 10); [ADR 0018](0018-ci-details.md), decision 6 (actionlint and zizmor run before each commit, see decision 2)
- **Extends:** [ADR 0010](0010-ci-cd.md), decision 16, and [ADR 0012](0012-security-baseline.md), decision 17 (the plan role is also denied billing and cost reads and the account's contact details, see decision 5)
- **Completes:** [ADR 0010](0010-ci-cd.md), decisions 13 (`demo-down` always runs a real destroy, with timeouts; see decisions 6 and 7), 14 (a second job posts the plan comment, see decision 8) and 16 (IAM Access Analyzer validates the roles' policies in every plan, see decision 4); [ADR 0011](0011-design-sanity-check-follow-ups.md), decision 7 (what `demo-down` does when no commit is recorded, and its timeouts; see decisions 6 and 7)

## Context

[PH-11](../roadmap.md#ph-11-ci-access-to-aws-and-the-teardown-safety-net) gives CI access to AWS for the first time. The direction was settled before: no stored keys, GitHub signs in to AWS with OpenID Connect (OIDC) ([ADR 0010](0010-ci-cd.md), decision 15); a read-only plan role for pull requests and a deploy role (decision 16); a plan comment that never blocks a merge (decision 14); a nightly `demo-down` that is merged and proven before any demo can exist ([ADR 0011](0011-design-sanity-check-follow-ups.md), decisions 2 and 7); and the rules that an environment, not a workflow, is what the deploy role trusts, and that no code runs next to AWS credentials that a pull request could change ([ADR 0012](0012-security-baseline.md), decisions 16 to 18).

Those left the details to the phase: how much the deploy role may do before any demo exists, where IAM Access Analyzer's policy validation runs, which billing access the roles get ([OP-094](https://github.com/luiki-dev/szop/issues/209)), what `demo-down` does when no commit is recorded, and whether actionlint and zizmor run before a commit ([OP-066](https://github.com/luiki-dev/szop/issues/79)). The brainstorm settled them, and its builder check found one more: the deploy role cannot trust an environment before it exists. Building the phase found two more (decisions 11 and 12), each when a real run or a policy check disagreed with an assumption.

This ADR records the decisions, with what was settled while building them. The [spec](../superpowers/specs/2026-10-17-PH-11-ci-access-to-aws-and-the-teardown-safety-net-design.md) holds the design in full.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|-------|--------------------|------------------------|
| 1 | The phase's scope | Keep all nine open points; move the Terraform scanner to PH-12; move it to a new phase | **The scanner ([OP-091](https://github.com/luiki-dev/szop/issues/201)) moves to a new phase, PH-35 "Security scanners", after PH-12, together with the image scan ([OP-090](https://github.com/luiki-dev/szop/issues/194)).** A scanner is a second new concept next to OIDC and IAM; PH-12 brings the first real image and the security groups, load balancer and RDS worth scanning, and one tool (Trivy) may cover both open points. PH-12 is already the largest phase of the stage. **[OP-069](https://github.com/luiki-dev/szop/issues/80) is taken off the phase and marked blocked**: actionlint's issue #732 is still open and 1.7.12 still rejects `$/`. |
| 2 | actionlint and zizmor locally ([OP-066](https://github.com/luiki-dev/szop/issues/79)) | CI only, as [ADR 0018](0018-ci-details.md), decision 6 left it; a lint-staged entry with the tools installed through the setup guide | **Both run in the pre-commit hook on staged workflow files, and `pnpm check:workflows` checks them all**, with the tools installed through the setup guide, the way Terraform and tflint are: actionlint as its pinned, checksum-verified release binary, zizmor with `uv tool install` in the version CI runs, which makes uv a prerequisite. No slip caught only by CI was remembered from PH-02, but PH-11 writes the first workflows that hold AWS credentials. A missing tool fails the commit, as `terraform fmt` does. Each version now lives in two places, CI and the setup guide, as tflint's does. Refines ADR 0018, decision 6. <br>**Settled while building:** lint-staged's glob reaches the `.github` folder, though it starts with a dot, and zizmor finds `.github/zizmor.yml` by itself when it is given single files, so the hook needs no `--config`. Handed only YAML it does not audit (an issue form, its own `zizmor.yml`), zizmor fails with "no inputs collected", so the hook passes it the workflows, the local actions and `dependabot.yml` only. CI's zizmor action took `latest` as its default version, so `ci.yml` now pins 1.30.1, the version of the setup guide. |
| 3 | How much the deploy role may do now | The full set of [ADR 0010](0010-ci-cd.md), decision 16, now; grow it with the code | **It grows phase by phase.** In PH-11 `szop-ci-deploy` may only read and write the demo's state and its lock file; an empty destroy needs nothing more. Each phase that adds a resource to `infra/demo` adds the permissions it needs, in the same PR, where the plan comment and Access Analyzer show them next to the resource. Permissions written now for resources not yet designed would be guesses, and guesses end up broad. **Cost:** PH-12 changes `infra/base` too and the owner applies it again, which is already one of its steps. Refines ADR 0010, decision 16. |
| 4 | Where the Access Analyzer check runs | In `infra-plan.yml`, automatically; a local script before applying base; once by hand in this phase | **In `infra-plan.yml`.** After each plan, the job takes every IAM policy out of the plan's JSON and sends it to `aws accessanalyzer validate-policy`; the findings are part of the plan comment. Every later PR that changes a role, PH-12's first, is checked without anyone remembering to. A policy holding a value only known after apply is reported as not checked yet. A local script relies on memory and leaves no proof in the PR; a one-off check leaves PH-12 unchecked. Completes ADR 0010, decision 16. <br>**Settled while building:** `ReadOnlyAccess` (default version v190) already grants `access-analyzer:ValidatePolicy`, so the plan role has no extra allow statement for it. On both trust policies Access Analyzer gives the suggestion `CONFIRM_AUDIENCE_CLAIM_TYPE` and the warning `SPECIFIC_GITHUB_REPO_AND_BRANCH_RECOMMENDED`, and the phase accepts them: each condition is a `StringEquals` on one value, with no wildcard; a pull request's subject carries no branch; and `demo-teardown` is limited to `main` by the environment's deployment-branch rule, a GitHub setting that the trust policy cannot see (see [GitHub settings](../development/github-settings.md#environments)). |
| 5 | Billing access ([OP-094](https://github.com/luiki-dev/szop/issues/209)) | — | **The runbook's one-time setup gains the root user's "Activate IAM Access" to billing, then the `project` and `group` cost allocation tags; `szop-ci-plan` is explicitly denied billing and cost reads** (Cost Explorer, Budgets, billing, cost and usage reports, invoices). `ReadOnlyAccess` includes some of them, and everything the plan job prints is public. **The plan role is also denied the account's contact details** (primary email, contact information, alternate contacts), which `ReadOnlyAccess` grants and a PR could print into a public log; added after Task 1's review. `szop-ci-deploy` has no billing or account permission to deny. Extends ADR 0010, decision 16, and [ADR 0012](0012-security-baseline.md), decision 17. |
| 6 | `demo-down` when no commit is recorded | Run a real destroy with `main`'s code; skip it | **It always runs a real destroy.** With no `deployed_commit` output in the demo's state (in PH-11, and later on every night with no demo up), it destroys with the code of `main`, which finds nothing and finishes within a minute. Every nightly run then exercises OIDC, the role, the backend and the lock, so a broken safety net shows on a quiet night and not on the night a demo is up. Skipping would make most nights prove only that the workflow starts. Completes [ADR 0011](0011-design-sanity-check-follow-ups.md), decision 7. |
| 7 | `demo-down`'s timeouts *(Claude's call)* | — | **Every Terraform command waits up to 15 minutes for the state lock (`-lock-timeout=15m`), and the job times out after 60 minutes**, since deleting RDS takes about ten. A `demo-up` that holds the lock longer than 15 minutes fails the nightly run, which GitHub emails to the owner. PH-12 may revisit both once real timings exist. Completes ADR 0011, decision 7. |
| 8 | Who posts the plan comment *(Claude's call)* | The plan job itself; a second job without AWS credentials | **A second job.** The `plan` job holds `id-token: write` and `contents: read` only, and passes the comment's text on as an artifact; the `comment` job holds `pull-requests: write` and no AWS credentials, and posts or updates the comment with `gh api`, without a third-party action. No job holds both a write token for the repository and AWS credentials. <br>**Settled while building:** the comment step, its upload and the `comment` job run on `!cancelled()`, not `always()`, so a cancelled run (a newer push) stops while a failed plan still gets its comment. A response from Access Analyzer that is not the expected JSON is reported as "validation failed", never as "no findings". The account ID is masked with `::add-mask::` in `infra-plan` and `demo-down`, so it shows as `***` in every later log line. The credentials step itself, which comes before the mask exists, echoes its `role-to-assume` input, so the role ARNs, and with them the account ID, appear in the public logs of both workflows; this is accepted (see Consequences). The owner approved these three after the review. |
| 9 | Proving the deploy role refuses pull requests *(Claude's call)* | Trust the policy and Access Analyzer; a throwaway proof PR | **A throwaway proof PR**, like PH-02's gate proofs ([#15](https://github.com/luiki-dev/szop/pull/15)): a branch with two workflow jobs. One, triggered by `pull_request`, asks for an OIDC token and tries to assume `szop-ci-deploy`, which AWS refuses. The other names `environment: demo-teardown` on the branch, which GitHub refuses before it runs. No job names `demo`, which would create that environment unprotected. The PR is closed without merging. It needs the deploy role's ARN as a variable, so it follows the owner's apply. A trust policy is the boundary of the whole setup, and seeing it refuse is the clearest lesson of the phase. |
| 10 | Trusting the `demo` environment before it exists | Trust `demo` now, as [ADR 0012](0012-security-baseline.md), decision 16 lists; create the protected `demo` environment now; accept the gap as a risk; leave `demo` out until PH-12 | **`szop-ci-deploy` trusts only `demo-teardown` in PH-11; PH-12 adds `demo` in the same PR that has the owner create it with the required reviewer.** GitHub creates a missing environment, unprotected, the first time a job names it, so trusting `demo` before it exists would hand the deploy role to any job on any branch that names it, without the owner's approval: the hole decision 16 closed. Nothing in PH-11 needs `demo`, so nothing trusts it, the same reasoning as decision 3. Creating it now adds an environment that is unused for a phase; a recorded risk leaves the trust boundary open. Refines ADR 0012, decision 16, for PH-11 only. Found by the spec's builder check. |
| 11 | Planning base without reading the secret | Plan base with `-refresh=false`; let the plan role read the one parameter; stop planning base in CI; move the secret out of base | **`infra-plan.yml` plans `infra/base` with `-refresh=false`; `infra/demo` keeps the full refresh.** Found while building: AWS provider 6.69.1 refreshes an `aws_ssm_parameter` with `GetParameter` and decryption even when its value is write-only, so the plan role's deny on secret values made base's plan fail. Without refresh, Terraform compares the code with the state and reads no live resource: the comment still shows exactly what the PR's code changes, including PH-12's role changes, which is its purpose. **Cost:** drift made outside Terraform does not show in the comment; only the owner changes base, and the owner's local plan before every apply still refreshes. Reading the parameter would let any same-repository PR print the Better Auth secret into a public log; not planning base would hide role changes from Access Analyzer; moving the secret reopens [ADR 0030](0030-domain-and-base-infrastructure-details.md) for a problem this solves. Refines [ADR 0010](0010-ci-cd.md), decision 14. |
| 12 | Listing the state bucket | Limit the deploy role's `s3:ListBucket` to the `demo/` prefix and have the owner create an empty demo state once; let it list the whole bucket | **The deploy role may list the whole state bucket; it still reads and writes only the demo's state and lock.** Found in Task 2's review: S3 answers a request for a missing object with 404 only when the caller may list the bucket, and with 403 otherwise, and the request carries no `s3:prefix` for a condition to match. Terraform's S3 backend treats only "not found" as "no state yet", so with the prefix limit every `demo-down` would fail until a demo state existed, and nothing in PH-11 creates one. **Cost:** the role sees the bucket's key names (`base/…`, `bootstrap/…`), which the backend files already publish, and none of their contents. An owner-created state would add a step, bend [ADR 0011](0011-design-sanity-check-follow-ups.md), decision 2's "no local apply of `infra/demo`", and break the safety net again if the object were ever deleted. |

## Settled while building

Facts the first plan did not have, found by Tasks 1 to 5 and kept here because they explain code that looks odd:

- **The OIDC provider has no `thumbprint_list`.** AWS validates GitHub's certificate chain against its own library of trusted root authorities and no longer uses the thumbprint, and the pinned AWS provider (6.69.1) accepts the provider without it.
- **The plan role needs no allow statement for Access Analyzer.** `ReadOnlyAccess` already grants `access-analyzer:ValidatePolicy` (decision 4).
- **Base's plan cannot refresh the secret** (decision 11), and **the deploy role must list the whole bucket** (decision 12). The second came with a check of the S3 backend's source: its workspace listing (`env:/`) tolerates an `AccessDenied` and falls back to the default workspace in Terraform 1.14, 1.16 and `main`, so that listing would not have failed `init`; only the missing-object answer did.
- **`demo-down` never falls back to `main`'s code.** If the recorded `deployed_commit` is not a full commit hash, or `git fetch` cannot find it, the job fails at once and loudly (the nightly failure email) instead of destroying with other code, since `main`'s code may not know a resource that a branch added and would leave it running (decision 6). The runbook says to destroy by hand then.
- **The actions in the new workflows** are pinned to full commit hashes: `aws-actions/configure-aws-credentials` v6.3.0, `actions/download-artifact` v8.0.2 and `actions/upload-artifact` v7.0.2, next to the `actions/checkout` and `hashicorp/setup-terraform` pins `ci.yml` already used.
- **Dependabot and OIDC are still unknown.** Whether a Dependabot pull request gets an OIDC token with `id-token: write` is checked on the first Dependabot `terraform` PR ([OP-019](https://github.com/luiki-dev/szop/issues/77)). If it gets none, `infra-plan` skips the PRs whose author is `dependabot[bot]` and provider bumps are planned locally.

## Consequences

- [PH-12](../roadmap.md#ph-12-first-deploy) widens `szop-ci-deploy` for each resource it adds to `infra/demo`, in the same PR, where the plan comment and Access Analyzer show the permission next to the resource (decision 3). It adds `repo:luiki-dev/szop:environment:demo` to the trust in the PR in which the owner creates that environment with its required reviewer (decision 10), writes the `deployed_commit` output that `demo-down` already reads, replaces the placeholder `demo-up.yml`, and has `demo-up` re-enable `demo-down` ([ADR 0010](0010-ci-cd.md), decision 13). It changes `infra/base`, so the owner applies base again.
- The `demo-teardown` environment (no reviewer, `main` only) and the two repository variables `AWS_PLAN_ROLE_ARN` and `AWS_DEPLOY_ROLE_ARN` are GitHub settings, listed in [GitHub settings](../development/github-settings.md). The environment must exist before `demo-down` reaches `main`: a job that names a missing environment creates it, unprotected.
- A plan comment for `infra/base` shows what the PR's code changes, not drift made outside Terraform (decision 11); the owner's local plan before every apply still refreshes. Everything the comment and the plan log print is public, which is acceptable only because secret values never enter Terraform state ([ADR 0008](0008-hosting.md), decision 22). That includes the role ARNs, and so the account ID, which GitHub echoes in the credentials step's input before the mask is registered; the account ID is not a secret, and an ARN opens nothing without a token that only a job of this repository can get. `terraform plan` can still run programs with the plan role, which is read-only and reads neither secrets, logs, costs nor the account's contact details ([ADR 0012](0012-security-baseline.md), decision 17); the [threat model](../architecture/threat-model.md#risks-accepted-on-purpose) lists both as risks accepted on purpose.
- Every nightly `demo-down` run exercises OIDC, the role, the backend and the lock, so a broken safety net shows on a quiet night (decision 6). A failed scheduled run is emailed to the user who last changed the schedule, the owner; the budget alerts stay the second net.
- actionlint and zizmor are installed by hand, as Terraform and tflint are, and their versions live in two places each: `ci.yml` and the setup guide (decision 2).
- The Terraform scanner and the image scan wait for the new [PH-35](../roadmap.md#ph-35-security-scanners) (decision 1); [OP-069](https://github.com/luiki-dev/szop/issues/80) stays blocked until actionlint accepts the `$/` syntax.
- Costs: the OIDC provider and the roles are free, and the workflows run on GitHub's free minutes for public repositories. An empty nightly destroy takes about a minute.
