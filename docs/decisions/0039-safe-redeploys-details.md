# ADR 0039 — Safe redeploys details

- **Status:** ✅ Accepted
- **Date:** 2026-10-21
- **Completes:** [ADR 0036](0036-scalability-and-isolation.md), decisions 3 (the rolling settings and the circuit breaker, see decision 7), 4 (the liveness route and the health check's settings, see decisions 5, 6 and 8) and 5 (the 30-second deregistration delay, see decision 9); [ADR 0038](0038-app-on-ecs-and-rds-details.md), decision 12 (the defaults it kept until this phase are tuned, see decisions 6, 8 and 9)
- **Extends:** [ADR 0020](0020-database-details.md), decision 5 (`/api/health`'s answer carries the commit the image was built from, see decisions 2 to 4)
- **Refines:** [ADR 0008](0008-hosting.md), decision 15 (the load balancer checks `/api/live`; `/api/health` is the readiness check for `demo-up` and for people, see decisions 5 and 6)

## Context

[PH-12c](../roadmap.md#ph-12c-app-on-ecs-and-rds) put the walking skeleton on one Elastic Container Service (ECS) task with ECS's and the load balancer's defaults. A redeploy already worked, since ECS's defaults start the new task beside the old one, but slowly and by accident. [PH-12d](../roadmap.md#ph-12d-safe-redeploys) makes it deliberate and proves it. The direction was settled by [ADR 0036](0036-scalability-and-isolation.md), decisions 3 to 5: rolling deploys at 100% and 200% with the circuit breaker and no rollback, a liveness route for the load balancer with `/api/health` as the readiness check, a 30-second deregistration delay, and the expand-then-contract rule for migrations. Those left the details to the phase, and three open points reached it: [OP-043](https://github.com/luiki-dev/szop/issues/84)'s last part (the deploy settings), [OP-075](https://github.com/luiki-dev/szop/issues/87) (the health check's grace period and thresholds) and [OP-101](https://github.com/luiki-dev/szop/issues/247) (the hardening of `demo-up`, `db-setup` and the deploy role that PH-12c's review left). All three are settled here. The owner chose how the redeploy is proven and asked for the commit in `/api/health`, and left every other detail to Claude, to be argued in the spec. The spec's builder check found decision 15 and the job's longer timeout in decision 11; building found what is under "Settled while building".

This ADR records the decisions, with what was settled while building them. The [spec](../superpowers/specs/2026-10-21-PH-12d-safe-redeploys-design.md) holds the design in full.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|---|---|---|
| 1 | How the redeploy is proven | Refreshing the page every few seconds; a script asking `/api/health` every second | **A script, `scripts/watch-demo.sh`, asking `/api/health` every second** _(the owner's choice)_, printing the time, the HTTP status, the commit and the schema version, with a summary at the end. Refreshing by hand misses a gap of a few seconds, the browser may answer from its cache, and it cannot tell which version answered. The script stays in the repository and the runbook, so PH-37 and PH-38 repeat the same check. Bash and `curl` only, no AWS credentials. |
| 2 | Seeing the switch to the new version | No: only the absence of errors; yes: the commit in the response | **`/api/health` answers with the commit the image was built from** _(the owner's choice)_, in both its `200` and its `503` body, so the script shows the moment the new task starts answering, and which version fails if one does. The bodies are `{"status":"ok","commit":"<sha>","database":{"status":"up","schemaVersion":"…"}}` and `{"status":"error","commit":"<sha>","database":{"status":"down"}}`. The status page of the single-page application (SPA) parses the body with the shared schema and ignores the new field. Extends ADR 0020, decision 5. |
| 3 | Where the app learns its commit _(Claude's call)_ | An environment variable in the task definition, from Terraform's `deployed_commit`; a build argument baked into the image | **A build argument `GIT_COMMIT`, baked into the image as an environment variable of the same name**, set in the final stage after the `COPY` lines so it invalidates no earlier layer. The image then always tells the truth about its own code, wherever it runs: on ECS, in `pnpm check:image` and in CI. A task definition variable says what was deployed, which is the same thing today but drifts the day someone runs the image another way. `demo-up`'s `build` job already knows the commit. **The setting is required, like every one** ([ADR 0019](0019-api-skeleton-details.md), decision 2): 40 lowercase hexadecimal characters or `unknown`, anything else refused like any other bad setting. The Dockerfile defaults the argument to `unknown`, and `.env.example` carries `GIT_COMMIT=unknown`, so `pnpm dev`, the tests and a plain `docker build` start as usual. The spec first made it optional, against decision 2 of ADR 0019; the plan caught it. |
| 4 | The commit on a public route _(Claude's call)_ | Hide it; show it | **Show it.** It tells an attacker which code to read for weaknesses, but the repository is public and the demo runs for hours, not months; knowing the version adds little to what reading `main` gives. The [threat model](../architecture/threat-model.md) records it. |
| 5 | The liveness route _(Claude's call)_ | `/api/live`; `/api/health/live`; `/livez`; an ECS container health check | **`GET /api/live`, answering `200` with `{"status":"ok"}`**, touching nothing but the process. Under `/api` like every API route, so the SPA's fallback never answers it; a sibling of `/api/health`, not a child, since it is not a part of that check. An ECS container health check would need a client in the slim image and, like a combined load balancer check, would replace tasks while the database is down. The route answers only once the server listens, which is after the migrations ([ADR 0008](0008-hosting.md), decision 14), so a task is never healthy before it has migrated. Neither route is request-logged: the load balancer asks `/api/live` every 10 seconds, and the watch script asks `/api/health` every second. Refines ADR 0008, decision 15; completes ADR 0036, decision 4. |
| 6 | The load balancer's health check _(Claude's call)_ | The defaults (every 30 seconds, 5 successes to be healthy, 2 failures to be unhealthy); tuned | **`/api/live` every 10 seconds, a 5-second timeout, healthy after 2 successes, unhealthy after 3 failures, `200` only.** A new task gets traffic about 20 seconds after it listens, instead of up to two and a half minutes; a hung task leaves the rotation after about 30 seconds, and one slow answer is not enough. Each of the load balancer's nodes checks on its own, so this is a few requests a minute, unlogged. Completes ADR 0036, decision 4, and ADR 0038, decision 12. |
| 7 | The deployment and the circuit breaker _(Claude's call)_ | ECS's defaults (100% and 200%, no circuit breaker); stop-first (0% and 100%); rolling with the circuit breaker | **A minimum of 100% and a maximum of 200% healthy, the circuit breaker on, rollback off, its threshold left at ECS's default**, as [ADR 0036](0036-scalability-and-isolation.md), decision 3 set. The default threshold is half the wanted count, at least 3: with one task, the deployment is `FAILED` after three tasks in a row fail to start or fail their health checks. ECS can now take a fixed count instead, but 3 is the floor anyway and needs no setting a reader must look up. A `FAILED` deployment launches no more tasks; the old task keeps serving. Completes ADR 0036, decision 3. |
| 8 | The grace period _(Claude's call)_, **changed in the demo run** | 60 seconds (PH-12c); 120 seconds; longer | **First 120 seconds, then 60 seconds** _(the second the owner's choice, after the demo)_. The reasoning for 120 was that ECS ignores the load balancer's verdict for this long after a task starts, so a slow image pull or a long migration does not get the task killed before it listens, and that a long grace period "only delays noticing a task that runs but never answers". **The redeploy showed that wrong:** ECS counts a new task healthy only once the grace period has passed, so the old task was deregistered exactly 120 seconds after the new one registered and both versions answered for about two minutes, while the task listened about 30 seconds after it started. 60 seconds is still twice the 30 seconds the task needed to listen, and the overlap fell from about two minutes to about 50 seconds. The price is a short startup budget: at 60 seconds a task must listen within about a minute of starting, about 30 seconds of headroom today, so the room for a slow image pull or a long migration shrank with it. PH-37 weighs it against the migration lock's wait. Completes ADR 0036, decision 4, and ADR 0038, decision 12. |
| 9 | The deregistration delay _(Claude's call)_ | 300 seconds (the default); 30 seconds | **30 seconds**, as [ADR 0036](0036-scalability-and-isolation.md), decision 5 set. Szop's requests take milliseconds; the old task stops taking new requests at once and has 30 seconds to finish what it holds, then ECS sends `SIGTERM`, and the app closes within 15 seconds ([ADR 0033](0033-app-ready-for-the-cloud-details.md), decision 6). Fastify's keep-alive timeout of 72 seconds stays above the load balancer's idle timeout of 60, so the load balancer never sends a request on a connection the app has just closed, which would be a `502`. Completes ADR 0036, decision 5, and ADR 0038, decision 12. |
| 10 | `demo-up` and a failed deployment _(Claude's call)_ | Wait for the step's limit; read the deployment's rollout state | **The start loop reads the primary deployment's `rolloutState`**: `COMPLETED` with one deployment left is success, `FAILED` stops the run at once with `rolloutStateReason` and the service's latest events. Without it a failing deploy would make the loop wait its full 15 minutes. **When the service's count is 0** (a fresh demo), `demo-up` starts it with `--force-new-deployment`, so the first start is a deployment the circuit breaker watches too; on a redeploy, Terraform's new task definition already started one. |
| 11 | `demo-up`'s waits ([OP-101](https://github.com/luiki-dev/szop/issues/247)) _(Claude's call)_ | Count tries; measure the time | **Every wait loop runs to a deadline in seconds** (bash's `SECONDS`), not a count of tries, so a slow `curl` cannot stretch "10 minutes" into 20: 10 minutes for `db-setup`, 15 for the start, 10 for `/api/health`. The job's `timeout-minutes` rises from 30 to 45, since the three deadlines alone add up to 35 minutes before the apply and the state lock's wait (found by the spec's builder check). *Download the image* and `docker load` move above *Configure AWS credentials*, so the artifact is in hand before any credentials exist ([ADR 0012](0012-security-baseline.md), decision 18). On `db-setup`'s deadline, the run stops the task with a reason naming `demo-up` and fails with the log stream's name. |
| 12 | OP-101's other points _(Claude's call)_ | Here; a later phase | **All of them here.** They touch the files this phase changes (`demo-up.yml`, the deploy role, `db-setup`), and the owner's runs check them for free: the first `demo-up` creates the database and its secret, which the new IAM conditions guard. Moving them would mean another phase with the same base apply and the same demo runs. In detail: **`db-setup`'s transaction** gets `statement_timeout` of `30s` and `lock_timeout` of `10s`, for itself only, so a lock it cannot get makes it fail with a clear error instead of hanging, and the app's pool is unchanged; **the deploy role** gets `ecs:StopTask` on `db-setup`'s tasks, `secretsmanager:CreateSecret` on `rds!db-*` only through RDS (`aws:ViaAWSService = true`), and `rds:CreateDBInstance` only with `rds:ManageMasterUserPassword = true` and `rds:PubliclyAccessible = false` (the settled keys are under "Settled while building"). |
| 13 | The runbook's timings _(Claude's call)_ | Keep the 300-second explanation; measure and explain | **Measure the redeploy and the destroy again with the 30-second delay, and replace the explanation** with what AWS documents: a deregistering target with no in-flight requests and no active connections is deregistered at once, without waiting for the delay. PH-12c's redeploy was quiet, so the 300 seconds never showed. The measurements are under "Settled while building": the destroy's service took 2:46 with the 30-second delay, against PH-12c's 7 minutes. |
| 14 | Where the expand-then-contract rule lives _(Claude's call)_ | `drizzle.md`; the testing guide; an ADR only | **A section "Migrations and rolling deploys" in `docs/development/tools/drizzle.md`**, next to the migration check, as [ADR 0036](0036-scalability-and-isolation.md), decision 3 placed it, before PH-16's first table. This ADR points to it. Completes ADR 0036, decision 3. |
| 15 | A page load mixing two versions of the SPA | Sticky sessions on the target group now; the gap recorded, decided in PH-37; ignored | **Recorded, decided in PH-37** _(the owner's choice)_, as [OP-103](https://github.com/luiki-dev/szop/issues/249). While both tasks are healthy, the load balancer routes each request on its own, so a browser can get `index.html` from the new task and ask the old one for an asset only the new build has; the old task answers `404` and the page loads blank. With one task the window lasts about a minute; with PH-37's two tasks replaced one at a time it lasts minutes, and sticky sessions there must be weighed against PH-37's goal that a request does not depend on which task answers it. The runbook and the architecture name the gap. Found by the spec's builder check. |
| 16 | One command for the code checks | None (four scripts by hand); `pnpm check` running the four; `pnpm check` running every check, including the image, Terraform and the workflows | **`pnpm check`, running `pnpm lint`, `pnpm format:check`, `pnpm typecheck` and `pnpm test` in that order, stopping at the first failure** _(the owner asked for the script; what it runs is Claude's call)_. These are the checks of CI's `lint`, `typecheck` and `test` jobs that need nothing beyond the setup guide's Node and PostgreSQL. The build with the end-to-end (E2E) tests, `check:image`, `check:infra` and `check:workflows` stay separate: they need Docker, browsers, Terraform or the workflow linters, take minutes, and matter only when their files change, as CI's change detection already decides. The cheapest checks run first, so a formatting slip fails in seconds, not after the tests. |

## Settled while building

Facts the plan did not have, found while building and in the owner's demo runs, and kept here because they explain code that looks odd or record what was proven:

- **`GIT_COMMIT` is required** (decision 3), which the spec had as optional; the plan caught it before any code. The Dockerfile's `ARG GIT_COMMIT=unknown` / `ENV GIT_COMMIT=$GIT_COMMIT` sit in the final stage after the `COPY` lines, and `.env.example` carries `GIT_COMMIT=unknown`.
- **Fastify 5's default keep-alive timeout is 72 seconds**, already above the load balancer's idle timeout of 60. A test pins it; nothing is set explicitly.
- **`db-setup`'s timeouts are transaction-local**, set with `set_config(…, true)`, so they end with its transaction; a held row lock makes it fail with PostgreSQL's error `55P03` (lock not available), which a test provokes.
- **Both IAM condition keys exist and the provider sends both.** `rds:ManageMasterUserPassword` and `rds:PubliclyAccessible` are condition keys of `CreateDBInstance`, so the database cannot be created with a password RDS does not manage or with a public address. **A review found that the old `DemoDatabases` statement granted `rds:CreateDBInstance` on every resource**, which would have bypassed the new conditions, since the action applies to the subnet group and the parameter groups too: the subnet group moved to its own statement, `UseSubnetGroup`, with the tag scoping. `ecs:StopTask` honours `aws:ResourceTag/Name` and `ecs:cluster`, and the app's own tasks carry no tags, so the deploy role can stop `db-setup`'s tasks only. That rests on the service reference and a policy simulation: the stop path never ran on AWS, since no `db-setup` reached its deadline.
- **`secretsmanager:TagResource` is needed after all.** Task 4 dropped it because CloudTrail showed no such call, and the first real `demo-up` was refused at `CreateDBInstance` with "The user isn't authorized to create a secret": RDS copies the instance's tags onto the master secret as it creates it, which needs `TagResource` and which CloudTrail logs as no call of its own. It is back under the same `aws:ViaAWSService = true` condition, which works for RDS's `CreateSecret` too, so the role still cannot create or tag such a secret itself.
- **Scaling from 0 with `--force-new-deployment` started two tasks, and the flag is kept.** `update-service --desired-count 1 --force-new-deployment` scaled the old, zero-count deployment with the new count as well as starting the new one, so two tasks started and one stopped a minute later. The duplicate ran about a minute; its migrations are harmless, since they find nothing to do once one task has migrated ([PH-37](../roadmap.md#ph-37-two-tasks) adds the advisory lock), and it added no time. That first start took 2:55 because the run had the 120-second grace period (it ran before the change to 60 seconds): the redeploy at 120 seconds took 3:03 too, and the fix-forward at 60 seconds 1:34. The circuit breaker watched the deployment (its primary deployment reached `COMPLETED`). The flag stays because ECS's circuit breaker watches a deployment in progress, and scaling a completed deployment from 0 to 1 starts none, so without it a crashing first start would wait out the 15-minute deadline with no reason given. Not verified on AWS: that a plain scale-up goes unwatched (inferred from AWS's documentation); that a crashing first start reaches `FAILED` (only a redeploy's failure was tested); and what the old deployment's task does beside a `FAILED` first deployment.
- **ECS counts a new task healthy only after the grace period** (decision 8): with 120 seconds the old task was deregistered exactly 120 seconds after the new one registered, while the task listened about 30 seconds after it started. With 60 seconds the overlap was about 50 seconds (deregistration 62 seconds after registration), and the start took 1:34.
- **The demo's measurements** (2026-10-21):
  - **Fresh demo** (run 39629706461): the deploy job about 10:26, the database about 5 minutes of it.
  - **Redeploy at a 120-second grace period** (run 39633480190): 322 requests from the watch script, none other than `200`; the start 3:03; both versions alternated for about two minutes.
  - **Failed deploy** (run 39635091967, the throwaway branch `test/ph-12d-failing-start`, whose app exits at startup): *Start the app* failed after 4:55 with "ECS deployment circuit breaker: tasks failed to start"; 532 requests, all `200` with the old commit.
  - **Fix forward at a 60-second grace period** (run 39636942935): 212 requests, none other than `200`; the deploy job 3:41, the start 1:34; the old target drained for about 25 seconds, since requests kept connections open.
  - **`demo-down`** (run 39638062357): the destroy 4:44 against PH-12c's about 9½ minutes, the service 2:46 (PH-12c: 7 minutes), the database 1:53; 33 resources destroyed, and only inactive task definitions and the Tag Editor's index lag left, as expected.
- **Retrying the same commit after a `FAILED` deployment starts a new deployment** (found by the final review). Such a run changes no task definition, so Terraform starts no deployment, and the start loop used to read the old `FAILED` one and fail at once. *Start the app* now reads the primary deployment's rollout state first and, when it is `FAILED`, runs `update-service --force-new-deployment`. It then waits for the deployment it expects, the one it started or the primary one before the wait, counting any other primary deployment as still in progress, and wants at least one task for success, which also closes a stale read just after a fresh start. Pressing `demo-up` again or *Re-run failed jobs* now recovers from a transient failure (the database unreachable during the migrations, a Fargate or ECR hiccup); a code fix still needs a new commit. It was tested against a stubbed AWS CLI only and has not run on AWS.
- **`rds:ModifyDBInstance` in `DemoDatabases` has no `PubliclyAccessible` or `ManageMasterUserPassword` condition**, so the deploy role could change those on an existing instance. Left to [OP-104](https://github.com/luiki-dev/szop/issues/253), for [PH-35](../roadmap.md#ph-35-security-scanners): the password half can be a `Deny` on `rds:ModifyDBInstance` with `Bool rds:ManageMasterUserPassword = false`; `PubliclyAccessible` has no condition key on `ModifyDBInstance`, so that half is a permanent residual, guarded by the security group and the private subnet group, which the same role manages.

## Consequences

- [PH-37](../roadmap.md#ph-37-two-tasks) weighs the grace period against the migration lock's wait: the grace period sets how long two versions overlap (decision 8). [OP-103](https://github.com/luiki-dev/szop/issues/249) is decided there too, since with two tasks replaced one at a time a page load can mix two versions of the SPA for minutes (decision 15).
- A migration must work with the code of the release before it (decision 14): during a deploy the old version runs on the new schema for about a minute, and a failed deploy is fixed forward, so a migration that breaks the old code means another migration. [PH-16](../roadmap.md#ph-16-guest-workspace-and-lists)'s first table is the first to be written under the rule.
- A database outage no longer replaces healthy tasks: the load balancer checks `/api/live`, so the tasks keep serving the SPA while `/api/health` answers `503` and `demo-up` and the watch script see it (decisions 5 and 6).
- The commit is public on `/api/health` (decision 4), and the deploy role gains `ecs:StopTask` on `db-setup`'s tasks, both recorded in the threat model.
- A failed deploy stops `demo-up` at *Start the app* within minutes and leaves the old task serving (decisions 7 and 10); the runbook says to fix forward and press again.
- The first start of a fresh demo, the redeploy and the destroy are faster than PH-12c's, with measured numbers in the runbook (decision 13).
- `scripts/watch-demo.sh` stays as the check for every later phase that changes how the demo deploys (decision 1).
