# ADR 0058 — Bug reports: a form, a Severity field and triage at a phase's start

- **Status:** ✅ Accepted
- **Date:** 2026-10-31
- **Extends:** [ADR 0024](0024-github-project-tracking.md), decision 6 (two more labels, `bug` and `cannot-reproduce`, see decisions 3 and 7); [ADR 0024](0024-github-project-tracking.md), decision 7 (a seventh status, ❔ New, see decision 11); [ADR 0024](0024-github-project-tracking.md), decision 8 (a Severity field, see decision 4); [ADR 0016](0016-toolchain-details.md), decision 11 (the bug form's areas follow the scope list, see decision 2)

## Context

Szop has had one way to track a defect: an open point (OP) under a later phase. After PH-16a, the owner found on the demo that the empty list's raccoon stands about 16 px off the right edge on a desktop. They told Claude, who filed it as OP-119 under PH-16b, without the screenshot the owner had given. The owner had also seen the same gap while the phase was being built, and could not reproduce it then.

Three things were missing:

- **A way for the owner to file a bug themselves**, at any time, outside a session, so the next session picks it up.
- **A shape for a bug:** what happens, what was expected, where, how to reproduce it, a screenshot, how bad it is. An open point has none of these fields, and the screenshot was lost.
- **A way to tell bugs from the rest:** with one `open-point` label, a defect in delivered work and a decision left to a later phase look the same.

Some findings of a phase's reviews are bugs too; today they become open points as well. Five open points were bugs in all but name (decision 9).

## Decisions

| # | Decision | Options considered | Outcome |
|---|---|---|---|
| 1 | How a bug is filed | The owner tells Claude in a session, and Claude files it; the owner files it on GitHub | **The owner files it on GitHub through an issue form, `.github/ISSUE_TEMPLATE/bug.yml`** _(the owner's choice)_. It works from a phone, between sessions. Claude files the bugs it finds, from a review or while building, with `gh` and the form's headings. |
| 2 | The form's fields | — | **What happens; What was expected; Where (demo or local, browser, device and window width); Steps to reproduce; Severity; Area; Evidence (screenshots and the rest)** _(the owner's choice; severity and area the owner's additions)_. These are the form's labels, and so the headings of a bug's body: Claude's `gh` reports and the converted open points use them too. Severity and Area are dropdowns, the rest text areas; all but Evidence are required. Screenshots are dropped or pasted into the evidence field, and GitHub hosts them. The area's options are the scopes in `commitlint.config.js` ([ADR 0016](0016-toolchain-details.md), decision 11), so a bug's area names the scope of its fix (`fix(web): …`); a PR that adds a scope adds it to the form too, and the comment above the scope list says so. |
| 3 | Telling a bug apart | An issue type; a `bug` label; the `open-point` label with a prefix in the title | **A `bug` label, set by the form** _(the owner's choice)_. Issue types need an organization ([ADR 0024](0024-github-project-tracking.md), decision 5). A bug has no ID of its own: the form cannot work out the next free number, so the issue number (`#323`) is its ID _(Claude's call)_. A bug never carries `open-point` too. |
| 4 | Severity | A label per level; a project field | **A single-select project field, Severity, with three colored options** _(the owner's choice; the levels and colors Claude's proposal)_: 🔴 **Critical**: breaks a use case, can lose data or is a security hole; 🟠 **Major**: works, but wrongly, or only on some devices; ⚪ **Minor**: cosmetic. A field shows as a colored token on the board, like a label. The options are named with their icons, as the statuses are (`🔴 Critical`), and the icons join the status vocabulary in `CLAUDE.md`. Claude creates the field through the GraphQL API, which takes the options' colors _(Claude's call)_. The reporter chooses the severity in the form; the form cannot set a project field, so it lands in the body under **Severity**, and the triage copies it into the field. When Claude disagrees, the two settle it in a comment on the bug, and the field takes the outcome _(the owner's choice)_. Severity does not mark whether a bug was triaged: the status does (decision 11). |
| 5 | Where a critical bug goes | — | **Into the phase in progress, or, with none in progress, it blocks the next phase** _(the owner's choice)_. The owner points the session to a critical bug filed during a phase; `/phase-tracking` checks for untriaged critical bugs at the end of a phase too. |
| 6 | Where the other bugs go | One pile, triaged in a session of its own; triage at the start of each phase | **Triage at the start of each phase's brainstorm, as a step of `/phase-tracking`** _(Claude's proposal, the owner's choice)_. Each new bug gets its Severity and goes to one of three places, always as a sub-issue of that phase: **this phase**, when it touches code the phase changes anyway, and then a task of its plan too (so the phase stays within [ADR 0014](0014-roadmap.md)'s size); **a later phase** of its area; or a **bug-fix phase**, a small phase of fixes only, put on the roadmap when several bugs have no natural home. A triage session of its own was not taken: it would cost a session of the weekly limit ([ADR 0052](0052-working-with-claude.md)) and wait on someone remembering it, while a phase's start comes anyway. |
| 7 | A bug that can't be reproduced | Close it; keep it open with a marker | **Kept open with a `cannot-reproduce` label, no parent and no phase** _(Claude's proposal, the owner's choice)_. The triage skips it until someone adds steps or sees it again; then the label goes and it is triaged like any other. |
| 8 | A phase's findings | Always an open point; always a bug; decided per finding | **Decided per finding, while the phase runs** _(the owner's choice)_, by one rule _(Claude's proposal)_: **a bug** is delivered work that behaves otherwise than the requirements, the design or common sense say; **an open point** is something not decided or not built yet, or an improvement. A critical finding is fixed in the phase, as today. |
| 9 | Existing open points that are bugs | Leave them; convert them now | **Converted now** _(the owner's choice; the list Claude's proposal, the owner's choice)_: OP-119 (#323, the raccoon, Minor, `web`), OP-117 (#320, a list change sent twice or after leaving, Major, `lists`), OP-114 (#317, the API's database tests time out under load, Major, `api`), OP-112 (#305, the catalog forgets its expansion and search, Major, `catalog`) and OP-106 (#284, the color scheme of another tab, Minor, `web`). Each loses `open-point` (and `candidate`) and gains `bug`; its title drops the `OP-NNN` prefix; its body gains the form's headings, filled from its text, and a **History** line "Was OP-NNN"; Severity is set; the parent stays. OP-115 (#318) stays an open point: the owner has already given it a new design. The mentions of their OP IDs in ADRs and other records stay as written; the living docs link the issues, so their links keep working. Claude converts them with `gh` in this ADR's session, once the labels and the field exist _(Claude's call)_. |
| 10 | The project's settings in the UI | — | **The "Item added to project" workflow sets ❔ New, `bug` is added to the auto-add workflow's filter, and Severity is shown in the Board and Backlog views** _(Claude's call)_, so a bug filed from the form lands on the project as ❔ New and its severity shows as a colored token. These are set in the UI only, so they are the owner's steps, listed in the PR. Claude adds the ❔ New option to the Status field through the API. |
| 11 | Marking a bug as not yet triaged | An empty Severity; a seventh status, ❔ New | **A seventh status, ❔ New, the default for every item added to the project** _(the owner's proposal; making it the default for all items Claude's proposal, the owner's choice)_. The triage moves a bug on to ⬜ Backlog, or to the status of the phase it joins. The form cannot set a status, and the "Item added" workflow sets one status for every item, with no filter by label; a GitHub Action could set it per label, but only with a personal token with access to the project, a new secret. So every new item starts as ❔ New: `/phase-tracking` moves the phases, open points and owner steps Claude files on to their status at once, and anything filed outside the process waits in ❔ New to be looked at. In `roadmap.md`'s stage tables, ❔ New reads ⬜ Not started. |

## Consequences

- **`project-tracking.md` and `/phase-tracking` gain the bug:** the two labels, the Severity field, the ❔ New status and the step that moves Claude's new items out of it, the query for untriaged items (Status ❔ New), the triage step at a phase's start, the check for critical bugs at its end, and the rows of "How items move". The Open Points view keeps its `label:open-point` filter, so bugs show on the Board and in Backlog, colored by Severity.
- **`CLAUDE.md`'s "Project tracking" list** names the triage among the moments that run `/phase-tracking`.
- **A bug is closed by the PR that fixes it** (`Closes #N`), like an open point; a phase's PR lists the bugs it fixes.
- **Two lists stay in step by hand:** the scopes in `commitlint.config.js` and the form's areas.
