# ADR 0050 — Seed catalog phase details

- **Status:** ✅ Accepted
- **Date:** 2026-10-28
- **Refines:** [ADR 0014](0014-roadmap.md), decision 7 (the PH-15 split: fast-check arrives in PH-15a, StrykerJS and `mutation.yml` in PH-15b; see "Changes to the roadmap"); [ADR 0022](0022-ring-tail-redesign.md), decision 13 (the search field of the catalog is a second exception to visible labels; see decision 10); [ADR 0051](0051-acceptance-criteria.md), decision 15 (a requirement's list of criteria is finalized by the phase that delivers its last part; see decision 14)

## Context

[PH-15a](../roadmap.md#ph-15a-seed-catalog-read-only) gives a visitor without a session the first real screen: **Catalog**, Szop's default catalog of categories and products, browsed as a tree and searched by name. It also brings the first domain rule in `packages/shared` (the category order), fast-check, the API's one JSON error shape ([OP-071](https://github.com/luiki-dev/szop/issues/94)), response serialization through the shared schemas ([OP-079](https://github.com/luiki-dev/szop/issues/96)) and the seed data tests ([OP-052](https://github.com/luiki-dev/szop/issues/93), its PH-15a part). The [spec](../superpowers/specs/2026-10-25-PH-15a-seed-catalog-design.md) holds the design in full; this ADR records the decisions and the alternatives. Decisions 1 to 14 were settled in the brainstorm, decisions 15 to 21 while the plan was written and built (Claude's calls), and decisions 22 to 24 were put to the owner during the build.

## Changes to the roadmap

PH-15 is split into PH-15a Seed catalog, read-only and PH-15b Mutation testing. With StrykerJS and `mutation.yml`, the phase held about ten tasks and two new concepts, which [ADR 0014](0014-roadmap.md), decision 6, does not allow. This refines decision 7 of the same ADR: fast-check arrives in PH-15a, StrykerJS and `mutation.yml` in PH-15b, which follows at once and mutates the order rule and the seed checks written here. The check that migrations match the schema ([OP-076](https://github.com/luiki-dev/szop/issues/95)) moves to [PH-16](../roadmap.md#ph-16-guest-workspace-and-lists), since this phase adds no table.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|---|---|---|
| 1 | The seed's format | JSON; TOML; CSV files; a TypeScript module. | **The seed is a YAML file, nested the way the store is**: categories hold their products and their subcategories, and the order of categories in the file is the order in the store. Products are shown alphabetically, whatever their order in the file (decision 12). There are no IDs and no `position` fields _(the owner asked for a human-editable standard format; YAML and the nested shape were Claude's proposal, which the owner approved)_. JSON has no comments and fails on one stray comma. TOML writes three-level nested lists awkwardly. CSV needs extra columns to encode the tree and its order. A TypeScript module is code, not data. YAML's pitfalls (indentation, implicit types) are caught by YAML 1.2 parsing and a Zod check (decision 3). |
| 2 | Where the seed lives | Seed tables in PostgreSQL loaded from the file; the file compiled into the SPA with no API. | **The API reads the file; there are no tables** _(the owner's choice, on Claude's recommendation)_. A visitor without a workspace always sees the seed ([ACC-1](../requirements/ACC-accounts-and-guest-mode.md#acc-1)), so this read path stays after PH-16. Seed tables would duplicate the per-workspace tables PH-16 creates. A compiled-in file would bypass the API contract and need rework when workspace data comes from the API. |
| 3 | Parsing and checking the seed | `js-yaml`; serving whatever parses. | **The file is parsed with the `yaml` package (YAML 1.2) and checked with a Zod schema at startup. A broken file stops the API from starting, with a message naming the entry** _(Claude's call)_. In YAML 1.2, `no` and `off` are plain strings, which avoids the "Norway problem". Failing at startup turns a bad edit into a failed deploy instead of a broken page, and the tests catch it before that. |
| 4 | The catalog response's shape | The nested tree as in the file. | **The catalog response is flat**: `categories` (`id`, `parentId`, `position`, `name`), `products` (`id`, `name`, `categoryId`, `unitId`), `units` (`id`, `name`). The same shape will serve a workspace's catalog later _(Claude's call)_. This is the shape the architecture gives the tables (`parent_id`, `position`). The shared order rule then works the same on the seed and on a workspace, and the client code will not change in PH-16. |
| 5 | The category order rule | Ordering in the API or in the page. | **The category order is one pure function in `packages/shared`, tested with examples and with fast-check properties** _(the roadmap's plan)_. [ORD-2](../requirements/ORD-list-display-and-ordering.md#ord-2) and [ORD-3](../requirements/ORD-list-display-and-ordering.md#ord-3) are domain rules shared by the catalog now and the list in PH-17. Properties over random trees find edge cases that examples miss. |
| 6 | Where search happens | Search on the server, a request per keystroke. | **The whole catalog comes in one request, and the page filters and expands it in the browser** _(Claude's call)_. About 500 products is a few tens of kB. Local filtering answers instantly, and offline reading ([NET-1](../requirements/NET-connectivity.md#net-1)) gets easier later. |
| 7 | The error shape | Leaving the 403 and 415 in Fastify's shape. | **Every API error uses one JSON shape**, `{ "error": { "code", "message" } }`, through `setErrorHandler` and a not-found handler for `/api/*`. The cross-site 403 and the JSON-only 415 move to it as well ([OP-071](https://github.com/luiki-dev/szop/issues/94)) _(Claude's call)_. One shape for every error the browser can receive, as [architecture, Errors](../architecture/architecture.md#errors) states. |
| 8 | Response serialization | An explicit `schema.parse` in each route. | **Responses are serialized through the shared Zod schemas with `fastify-type-provider-zod`** (its validator and serializer compilers, set once on the app) ([OP-079](https://github.com/luiki-dev/szop/issues/96)) _(Claude's call)_. The contract is enforced by Fastify for every route that declares a schema, inputs included once routes take any, and the route types follow the schema. |
| 9 | The tree on the page | Subcategories as small headings inside an open top-level card (the first mockup; rejected because they blended into the products, and the tree can be 5 levels deep). | **The page shows the tree with every category collapsible at every level, indented by level**. Category rows are set apart from product rows by a chevron, a bold name, a count pill and a tinted band. All categories start collapsed. "Expand all" and "Collapse all" are icon buttons on a phone and icon-and-label buttons from `lg` _(the owner's choices; the styling is Claude's, approved on the mockups)_. The mockups in the [spec](../superpowers/specs/2026-10-25-PH-15a-seed-catalog-design.md#the-catalog-page). |
| 10 | How search shows its results | A dropdown of suggestions. | **Search narrows the tree instead of showing a list of suggestions.** It matches product names and category names. Each match is shown with the path to it, opened, and the matched text highlighted. A matching category is shown on its path, collapsed, unless something inside it matches too _(the owner's choices; the last one changed at the review of the acceptance criteria, which replaced "a matching category shows its whole contents")_. A dropdown would repeat the smart input of [PH-23](../roadmap.md#ph-23-smart-input) and hide where a product lives. The same narrowed tree will serve the catalog browser of [PH-24](../roadmap.md#ph-24-catalog-browser). |
| 11 | The seed content | Prices in the seed. | **The seed content is generated by Claude and then adjusted by the owner**: English, about 20 top-level categories with 5 or 6 subcategories each, a few typical products per subcategory (about 300 to 500 in total), a short list of units, and no default prices _(the owner's choices: language, store profile, counts, owner edits; no prices and the product count are Claude's calls)_. No single price is right for every store. |
| 12 | The order within a category | Products in the file's order too, with a `position` on products. | **Categories keep the file's order; products within a category are sorted alphabetically** _(the owner's choice)_. Scanning a category by eye is easier alphabetically, and it matches how [ORD-2](../requirements/ORD-list-display-and-ordering.md#ord-2) sorts list items. Products need no `position`, so the shape PH-16 builds tables from stays smaller. |
| 13 | How names sort | English rules, with Polish left to PH-17a. | **Names sort by Polish rules: `compareNames` uses `Intl.Collator("pl", { numeric: true })`** _(the owner's choice, on Claude's proposal)_. The rule is written once, in `packages/shared`, and the list in PH-17a sorts with it. Polish rules put "śmietana" between "ser" and "tofu" ([ORD-2](../requirements/ORD-list-display-and-ordering.md#ord-2), criterion 2.3); English names sort the same way under both. This settles the sorting part of [OP-041](https://github.com/luiki-dev/szop/issues/100). |
| 14 | Who finalizes a list of criteria | The rule of [ADR 0051](0051-acceptance-criteria.md), decision 15: the first phase that delivers any part reviews the whole list. | **A requirement's list of criteria is finalized by the phase that delivers its last part; an earlier phase reviews only the criteria it delivers** _(the owner's choice, on Claude's recommendation)_. Lists such as [APP-1](../requirements/APP-app-wide-behavior.md#app-1) and [NFR-4](../requirements/NFR-non-functional-requirements.md#nfr-4) span phases up to PH-26; nobody can judge their later criteria without those phases' context, so "finalized" would promise what it cannot. No requirement reaches ✅ Done unfinalized, because the phase that delivers its last part finalizes it first. This refines ADR 0051, decision 15. In this phase only [PRD-2](../requirements/PRD-catalog.md#prd-2) is finalized. |
| 15 | Categories without a parent, and cycles | Rejecting such a catalog; throwing | **`orderCategories` treats a category whose parent does not exist as top-level, and drops categories reachable only through a cycle** _(Claude's call)_. The seed check already refuses such a file, but the order rule is shared with workspace catalogs in PH-16, and a pure function that never throws or loops cannot take a page down. The function's comment says so, and the property tests cover both. |
| 16 | The health route's 503 | Serializing only the 200 | **The health route declares `response: { 200: healthSchema, 503: healthSchema }`, so both bodies go through the serializer** _(Claude's call)_. One pattern for every status code of every route. The returned bodies use `satisfies Health` to keep their literal types. |
| 17 | The `muted` role | A new palette step; reusing `card` | **`muted` is `gray-50` in light, and `color-mix(in oklab, var(--color-gray-800) 50%, var(--color-gray-700))` in dark** _(Claude's call)_, the tint of the category rows. The pairs `foreground`, `muted-foreground` (4.5) and `link` (3) on `muted` are in `design.spec.ts`. |
| 18 | The count pills | `muted` pills; `primary` pills | **`bg-accent text-accent-foreground`, with the search's `<mark>` in the same pair** _(Claude's call)_. The pair (4.5) is checked in `design.spec.ts`. |
| 19 | Counts during a search | The count of matching products only | **The pills and the line above the tree count what is shown** _(Claude's call, as the spec words it)_. A category that matches by name but has nothing matching inside it shows its whole product count ("plant" gives "1 product"), not the plan's 0. |
| 20 | Fetching the catalog | TanStack Query's defaults | **`retry: false` and `staleTime: Infinity`** _(Claude's call)_. "Try again" is the retry, and the seed changes only with a deploy. |
| 21 | Lazy-loading the catalog page | Loading it on demand from the start | **Not needed** _(Claude's call)_. The first-screen JavaScript is 150.2 KB Brotli of the 200 KB budget ([NFR-3](../requirements/NFR-non-functional-requirements.md#nfr-3)). |
| 22 | The type provider's peers | Marking `@fastify/swagger` and `openapi-types` optional through `packageExtensions`, with both as dev dependencies; the spec's fallback, an explicit `catalogSchema.parse` in the route | **`fastify-type-provider-zod` 7.0.0 stays as it is, and pnpm installs its two peers, `@fastify/swagger` 9.9.2 and `openapi-types` 12.1.3, which therefore ship in the production image** _(the owner's choice, on Claude's recommendation)_. Both are non-optional peers, but the provider's runtime `.js` never imports them: only its `.d.ts` files reference them, so they are never loaded. The alternatives add configuration or give up decision 8 to save a few unused files. |
| 23 | The focus ring on links | Leaving [NFR-2](../requirements/NFR-non-functional-requirements.md#nfr-2).8 unfinalized | **The criterion stands as written, "the focus ring is drawn in the `ring` color, on links as on buttons", and is ✅ in this phase** _(the owner's choice)_, with the test `NFR-2.8: the focus ring is drawn in the ring color, on links as on buttons` in `e2e/tests/shell.spec.ts`. |
| 24 | The scroll position between pages | A separate pull request after the phase; an open point for later; a hand-written `useEffect` that scrolls to the top on every navigation | **The app shell renders React Router's `ScrollRestoration`, and [APP-1](../requirements/APP-app-wide-behavior.md#app-1) gains the criterion APP-1.10, ✅ in this phase**: "A page opened from the menu or a link starts at the top; Back and Forward return to where the page was scrolled" _(the owner's choice: fix it in this phase and add the criterion, on Claude's proposal)_. The bug predates the phase (the router never rendered `ScrollRestoration`, so a navigation kept the window's scroll), but the catalog is the second long page and surfaced it. A separate PR or an open point would leave a known bug in a phase that touches the same shell. A hand-written `useEffect` is rejected: it fixes the top but loses the restoring on Back and Forward. |

## Consequences

- The catalog is read from `apps/api/src/catalog/seed.yaml` at startup. A broken file stops the API with a message naming the entry, before it touches the database. The seed uses 130 of 300 categories, 431 of 2,000 products, 6 of 50 units and 3 of 5 levels ([OP-052](https://github.com/luiki-dev/szop/issues/93)).
- Every API error is `{ "error": { "code", "message" } }`. The codes: `invalid_input` (400), `forbidden_cross_site` (403), `not_found` (404), `unsupported_media_type` (415), any other 4xx as the snake-case status text, and `internal_error` (500, always "Internal server error"; the error's own text is only logged). A response that fails its schema is a 500.
- A route that declares a response schema is serialized through it; a new route does the same, for each status it can return.
- `compareNames` uses the collator's default sensitivity, so "milk" and "Milk" sort next to each other without being equal.
- The category order rule and `compareNames` live in `packages/shared`, where the list of [PH-17a](../roadmap.md#ph-17a-list-items) will use them.

## Settled while building

- **Indentation uses classes picked by depth** (`pl-*`), not a `style` attribute, so the Content Security Policy stays as it is.
- **`CatalogTree` takes a `unitNames` map** (unit id to name) besides the plan's props, so a product shows its unit's name.
- **The search's hand toggles reset on every change of the query text**, a repeated query included; the browsing set of open categories is not touched while searching, and clearing the field (also with Esc, with focus staying in it) brings it back.
- **A response that does not match the shared schema** shows the error card with "Try again", not a blank page.
