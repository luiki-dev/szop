# ADR 0021 — SPA skeleton details

- **Status:** ✅ Accepted
- **Date:** 2026-10-07
- **Refines:** [ADR 0005](0005-development-environment.md), decisions 8 and 10 (the first consumer of `packages/shared`, see decision 1; the proxy's target, see decision 3); [ADR 0007](0007-testing-strategy.md), decision 10 (how the typed MSW handlers are set up, see decisions 1 and 7)
- **Completes:** [ADR 0002](0002-technical-architecture.md), decision 10 (React Router's mode, see decision 4)

## Context

[PH-05](../roadmap.md#ph-05-spa-skeleton) brought the single-page application (SPA). [ADR 0002](0002-technical-architecture.md) (React, React Router, TanStack Query), [ADR 0005](0005-development-environment.md) (Vite's proxy, `packages/shared` consumed from source) and [ADR 0007](0007-testing-strategy.md) (Vitest, jsdom, Testing Library and Mock Service Worker (MSW)) set its direction; its brainstorm and the [spec](../superpowers/specs/2026-10-07-PH-05-spa-skeleton-design.md) settled the details. Decisions 1 to 8 were taken in the brainstorm; decision 9 and the "settled while building" notes in the cells came from the implementation. Each decision refines an accepted ADR or fills a detail it left open.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|-------|--------------------|------------------------|
| 1 | Where the health response's shape lives | `packages/shared` now, used by the web client, the MSW handlers and the API's test; a schema in `apps/web` only, with `packages/shared` arriving in PH-15 | **`packages/shared` now,** holding one Zod schema for `/api/health`. The contract is then really shared: the API's test fails when the API drifts from it, and the typed MSW handlers fail when a fake drifts ([ADR 0007](0007-testing-strategy.md), decision 10). It also tries the wiring of [ADR 0005](0005-development-environment.md), decision 8 (a package consumed from source by tsx, Vite and Vitest) while the app is tiny. The price is one more workspace package. A schema in `apps/web` alone would be smaller, but nothing would tie it to the API's response, so the type safety would cover the web against itself only. |
| 2 | What the page shows | Three states, with a 503 body treated as data; the happy path only, with any other response shown as "API unavailable" | **Four states:** in flight, ok, reachable with the database down, and unreachable. The client parses both the 200 and the 503 body with the shared schema, so the page tells which hop broke: the browser to the API, or the API to the database. This is what the health route was designed to show ([ADR 0020](0020-database-details.md), decision 11), and it gives the first component tests real cases. The happy path alone would hide a database outage behind the same message as a dead API. |
| 3 | Where the proxy finds the API | A constant in `vite.config.ts`; a required `apps/web/.env` setting; Vite reading `apps/api/.env` | **A constant, `http://127.0.0.1:3000`,** with a comment pointing to `apps/api/.env.example`. [ADR 0005](0005-development-environment.md), decision 11 says the SPA needs almost no configuration, and [ADR 0019](0019-api-skeleton-details.md), decision 2's no-defaults rule guards deployments from a silently wrong value, which a development-only constant that never ships cannot cause. PH-06 serves the SPA from the API on one origin, so the proxy does not exist in production. If someone changes `PORT`, the page shows "Can't reach the API", a visible symptom. A second `.env` would add a setup step for one value that is the same on every machine, and Vite reading the API's file would couple two packages. |
| 4 | React Router's mode | The data router (`createBrowserRouter` with `RouterProvider`); the declarative `<BrowserRouter>` | **The data router.** The routes are one array, so the nesting the app needs later (the app shell of PH-14 around every page, `/lists/:id` beneath it) is `children`. Tests build the same table with `createMemoryRouter`, so they run the real route definitions. Its `loader` feature stays unused, because TanStack Query owns data fetching ([ADR 0002](0002-technical-architecture.md), decision 11), and the docs say so. The declarative style is smaller, but it is the older form and tests would wrap components in a `<MemoryRouter>` that can drift from the real routes. <br>**In the code:** `RouterProvider` comes from `react-router/dom` and `createBrowserRouter` and `createMemoryRouter` from `react-router` (version 8.4); `routes.tsx` exports the one route table, and `app.tsx` and the tests both build their routers from it. |
| 5 | Retries of the health query | TanStack Query's default of three retries with growing delays; `retry: false` on this query | **`retry: false`** on `useHealth`. The default would show a spinner for about seven seconds before reporting an error, which suits most data and hides the failure on a page whose whole job is to show it. Later queries keep the default. |
| 6 | TypeScript module settings of the web package | The base's `nodenext`; `esnext` with `moduleResolution: "bundler"` | **`bundler` for `apps/web`.** Vite is the bundler, and this is the setup its documentation uses. It resolves `@szop/shared` through its `package.json` and lets the `vite/client` types and later asset imports work. The API keeps `nodenext`; the `.ts` import specifiers of [ADR 0019](0019-api-skeleton-details.md), decision 6 stay everywhere. <br>**Settled while building:** `moduleResolution: "bundler"` resolves `@szop/shared`, whose `exports` entry points at `src/index.ts`, with no workaround, and `apps/api` (`nodenext`) resolves it too. |
| 7 | How component tests are set up | A shared `QueryClient` and mocked client module; a fresh `QueryClient` per test and MSW at the network | **MSW at the network, a fresh `QueryClient` per test,** the real route table through `createMemoryRouter`, elements found by role and text. The real client, hook and schema run unchanged ([ADR 0007](0007-testing-strategy.md), decisions 10 and 16). A request without a handler fails the test, naming the request, so a request nobody planned for cannot pass unnoticed. Handlers are typed with the shared schema. <br>**Settled while building:** (1) a plain `fetch("/api/health")` works under jsdom with MSW 3, which resolves the relative URL against jsdom's `location`, so neither the client nor the setup file resolves it against `window.location.origin`. (2) MSW 3 renamed the option that reports a request without a handler: the server starts with `server.listen({ onUnhandledFrame(…) })`, where version 2 had `onUnhandledRequest`; the old name fails the type check and is silently ignored at runtime. (2b) The ready-made `"error"` strategy was tried first and is not enough: in MSW 3.0.2 it prints `[MSW] Error: …` and rejects the request, but does not fail the test, and a rejected `fetch` renders "Can't reach the API", which five of the seven tests expect, so a request to a path without a handler would leave them green. `onUnhandledFrame` therefore takes a callback that records the request (method and URL) and throws, which rejects the request (a callback that returns lets it through to the real network), and an `afterEach` in `setup.ts` fails the test that made it, naming the request. Shown red and green with a throwaway test that swallowed an unhandled `fetch`. (3) The `web` project uses `@vitejs/plugin-react`, as `vite.config.ts` does; whether `jsx: "react-jsx"` alone would do was not tried. (4) Vitest has no globals here, so the setup file calls Testing Library's `cleanup` after each test itself. |
| 8 | Install scripts of new dependencies | Allow them as they appear; deny them unless something breaks | **Deny them unless something breaks** ([ADR 0012](0012-security-baseline.md), decision 18, as for esbuild in [ADR 0019](0019-api-skeleton-details.md), decision 11). pnpm 12 fails the install when a dependency with an install script is not listed in `allowBuilds`; the owner decides each entry, with the evidence shown first. <br>**Settled while building:** none of the new dependencies was blocked (`ERR_PNPM_IGNORED_BUILDS` never appeared), so `allowBuilds` is unchanged; only the comment at the top of `pnpm-workspace.yaml` was updated. |
| 9 | The React Hooks lint preset | — | **`reactHooks.configs.flat.recommended`** from `eslint-plugin-react-hooks` 7.1, applied to `apps/web/**/*.{ts,tsx}` only ([ADR 0005](0005-development-environment.md), decision 12). Settled while building, since the name differs between plugin versions; a throwaway conditional `useState` was flagged by `rules-of-hooks`, which shows the preset is active. |

## Consequences

- **`packages/shared` exists** and holds the health response's schema. `apps/web` consumes it from source and, in a test, `apps/api` does: `health/routes.test.ts` checks the real responses against the schema, while the route's code is unchanged ([OP-079](../open-points.md#op-079) tracks the API serializing through the schema).
- **`pnpm test` runs three projects**, `api`, `web` and `hooks`: at the end of PH-05, 71 tests in 6 files. The `web` project has seven component tests: ok (in flight, then ok), database down, request fails, three unexpected responses (a 500 with a valid healthy body, a 200 missing `schemaVersion`, a 200 that is not JSON) and recovery after a failure. Removing the client's status check fails the 500 case, and removing `retry: false` fails the five error-state tests. The recovery test calls `queryClient.refetchQueries` directly; a real tab refocus is not simulated.
- **A path other than `/` shows React Router's default error screen** ("Unexpected Application Error! 404 Not Found") until the first feature phases add a not-found route and error boundaries.
- **A hanging API leaves the page on "Checking the API…"** until timeouts arrive with [OP-040](../open-points.md#op-040). With the API stopped, Vite's proxy answers `502` with an empty body, which is neither 200 nor 503, so the client throws and the page shows "Can't reach the API".
- **`pnpm peers check` reports an unmet optional peer**, `msw ^2.4.9` from `@vitest/mocker`, while MSW 3 is installed. It is harmless: the peer is optional, and the tests pass.
- **Open points:** the PH-05 parts of [OP-010](../open-points.md#op-010) and [OP-012](../open-points.md#op-012) are ✅ done, and both move to the phases of their next parts (PH-07 for each); [OP-007](../open-points.md#op-007) gains a note that `packages/shared` exists; [OP-079](../open-points.md#op-079) (the API serializes its responses through the shared schemas) and [OP-080](../open-points.md#op-080) (`@testing-library/user-event` joins with the first interaction) are new; [OP-067](../open-points.md#op-067) moves to PH-06, since it does not depend on this phase.
- **The living docs and tool pages are updated:** the [architecture](../architecture/architecture.md), the [stack overview](../architecture/stack-overview.md), the [testing guide](../development/testing.md), [`setup.md`](../development/setup.md), the tool pages for [Vite](../development/tools/vite.md), [Testing Library](../development/tools/testing-library.md), [MSW](../development/tools/msw.md) and [Vitest](../development/tools/vitest.md), the [glossary](../glossary.md) and the README.
