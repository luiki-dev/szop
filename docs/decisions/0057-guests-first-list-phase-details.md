# ADR 0057 — Guest's first list phase details

- **Status:** ✅ Accepted
- **Date:** 2026-10-30
- **Refines:** [ADR 0012](0012-security-baseline.md), decision 6 (a workspace-owned table's primary key is `(workspace_id, id)`, which is the composite unique key; see decision 14)

## Context

[PH-16a](../roadmap.md#ph-16a-guests-first-list) is the first phase that stores a user's data. A visitor creates their first list, which gives them an anonymous session from Better Auth and an empty workspace; they see their lists on the home screen, open one, and rename it. It brings the first tables, the conventions every later migration follows ([OP-041](https://github.com/luiki-dev/szop/issues/100)), the first part of the access layer ([OP-054](https://github.com/luiki-dev/szop/issues/102)), the session lifetime ([OP-039](https://github.com/luiki-dev/szop/issues/98)) and the check that migrations match the schema ([OP-076](https://github.com/luiki-dev/szop/issues/95)).

Before the brainstorm, a spike tried Better Auth 1.7.14's anonymous plugin ([OP-038](https://github.com/luiki-dev/szop/issues/97), [results](https://github.com/luiki-dev/szop/issues/97#issuecomment-6529445115)). For this phase it showed that Better Auth's user-creation hook also fires for anonymous users, so a workspace created there would be created again at sign-up, and that a sliding session works with `expiresIn` and `updateAge`. Its other findings, about linking a guest to an account, belong to [PH-18](../roadmap.md#ph-18-registration-and-login) and [PH-19](../roadmap.md#ph-19-guest-data-on-login).

The [spec](../superpowers/specs/2026-10-30-PH-16a-guests-first-list-design.md) holds the design in full; this ADR records the decisions and the alternatives. All were settled in the brainstorm, and decision 20 on the screens' mockups after it.

## Changes to the roadmap

PH-16 Guest workspace and lists is split into three phases, and its ID is retired. It held about 25 acceptance criteria and three new concepts: anonymous sessions, workspace-owned data with the access layer, and the SPA's first changes ([ADR 0014](0014-roadmap.md), decision 6).

- **[PH-16a Guest's first list](../roadmap.md#ph-16a-guests-first-list):** an anonymous session, an empty workspace, creating, viewing and renaming lists. The new concept is the session.
- **[PH-16b Workspace from the default data](../roadmap.md#ph-16b-workspace-from-the-default-data):** the workspace is created as a copy of the seed catalog and units, `/catalog` reads it, two tabs end up in one workspace; the two-workspace test helper and the schema test. The new concept is the copy of the seed with composite keys.
- **[PH-16c Managing lists](../roadmap.md#ph-16c-managing-lists):** deleting a list after confirming it, the not-found page, and changes that survive a weak connection. The new concept is resilient changes.

Criteria move between phases with the split: renaming ([LST-1](../requirements/LST-shopping-lists.md#lst-1).2), the back arrow inside a list ([APP-1](../requirements/APP-app-wide-behavior.md#app-1).6, from PH-17a), the session cookie ([NFR-4](../requirements/NFR-non-functional-requirements.md#nfr-4).9, from PH-18) and the limit on list names ([LIM-2](../requirements/LIM-limits.md#lim-2), its list-name part) come to PH-16a; creating the workspace from the default data ([ACC-1](../requirements/ACC-accounts-and-guest-mode.md#acc-1).4, ACC-1.5, ACC-1.6, ACC-1.9) and the default units ([UNT-1](../requirements/UNT-units.md#unt-1).1) go to PH-16b; confirming a deletion ([APP-3](../requirements/APP-app-wide-behavior.md#app-3).3) and the not-found page ([APP-5](../requirements/APP-app-wide-behavior.md#app-5)) go to PH-16c.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|---|---|---|
| 1 | The empty lists page | "No lists yet" with "New list", as [LST-2](../requirements/LST-shopping-lists.md#lst-2).3 and [APP-4](../requirements/APP-app-wide-behavior.md#app-4).2 said. | **With no list yet, the lists page shows the raccoon and "Create your first list", both in light, muted greys, and offers "New list"** _(the owner's choice)_. The muted look is checked on the screen once it is built. LST-2.3 and APP-4.2's example change to this wording. |
| 2 | Where "New list" leads | A new card on the lists page with its name field focused, staying on the lists page. | **"New list" opens the new list's own screen with its name field focused** ([LST-1](../requirements/LST-shopping-lists.md#lst-1).5) _(the owner's choice)_. Creating a list and then adding items is one path, without a stop on the lists page. This brings the list's screen, empty, and its back arrow ([APP-1](../requirements/APP-app-wide-behavior.md#app-1).6) into this phase. |
| 3 | When the list is stored | Storing it with a default name as soon as "New list" is pressed. | **The list is stored when Enter is pressed with a non-empty name; Esc or an empty name leaves without storing anything** _(Claude's proposal, which the owner accepted)_. A visitor who opens "New list" and leaves has changed nothing, so nothing is stored and no session is created ([ACC-1](../requirements/ACC-accounts-and-guest-mode.md#acc-1).3). |
| 4 | Where a list is renamed | An action on the list's card on the lists page (a ⋮ menu or a pencil); long-press on a phone. | **On the list's screen: the title is an editable field, the same as when creating, and a ⋮ menu in the header holds "Rename", which focuses it. The cards on the lists page only open the list** _(Claude's recommendation, which the owner accepted; renaming moves into this phase as a result)_. The ⋮ menu makes the action visible and reachable by keyboard and screen reader, and gives the list's later actions a place (delete in PH-16c; archive, duplicate and reset in PH-25). Actions on every card would clutter a page of many cards and repeat the same actions in two places. Where ⋮ sits next to the raccoon tile at the header's right ([visual design](../architecture/visual-design.md), the list screen) is settled on the mockups: decision 20. |
| 5 | The order of lists and the card | Oldest first; counts on the card, as in the mockup. | **The lists page shows the newest list first, and a card shows only the list's name** _(the owner's choice)_. The counts on the mockup's cards come with items in PH-17a. |
| 6 | Manual order of lists | A requirement in the MVP with a phase of its own; 🔜 Later; adding drag and drop to this phase. | **A future extension (💡), together with the manual order of items on a list** _(the owner's choice, on Claude's recommendation)_. Dragging is a second big concept (a drag-and-drop library, a keyboard alternative WCAG 2.2's 2.5.7 requires, a `position` and how it is recomputed) and would split this phase again. Ordering by `created_at` needs nothing that a later `position`, filled from `created_at`, would undo. |
| 7 | The empty list's screen | The raccoon in the middle, as on the lists page. | **The raccoon peeks in from the bottom edge, cut halfway between its eyes and its nose, under "Nothing on this list yet"** _(the owner's idea; "Nothing on this list yet" stays above it as Claude's assumption)_. In PH-17a the add bar takes the bottom of the screen, so that phase would move or hide it.<br><br>🔍 The mockups moved it to the side, out of the add bar's way: decision 20. |
| 8 | IDs | `bigint` from a sequence; random UUIDv4. | **Every ID is a UUIDv7 (`uuid` in PostgreSQL). The browser generates the IDs of records the user creates (a list now, items later), and the server checks them; records the server creates (a workspace) get `uuidv7()` from the database** _(the owner's choice, on Claude's recommendation)_. A sequence's ID is known only after the server answers, so an optimistic screen needs temporary IDs, a retried create makes a duplicate, and the numbers show how many lists exist. A UUID from the browser makes a retried create return the existing record ([OP-040](https://github.com/luiki-dev/szop/issues/99)), and the new list's screen has its real address at once. UUIDv7 starts with the time, so new rows land at the end of the index, unlike UUIDv4. PostgreSQL 18, which runs locally and on RDS, has `uuidv7()` built in. A client choosing someone else's ID gains nothing: the key is `(workspace_id, id)` (decision 14). |
| 9 | Who migrates Better Auth's tables | Better Auth's own migrator (`auth migrate`). | **Better Auth's CLI generates its tables as a Drizzle schema once; the file is committed as part of the schema, and `drizzle-kit` migrates them with every other table** _(the owner's choice, on Claude's recommendation)_. Two migration systems on one database would hide Better Auth's tables from the migration check (decision 16) and from foreign keys in the schema. An upgrade of Better Auth that changes its tables means generating the schema again and comparing. |
| 10 | Better Auth's IDs | Better Auth's default random 32-character text IDs. | **`advanced.database.generateId: "uuid"`, with the columns as `uuid` defaulting to `uuidv7()`**, so PostgreSQL generates them _(the owner's choice, on Claude's recommendation)_. One ID convention in every table; `workspaces.user_id` is a `uuid` like every other key. |
| 11 | Where the session lives | Better Auth's `cookieCache`, a signed copy of the session in a cookie for a few minutes. | **The session lives only in the database: every request reads it from `sessions`. It lasts 30 days and slides: a request moves the end back to 30 days at most once a day (`expiresIn` 30 days, `updateAge` 1 day)** _(the owner's choice, on Claude's recommendation)_. A session removed from the database stops working at once, which [NFR-4](../requirements/NFR-non-functional-requirements.md#nfr-4).9 asks for; with `cookieCache` it would keep working until the copy expires, and one more cookie would need guarding. One read per request costs nothing at Szop's scale. 30 days from the last visit outlives guest retention ([ACC-7](../requirements/ACC-accounts-and-guest-mode.md#acc-7)), as [OP-039](https://github.com/luiki-dev/szop/issues/98) asks. |
| 12 | A workspace's owner | A `workspace_id` on the user. | **`workspaces.user_id` is `uuid NOT NULL UNIQUE`, a foreign key to `users.id` with `ON DELETE CASCADE`** _(the owner's choice, on Claude's recommendation)_. One workspace per user, as the architecture says, and the database refuses a second one if two first changes race. Deleting a user deletes their workspace and everything in it, which the guest cleanup ([PH-31](../roadmap.md#ph-31-automatic-cleanup)) and account deletion ([PH-30](../roadmap.md#ph-30-settings-and-account-deletion)) build on. Moving a workspace to an account at registration is PH-18's choice. |
| 13 | The first change | **B:** `POST /api/lists` without a session creates the anonymous user (calling Better Auth inside), the workspace and the list in one request. **C:** a separate `POST /api/workspace` between the session and the list. | **A: the browser asks Better Auth for an anonymous session (`POST /api/auth/sign-in/anonymous`) when it has none, then sends the change; the server finds or creates the workspace inside the change's transaction. The workspace is never created in Better Auth's user-creation hook** _(the owner's choice, on Claude's recommendation)_. Better Auth's endpoints are used as intended, and every later first change (an item, a category) works the same way, since the workspace comes with the first write, whatever it is. B makes every write route able to sign a guest in and handle Better Auth's cookie; C adds a request and makes the client track whether the workspace exists. A guest whose second request fails is left with a session and no workspace, which is harmless: their next change creates it, and the guest cleanup removes guests without one ([OP-039](https://github.com/luiki-dev/szop/issues/98)). The spike showed the hook fires for anonymous users too, so a workspace made there would be made again at sign-up. |
| 14 | Table conventions | Better Auth's table names `user` and `session`; only `created_at`; `PRIMARY KEY (id)` with `UNIQUE (workspace_id, id)`, as ADR 0012 worded it; Drizzle's generated constraint names; soft deletes. | **Tables are plural and `snake_case` (`workspaces`, `lists`), Better Auth's included through its `modelName` (`users`, `sessions`, `accounts`, `verifications`); columns are `snake_case`, fields `camelCase` in TypeScript. Every table has `created_at` and `updated_at`, both `timestamptz NOT NULL DEFAULT now()`, and Drizzle's `$onUpdate` sets `updated_at`. A workspace-owned table's primary key is `(workspace_id, id)`. Constraints are named explicitly in PostgreSQL's own style (`lists_pkey`, `workspaces_user_id_key`, `lists_workspace_id_fkey`). Names are trimmed and normalized to Unicode NFC by the shared schemas. Rows are deleted, not marked deleted** _(the owner's choices, on Claude's recommendations; `updated_at` everywhere is the owner's addition)_. `user` is a reserved word in PostgreSQL. `updated_at` costs 8 bytes a row and helps debugging, and a column added later would be empty for every older row; `$onUpdate` covers every write, since all of them go through the repositories, so no trigger is needed. With `(workspace_id, id)` as the primary key, the same ID in two workspaces is two separate records, so a create with an ID from another workspace succeeds as if nothing were there ([OP-040](https://github.com/luiki-dev/szop/issues/99)); a separate `UNIQUE` would make it a conflict the API must hide. Nothing looks a record up by its ID alone ([ADR 0012](0012-security-baseline.md), decision 5), so an `id` unique only within a workspace changes nothing. This refines ADR 0012, decision 6. Drizzle's generated names can pass PostgreSQL's 63 characters, and the API recognizes a violation by its constraint's name. NFC makes "ó" typed as one character or as "o" plus an accent the same text; comparing names regardless of case is [PH-23](../roadmap.md#ph-23-smart-input)'s. |
| 15 | The access layer and the routes | Building the whole access layer of [ADR 0012](0012-security-baseline.md), decisions 3 to 6, here. | **This phase builds what its one table needs, in its final shape: an auth hook that puts the user (or none) on the request; `ownWorkspace` for reading (the workspace or none) and for writing (find or create, with `INSERT … ON CONFLICT (user_id) DO NOTHING` and a read); `requireListAccess` (owner only, otherwise 404); a list repository whose every function takes `workspaceId`. The routes: `GET /api/lists`, `POST /api/lists`, `GET /api/lists/:id`, `PATCH /api/lists/:id`. A repeated `POST` with an existing ID returns the existing list with 200, whatever name it carries** _(the owner's choice, on Claude's recommendation)_. The two-workspace test helper and the schema test come with the first references between tables in PH-16b. A repeated create with another name happens only when the client contradicts itself, and the client shows whatever the server returns. |
| 16 | The migration check | A job of its own; a Husky pre-commit hook. | **A step in the `lint` job of `ci.yml` runs `pnpm --filter @szop/api db:generate` and fails, naming the fix, if it wrote anything into `apps/api/drizzle/`** ([OP-076](https://github.com/luiki-dev/szop/issues/95)) _(the owner's choice, on Claude's recommendation)_. `drizzle-kit generate` never connects to a database, so the step needs nothing the job lacks. A job of its own costs another runner's setup; a pre-commit hook slows every commit, and CI must check anyway. |
| 17 | Testing the session | Waiting for real time to pass; a fake clock. | **API tests move `expires_at` in the database: a read with 2 days left slides it back to 30 days, and a session in the past reads as none; a removed session row stops working at the next request** _(Claude's call, from the spike)_. Better Auth does not read the app's clock. |
| 18 | The session cookie | Leaving [NFR-4](../requirements/NFR-non-functional-requirements.md#nfr-4).9 to PH-18, as planned. | **NFR-4.9 is delivered here: the first session cookie is `HttpOnly`, `Secure`, `SameSite=Lax`, has no `Domain` and carries the `__Host-` prefix, or `__Secure-` if Better Auth cannot use it** _(the owner's choice, on Claude's recommendation)_. The cookie first exists in this phase, and a cookie with weaker attributes until PH-18 would be a gap with nothing to gain. Its "revoked at once" half comes with decision 11. |
| 19 | The home screen | Keeping the Start page alongside the lists. | **The lists page replaces the Start page at `/`, and "Lists" replaces "Start" in the menu** _(Claude's call)_. [APP-1](../requirements/APP-app-wide-behavior.md#app-1).5 makes the active lists the home screen; the Start page held the place until then ([ADR 0049](0049-app-shell-phase-details.md)). |
| 20 | The screens on the mockups | **The empty lists page:** the raccoon at 30% with larger gray-500 text ("Quieter"); a one-tone silhouette at 8–10% ("Watermark"). **⋮ in the list's header:** in the corner with the tile before it; the raccoon tile as the menu button, with a ⋮ badge; no tile in this header. **The title as a field:** a plain title until focused; a bordered field even at rest. **The peeking raccoon:** at the bottom edge, as decision 7 had it; on a desktop, at the bottom of the content column. **Where the mockups live:** `docs/architecture/visual-design/`. | **The mockups of the [spec](../superpowers/specs/2026-10-30-PH-16a-guests-first-list-design.md#the-screens) are the screens' design** _(the owner's choices, on mockups Claude drew, unless marked)_:<br>- **the empty lists page is "Soft":** the raccoon in grayscale at 55% opacity, "Create your first list" in `muted-foreground`. ## Consequences

- The schema gains Better Auth's four tables, `workspaces` and `lists`. Every later table follows decision 14, and every user-created record gets its ID from the browser.
- A visitor gets a session cookie at their first change and not before; a request that only reads still stores nothing.
- The API reads `BETTER_AUTH_SECRET`. On the demo, the task reads it from the parameter `infra/base` already holds (`/szop/better-auth-secret`), so the task role's permission and the task definition change, and `infra/base` is applied from the branch ([ADR 0008](0008-hosting.md), decisions 21 and 22).
- The guest cleanup of PH-31 removes anonymous users whose session has expired and those who have no workspace; both stay in the database until then.
- `architecture.md` no longer says that creating the anonymous user creates its workspace.

## Settled while building

- **Task 1: Better Auth's generated tables were kept apart from its relations.** The CLI (1.4.21, run with `pnpm dlx` against the installed `better-auth` 1.7.14) also writes Drizzle `relations`; `auth-schema.ts` leaves them out, as nothing uses them. Its `unique()` and index names were replaced by the decision 14 names (`users_email_key`, `sessions_token_key`, `sessions_user_id_idx`, ...), and `is_anonymous` stays nullable with default `false`, as Better Auth generates it.
- **Task 1: `lists` has a `CHECK` on the name** (`lists_name_check`, 1 to 100 characters), the builder's call the spec allows.
- **Task 1: the migration keeps drizzle-kit's generated name** (`0001_fuzzy_goblin_queen`). Tests that assumed a single migration now read the journal.
- **Task 2: the session cookie is `__Host-` on https.** Better Auth adds `__Secure-` only when `advanced.useSecureCookies` is true, and a custom `advanced.cookies.session_token.name` is merged last. So on an https origin `createAuth` sets `useSecureCookies: false` (left unset it follows the https `baseURL`), names the cookie `__Host-better-auth.session_token` and sets `defaultCookieAttributes: { secure: true }`, which keeps `Secure` on the other cookies. The cookie has `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/` and no `Domain`, as `__Host-` requires. On http it is `better-auth.session_token`, with no prefix and no `Secure`. (An earlier draft of this note said `__Host-` was out of reach; it was wrong.)
- **Task 2: Better Auth's rate limiter stays on and uses the API's proxy list.** Under `NODE_ENV=production` (the image, so the demo) Better Auth limits its endpoints in memory, per task (sign-in: 3 per 10 seconds per client IP); it is off in tests. It reads the client IP from `X-Forwarded-For` and, without a trusted-proxy list, resolves a multi-entry header to no IP, so every request would share one bucket. `createAuth` receives the API's `TRUSTED_PROXIES` as `advanced.ipAddress.trustedProxies`, so it resolves the same client IP as the API. A test checks that the option carries the config value; the limiter itself is off under test and is not exercised.
- **Task 2: `generateId: "uuid"` leaves the ID to the database.** The sign-in wrote a version 7 ID, the column's `uuidv7()` default, so `generateId: () => uuidv7()` is not needed. `uuidv7()` in `@szop/shared` is for the IDs the browser creates.
- **Task 2: the adapter's `schema` is keyed by our table names** (`users`, `sessions`, ...), since `modelName` renames the models before the lookup; keyed `user`, `session`, ... it fails with "Drizzle schema mismatch".
- **Task 2: `authRoutes` takes its origin from `auth.options.baseURL`**, so its options stay `{ auth }`.
- **Task 3: the access layer throws plain errors with a `statusCode`** (401, 404), which `errorHandler` turns into the API's body, so the 404 for a foreign list and for a missing one is byte-identical. The routes call `sendError` only where there is no throw (a malformed path ID, a list gone between the check and the read).
- **Task 3: `createListSchema` is not strict.** An unknown field in the body is ignored, not refused; the brief allowed either.
- **Task 3: a list ID that is not a UUID is 404 even on `PATCH`**, before the body is looked at; an invalid body for a valid ID is 400.
