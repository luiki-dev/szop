# ADR 0054 — Leaner documentation per phase

- **Status:** ✅ Accepted
- **Date:** 2026-10-28
- **Refines:** [ADR 0004](0004-implementation-process.md), decision 9 and [ADR 0011](0011-design-sanity-check-follow-ups.md), decision 4 (the roles of specs, plans and ADRs, see decisions 3, 10 and 11; ADR notes go in two places, see decision 13); [ADR 0011](0011-design-sanity-check-follow-ups.md), decision 3 (the definition of done in the PR: short items, a bare N/A, one demo item, see decision 8); [ADR 0027](0027-open-points-on-github.md), decision 3 (the phase issue's body is a link, not a copy, see decision 5)
- **Supersedes:** the rule of [project tracking](../development/project-tracking.md) that the PR description lists the issue changes it made, set by ADR 0027's consequences (see decision 6)

## Context

The owner had the impression that every phase produces more documentation than the one before, some of it unnecessary. The [documentation volume audit](../audits/2026-10-28-documentation-volume.md) found that the documents in the repo had not grown, but the PR description had: from about 5.5k characters in PH-12c to 13k in PH-15a. It also found facts written in up to six places (D1 to D11) and ten candidates for removal. The owner reviews PRs as a reviewer and a learner. The goal is to keep what they read and remove what they skip or what another place already holds, without losing anything they need.

The owner went through the duplicates and candidates one by one. Their answers decided most rows: they skip the PR's "How it was tested" entirely, look up decisions in the ADR, read a phase's plan in `roadmap.md`, use the requirements index, read the PR's list of criteria, find the definition-of-done block in the PR unreadable, do not read the plan's Global Constraints, and learn that a decision changed from the note in its cell.

## Decisions

| # | Decision | Options considered | Outcome |
|---|---|---|---|
| 1 | The PR's "How it was tested" | Keep it; keep only what was checked by hand and the review's findings; drop it | **Dropped, with its section in the PR template** _(the owner's choice)_. The owner skipped all of it. The case lists repeat the spec's tests and the test names, CI shows the suites pass, and the demo check covers what is checked by hand. The first-screen JavaScript size is not reported in the PR either. |
| 2 | Review findings left for later | Listed in the PR; open-point issues | **After the whole-branch review, the session that ran it lists the findings it did not fix to the owner, and the owner chooses which become open-point issues, created in that session before the PR opens; the ones not chosen are dropped and noted as declined in the phase ADR's "Settled while building"** _(the owner's choice)_. A chosen finding is a sub-issue of the phase that will settle it, and its **Source** names the phase and the review. Nothing deferred lives only in a PR's text.<br>✏️ **Refined by [ADR 0059](0059-session-skills.md), decisions 6 and 7:** one findings list, triaged once with a recommendation for each finding, bugs included. |
| 3 | Where a phase's decisions live | In the spec, copied into the ADR at the end (today); in the spec only; in the ADR only | **In the phase ADR only, which is created in the same commit as the spec** _(the owner's choice)_. The owner looks decisions up in the ADR. The spec links to the ADR's decisions instead of holding a Decisions table, and the ADR alone holds "Changes to the roadmap". Decisions settled while building are added to the ADR's "Settled while building". |
| 4 | The phase ADR's status while the phase runs | 📝 Proposed until the PR opens, then a commit flipping it; ✅ Accepted from the first commit | **✅ Accepted from the first commit** _(Claude's recommendation, the owner's choice)_. Nothing in the repo changes a file when a PR merges. The ADR reaches `main` only through the merge, which is the owner's approval, so every ADR on `main` is accepted. A flip would be one more bookkeeping commit per phase. |
| 5 | The phase issue's body | A full copy of the roadmap entry, kept in sync (today); a link and the **Also** section | **A link to the phase's entry in `roadmap.md`, and the Also section** _(Claude's proposal, the owner's choice)_. The owner reads a phase's plan in `roadmap.md`. Also stays: it exists only on GitHub. Owner steps are sub-issues and "Depends on" is a "Blocked by" link, so the board loses nothing. The sync step at every PR that changes an entry is gone. **The existing phase issues are rewritten once** to the new body _(the owner's choice, after first declining: a frozen copy would drift)_. |
| 6 | The PR's Links section | Keep it; keep only the criteria and `Closes #N` | **Only the list of acceptance criteria (✅ delivered, 🚧 in part, each linked) and the `Closes #N` lines** _(the owner's choice)_. The roadmap, spec and plan links are in the stage table and the project's fields; the phase ADR is linked from "What and why" (decision 7); an issue's changes are in its timeline. New open points are not listed: their **Source** says where they came from. |
| 7 | The PR's "What and why" and "Rulings I made" | Keep both; feature bullets with a link to the ADR | **"What and why" holds what the PR delivers as bullets and links the phase ADR; it does not explain decisions again. There is no "Rulings" section** _(the owner's choice)_. The rulings land in the ADR's "Settled while building". |
| 8 | The definition of done in the PR | Every item with its full text and the demo block's fields (today); short items linking the definition | **One short label per item, under a link to `definition-of-done.md`. An item that does not apply shows `➖ N/A` in place of its checkbox, without a reason. The demo check is one item; the PR records no runs, commit, scores or Core Web Vitals** _(the owner's choice)_. The block was unreadable. The definition, the fixed demo checks and the thresholds stay in `definition-of-done.md`, and what a phase checks at the demo stays in the spec. The demo check is still done the same way and must still cover the final head. **One trace stays:** when the PR has acceptance criteria to be checked at the demo, the demo item has one line under it, "Checked at the demo:" with their linked IDs, which Claude fills from the spec and the owner's tick confirms. That line is what turns those criteria ✅ _(the owner's choice, at the builder check)_. |
| 9 | The PR's "Token usage" | Shrink it; move it; keep it | **Kept as [ADR 0052](0052-working-with-claude.md), decision 10, sets it** _(the owner's choice)_. |
| 10 | The spec's sections | Keep them (today); drop what the plan or the ADR repeats | **The spec has no Decisions table, "Changes to the roadmap", "Definition of done for this phase" or "Order of work". "Goal" is one sentence linking the roadmap entry. Acceptance criteria are a list of linked IDs, each marked whole or in part. "Documentation" (the living docs the phase changes) and "Demo check" (the behaviors to check at the demo) stay** _(Claude's proposal, the owner's choice: they look at the order only in the plan)_. |
| 11 | The plan | Unchanged; the order on top and only the phase's constraints | **The plan starts with "Order of work", its tasks in order, each linking its section. It does not list the criteria or the docs again: it links the spec. Its Global Constraints hold only what belongs to this phase. The rules for the whole repo live in `docs/superpowers/plans/CLAUDE.md`, and the session that dispatches an implementer tells it to read that file before its task** _(the order is the owner's request; the rest Claude's proposal, the owner's choice: they do not read the Global Constraints, and an instruction to read the file keeps the prompt shorter than pasting it)_. An implementer sees only its task's text, not the plan, so it would not come across the file on its own. |
| 12 | The criteria's statuses | One summary dropped; a script generating the counts; both kept | **The requirement's status line and the index row both stay, written by hand** _(the owner's choice)_. The owner uses the index for progress and wants the status at the requirement too. A script would be a new tool and a CI check to save one edit per phase. |
| 13 | Notes between ADRs | Three places: the new ADR's header, the earlier ADR's status line, the decision's cell (today); two places | **The new ADR's header and the note at the bottom of the decision's cell. The earlier ADR's status line gets a note only when the whole ADR is affected** (superseded or deprecated), since there is no cell for that _(Claude's proposal, the owner's choice: they learn of a change from the cell)_. |
| 14 | Built screenshots | Committed next to the spec (today); attached to the PR | **Committed, as today** _(the owner's choice)_. `gh` cannot upload images to a PR, so attaching them would fall to the owner. |
| 15 | Measuring the result | No measurement; a simulation on the audit's sample | **A simulation on the audit's sample: PH-15a's spec, plan, ADR, phase issue body and PR description rewritten under these rules, with the words and tokens counted before and after, recorded as an audit of its own** _(the owner's request)_. |

## Consequences

- **Files changed:** the [PR template](../../.github/pull_request_template.md), [`definition-of-done.md`](../development/definition-of-done.md), [project tracking](../development/project-tracking.md), [`phase-walkthrough.md`](../development/phase-walkthrough.md), [`git-workflow.md`](../development/git-workflow.md) and [`working-with-claude.md`](../development/working-with-claude.md) where they restate these rules, `docs/superpowers/plans/CLAUDE.md`, and `CLAUDE.md`. The [design spec](../superpowers/specs/2026-10-28-leaner-documentation-design.md) lists the changes file by file.
- **Earlier ADRs:** following decision 13, ADR 0004, decision 9, and ADR 0011, decisions 3 and 4, and ADR 0027, decision 3, get a note in their cells; their status lines do not change.
- **The phase issues are rewritten once,** by script, to the body of decision 5.
- **The first phase to follow these rules** is the next one to start its brainstorm. PH-15a, whose PR is open, stays as written.

## Settled while building

- **The simulation on PH-15a:** [the audit](../audits/2026-10-28-documentation-volume-simulation.md) rewrote PH-15a's spec, plan, ADR, phase issue body and PR description under these rules: about 20% fewer tokens in total (an estimate, characters divided by four), 49% fewer in the PR description and 29% in the spec.
- **The phase issues were rewritten against `origin/main`'s roadmap**, not the branch's, since the branch was behind `main` (PH-15b was missing). The script compared text, not issue numbers, because the roadmap names many dependencies without them; owner-step references were accepted when each named an `owner` issue. For [#49](https://github.com/luiki-dev/szop/issues/49) and [#290](https://github.com/luiki-dev/szop/issues/290) the body won, as the owner decided, and the roadmap entries were corrected in this branch.
- **Decision 2 was tightened during building,** after the owner asked who decides which unfixed review findings become issues: the owner chooses, and the rest are noted as declined here.
- **The simulation's sample is PH-15a's final PR head** (`9e7c4dd`), since the branch was deleted at the merge.
