# ADR 0040 — Two tasks details

- **Status:** ✅ Accepted
- **Date:** 2026-10-21
- **Completes:** [ADR 0036](0036-scalability-and-isolation.md), decisions 1 (two tasks from PH-37: `demo-up` sets the count, see decisions 10 and 11) and 14 (the `scale` profile and the test of two migrators, see decisions 8 and 9); [ADR 0039](0039-safe-redeploys-details.md), decision 15 (OP-103 decided: the gap is accepted, see decision 1)
- **Extends:** [ADR 0020](0020-database-details.md), decision 5 (`/api/health`'s answer names the instance that gave it, see decision 2); [ADR 0039](0039-safe-redeploys-details.md), decision 1 (the watch script prints the instance and counts the answers of each, see decision 2)
- **Refines:** [ADR 0036](0036-scalability-and-isolation.md), decisions 2 (the lock is held on a connection checked out of the pool, see decision 4), 10 (request IDs are always a random UUID, never the load balancer's trace ID, see decision 3) and 11 (5 connections per task, the lock's connection among them, see decisions 4 and 7)

## Context

[PH-12c](../roadmap.md#ph-12c-app-on-ecs-and-rds) put the walking skeleton on one Elastic Container Service (ECS) task and [PH-12d](../roadmap.md#ph-12d-safe-redeploys) made its redeploys safe, built the way two tasks need. [PH-37](../roadmap.md#ph-37-two-tasks) runs two. The direction was settled by [ADR 0036](0036-scalability-and-isolation.md), decisions 1, 2, 10, 11 and 14: two tasks, a PostgreSQL advisory lock around the migrations, request IDs unique across tasks, a pool of at most 5 connections with a budget, and a Compose profile with two app containers behind nginx. Those left the details to the phase, and two open points reached it: [OP-103](https://github.com/luiki-dev/szop/issues/249) (a page load mixing two versions of the single-page application, SPA, during a rolling deploy) and [OP-033](https://github.com/luiki-dev/szop/issues/116)'s part for this phase (the migration lock). The owner chose how the phase is proven (two running tasks in the ECS console, and requests seen reaching both) and accepted OP-103's gap, and left every other detail to Claude, to be argued in the spec. The spec's builder check found the retry branch in decision 10 and the shutdown note in decision 5; building found what is under "Settled while building".

This ADR records the decisions, with what was settled while building them. The [spec](../superpowers/specs/2026-10-21-PH-37-two-tasks-design.md) holds the design in full.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|---|---|---|
| 1 | A page load mixing two SPA versions ([OP-103](https://github.com/luiki-dev/szop/issues/249)) | Sticky sessions on the target group; the previous release's assets kept reachable (storage shared between releases); a client that reloads once when an asset is missing; the gap accepted and recorded | **The gap accepted and recorded** _(the owner's choice)_. While the old and the new tasks are both healthy, the load balancer routes each request on its own, so a browser can get `index.html` from a new task and ask an old one for an asset only the new build has; the old task answers `404` and the page loads blank until a reload. The demo is redeployed a few times a phase, its main user is the owner, and a reload fixes it. Sticky sessions fight this phase's goal that a request does not depend on which task answers it; shared asset storage brings a new component; a reload-on-error client is code to maintain for a demo. Revisited with [OP-033](https://github.com/luiki-dev/szop/issues/116)'s list if Szop ever runs always-on. |
| 2 | Seeing requests reach both tasks | The task's ID from the ECS metadata endpoint; the host name or IP address; a random ID per process | **A random instance ID per process**, 8 hexadecimal characters drawn at startup (`apps/api/src/instance.ts`), in both `/api/health` bodies as `instance` and in the `migrations applied` log line. It works the same on ECS, in Compose and in the tests, needs no ECS endpoint, and tells an attacker nothing: it is not an address, and it changes with every start. The startup line ties an ID to its task's log stream. `scripts/watch-demo.sh` prints it and counts each instance's answers; `pnpm check:scale` counts the distinct values. Extends ADR 0020, decision 5 and ADR 0039, decision 1. |
| 3 | Request IDs | The load balancer's `X-Amzn-Trace-Id` where present, a UUID otherwise (ADR 0036, decision 10, which left trusting the trace ID to this phase); always a random UUID | **Always a random universally unique identifier (UUID)**, `crypto.randomUUID()` as Fastify's `genReqId`. The load balancer keeps a `Root` field the client sends, so a client could give many requests the same ID, or one that looks like another request's, and make the logs lie. Correlating with the load balancer would need its access logs, which Szop does not keep. Fastify 5 ignores an incoming `request-id` header by default (`requestIdHeader: false`), which stays. Refines ADR 0036, decision 10. |
| 4 | The connection the migration lock is held on | A separate `pg.Client`; a connection checked out of the app's pool | **A connection checked out of the app's pool** (`pool.connect()`), held from before the migration check until after the migration, then unlocked and released. The audit's [check A](../audits/2026-10-19-scalability-and-isolation-analysis.md#check-a-two-migrators-at-once) proved this shape. It needs no second set of connection settings, and while the lock is held the migration uses a second pooled connection, two of the five. A session-level lock outlives a released connection, so the code unlocks before it releases, and on any error releases the connection as broken (`client.release(error)`), so the pool closes it and PostgreSQL drops the lock with the session. Refines ADR 0036, decisions 2 ("a connection of its own") and 11 (5 + 1 becomes 5). |
| 5 | Waiting for the lock | `pg_advisory_lock` with no limit; with `lock_timeout`; `pg_try_advisory_lock` in a loop | **`pg_advisory_lock` with no limit**, logging `waiting for the migration lock` before and `migration lock taken` after. A holder that dies loses its session and its lock at once. A holder that hangs keeps every task from listening, so they fail the load balancer's checks after the 60-second grace period and ECS replaces them, the outcome a timeout would give, with no number to tune. The grace period stays at 60 seconds: a task waits only as long as another's migration. A task stopped while it waits holds its connection, so the pool's `end()` waits too, and the existing 10-second shutdown deadline ends the process. |
| 6 | The lock's key | A hash of a name computed at runtime; a fixed number | **The fixed 64-bit number `0x537a6f7000000001`** ("Szop" in ASCII, then 1), `migrationLockKey` in `apps/api/src/db/migration-lock.ts`. PostgreSQL's `hashtext` is not a documented stable interface; a constant is plain to read in `pg_locks`. [PH-31](../roadmap.md#ph-31-automatic-cleanup)'s cleanup lock takes another constant beside it. |
| 7 | The pool and the connection budget | node-postgres's default of 10; 5 per task | **At most 5 connections per task** (`max: 5`). The worst case is every task doubled by a deploy: 2 × 2 × 5 = 20 connections now and 4 × 2 × 5 = 40 at PH-38's maximum, plus `db-setup`'s one and the owner's occasional `psql`; it must stay under about 80% of the database's `max_connections` (79 on the demo's `db.t4g.micro`, see "Settled while building": 80% is about 63). Szop's requests hold a connection for milliseconds; a request that finds the pool busy waits for a free connection, up to the existing 2-second connection timeout. Refines ADR 0036, decision 11. |
| 8 | Reading `max_connections` | ECS Exec into a task and `psql`; `db-setup` prints it; the app logs it at startup | **The app logs it at startup**, as `maxConnections` in the `migrations applied` line. The value is then in CloudWatch for every task, with no interactive session and no new permissions. `SHOW max_connections` needs no privilege. |
| 9 | Two app containers in Compose, and their check | One service with `deploy.replicas: 2` behind nginx resolving it; two named services | **Two named services, `app-a` and `app-b`, under the profile `scale`, behind nginx on `127.0.0.1:8081`**, sharing the `app` service's settings through a YAML anchor (`x-app`), on a database of their own, `szop_scale`. Named services make the logs and a failure readable, and nginx resolves a name once at startup. `scripts/check-scale.sh` (`pnpm check:scale`) creates the database fresh, so both migrate at the same time, starts the profile, sends 10 requests to `/api/health` through nginx and requires exactly two distinct instances, all `200`, then requires each migration to be recorded once. CI's `docker` job runs it after the image check. The test of two migrators proves the lock; the script proves the wiring. Completes ADR 0036, decision 14. |
| 10 | The service's count | Terraform's `desired_count`; `demo-up`'s start step | **`demo-up`'s start step sets 2.** Terraform keeps creating the service at 0 and ignoring its count, as PH-12c decided, so PH-38's autoscaling can own it later. A fresh demo, and the retry after a `FAILED` deployment, set 2 with `--force-new-deployment`; a service at another count (a demo started before this phase) is set to 2 without forcing, so Terraform's deployment, if one started, continues with two. Completes ADR 0036, decision 1. |
| 11 | One task per availability zone | A placement strategy in Terraform; ECS's default for Fargate | **ECS's default:** Fargate services spread tasks across the availability zones (AZs) of their subnets, and the service has one public subnet in each of two zones. A placement strategy is not accepted on Fargate. The owner's check confirms it in the console. |

## Settled while building

Facts the plan did not have, found while building and in the owner's demo run, and kept here because they explain code that looks odd or record what was proven:

- **The test of two migrators failed as the audit predicted** against a lock that did nothing: the data migration ran twice (`n = 2`), and on a fresh database both created Drizzle's schema and one failed with a duplicate key on `pg_namespace`. With the lock, five runs in a row passed.
- **nginx needs a shared `zone` in the upstream** for round-robin across two servers. The official image starts one worker process per CPU, and without a shared zone each keeps its own turn, starting at `app-a`; since each new connection may land on another worker, nearly every request went to `app-a`, and the first run of `pnpm check:scale` saw one instance. `zone app 64k` shares the turn.
- **The two apps took the lock one after the other in Compose:** in one run `app-b` took it 2 ms after asking, and `app-a` waited about 25 ms, until `app-b`'s migration had committed.
- **The image is built once** through the `app` service, and the `scale` profile starts with `--no-build`, so the two apps never build a second copy of `szop:local`.
- **`max_connections` is 79 on `db.t4g.micro`**, read from the `migrations applied` lines of PH-37's demo, not the 112 ADR 0036 estimated. 80% of it is about 63, so the budget holds: 20 connections (+1 for `db-setup`) with two tasks, 40 (+1) at PH-38's four.
- **The demo** (run 39675322988, 2026-10-21): the deploy job 11:46, *Start the app* 4:27. The two tasks ran in `eu-central-1a` and `eu-central-1b`, as Fargate's default spread promised; `scripts/watch-demo.sh` got 18 answers, all `200`, 9 from each instance. **On the demo no task had to wait for the lock:** the tasks started 5 to 60 seconds apart and the (empty) migration took about 100 ms, so each took the lock within 7 ms; the waiting is proven by the test and by `pnpm check:scale`. **Four log streams for two tasks:** as PH-12d found, `update-service --desired-count 2 --force-new-deployment` from zero also scaled Terraform's empty first deployment, so its two tasks ran and were drained about a minute later, and the start step showed `3 of 2 task(s) running` meanwhile. **One task failed to start** with `CannotPullContainerError … i/o timeout` on the image registry; ECS started another 40 seconds later.
- **nginx is pinned to its stable line** (`1.30.6-alpine`, an even minor version), not the newer mainline 1.31.

## Consequences

- The demo runs two tasks; a redeploy starts two new ones beside the two old ones (the maximum of 200%), so up to four run for about a minute, and every new task's startup goes through the lock.
- Every migration from now on runs under the lock, locally, in the tests' template setup excepted (`global-setup.ts` migrates one template with nothing beside it), in Compose and on the demo.
- A page load during a deploy can still come up blank once (decision 1); the runbook and the architecture say so, and a reload fixes it.
- The instance ID is public on `/api/health` (decision 2), and request IDs no longer come from anything a client can send (decision 3), both recorded in the threat model.
- `pnpm check:scale` is the place for later checks between instances; [PH-20](../roadmap.md#ph-20-quotas-and-rate-limits)'s rate limits in Redis and [PH-33](../roadmap.md#ph-33-live-updates)'s fan-out add theirs there or in tests of their own ([ADR 0036](0036-scalability-and-isolation.md), decision 14).
- [PH-38](../roadmap.md#ph-38-autoscaling) checks the budget again at four tasks (decision 7).
