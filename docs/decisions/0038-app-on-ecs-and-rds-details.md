# ADR 0038 — App on ECS and RDS details

- **Status:** ✅ Accepted
- **Date:** 2026-10-21
- **Completes:** [ADR 0008](0008-hosting.md), decisions 19 (PostgreSQL 18 on RDS, its master user and settings, see decision 14), 22 (`szop_app`'s password in SSM and the master password kept by RDS, see decisions 4 and 7) and 23 (the exact permissions of the app's two roles, see decisions 11 and 16)
- **Refines:** [ADR 0008](0008-hosting.md), decision 20 (the database is queried through Node and the app's `pg`, not `psql`, see decision 13); [ADR 0010](0010-ci-cd.md), decisions 10 and 11 (the image is built in a job of its own before Terraform and pushed only if missing; `demo-up` runs `db-setup` and then starts the service, see decisions 5, 6 and 9); [ADR 0012](0012-security-baseline.md), decision 16 (only `deploy` waits for the approval, the `build` job runs outside the `demo` environment, see decision 9); [ADR 0028](0028-container-image-details.md), decision 10 (the root filesystem stays writable on ECS, for ECS Exec, see decision 16); [ADR 0036](0036-scalability-and-isolation.md), decisions 3 to 5 and 17 (the safe redeploys are built in PH-12d, not PH-12c, see decision 1); [ADR 0037](0037-twelve-phases-a-diagram-row.md), decision 1 (a row of the README's roadmap diagram holds at most ten phases, see decision 2)

## Context

[PH-12c](../roadmap.md#ph-12c-app-on-ecs-and-rds) runs the walking skeleton on AWS for the first time. Pressing `demo-up` builds the commit's image, creates the database and one Elastic Container Service (ECS) task, and `https://szop.dzwoniec.com` shows the single-page application (SPA)'s status page: the API up, the database up, and the schema version. The direction was settled before: ECS on Fargate, RDS for PostgreSQL, the network and the secrets of [ADR 0008](0008-hosting.md), decisions 10, 14 to 16 and 19 to 23; the image built on demand by `demo-up` ([ADR 0010](0010-ci-cd.md), decisions 10 and 11); the deploy role that grows with `infra/demo` ([ADR 0032](0032-ci-access-and-teardown-details.md), decision 3; [ADR 0034](0034-network-and-demo-up-details.md), decisions 8 and 9); the app's TLS and migration check of [ADR 0033](0033-app-ready-for-the-cloud-details.md).

Those left the details to the phase, and nine open points reached it: secret values kept out of Terraform state ([OP-016](https://github.com/luiki-dev/szop/issues/75)), TLS to RDS ([OP-017](https://github.com/luiki-dev/szop/issues/68)), the runbook ([OP-018](https://github.com/luiki-dev/szop/issues/73)), building the image next to Terraform ([OP-021](https://github.com/luiki-dev/szop/issues/83)), the database role the app uses ([OP-074](https://github.com/luiki-dev/szop/issues/86)), the plan role's data reads ([OP-096](https://github.com/luiki-dev/szop/issues/218)) and a destroy that fails halfway ([OP-099](https://github.com/luiki-dev/szop/issues/228)), all settled here; and the PH-12c parts of [OP-013](https://github.com/luiki-dev/szop/issues/66), [OP-019](https://github.com/luiki-dev/szop/issues/77), [OP-020](https://github.com/luiki-dev/szop/issues/78), [OP-043](https://github.com/luiki-dev/szop/issues/84) and [OP-053](https://github.com/luiki-dev/szop/issues/26), which go on to later phases. With [ADR 0036](0036-scalability-and-isolation.md)'s safe redeploys the phase was too large, and the brainstorm split them off first (decision 1). Its builder check found decisions 9, 15 and 16.

This ADR records the decisions, with what was settled while building them. The [spec](../superpowers/specs/2026-10-20-PH-12c-app-on-ecs-and-rds-design.md) holds the design in full.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|-------|--------------------|------------------------|
| 1 | The phase's scope | Keep PH-12c whole; split off safe redeploys | **Split** *(the owner's choice)*. With [ADR 0036](0036-scalability-and-isolation.md)'s safe redeploys, PH-12c held about twelve tasks and three concepts new to the project: ECS, RDS and rolling deploys with two versions at once ([ADR 0014](0014-roadmap.md), decision 6). The rolling deploys, the circuit breaker, the deregistration delay, the liveness route, the grace period's tuning and the expand-then-contract rule became [PH-12d Safe redeploys](../roadmap.md#ph-12d-safe-redeploys), right after PH-12c; [PH-37](../roadmap.md#ph-37-two-tasks) now depends on it. ECS's defaults already deploy at 100% and 200%, so PH-12c's redeploys work, slowly. Refines ADR 0036, decisions 3 to 5 (built in PH-12d) and 17 (the roadmap). |
| 2 | The README's roadmap diagram | Twelve phases a row ([ADR 0037](0037-twelve-phases-a-diagram-row.md)); fewer | **At most ten phases a row, so the diagram is about 84 characters wide** *(the owner's choice)*. Stage 3, now thirteen phases, wraps after PH-35 onto a second row; Stage 4's nineteen are ten and nine. A narrower diagram reads better on small screens, and a stage that wraps costs nothing. No ADR of its own: this one records it. Refines ADR 0037, decision 1. |
| 3 | What the demo shows | The SPA's status page at `/`; `/` redirecting to `/api/health` | **The SPA's status page** *(the owner's choice)*. It already shows `API: ok`, `Database: up` and the schema version from `/api/health`, and proves the SPA's files are served from the image too. A redirect would hide the page, make the owner's Lighthouse run measure JSON, and have to go again when PH-16 puts lists at `/`. |
| 4 | The database role the app uses ([OP-074](https://github.com/luiki-dev/szop/issues/86)) | RDS's master user; one role owning the database; a migration role and a runtime role | **One role, `szop_app`, owning the database `szop`** *(the owner's choice)*: it logs in, owns the database and so its `public` schema, and creates and changes tables there, since the app migrates itself ([ADR 0008](0008-hosting.md), decision 14); it has no `CREATEROLE`, no `CREATEDB` and no membership in `rds_superuser`. The master user only creates and updates it, and the app never sees the master password. Using the master user in an app is the practice AWS advises against: a compromised app could create roles that survive a password change. The full pattern, a runtime role that cannot create or change tables, needs migrations run as a step of their own with their own role, which ADR 0036, decision 2 left for later; it is added to [OP-033](https://github.com/luiki-dev/szop/issues/116). Locally the app and the tests keep the superuser `szop`. Completes ADR 0008, decision 22. |
| 5 | Who creates `szop_app` | A one-off ECS task run by `demo-up`; an init container in the app's task | **A one-off task, `db-setup`, run by `demo-up`** *(the owner's choice)*, with its own task definition: the same image, another command, the master password injected. It is explicit and runs once per `demo-up`, so the master password is used once per deploy. An init container would need no workflow step and no CI permission to run tasks, but would hand the master password to every task start. Refines ADR 0010, decision 11. |
| 6 | Starting the service after `db-setup` *(Claude's call)* | Let the first task fail until the role exists; two applies; a service created at zero tasks | **Terraform creates the service at zero tasks and then ignores its count; `demo-up` runs `db-setup`, then sets the count to 1.** A first task started before the role exists would fail and be restarted until it does, filling the log and, from PH-12d, tripping the circuit breaker. On a redeploy the role exists, `db-setup` changes nothing and the count is already 1. Ignoring the count is what [PH-38](../roadmap.md#ph-38-autoscaling)'s autoscaling needs anyway. Refines ADR 0010, decision 11. |
| 7 | `szop_app`'s password *(Claude's call)* | Generated by Terraform into state; a write-only SSM parameter in base; IAM database authentication | **An SSM `SecureString` `/szop/db-app-password` in `infra/base`, from an ephemeral random password through a write-only argument**, the Better Auth secret's pattern ([ADR 0030](0030-domain-and-base-infrastructure-details.md), decision 10), so its value never enters state ([OP-016](https://github.com/luiki-dev/szop/issues/75)). It lives in base because the database is recreated each session and the role with it, but the password need not change. The master password is created and kept by RDS in Secrets Manager (`manage_master_user_password`), so it never enters state either. IAM authentication would remove the password, but needs the AWS SDK in the app and a token refreshed for every new connection, a concept of its own. Completes ADR 0008, decision 22. |
| 8 | A destroy that fails halfway ([OP-099](https://github.com/luiki-dev/szop/issues/228)) | Keep the deployed commit in an SSM parameter outside Terraform; the runbook's manual step | **The runbook's manual step** *(the owner's choice)*. A destroy is driven by the state, so `main`'s code still removes every resource a failed destroy left; the runbook says to take the commit from the failed run's summary. A parameter would be another moving part and more permissions for the deploy role. |
| 9 | Building the image ([OP-021](https://github.com/luiki-dev/szop/issues/83)) *(Claude's call)* | In parallel with Terraform; before it, in the job that holds AWS credentials; before it, in a job without them | **A `build` job without AWS credentials builds the image and hands it to `deploy` as a workflow artifact; `deploy` pushes it only if ECR lacks the tag, then applies.** Not in parallel: on a redeploy Terraform swaps the task definition at once, and the new task would try to pull an image not yet pushed. In a job of its own, the Dockerfile's `pnpm install` and build run with no AWS credentials on the runner ([ADR 0012](0012-security-baseline.md), decision 18); `build` needs no approval, so it runs while the owner approves `deploy`. The image is a single-platform one with no attestation manifests, so ECR's lifecycle rules count one image per tag ([OP-013](https://github.com/luiki-dev/szop/issues/66)'s note). Found by the spec's builder check. Refines ADR 0010, decisions 10 (built every run, pushed only if missing) and 11 (before Terraform, not in parallel), and ADR 0012, decision 16, whose image and deploy jobs waited together behind one approval: the approval guards the deploy role's token, and `build` asks for none, so only `deploy` declares `environment: demo`. |
| 10 | `TRUSTED_PROXIES` on the demo ([OP-053](https://github.com/luiki-dev/szop/issues/26)) *(Claude's call)* | The VPC's range; the public subnets' ranges | **The two public subnets' ranges, `10.0.0.0/24,10.0.1.0/24`**, where the load balancer's nodes live, from `infra/demo`'s locals. The narrowest list that holds every address the load balancer connects from; the task's security group lets nothing else reach the app's port anyway. |
| 11 | The execution role of `db-setup` *(Claude's call)* | Its own role; the app's task execution role | **The app's task execution role**, which may then read the RDS-managed master secret too. The execution role is used by ECS to start a task, never by the code inside it, so the app's container still cannot read the master secret: only a task definition that names it gets it, and only the deploy role registers task definitions. A third role would add an IAM role and its pass permission for no change in what the app can reach. The execution role pulls from the registry `szop` only, writes to the log group `/szop/app` only, and reads `/szop/db-app-password` and the demo's master secret; not AWS's `AmazonECSTaskExecutionRolePolicy`, which allows every registry and every log group. Completes ADR 0008, decision 23. |
| 12 | The health check until PH-12d *(Claude's call)* | ECS's and the load balancer's defaults; tuned now | **Defaults, with a 60-second grace period**: the target group checks `/api/health` (its default interval and thresholds), the deregistration delay stays 300 seconds, and the service ignores failed health checks for 60 seconds after a task starts, so the migrations at startup are not cut short. PH-12d tunes all of these ([OP-075](https://github.com/luiki-dev/szop/issues/87)). |
| 13 | Querying the database while debugging *(Claude's call)* | `psql` added to the image; Node and the app's `pg` through ECS Exec | **Node and the app's `pg`**: the runbook gives a short `node --input-type=module -e '…'` command that connects with the app's own settings and prints a query's rows. Adding the PostgreSQL client to the image would grow it for a tool used rarely, by hand. Refines ADR 0008, decision 20, which named `psql`. |
| 14 | The database's version and master user *(Claude's call)* | — | **PostgreSQL 18, the major version of `compose.yaml`'s `postgres:18.6`**, given as `engine_version = "18"` so RDS picks its default minor version (18.3 at the first demo), with minor upgrades on; **master user `szop_admin`**, a name that says what it is for (`postgres` and `rdsadmin` are reserved or confusing); the default parameter group, whose `rds.force_ssl` is on, so the database refuses connections without TLS. Compose and RDS keep one major version, as ADR 0008, decision 19 has it; had RDS not offered 18 in `eu-central-1`, the phase would have stopped and asked. Completes ADR 0008, decision 19. |
| 15 | What may remain after `demo-down` *(Claude's call)* | Delete every leftover; accept named, free ones | **Inactive task definition revisions are accepted.** Terraform's destroy deregisters each revision, which leaves it `INACTIVE`: it costs nothing, cannot start a task and keeps its tags, so the Tag Editor lists it. Deleting them would need `ecs:DeleteTaskDefinitions` and a `demo-down` step for a cosmetic gain. The success criterion and the runbook's check name them as the one expected leftover. Found by the spec's builder check. |
| 16 | A read-only root filesystem, or ECS Exec | ECS Exec with a writable root filesystem; a read-only one without ECS Exec, the app logging its TLS state; a `debug` switch on `demo-up` turning ECS Exec on and the read-only filesystem off | **ECS Exec, with a writable root filesystem** *(the owner's choice)*. ECS Exec is not supported with `readonlyRootFilesystem`: the agent it injects writes into the container. The read-only filesystem adds little here: the app runs as `node`, and its files belong to root and are read-only to `node` ([ADR 0028](0028-container-image-details.md), decision 10), so a compromised app cannot change its code, only write to scratch places such as `/tmp`. Compose keeps `read_only: true`, which still proves in CI that the app writes nothing to disk. The task role holds only the four `ssmmessages:` actions ECS Exec needs; SES's permission arrives with [PH-18](../roadmap.md#ph-18-registration-and-login). Found by the spec's builder check. Refines ADR 0028, decision 10, which prepared the image for ECS's `readonlyRootFilesystem`; keeps ADR 0008, decision 20; completes ADR 0008, decision 23. |

## Settled while building

Facts the plan did not have, found while building and kept here because they explain code that looks odd or record what was proven:

- **`db-setup` needs `GRANT szop_app TO CURRENT_USER` on PostgreSQL 18.** RDS's master user is not a superuser but holds `CREATEROLE` and `CREATEDB`. Since PostgreSQL 16, a role's creator gets `ADMIN OPTION` on it but not membership, and `ALTER DATABASE … OWNER TO szop_app` needs the right to `SET ROLE` to the new owner; without the grant, seven tests failed with "must be able to SET ROLE". The tests now run `db-setup` as such a non-superuser too. When the role exists, `db-setup` only changes its password: a non-superuser may not touch `SUPERUSER`, even to keep it off.
- **The password is sent as a Salted Challenge Response Authentication Mechanism (SCRAM) verifier, never in clear text.** PostgreSQL's default `log_min_error_statement = error` writes a failing statement's text to the server log, which would include `PASSWORD '<cleartext>'`, and turning that off for one transaction (`SET LOCAL`) is for superusers only. So `db-setup` computes the SCRAM-SHA-256 verifier itself (4096 iterations, a random 16-byte salt) and sends that. In exchange `APP_DATABASE_PASSWORD` must be printable ASCII, where SASLprep changes nothing; base's generated password is letters and digits. Found by a review.
- **`db-setup` has two files.** Its entry point is `apps/api/src/db-setup.ts`, run as `node src/db-setup.ts`, and its logic is in `apps/api/src/db/setup-role.ts`, so `process.env` stays out of the tested code ([ADR 0019](0019-api-skeleton-details.md), decision 10); the spec named one file.
- **The deploy role's new policies** are `szop-ci-deploy-demo-database`, `-demo-service` and `szop-ci-deploy-image`, with ADR 0034, decision 8's tag scoping. RDS has no key that limits tagging to the moment of creation, so `rds:AddTagsToResource` is scoped by the request's tags only: the same accepted gap as ACM's in ADR 0034, decision 8, harmless while the account holds no database outside the demo. `CreateDBInstance` also needed `kms:DescribeKey` and the default parameter and option groups; `ecs:DeregisterTaskDefinition` supports no resource scoping; the task's and the load balancer's new egress rules went into `szop-ci-deploy-demo-network`. 81 policy simulations ran before the apply, and the real runs needed no permission added.
- **The plan role's `DenyDataReads`** ([OP-096](https://github.com/luiki-dev/szop/issues/218)) denies RDS's log files, Performance Insights' SQL text and DynamoDB's items, every such read `ReadOnlyAccess` grants for RDS, ECS, ECR and DynamoDB. Pulling images stays allowed: the image holds the public code only. ECS's reads return configuration, and task definitions hold no secret values.
- **The image tag is `coalesce(var.deployed_commit, "none")`.** `demo-down` destroys with a null commit, and a null in the task definition's image failed the destroy (reproduced locally), as PH-12b's placeholder page did. `WEB_ROOT` comes from the image's `ENV` (`/app/apps/web/dist`), not from the task definition.
- **The image is built with `provenance: false` and `sbom: false`**, so ECR holds one plain manifest per tag (decision 9), and with no build cache. Starting the service polls `describe-services` for up to 15 minutes instead of ECS's 10-minute waiter, since a redeploy waits for the old task's 300 seconds of draining.
- **A security group rule's description rejects an apostrophe too.** The first real `demo-up` failed at the apply: EC2 refused four rule descriptions holding one ("Invalid rule description"), as PH-12b's group description would have. Fixed and run again, which continued from the partial state.
- **RDS offered PostgreSQL 18.1 to 18.6** in `eu-central-1`; the instance got 18.3 with `default.postgres18`, `rds.force_ssl = 1`, and `log_statement` and `log_min_error_statement` at their defaults.
- **RDS tags the master password's secret.** It copies the instance's tags (`project`, `group`, `Name`) onto the secret `rds!db-<uuid>`, with rotation on (every 7 days by default; a demo lives hours). The execution role's read of `rds!db-*` is narrowed by `aws:ResourceTag/project` = `szop` and `aws:ResourceTag/group` = `demo`, proven by a real redeploy whose `db-setup` succeeded (decision 11). RDS deletes the secret with the instance, leaving none behind, not even one scheduled for deletion.
- **The first demo's timings** (two runs): the build 51 seconds, the push 36 to 37, the apply about 6 minutes, of which RDS took 5; `db-setup` 53 to 60 seconds; starting the service 51 seconds; `/api/health` answered at once. About 9 minutes from the approval. A redeploy took about 3 minutes (the push 30 seconds, the apply 12, `db-setup` 53 with `"created":false`, the start 83). In its ECS events the old task was reported stopped before it was deregistered and drained, worth a look in PH-12d. `demo-down` destroyed 33 resources in 9 minutes 36 seconds: the service 7 minutes 7 seconds (the default 300 seconds of draining), RDS 1 minute 52. The 30-minute deploy timeout, the 60-minute destroy timeout and the 15-minute lock wait fit.
- **Checked on the demo:** `/api/health` answered `{"status":"ok","database":{"status":"up","schemaVersion":"0000_init"}}` and the SPA's status page showed it; a request with a forged `X-Forwarded-For: 203.0.113.7` was logged with the real client address and the forged one nowhere (decision 10); through ECS Exec, `SELECT ssl FROM pg_stat_ssl WHERE pid = pg_backend_pid()` returned `true` ([OP-017](https://github.com/luiki-dev/szop/issues/68)), and the shell inherits the task's environment, `DATABASE_PASSWORD` included; neither password is in base's or demo's state ([OP-016](https://github.com/luiki-dev/szop/issues/75)); Lighthouse 13.4.1 on mobile scored Performance 100, Accessibility 100, Best Practices 100 and SEO 90 (no meta description, left to [PH-14](../roadmap.md#ph-14-app-shell-and-design-system)).
- **The Tag Editor lags again.** After `demo-down`, the Resource Groups Tagging API still listed the cluster and the service (`INACTIVE`), stopped tasks, subnets and security group rules that ECS and EC2 reported gone; the inactive task definition revisions remain, as decision 15 expected.

## Consequences

- [PH-12d](../roadmap.md#ph-12d-safe-redeploys) replaces this phase's defaults (decision 12): the health check's grace period, interval and thresholds, the 300-second deregistration delay that the redeploy and the destroy wait for, and the rolling settings with the circuit breaker; it adds the liveness route. Its brainstorm looks at the old task stopping before its deregistration in the redeploy's events.
- [PH-18](../roadmap.md#ph-18-registration-and-login) adds SES's permission to the task role and the Better Auth secret to the execution role and the app's task definition, when the app first sends mail and reads the secret.
- [OP-033](https://github.com/luiki-dev/szop/issues/116) gains a step for an always-on Szop: separate migration and runtime roles (decision 4).
- The deploy role can run any code with the master secret in reach: it registers task definitions, pushes images and passes the execution role. This is accepted as part of trusting the deploy role, whose gate is the owner's approval of each `demo-up` run (the [threat model](../architecture/threat-model.md)).
- The task's root filesystem is writable on ECS (decision 16); what protects the code there is that its files belong to root.
- `APP_DATABASE_PASSWORD` must stay printable ASCII, since `db-setup` does not apply SASLprep.
- Costs: the task, the database and its storage bill only while a demo is up, about $0.079 per demo hour with the load balancer ([the analysis, costs](../audits/2026-10-19-scalability-and-isolation-analysis.md#costs)); between sessions, cents for the images, the parameter and the logs.
