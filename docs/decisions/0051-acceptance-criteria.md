# ADR 0051 — Acceptance criteria and their status

- **Status:** ✅ Accepted
- **Date:** 2026-10-26
- **Refines:** [ADR 0024](0024-github-project-tracking.md), decision 1 and [ADR 0027](0027-open-points-on-github.md), decision 1 (GitHub stays the source of status for phases and open points; the status of requirements lives in the requirements, see decision 2); [ADR 0011](0011-design-sanity-check-follow-ups.md), decision 4 (the functional requirements also answer how far along each requirement is, see decision 2)
- **Extends:** [ADR 0004](0004-implementation-process.md), decision 7 (the definition of done gains the rule for ✅ criteria, see decision 4) and decision 8 (a phase's brainstorm finalizes the criteria of the requirements it delivers, see decision 15)

## Context

The MVP's feature phases were about to start, and two things were missing. The details of a requirement, decided in phase brainstorms, lived only in the specs of finished phases, which are never updated. And nothing showed how far along each requirement was: that took a search through the roadmap's "Delivers" lines, the phase issues and the specs. A sweep of the ADRs, the living docs, the specs and the open-point issues found about 300 to 340 behaviors that had been decided or assumed but were written down in no requirement.

[PH-40](../roadmap.md#ph-40-acceptance-criteria) settled how requirements carry their details and their status, and wrote them for every requirement. Its [spec](../superpowers/specs/2026-10-26-PH-40-acceptance-criteria-design.md) holds the design.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|---|---|---|
| 1 | What carries a requirement's details | User stories; acceptance criteria; Gherkin scenarios run by playwright-bdd; one GitHub issue per requirement; tests tagged by ID with a generated coverage report | **Acceptance criteria** _(Claude's recommendation, the owner's choice)_: short, checkable statements of what must be true for the requirement to be met. Each requirement already says what happens and the use cases say who does it and why, so stories would mostly repeat them. Gherkin adds a test layer of its own next to [ADR 0007](0007-testing-strategy.md). Issues per requirement keep the criteria outside the repository, where PRs cannot review them. A coverage report needs a script the owner did not want (decision 4). |
| 2 | Where the status of requirements lives | On GitHub, beside the status of phases; in the requirements | **In the requirements** _(the owner's choice)_, where the owner looks for what is left. Criteria change in the same PR as the code that delivers them, so their status cannot lag behind the merge. GitHub stays the source of status for phases and open points. |
| 3 | When criteria are written | When the phase delivering a requirement starts; for every requirement at once | **For every requirement at once, marked ❔ draft until a phase finalizes them** _(the owner's choice)_. Much of what was decided lived in ADRs, specs and open points; written down now, it can be seen whole and moved between requirements, and it can change the plan of later phases. |
| 4 | When a criterion is done, and how its tests are found | The criterion names its test files; a script reports coverage; the test names the criterion | **✅ only when a phase delivered it and a test covers it; the test's name starts with the criterion's ID** _(the owner's rule; the direction of the link is Claude's proposal)_. A criterion is often covered by several tests on different layers, so naming them would make the criterion long and stale whenever a file moves. `grep` finds every test of a criterion, and a reviewer checks the rule without tooling. A check that is not a test names the ID in a comment; a criterion only a person can check is marked as checked at the demo. |
| 5 | How the file is split | The index keeps each requirement's text under today's anchors and the area files hold only criteria; every requirement moves with its criteria | **Every requirement moves with its criteria to its area's file; `functional-requirements.md` becomes the index, and every link is rewritten once** _(the owner's choice)_. A requirement and its criteria belong together. The links in the repository and in issue bodies were rewritten by a script, as [ADR 0027](0027-open-points-on-github.md), decision 2 did for the open points. |
| 6 | The area files | Files grouping several areas; one file per area named by its code; one per area named by code and name | **One file per area, named `<AREA-CODE>-<full-area-name>.md`**, such as `ACC-accounts-and-guest-mode.md`, with the use cases in `UC-use-cases.md` _(the name is the owner's choice)_. The prefix says where to look, and the rest of the name what the area is. |
| 7 | A criterion's ID | Headings per criterion; rows of a table | **The requirement's ID, a dot and a number (`ACC-1.1`), as a row of the requirement's criteria table** _(Claude's call)_. A heading "ACC-1.1" would get the anchor `#acc-11`, the same as "ACC-11". Links go to the requirement. A number is never reused; a criterion that moves gets a new ID in its new place. |
| 8 | Behavior no requirement held | Under APR; new areas | **A new area, APP, for what every screen shares (the menu, messages, loading and empty states, the not-found page, forms), and NFR-4 for security that can be observed from outside** _(Claude's proposal, the owner's choice)_. APR stays about appearance. Security is a quality of every part, like accessibility; the account rules stay in ACC. |
| 9 | Candidate open points | Criteria for them; none until picked up | **None until a candidate is picked up** _(Claude's proposal, the owner's choice)_. Otherwise the index of what is left would list work nobody planned. |
| 10 | The landing page and `/design` | Requirements for both; outside the requirements | **Outside** _(the owner's choice)_. They are tools of the project, not Szop's features, and [ADR 0044](0044-landing-page-details.md) and [ADR 0048](0048-design-system-phase-details.md) describe them. |
| 11 | How the work was cut | Four phases interleaved with feature work; one phase | **One phase, before further feature work** _(the owner's choice)_. The criteria could change the shape of later phases, and the owner wanted the whole picture first. One new concept and about eight tasks fit [ADR 0014](0014-roadmap.md), decision 6. |
| 12 | Delivered criteria without a test | One open point under the next phase; no tests in PH-40 | **Listed at the owner's review in the middle of PH-40, who decides by their number: a few small tests in PH-40, a phase of their own, or open points for the phases that next work in their areas** _(the owner's choice)_. Until a test covers it, such a criterion stays 🚧. |
| 13 | Criteria that apply to every screen | 🚧 until every MVP screen exists; one criterion per screen | **A general rule, ✅ when everything that exists meets it and a test checks it; later phases keep it true. What one screen must do belongs to that screen's requirement** _(Claude's recommendation, the owner's choice)_. Most such rules are enforced by a mechanism that runs everywhere, such as axe in every E2E journey, and the definition of done's first item keeps them true. |
| 14 | The owner's review during PH-40 | After every area; only in the PR; once, after the first criteria | **Once, after the first criteria are written** _(Claude's recommendation, the owner's choice)_. Style and granularity are settled there, before about 300 rows follow. |
| 15 | Whether a requirement's list of criteria is complete | A requirement's status taken from its criteria alone; a mark of its own | **A mark of its own: ❔ Criteria not finalized until a brainstorm reviews the whole requirement with the owner, ✅ Criteria finalized after. A requirement is ✅ Done only when its list is finalized and every criterion is ✅** _(the owner's choice)_. Criteria written from earlier decisions can miss some; without the mark, a requirement whose known criteria are all ✅ would read as done. The first phase that delivers any part of a requirement reviews it whole. |

## Consequences

- `docs/requirements/` holds the index (`functional-requirements.md`), one file per area, the non-functional requirements and the use cases. The index explains criteria and statuses and shows the status of every requirement.
- A criterion's statuses are ❔ Draft, ⬜ Not started, 🚧 In progress, ✅ Done, ➡️ Moved and ✖️ Dropped; ➡️ joins the icon vocabulary.
- Each phase's brainstorm reviews and finalizes the criteria of the requirements it delivers, and its PR marks the delivered ones ✅, each with a test whose name carries its ID ([definition of done](../development/definition-of-done.md), items 1 and 6; [testing.md](../development/testing.md#rules)).
- The status of the index and of each requirement's line is kept by hand, in the PR that changes a criterion. No script in the repository checks it.
- The roadmap's "Delivers" keeps linking requirements; a "(part: …)" note may name the criteria it covers.
