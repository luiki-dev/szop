# ADR 0034 — Network and demo-up details

- **Status:** ✅ Accepted
- **Date:** 2026-10-18
- **Completes:** [ADR 0008](0008-hosting.md), decisions 6 (`infra/demo` finds base's resources by name, see decision 1) and 16 (the address ranges, see decision 2); [ADR 0010](0010-ci-cd.md), decisions 11 (the optional `ref` input and the page check, see decisions 3 and 6) and 13 (the separate job that re-enables `demo-down`, see decision 5); [ADR 0011](0011-design-sanity-check-follow-ups.md), decision 7 (a precondition makes every apply record its commit, see decision 7); [ADR 0032](0032-ci-access-and-teardown-details.md), decision 3 (the deploy role's first growth, through managed policies, see decision 9)
- **Revisits:** [ADR 0032](0032-ci-access-and-teardown-details.md), decision 4 (the `SPECIFIC_GITHUB_REPO_AND_BRANCH_RECOMMENDED` warning is back on the deploy role's trust, from the `demo` statement, and is accepted again; see Settled while building)

## Context

[PH-12b](../roadmap.md#ph-12b-network-and-the-demo-up-button) creates the first demo: pressing `demo-up` builds the network, the load balancer and the certificate, and `https://szop.dzwoniec.com` answers with a fixed placeholder page; the app itself comes in [PH-12c](../roadmap.md#ph-12c-app-on-ecs-and-rds). The direction was settled before: the network of [ADR 0008](0008-hosting.md), decision 16, the certificate created per session ([ADR 0030](0030-domain-and-base-infrastructure-details.md), decision 5), the `demo-up` workflow of [ADR 0010](0010-ci-cd.md), decisions 11 and 13, [ADR 0011](0011-design-sanity-check-follow-ups.md), decision 7, and the deploy role that grows with `infra/demo` and trusts `demo` only from this phase on ([ADR 0032](0032-ci-access-and-teardown-details.md), decisions 3, 10 and 14).

Those left the details to the phase: how `infra/demo` finds base's resources ([OP-014](https://github.com/luiki-dev/szop/issues/82)), the address ranges, what the placeholder page says, who re-enables `demo-down`, and how the deploy role's permissions are written and scoped. The brainstorm settled them, and its builder check found three more (decisions 6, 8 and 9). Destroying base once Szop is shut down for good ([OP-093](https://github.com/luiki-dev/szop/issues/208)) became a chapter of the runbook.

This ADR records the decisions, with what was settled while building them. The [spec](../superpowers/specs/2026-10-18-PH-12b-network-and-the-demo-up-button-design.md) holds the design in full.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|-------|--------------------|------------------------|
| 1 | How `infra/demo` finds base's resources ([OP-014](https://github.com/luiki-dev/szop/issues/82)) | Base's outputs through `terraform_remote_state`; lookups by name through data sources | **Lookups by name.** `infra/demo` asks AWS for base's resources by their fixed names (in this phase the hosted zone `dzwoniec.com`; in PH-12c the registry, the log group, the app's roles, and the secret's ARN, built from the account ID and the parameter's name, since `data "aws_ssm_parameter"` would read its value). The names live in one `locals` block in `infra/demo`. Reading base's outputs would give `szop-ci-deploy` `s3:GetObject` on base's whole state, a description of every IAM policy and the OIDC setup that any approved `demo-up` run could print, against [ADR 0010](0010-ci-cd.md), decision 16's rule that the deploy role cannot reach base. With lookups, the role reads only what it looks up, which it mostly needs anyway to use it; separately owned stacks commonly meet this way. **Cost:** each name is written in both modules, and a rename in base breaks demo's next plan, loudly. Completes ADR 0008, decision 6. |
| 2 | The network's layout *(Claude's call)* | — | **`10.0.0.0/16`, with public subnets `10.0.0.0/24` and `10.0.1.0/24` and private subnets `10.0.10.0/24` and `10.0.11.0/24`, in `eu-central-1a` and `eu-central-1b`.** The private subnets are created now, though RDS arrives in PH-12c: the network is this phase's concept, and subnets cost nothing. Public subnets do not give instances public addresses by default; PH-12c's service asks for one itself. No NAT gateway and no VPC endpoints, as decided. Completes ADR 0008, decision 16. |
| 3 | The placeholder page *(Claude's call)* | A plain "OK"; a page naming the deployed commit | **A short HTML page that says the demo is up, that the app arrives in PH-12c, and which commit it was deployed from.** `demo-up` waits until the page shows its own commit, and the owner's check sees the same, so both prove that this run's code is what answers, not an older demo or a cached page. A fixed response's body is limited to 1024 bytes, so the page is a few lines of plain HTML with no styles or scripts. Completes ADR 0010, decision 11. |
| 4 | The load balancer's TLS policy *(Claude's call)* | The console's default `ELBSecurityPolicy-TLS13-1-2-2021-06`; the newest restricted policy | **`ELBSecurityPolicy-TLS13-1-2-Res-PQ-2025-09`:** TLS 1.3 and 1.2 with only strong ciphers, and post-quantum key exchange where the browser offers it. It is the newest restricted policy in `eu-central-1`; the older default still accepts weaker TLS 1.2 ciphers that no supported browser needs ([NFR](../requirements/NFR-non-functional-requirements.md)). |
| 5 | Who re-enables `demo-down` *(Claude's call)* | A step in the deploy job; a job of its own | **A job of its own, `enable-teardown`, with `actions: write` and no AWS credentials**, the split of [ADR 0032](0032-ci-access-and-teardown-details.md), decision 8: no job holds a write token for the repository and AWS credentials together. It runs first and needs no approval, so the safety net is back on even if the deploy is rejected or fails halfway. Completes ADR 0010, decision 13. |
| 6 | The `ref` input *(Claude's call)* | Required; optional | **Optional.** Left empty, `demo-up` deploys the commit of the branch chosen in *Use workflow from*, which is the usual case: the button is pressed on the branch being checked. A branch, a tag or a full 40-digit commit hash in the input deploys that instead. A short hash is not accepted: `actions/checkout` looks it up as a branch name and fails, and supporting it would mean fetching the whole history first; the input's description says so. Found by the spec's builder check. Completes ADR 0010, decision 11. |
| 7 | Making sure every apply records its commit *(Claude's call)* | A required variable; an optional variable checked by a precondition | **`deployed_commit` is optional (null by default), and a precondition refuses to create or change the demo without it.** A destroy never asks for it, so `demo-down` and the runbook's local destroy keep working unchanged; an apply without it, from CI or a laptop, fails before it creates anything, so no demo can exist that `demo-down` would destroy with the wrong code. A required variable would make every destroy pass a value it does not use, and `demo-down`'s fallback to `main`'s code would need a made-up one. Completes [ADR 0011](0011-design-sanity-check-follow-ups.md), decision 7. |
| 8 | Which tag the deploy role's conditions check *(Claude's call)* | `project` = `szop`; `group` = `demo` as well | **Both: `project` = `szop` and `group` = `demo`**, in the request when creating and on the resource when changing or deleting. Base and bootstrap carry `project` = `szop` too, so that tag alone would not keep the role away from base's resources; `group` = `demo`, which only `infra/demo`'s provider sets, enforces [ADR 0010](0010-ci-cd.md), decision 16's "the deploy role cannot change base" in IAM. Harmless today, since base has no EC2, load balancer or ACM resource, but PH-12c copies the pattern to ECR and CloudWatch Logs, where base's registry and log group live. **Cost:** ACM has no key that limits tagging to the moment of creation, so `acm:AddTagsToCertificate` could also tag an existing certificate and so bring it within the role's reach; this gap is accepted, since the account holds no certificate outside the demo (base keeps none, [ADR 0030](0030-domain-and-base-infrastructure-details.md), decision 5). Found by the spec's builder check. |
| 9 | Where the deploy role's permissions live *(Claude's call)* | More inline policies on the role; customer managed policies attached to it | **Customer managed policies, `szop-ci-deploy-demo-network`, `-load-balancer` and `-dns`, one per area, attached to `szop-ci-deploy`**; the existing inline `state` policy stays. All inline policies of a role share 10,240 characters, which PH-12c's ECS, RDS, ECR, logs and `iam:PassRole` statements would likely exceed; a managed policy holds up to 6,144 characters each, and a role takes up to 10 of them. Splitting by area keeps each one readable in the plan comment. The role keeps growing phase by phase, now through a new policy per area. Found by the spec's builder check. Completes ADR 0032, decision 3. |

## Settled while building

Facts the plan did not have, found while building and kept here because they explain code that looks odd or record what was proven:

- **A precondition is skipped on destroy.** Proved on a throwaway configuration with local state: apply with the variable set, destroy without it, and the destroy succeeds. Terraform does not evaluate a resource's preconditions when destroying it, so `demo-down` and a local destroy work with `deployed_commit` null (decision 7). The page's text uses `coalesce(var.deployed_commit, "none")` so that the template still evaluates when the variable is null.
- **A security group's description rejects an apostrophe.** EC2 accepts only letters, digits, spaces and `._-:/()#,@[]+=&;{}!$*` there. "The demo's load balancer" would have failed the first real apply, once the VPC existed, and `terraform plan` cannot catch it. A review found it and it was fixed before any run.
- **The load balancer depends on the internet gateway.** Nothing else ties the two together, and an internet-facing load balancer created before its VPC has a gateway fails with `InvalidSubnet`, which the provider does not retry; on destroy the same edge makes the load balancer go first. Found by the spec's builder check.
- **The deploy role's actions came from two sources.** They were derived from the AWS Service Authorization Reference and checked against the source of each resource in the AWS provider (6.69.1), in a review. For example: an `aws_security_group` with no `egress` block revokes the default egress rule on creation (`RevokeSecurityGroupEgress`); an `aws_vpc_security_group_ingress_rule` tags its rule in the `AuthorizeSecurityGroupIngress` call (`ec2:CreateTags` with `ec2:CreateAction`); `CreateListener` is evaluated on the load balancer only, with `aws:RequestTag` and `aws:ResourceTag` as action-level keys; the provider's load balancer delete only waits for the load balancer's network interfaces to go (`DescribeNetworkInterfaces`), so `ec2:DeleteNetworkInterface` is not needed; `ModifyListener` applies a changed fixed response in place.
- **The policies are small and were tested.** `szop-ci-deploy-demo-network` has 2,271 characters, `-load-balancer` 2,322 and `-dns` 881, each far under 6,144. IAM Access Analyzer reports no findings on the three. The IAM policy simulator allowed all 96 cases that should work and denied all 32 that should not (deletes of `group` = `base` resources, creates without the tags, changes to the apex's or MX records, `CreateTags` with a foreign `CreateAction`, subnets in the default VPC and others).
- **Every permission was right the first time.** The first real `demo-up` and `demo-down` needed no permission added.
- **The warning is back, and accepted.** Access Analyzer's `SPECIFIC_GITHUB_REPO_AND_BRANCH_RECOMMENDED` warning returned on `szop-ci-deploy`'s trust, from the new `GitHubDemo` statement, which deliberately has no `ref` pin: `demo-up` runs from any branch, gated by the owner's required review. It is accepted as [ADR 0032](0032-ci-access-and-teardown-details.md), decision 4, accepted it for the plan role; the `GitHubDemoTeardown` statement keeps its `main` pin. The `CONFIRM_AUDIENCE_CLAIM_TYPE` suggestion appears once per statement, so twice on the deploy role.
- **The `demo` environment was first saved without its required reviewer.** GitHub reported no protection rules, after base had already been applied with the `demo` trust. The check through the API (`gh api repos/luiki-dev/szop/environments/demo`) found it before any run, the owner added the reviewer, and the check was repeated. The runbook now asks for that check right after the environment is created and before base is applied with the trust that names it.
- **The first demo's timings** (2026-10-18). `demo-up`'s deploy job took 205 seconds from the approval, of which the apply took 181 (19 resources added): the load balancer 2 min 14 s, the certificate's validation record about 30 s, the `szop` record about 30 s. The page answered at the wait's first try. `enable-teardown` took 3 seconds, and `gh workflow enable` on an already enabled workflow succeeds with `actions: write`. `demo-down`'s job took about 85 seconds, the destroy about a minute, with 19 resources destroyed and the recorded commit checked out and used. The 30-minute deploy timeout, the 60-minute destroy timeout and the 15-minute lock wait fit comfortably.
- **A redeploy changes the listener in place.** A plan with another commit while the demo was up showed 0 to add, 1 to change (the HTTPS listener's fixed response) and 0 to destroy.
- **Checked from outside.** `http://szop.dzwoniec.com` answers 301 to `https://szop.dzwoniec.com:443/`; the certificate is issued by Amazon RSA 2048 M04; TLS 1.3 is negotiated.
- **The Tag Editor lags behind deletions.** The Resource Groups Tagging API behind it still listed two deleted security group rules after the destroy, while EC2 reported them as not found. The runbook says to check such a leftover in its own service.
- **commitlint's scopes have no `ci`.** Commits that change workflows use `feat(infra)` or `docs(infra)`.

## Consequences

- [PH-12c](../roadmap.md#ph-12c-app-on-ecs-and-rds) adds ECS, RDS and the app's roles with the same tag scoping (decision 8) and a new managed policy per area (decision 9), in the same PR, where the plan comment and Access Analyzer show them next to the resources. It looks up base's registry, log group, roles and secret by name (decision 1). It puts the service in the public subnets, with the private subnets waiting for RDS (decision 2).
- Waiting for `/api/health` replaces `demo-up`'s wait for the placeholder page (decision 3), and the 30-minute and 60-minute timeouts and the 15-minute lock wait are revisited with RDS, whose deletion alone takes about ten minutes ([ADR 0032](0032-ci-access-and-teardown-details.md), decision 7).
- The ACM tagging gap (decision 8) stays accepted while the account holds no certificate outside the demo.
- `szop-ci-deploy` now trusts two environments: `demo-teardown` pinned to `main`, and `demo` from any branch. What keeps a branch's code from the role is the owner's approval of every `demo-up` run, so the environment's required reviewer is part of the security setup and its protection is checked through the API when it is created.
- A rename of the zone or of any other name in `infra/demo/locals.tf` or `infra/base/locals.tf` must be made in both modules (decision 1).
- Costs: the load balancer is the one new resource that bills, and only while a demo is up; the network, the certificate and the DNS records add nothing to speak of. The workflows run on GitHub's free minutes for public repositories.
