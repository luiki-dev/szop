# ADR 0042 — Releases details

- **Status:** ✅ Accepted
- **Date:** 2026-10-23
- **Refines:** [ADR 0009](0009-git-workflow.md), decision 11 (release notes come from GitHub, one line per merged PR, and the release PR's branch is `release-please--branches--main--components--szop`, see decisions 1, 2 and 7); [ADR 0010](0010-ci-cd.md), decision 17 (three jobs, the `release` environment without a reviewer, the image's version tag without the `v`, see decisions 6, 8 and 9); [ADR 0030](0030-domain-and-base-infrastructure-details.md), decision 9 (the lifecycle policy's rule 1 shields `*.*.*`, not `v*`, see decision 6)
- **Completes:** [ADR 0010](0010-ci-cd.md), decision 16 (`szop-ci-release`'s trust and permissions, see decision 10)

## Context

[ADR 0009](0009-git-workflow.md), decision 11 chose release-please to cut versions, and [ADR 0010](0010-ci-cd.md), decision 17 said how it runs: on every push to `main`, as a GitHub App, with a follow-up job that gives the release commit's image its version. [PH-13](../roadmap.md#ph-13-releases) builds it and releases the walking skeleton as `v0.1.0`.

One question was left open since the design sanity check ([OP-025](https://github.com/luiki-dev/szop/issues/89)): release-please reads every commit that reaches `main`, and Szop merges with merge commits, so a phase could appear twice in the changelog and its review fixes as fixes of unreleased code. Before the brainstorm the owner ran release-please in a throwaway repository with merge commits to find out ([#150](https://github.com/luiki-dev/szop/issues/150#issuecomment-6367966572)). The owner chose how release notes are made, which PRs they list, what the first release lists, where the version is written, the image tag, the environment's protection and the jobs' layout; the rest was Claude's call, argued in the [spec](../superpowers/specs/2026-10-23-PH-13-releases-design.md), which holds the design in full.

## The trial

Run on 2026-10-23 in [luiki-dev/release-please-trial](https://github.com/luiki-dev/release-please-trial): `googleapis/release-please-action@v4` with the workflow's `GITHUB_TOKEN`, `release-type: node`, `bump-minor-pre-major`, merge commits only. Each round was a branch of three empty commits (`feat`, `test`, a review-fix `fix`) merged through a PR titled as a `feat`, as a Szop phase is.

| Round | Tried | Result |
|---|---|---|
| 1, first repository | Defaults, manifest `0.0.0` | ❌ First release `1.0.0`, tag `trial-v1.0.0`: with no earlier tag the manifest is ignored and the default initial version is used; the package's name goes into the tag, the release PR's title and the Release's name |
| 1, again | `initial-version: "0.1.0"`, `include-component-in-tag: false` | ✅ Tag and Release `v0.1.0`, release PR `chore(main): release 0.1.0` |
| 1 | Option B: merge message = PR title (Szop's setting) | ✖️ The PR title **and** the task commits listed, so one feature twice; the review fix listed as a bug fix |
| 2 | Option A: GitHub's default merge message | ✖️ As B: the "Merge pull request" header is skipped, the PR title in the body is parsed, and the `(#N)` link is lost |
| 3 | Option D: `BEGIN_COMMIT_OVERRIDE` in the PR description | ✖️ The override replaces **every** commit of the PR: one entry four times, the `test` and `fix` commits turned into `feat` |
| 4 | `Release-As: 1.0.0` footer on a branch commit, merged through a PR | ✅ The release PR proposes `1.0.0` |
| 5 | Option E: `changelog-type: github` | ✅ One entry per merged PR; the version is still computed from the commits (`1.1.0`) |

A, B and D fail for one reason: release-please reads every commit that reaches `main`, the branch commits a merge commit brings in included, has no first-parent option, and applies a PR's override to every commit associated with that PR.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|---|---|---|
| 1 | How release notes work with merge commits ([OP-025](https://github.com/luiki-dev/szop/issues/89)) | (A) GitHub's default merge message; (B) the PR title as the merge message, as before; (C) squash merges; (D) `BEGIN_COMMIT_OVERRIDE` in the PR description; (E) `changelog-type: github`, notes from GitHub | **E: release notes from GitHub, merge commits stay** _(the owner's choice, after the trial)_. One line per merged PR, with its title, author and link; [ADR 0009](0009-git-workflow.md), decision 6 is unchanged and the task commits stay in `main`'s history. The version is still computed from the commits, where duplicates do no harm: the highest bump wins. A, B and D list the task commits next to the PR, and D multiplies one entry by the PR's commit count. C gives clean notes grouped by type, but would supersede ADR 0009, decision 6, lose the task commits on `main` and change the ruleset. **Cost:** notes are grouped only by label, not by commit type, and every merged PR is listed unless excluded (decision 2). |
| 2 | Which PRs the notes list | Every PR; Dependabot's excluded, a flat list; categories by label | **Every PR except Dependabot's and those labelled `skip-changelog`, as a flat list** _(the owner's choice)_. `.github/release.yml` excludes them. The label is set **by hand**, by Claude when it opens a PR for a change readers of the notes do not need (Claude Code's settings, process docs) or by the owner; it hides the PR from the notes and does not change the version. It works whenever it is set before the release PR is merged: release-please asks for the notes again on every push to `main`. Categories would need a label on every PR, by hand or by a labelling workflow; labelling by path (`actions/labeler`) is a workflow with write access to PRs, not worth it until the label is often forgotten. |
| 3 | The first release's notes | Every PR since the repository began; the old `docs:` PRs labelled `skip-changelog`; notes written by hand | **Every PR** _(the owner's choice)_. With no earlier tag GitHub lists every merged PR, 44 of them: the walking skeleton's real history, and in a learning project its decisions are part of the product. It happens once and costs nothing. Notes written by hand would be overwritten on the next push to `main`. |
| 4 | Where the version is written | `release-type: node`, the root `package.json`; `release-type: simple`, a `version.txt`; `node` and every workspace's `package.json` too | **`release-type: node`, the root `package.json`** _(the owner's choice)_. Each release PR raises its `"version"`; the workspaces stay without one, since none is ever published. A `version.txt` is a file nobody reads; four `package.json` files per release PR serve nobody. |
| 5 | Settings the trial showed are needed _(Claude's proposal, accepted)_ | — | **`initial-version: "0.1.0"`**, without which the first release is `1.0.0`, and **`include-component-in-tag: false`**, without which the tag is `szop-v0.1.0`, which the `version-tags` ruleset's `v*` would not even match. |
| 6 | The image's version tag ([OP-026](https://github.com/luiki-dev/szop/issues/90)) | `szop:0.1.0`; `szop:v0.1.0`; both | **`szop:0.1.0`, without the git tag's `v`** _(the owner's choice)_. It is the convention for images (official images, `docker/metadata-action`'s semver pattern), and it equals `package.json`'s `version`. ECR's lifecycle rule 1 shielded released images by the pattern `v*` ([ADR 0030](0030-domain-and-base-infrastructure-details.md), decision 9), which `0.1.0` does not match, so the release image would have expired once 10 newer images existed. **Rule 1's pattern becomes `*.*.*`** _(found while designing)_: ECR allows several wildcards in a pattern, and a commit hash has no dots, so only versions match. |
| 7 | The release PR's branch ([OP-027](https://github.com/luiki-dev/szop/issues/91)) | — | **Accepted as release-please names it: `release-please--branches--main--components--szop`.** Nothing in Szop stops it: the `main` ruleset targets only `main`, no rule restricts branch names, `ci.yml` and `pr-title.yml` run on every PR to `main`, and the release commit `chore(main): release 0.1.0` passes commitlint (`main` is on the scope list). `type/short-description` is the rule for branches people and Claude create; the bot's branch is the one exception. |
| 8 | A required reviewer on the `release` environment | No reviewer, `main` only; a reviewer on the environment; a reviewer for the image job only, through a second environment | **No reviewer; deployments from `main` only** _(the owner's choice)_. The workflow runs on every push to `main`, so a reviewer would mean approving every merge, released or not; the owner's merge of the release PR is the approval. The role behind the environment can only push and tag images, AWS pins it to `main` as well (decision 10), and a PR's workflow cannot use the environment. A second environment for the image job would add a role subject and settings to guard a tag. |
| 9 | How the release job delivers the image | (A) three jobs: `release-please`, `build` without AWS, `publish` with AWS; (B) re-tag only, and fail when the image is missing; (C) one job that builds and pushes with AWS credentials | **A, in its simple form** _(the owner's choice)_. As `demo-up` does ([ADR 0038](0038-app-on-ecs-and-rds-details.md), decision 9), the build runs without AWS credentials and hands the image to the job that holds them, which runs no `pnpm install` and no project script ([ADR 0012](0012-security-baseline.md), decision 18). `build` runs on every release, even when ECR already holds the commit's image and `publish` only adds the tag; that happens on a re-run after a partial push, and costs about five minutes of a free runner. Checking ECR first would need another job with AWS credentials before `build`. B fails on almost every release, since the release commit is created by the merge and was never deployed; C builds next to AWS credentials. |
| 10 | The release role _(Claude's proposal, accepted)_ | — | **`szop-ci-release`**, trusted, as `szop-ci-deploy` is for `demo-teardown` ([ADR 0032](0032-ci-access-and-teardown-details.md), decisions 13 and 14), for the immutable subject `repo:luiki-dev@290870182/szop@1380292421:environment:release` **and** the ref `refs/heads/main`. One inline policy: `ecr:GetAuthorizationToken` (account-wide, in `eu-central-1`), and on the repository `szop` only the actions to find an image, read its manifest, add a tag and push layers. No layer downloads, no deletes; immutable tags refuse to move a tag. |
| 11 | [OP-102](https://github.com/luiki-dev/szop/issues/248) | — | **`szop-ci-plan`'s `DenyLogContents` also denies `logs:GetQueryResults`, `logs:GetLogRecord` and `logs:ListAnomalies`**: the results of a Logs Insights query the owner ran, a single log record, and an anomaly's sample lines, which `ReadOnlyAccess` grants through `logs:Get*` and by name. |
| 12 | The manifest and Prettier _(found while writing the spec)_ | Format the manifest in each release PR; ignore it | **`.release-please-manifest.json` is in `.prettierignore`, as a generated file.** release-please writes it compactly (`{".":"0.1.0"}`), which `prettier --check` rejects, so every release PR's `lint` job would fail. `CHANGELOG.md` is Markdown, which Prettier already skips; `package.json` keeps its formatting, since release-please keeps the file's indentation. |
| 13 | `1.0.0` | — | **As [ADR 0009](0009-git-workflow.md) planned:** a commit with the footer `Release-As: 1.0.0` on a branch, merged through a PR, makes the release PR propose `1.0.0`. An empty commit (`git commit --allow-empty`) is enough. |

## Settled while building

- **The actions:** `googleapis/release-please-action` **v5.0.0** (2026-04-22; its only breaking change from v4, which the trial used, is the Node 24 runtime) and `actions/create-github-app-token` **v3.2.0** (2026-05-12; v3.3.0 was 11 days old, under the two-week rule). Both pinned by commit hash.
- **The App's client ID, not its App ID:** `create-github-app-token` v3.2.0 deprecates `app-id` for `client-id`, so the variable in `release` is **`RELEASE_APP_CLIENT_ID`** (the `Iv23…` value on the App's settings page), not the `RELEASE_APP_ID` the spec named.
- **release-please's outputs** for the root package are `release_created` (set, as `true`, only when a release was just published), `tag_name`, `version` and `sha`; read in the action's source. On an ordinary push `release_created` is unset, so `build` and `publish` are skipped.
- **Dependabot's login in `.github/release.yml` is `dependabot[bot]`.** Checked with GitHub's notes API (`POST /repos/luiki-dev/szop/releases/generate-notes`, which creates nothing): with `dependabot`, the first release's preview still listed Dependabot's eight PRs; with `dependabot[bot]` it listed none, and 44 PRs remained. The API reads `release.yml` from the target branch.
- **One Dependabot line stays in `v0.1.0`:** GitHub's notes end with a "New Contributors" section, which `release.yml` cannot exclude, and it names `@dependabot[bot]`'s first PR. It appears in the first release only.
- **`ReadOnlyAccess` is still v190** (2026-09-24), read from the public mirror of AWS managed policies, [z0ph/MAMIP](https://github.com/z0ph/MAMIP), since `docs.aws.amazon.com` was out of the session's reach. Its `logs:` grants are `logs:Describe*`, `logs:Get*`, `logs:FilterLogEvents`, `logs:StartQuery`, `logs:StartLiveTail`, `logs:TestMetricFilter` and a list of `List*` actions. The service authorization reference for CloudWatch Logs (`servicereference.us-east-1.amazonaws.com`) lists every action; of those granted, the ones that return log contents are the four already denied, `GetQueryResults`, `GetLogRecord` and `ListAnomalies` (anomalies carry sample log lines). The others return configuration or field names. `logs:Unmask` is not granted.
- **`ecr:DescribeRepositories`** is in the release role too: `publish` reads the registry's address for `docker login` from it, as `demo-up` does.
- **Re-tagging** reads the commit image's manifest with `batch-get-image`, accepting the Docker and OCI manifest and index media types, and writes it back with `put-image` under the version tag, with its media type, so the digest stays the same and no layer is pulled.
- **`publish` is safe to re-run:** it first looks for the version tag and, if a run already wrote it, does nothing but the summary; `put-image` on an existing immutable tag would otherwise fail and leave a finished release red (found by the final review).
- **The manifest and Prettier:** `pnpm format:check` failed on a compact manifest without the ignore entry and passed with it.

## Consequences

- Merging a release PR tags the version, publishes the GitHub Release and pushes `szop:<version>` with no further step; the owner chooses when, by merging.
- Release notes list PRs by title. A PR title that reads well in the notes matters a little more now; it already becomes the merge commit's message.
- A PR the notes do not need gets `skip-changelog` by hand; a forgotten label means one line too many, fixable until the release PR is merged.
- The App's private key is the setup's only long-lived secret. Rotating it is generating a new key in the App's settings, storing it in `release` and deleting the old one.
- Every release PR changes `package.json`, so CI runs in full on it; it passes `lint` because the manifest is ignored by Prettier.
- Released images are never expired, by the `*.*.*` pattern; any tag with two dots would be kept too, and no such tag is pushed but versions.
- The release image is built from the release commit and is not demo-checked; the commit changes only the version and the changelog against code that was checked ([OP-019](https://github.com/luiki-dev/szop/issues/77), C10).
- `1.0.0` is cut with a `Release-As: 1.0.0` footer when the MVP is done.
