# ADR 0009 — Git workflow

- **Status:** Accepted — decision 1 revisited and confirmed by [ADR 0010](0010-ci-cd.md) (the repository stays public); the CI/CD items of the consequences answered by ADR 0010; the definition of done restated in decision 8 is kept in `docs/development/definition-of-done.md` ([ADR 0011](0011-design-sanity-check-follow-ups.md), decision 3); decision 13 refined by ADR 0011, decision 8 (creating `v*` tags is restricted, and only the release GitHub App bypasses the tag ruleset)
- **Date:** 2026-09-28
- **Completes:** [ADR 0006](0006-git-workflow-topic.md) (the git workflow topic itself) and the open point of [ADR 0008](0008-hosting.md), decision 13 (the versioning scheme behind version tags)

## Context

The git workflow is the fourth foundation topic of [ADR 0004](0004-implementation-process.md), added by [ADR 0006](0006-git-workflow-topic.md) right before CI/CD. Like every foundation topic, it settles direction and constraints only. The tooling it needs (commitlint, release-please, required status checks) is set up in the roadmap phases that introduce it.

The starting point:

- **One human contributor, and Claude Code as the main author.** ADR 0006 named the pull request (PR) as the place where the owner reviews Claude's work before it reaches `main`.
- **Claude Code works through the owner's GitHub account** (`gh` is logged in as the owner), so every PR is authored by the owner. Commits carry a `Co-Authored-By` trailer, which GitHub shows as a second author.
- **The repository is on GitHub, private, on the Free plan.** Branch protection rules and rulesets are **not enforced on private repositories** on that plan; they are on public ones, or with GitHub Pro.
- **A pre-commit hook** (husky with lint-staged) formats and lints staged files; type checks and tests belong to CI ([ADR 0005](0005-development-environment.md), decision 13).
- **The work is split into roadmap phases**, each a vertical slice with its own spec and plan, and each finished when it meets the shared definition of done ([ADR 0004](0004-implementation-process.md), decisions 5–8).
- **There is one environment, an on-demand demo** that exists for a few hours and is created from any image, identified by the commit hash ([ADR 0008](0008-hosting.md), decisions 1, 13 and 29). Nothing stays deployed between sessions, so **tagging a version and deploying are separate acts**: a version marks a milestone in the code, it does not replace what is running.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|-------|--------------------|------------------------|
| 1 | Repository visibility | Public; private, with the rules kept by convention; private with GitHub Pro | **Public.** Rulesets are then enforced for free, and the repository serves as the portfolio piece the demo already is (ADR 0008). GitHub Actions minutes are also unlimited for public repositories. Secrets never appear in git by design (ADR 0008, decision 22). The author email of every commit, past ones included, becomes public with the history. Staying private would leave every rule unenforced; GitHub Pro costs about $4 a month to keep private what has no reason to be. |
| 2 | Branching model | GitHub flow; trunk-based development with direct commits to `main`; git flow | **GitHub flow.** `main` is the only long-lived branch and is always releasable. Every change is made on a short-lived branch and reaches `main` only through a PR. Direct commits to `main` are how teams with strong automated tests and pairing work, but they remove the PR as the review point ADR 0006 asked for. Git flow's long-lived `develop`, `release/*` and `hotfix/*` branches serve products that ship numbered releases to several supported versions; with one ephemeral environment they add merges without a purpose. |
| 3 | Unit of a branch and a PR | One per roadmap phase; one per plan task; a long-lived phase branch with a PR per task into it | **One branch and one PR per phase.** The phase is the unit of the definition of done, and the superpowers workflow is built around it (brainstorm, spec, plan, execute on a branch, then `finishing-a-development-branch` opens the PR). **Commits follow the plan's tasks**, so a large PR can be reviewed commit by commit, and **the roadmap keeps phases small enough to review**: a phase that looks too big is split on the roadmap, not into several PRs. Reviews lose effectiveness past a few hundred lines, which argues for a PR per task, but that means about ten PRs and CI runs per phase and half-built features on `main` between them. A phase branch collecting task PRs is a small git flow in disguise. **Changes outside phases** (a foundation ADR, a typo fix, a dependency bump) get their own small branch and PR. |
| 4 | Branch names | Free-form; `type/short-description` | **`type/short-description`**, using the Conventional Commits types of decision 9: `feat/shopping-lists`, `docs/adr-0009-git-workflow`, `chore/bump-vitest`. The name says what kind of change the branch holds before it is opened. |
| 5 | Where a branch is worked on | A plain branch in the main checkout; a git worktree per branch | **A plain branch in the main checkout.** A worktree (a second working directory of the same repository) lets two branches be checked out at once, which the superpowers workflow offers. Each one needs its own `pnpm install` and `.env`, and its own Docker Compose ports to avoid clashes. With one phase at a time, that buys nothing. Worktrees remain an option for parallel work. |
| 6 | Merge strategy | Merge commit; squash merge; rebase merge | **Merge commit.** The branch's commits land in `main` unchanged, plus one merge commit that marks the phase. `git log --first-parent` reads as one line per phase, `git bisect` can narrow a bug down to a single task, and the branch's commit hashes survive, so an image tagged with a branch commit's hash points at a commit in `main` afterwards. The history is a graph, not a line, and review-fix commits stay in it. A squash merge keeps `main` tidy but leaves the task-by-task history only in the PR on GitHub, stops `git bisect` at "somewhere in this phase" and gives the result a new hash. A rebase merge keeps the task commits in a line but gives each a new hash and marks neither where a phase starts nor where it ends. The other two methods are turned off (decision 14). |
| 7 | Who approves a PR | The owner's merge is the approval; a separate machine account for Claude, with a required approving review; a GitHub App for Claude | **The owner's merge is the approval.** GitHub does not let an author approve their own PR, and every PR is authored by the owner's account, so a required approving review would block every merge or be bypassed every time. The owner reads the PR, comments, and merges; **Claude opens PRs and addresses review comments but never merges one**, a rule kept by `CLAUDE.md`, not by GitHub. A machine account for Claude would let GitHub enforce the review, at the cost of a second account, its credentials in WSL and commits authored by the bot. A GitHub App gives the same with short-lived tokens, but suits Claude working inside GitHub (in Actions), not a local Claude Code. Either can be added later. |
| 8 | What a PR holds and when it is merged | — | **A phase's spec, plan and code go on its branch**, so the PR shows the design next to its implementation. **Claude reviews its own work before opening the PR** (the superpowers code review step), so the owner's review starts from cleaner code. **A PR template** (`.github/pull_request_template.md`) asks for what and why, links to the roadmap phase, spec, plan, requirement IDs and ADRs, how the change was tested, and the definition-of-done checklist. **A phase PR is merged once the definition of done is met on its branch**: the tests pass, CI is green, the docs are updated (roadmap status included), and the check of ADR 0008, decision 29 was run from the branch's image. |
| 9 | Commit messages | Conventional Commits checked by commitlint; plain imperative subjects following the classic git guidelines; Conventional Commits by convention only | **Conventional Commits, checked by commitlint.** Every subject has the form `type(scope): description`. The types are `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`, `ci` and `chore`; the scope is optional and names a workspace or area (`web`, `api`, `shared`, `infra`, `adr`, `deps`); `!` or a `BREAKING CHANGE:` footer marks a breaking change. It is the most widespread convention, and release tools read it (decision 11). **commitlint** with `@commitlint/config-conventional` checks every message in husky's `commit-msg` hook, and CI checks the PR title, since it becomes the merge commit's message (decision 14). The classic rules still apply: an imperative subject, a body explaining *why* when it is not obvious, and the co-author trailer. Plain subjects give tools nothing to read; a convention nobody checks drifts. Existing commits keep their plain subjects. |
| 10 | Versioning scheme | Semantic Versioning (SemVer); Calendar Versioning (CalVer); commit hashes only | **SemVer, one version for the whole repository**, `0.x` until the MVP is complete. A `feat` raises MINOR, a `fix` raises PATCH, and while in `0.x` a breaking change also raises only MINOR. **`1.0.0` marks the finished MVP.** SemVer was designed for code others depend on, where MAJOR means "this breaks you"; Szop has no outside consumers, so the numbers mean what this decision says, which is how most applications use SemVer. `apps/web`, `apps/api` and `packages/shared` ship together in one image and are never published, so they share the version. CalVer (`2026.10.0`) says when, not what. Commit hashes alone already identify every image (ADR 0008, decision 13) but mark no milestones. |
| 11 | How versions are cut | release-please; semantic-release; tags created by hand | **release-please**, a GitHub Action from Google. It reads the Conventional Commits on `main` and keeps an open **release PR** with the next version and the `CHANGELOG.md` entry. **Merging the release PR is the release:** it creates the `vX.Y.Z` tag and a GitHub Release, and the tag gives the image its version (ADR 0008, decision 13). The owner merges it when a milestone is worth marking, typically after a phase; **the first release, `v0.1.0`, is expected after the walking skeleton.** The release is a deliberate human step with automated bookkeeping. semantic-release releases automatically on every merge with a `feat` or `fix`, so the owner never chooses when, and it is more at home in libraries. Tags made by hand need no tool, but every number is chosen manually and the commit convention drives nothing. |
| 12 | Protection mechanism | Rulesets; classic branch protection rules | **Rulesets**, GitHub's newer mechanism. They can target tags as well as branches, several can apply at once, their bypass list is explicit, and they can be exported as JSON. Classic branch protection covers branches only and is the older way. |
| 13 | Rules | — | **Ruleset for `main`:** deletion and force pushes are blocked; a PR is required, with **no required approvals** (decision 7), **all review conversations resolved** (so no comment is silently skipped) and **merge commit as the only allowed method**. **Required status checks, with the branch up to date with `main`**, are added by the CI/CD phase, since until CI exists there are no checks to require: what gets merged is then exactly what CI tested. **The bypass list is empty**: the rules apply to the owner too, who as admin can still edit the ruleset in an emergency, visibly. **Ruleset for `v*` tags:** a tag cannot be deleted or moved once it exists, matching ECR's immutable image tags (ADR 0008, decision 13). |
| 14 | Repository settings | — | **Merge commits only**, squash and rebase merges off; the merge commit message is **the PR title**, so it reads `feat(lists): add shopping lists (#12)` rather than GitHub's default "Merge pull request #12 from…". **Head branches are deleted automatically** after a merge, and GitHub **always suggests updating a PR branch** when `main` has moved. Auto-merge stays off, since the owner's merge is the approval. **Secret scanning with push protection** and **Dependabot alerts** are on: free for public repositories, and a safety net for secrets that must never reach git. **Dependabot version update PRs belong to CI/CD.** **The roadmap is the tracker:** GitHub Issues and Projects are not part of the process. |
| 15 | How settings are managed | By hand, documented; the Terraform GitHub provider; a script calling the GitHub API | **By hand in GitHub's web interface, documented in `docs/development/github-settings.md`** with every setting, its value, where it lives in GitHub and the decision behind it. The Terraform GitHub provider would fit ADR 0008, but means more infrastructure as code (IaC) and a token with admin rights for about ten checkboxes. A script is a smaller version of the same. |
| 16 | Rollout | — | **This ADR is the first change to follow the workflow**, on the branch `docs/adr-0009-git-workflow`, together with the PR template and the new docs. While its PR is open, the repository is made public and the settings are applied following `github-settings.md`; the owner's merge of that PR is the first under the new ruleset. **The development environment phase** adds commitlint and the `commit-msg` hook, since both need `package.json` and husky. **The CI/CD topic and phase** add the required status checks, the PR title check and release-please, and build images from version tags. |
| 17 | Documentation | — | **`docs/development/git-workflow.md`** is the day-to-day guide: branch, commit, PR, review, merge and release, with commands, examples and the reason for each step. **`docs/development/github-settings.md`** lists the GitHub settings (decision 15). **`CLAUDE.md`** holds the rules Claude follows and links to both. This ADR explains *why*; the guide explains *how*. |
| 18 | Deliberately left out | — | **Signed commits:** they prove which key made a commit, which matters when many people push; here one person pushes from one machine. **Required linear history:** it contradicts merge commits (decision 6). **Required approving reviews and a machine account** (decision 7). **Git flow and a PR per task** (decisions 2 and 3). **Worktrees by default** (decision 5). **Settings as code** (decision 15). **GitHub Issues and Projects for planning** (decision 14). Each can be added when a real need appears. |

## Consequences

- **Direct commits to `main` end with this ADR's merge.** The interim rule of ADR 0006 ("until the git workflow ADR exists, changes are committed directly to `main`") no longer applies.
- **`CLAUDE.md` gains the git workflow rules** for Claude: never commit to `main`, one branch per change, Conventional Commits, fill in the PR template, never merge a PR.
- **The development environment phase** adds commitlint with `@commitlint/config-conventional` and husky's `commit-msg` hook. Until then, commit messages follow the convention without a check.
- **The CI/CD topic must provide:** the required status checks and the "up to date with `main`" rule (decision 13); a check of the PR title against Conventional Commits; the release-please workflow, configured so that a breaking change in `0.x` raises only MINOR (its `bump-minor-pre-major` option) and `1.0.0` is set explicitly when the MVP is done (a `Release-As: 1.0.0` footer); building the versioned image from a version tag; and Dependabot version updates. **One known pitfall:** PRs created with the workflow's default `GITHUB_TOKEN` do not trigger other workflows, so release-please's PR would never get its required checks; it needs a GitHub App token or a personal access token.
- **Keeping a branch up to date** means merging `main` into it (GitHub's "Update branch" button does this), not rebasing it, so the hashes of commits whose images were checked stay valid.
- **The roadmap sizes phases** so that each phase's PR stays reviewable commit by commit.
- ADR 0008, decision 13 is completed: version tags follow decision 10 and are created as decision 11 describes.
