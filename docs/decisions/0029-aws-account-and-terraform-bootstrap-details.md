# ADR 0029 — AWS account and Terraform bootstrap details

- **Status:** ✅ Accepted
- **Date:** 2026-10-15
- **Completes:** [ADR 0008](0008-hosting.md), decisions 7 (bootstrap's own state, see decision 4), 25 (the account and the people's access, see decisions 1 to 3), 26 (the budget, see decision 8) and 30 (installing Terraform and tflint, see decisions 9 and 11); [ADR 0010](0010-ci-cd.md), decisions 7 (the `infra` job, see decisions 11 and 12) and 18 (the `terraform` ecosystem, see decision 13)

## Context

[PH-09](../roadmap.md#ph-09-aws-account-and-terraform-bootstrap) gives Szop its AWS account, managed with Terraform. [ADR 0008](0008-hosting.md) set the direction: Terraform in three root modules (decisions 4 to 6), the state in an S3 bucket created by `infra/bootstrap` with S3's native lock (decision 7), Frankfurt (decision 8), people signing in through IAM Identity Center with no long-lived keys (decision 25), budget alerts and default tags (decision 26), the Terraform CLI, the AWS CLI and the Session Manager plugin (decision 30), and a runbook (decision 31). [ADR 0010](0010-ci-cd.md) planned the `infra` job with no AWS credentials (decision 7) and Dependabot's `terraform` ecosystem (decision 18). Those left the details to the phase: which account, how bootstrap's state is kept, the bucket's name and protections, the budget's settings, how the tools are installed and pinned, and how the checks run.

The owner already had an AWS account, used only for learning, on the Free plan, with $169 in credits, an IAM user whose access key the CLI used, and a few leftovers from earlier experiments. This ADR records the brainstorm's decisions, with what was settled while building them.

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|-------|--------------------|------------------------|
| 1 | Which account | A brand-new account; a member account in an AWS Organization; the owner's existing account | **The owner's existing account, which becomes Szop's own.** It ran nothing else, so Szop is the only thing in it, as ADR 0008 asks. The runbook starts with a **clean-up audit**: old IAM users, their access keys and roles, resources left in any region, access keys on the root user. A member account adds an organization structure one person does not need, and a new account one more root user to secure. <br>**Settled while building:** the bill by service turned out to be the better inventory than Tag Editor, which misses some resource types: it found a leftover AWS WAF web ACL (about $5 a month), deleted in the audit. The runbook names the bill first. |
| 2 | Free or Paid plan | Stay on the Free plan; upgrade to the Paid plan | **Paid.** The Free plan closes the account after six months or when the credits run out, which does not fit permanent `infra/base` resources or a domain registered for a year. IAM Identity Center's organization instance, the one that gives people access to AWS accounts, needs AWS Organizations, and creating an organization upgrades a Free plan to Paid on its own; the runbook says so before the click. The Paid plan has no fixed fee; the remaining credits keep applying for up to 12 months from sign-up, and the budget alerts (decision 8) take over from the Free plan's hard cap. |
| 3 | People's access to AWS | IAM Identity Center (ADR 0008, decision 25); an IAM user with a console password, MFA, no access keys and `aws login` | **IAM Identity Center, as decided.** One user with MFA at every sign-in, one permission set `AdministratorAccess` with an 8-hour session, and an SSO profile `szop` for the CLI and Terraform. `aws login` (AWS CLI v2, late 2025) gives an IAM user short-lived credentials too, without an organization, but Identity Center is the pattern workplaces use, and the Paid plan is needed anyway. **The old IAM users and every stored key are deleted only after the `szop` profile works**, so the owner is never locked out; afterwards a command without a profile fails instead of falling back to a key. Every command uses `AWS_PROFILE=szop`; the profile is not written into the Terraform code, because CI authenticates without profiles (PH-11). |
| 4 | Bootstrap's own state | Kept local for good; moved into the bucket after the first apply | **Moved into the bucket** under `bootstrap/terraform.tfstate`, after a first apply with local state. Bootstrap's state is then versioned and kept off the owner's machine. The move happens on the phase's branch: the module is committed without `backend.tf`, applied, then `backend.tf` is added and the owner runs `terraform init -migrate-state`. Destroying bootstrap means moving the state back first: a documented, one-off step in the runbook. |
| 5 | The bucket's name | A fixed name with a random suffix; a name with the account ID; a name kept out of git (partial backend configuration) | **`szop-tfstate-ntrtcr`**, written in every `backend` block. A `backend` block cannot use variables, so the name must be a literal somewhere; committed, `terraform init` works unchanged on the owner's machine and in CI. The suffix keeps the global name free and reveals nothing; the bucket's policy and IAM protect it, not its name. A partial configuration would add `-backend-config` to every `init`, in the docs and the workflows. |
| 6 | The alert address and the account ID | Committed in the code; a gitignored `terraform.tfvars` | **A gitignored `terraform.tfvars`**, with a committed `terraform.tfvars.example`. Bootstrap is applied only from the owner's machine, so CI never needs the values, and the address may differ from the one in the commits. Both variables are validated (12 digits; an address with one `@`), so a wrong value stops the run before it reaches AWS, and the runbook's first `plan` runs with `-input=false`, so a missing file stops it too instead of Terraform asking for the values. The account ID feeds **`allowed_account_ids`**, so Terraform refuses to run against any other account. |
| 7 | The bucket's protections | — | **Versioning; the public access block; `BucketOwnerEnforced` ownership; SSE-S3 encryption; a policy that denies requests without TLS; a lifecycle rule; `prevent_destroy`; `force_destroy = false`.** The ownership and encryption settings are AWS's defaults since 2023, written out so the code explains them and they cannot drift. A customer-managed KMS key would cost $1 a month and protect nothing more here. The lifecycle rule expires old versions after 90 days and removes the delete markers they leave, since every run's `.tflock` file leaves both behind, and aborts unfinished uploads after 7 days. `prevent_destroy` stops a stray `terraform destroy` from deleting the bucket every state lives in. |
| 8 | The budget | — | **One monthly cost budget, `szop-monthly`, limit $10, with two email alerts: forecast above $5 and actual above $10**, the thresholds of ADR 0008, decision 26. **Credits are excluded** (`include_credit = false`): by default AWS Budgets counts costs after credits, so it would see $0 and stay silent while a forgotten demo used them up. <br>**Settled while building:** the budget is the only billing alert. The planned Free Tier usage alerts and CloudWatch billing alerts were dropped: the first end with the Free plan, the second serve only CloudWatch billing alarms, cannot be turned off again, and were not offered on the account's preferences page. |
| 9 | Installing Terraform and pinning its version | tenv with `.terraform-version`; HashiCorp's apt repository, pinned | **tenv, with `.terraform-version` at the repository root** (1.16.5). It is the pattern of `nvm` and `.nvmrc`: tenv reads the file and installs the version, CI reads the same file, and an upgrade is one line. tenv is the maintained successor of tfenv. `required_version = "~> 1.16"` in the code keeps a compatible range. The apt package would leave the version in the setup guide and in `ci.yml`, kept in step by hand. |
| 10 | A security scanner | Add one now (Trivy, Checkov); defer it; none | **Deferred**, as [OP-091](https://github.com/luiki-dev/szop/issues/201) under PH-11. Bootstrap holds one bucket and one budget, whose protections are written out and reviewed in this phase; a scanner earns its keep once IAM policies (PH-11), security groups, the load balancer and RDS (PH-12) arrive. The phase keeps to one concept. |
| 11 | How tflint is installed and configured | — | **A checksum-verified release binary, on the owner's machine and in CI**, as actionlint is in CI. `infra/.tflint.hcl` enables the bundled `terraform` ruleset with its `recommended` preset and the `aws` ruleset (`tflint-ruleset-aws`), pinned to a version; `tflint --init` downloads the plugin and checks its signature. CI passes `GITHUB_TOKEN` only so the download is not rate-limited. <br>**Settled while building:** a failed download (GitHub's API answered 500 on the owner's first run) now ends with its own `FAIL:` line, and the tflint page covers retrying and the anonymous rate limit. |
| 12 | Where the checks run | Separate commands in `ci.yml` and the docs; one script | **One script, `scripts/check-infra.sh`**, run as `pnpm check:infra` and by the `infra` job, as `check:image` is for the image: `terraform fmt -check`, `terraform init -backend=false` and `terraform validate` for every module, then tflint, with no AWS access. `pnpm infra:fmt` rewrites formatting, and the pre-commit hook runs `terraform fmt` on staged `.tf` files. <br>**Settled while building:** the script gives each module its own Terraform data directory in `~/.cache/szop/terraform-check/`. Once bootstrap's `.terraform/` was initialized with its S3 backend, `init -backend=false` in it reloaded the backend and asked for AWS credentials; CI, on a clean checkout, never saw this. |
| 13 | Dependabot's `terraform` entry | One directory per module; a glob | **`directories: ["/infra/*"]`**, so `base` and `demo` are covered when they arrive. Weekly on Monday, the 7-day cooldown, minor and patch updates grouped, `build(deps): …`. **AWS provider majors are not ignored:** they come as separate PRs, and unlike Node's or PostgreSQL's they change nothing else with them. The lock file starts at provider 6.68.0, the newest release a week old; Dependabot proposes the next ones. Terraform itself, tflint and its ruleset are not seen by Dependabot and are bumped by hand. |

## Consequences

- **The owner's steps, done in PH-09:** the account's clean-up audit, root MFA, IAM Identity Center (the account is now on the Paid plan) and the `szop` profile; the tools installed through the setup guide; bootstrap applied and its state moved. All are in the [runbook](../operations/demo-environment.md) and the [setup guide](../development/setup.md#8-terraform-tflint-and-the-aws-cli).
- **Every later module** copies bootstrap's `backend.tf` with its own `key`, and uses the same `providers.tf` pattern with its own `group` tag.
- **Manual bumps:** Terraform (`.terraform-version`), tflint (`TFLINT_VERSION` and `TFLINT_SHA256` in `ci.yml` and the setup guide) and the AWS ruleset (`infra/.tflint.hcl`), each at least 7 days old, as the [Terraform](../development/tools/terraform.md#updating) and [tflint](../development/tools/tflint.md#updating) pages describe.
- **Open points:** [OP-091](https://github.com/luiki-dev/szop/issues/201), a security scanner for the Terraform code, under PH-11; [OP-092](https://github.com/luiki-dev/szop/issues/202), what the domain serves while no demo runs, under PH-10.
- **A PR touching only `infra/` also runs the code jobs**, since change detection counts every non-Markdown file as code ([ADR 0018](0018-ci-details.md), decision 2). Left as it is: it costs CI minutes, not correctness.
