# ADR 0007 — Testing strategy

- **Status:** ✅ Accepted — decisions 6 and 15 completed by [ADR 0008](0008-hosting.md) (load testing left out; the API serves the SPA, so the E2E environment is one process); CI's PostgreSQL service, Playwright browsers and the storage of failed runs' traces provided by [ADR 0010](0010-ci-cd.md); decisions 5 and 6 extended by [ADR 0013](0013-visual-design.md) (a Firefox desktop project; axe's WCAG 2.2 AA rule sets in light and dark; journeys fail on a CSP violation)
- **Date:** 2026-09-27
- **Refines:** decision 7 of [ADR 0004](0004-implementation-process.md) (what "the tests pass" means in the definition of done)

## Context

The testing strategy is the second foundation topic of [ADR 0004](0004-implementation-process.md), after the development environment ([ADR 0005](0005-development-environment.md)). Like every foundation topic, it settles direction and constraints only. The configuration and the first tests are written in the roadmap phases that set up the environment and build the walking skeleton.

The starting point:

- **Claude Code writes most of the code** and the owner reviews it. Tests are a large part of how the owner knows the code works without reading every line.
- **The owner's background** is backend unit testing with JUnit and mocks, plus first steps with pytest and Vitest. Integration tests against a real database, HTTP-level API tests, component tests and end-to-end (E2E) browser tests are new ground.
- **The architecture already helps testing** ([architecture.md](../architecture/architecture.md)): services receive their dependencies (database client, email sender, clock) explicitly, the API is layered into routes → service → repository, and the shared Zod schemas and pure domain rules live in `packages/shared`.
- **ADR 0005 left slots for this topic:** where test databases come from, and which test extensions the editor recommends. It also keeps tests out of the pre-commit hook: they belong to CI.
- **The app is used on phones in stores** and on desktops for planning ([functional requirements](../requirements/functional-requirements.md)).

## Decisions

| # | Topic | Options considered | Decision and reasoning |
|---|-------|--------------------|------------------------|
| 1 | What the tests are for | A safety net for reviewing Claude's code; a living specification traceable to requirement IDs; a learning vehicle; a balanced, typical mix | **A safety net, and a learning vehicle.** Tests should give real confidence that the app works, so review can focus on behavior and tests. And since learning is a goal of the project, a kind of test may earn its place because it is worth learning, not only because a project this size strictly needs it. |
| 2 | Shape of the test suite | Classic test pyramid (many unit tests with mocked collaborators); integration-heavy "testing trophy"; service tests with the database faked in memory | **Integration-heavy (testing trophy).** Pure logic gets unit tests. Most tests are **API tests**: real HTTP requests through routes → service → repository into a **real PostgreSQL**. Only the edges (email, clock) are faked. The frontend is tested at the component and page level with the network faked. A few E2E journeys sit on top. A pyramid with mocked repositories tests assumptions about the database rather than the database: queries, constraints, cascades ([CAT-3](../requirements/functional-requirements.md#cat-3)) and transactions go untested, and tests that mirror the code's structure break on every refactoring. An in-memory fake database has the same blind spots plus a second implementation to keep in step with PostgreSQL. |
| 3 | When tests are written | Test-driven development (TDD) everywhere; TDD for logic and test-after for UI; test-after everywhere | **TDD for domain rules, services and API routes; test-after for components and pages, in the same phase.** TDD pays off most where the rules are, and it is the superpowers workflow's default. Test-first for UI whose shape is still settling produces tests that are rewritten with the markup. Test-after everywhere tends to produce tests confirming what the code does rather than what it should do. **Every bug fix starts with a failing test** that reproduces it. |
| 4 | E2E scope | Smoke tests only; one journey per use case; broad E2E coverage | **One E2E journey per use case** ([UC-1](../requirements/functional-requirements.md#uc-1-first-visit-as-a-guest) … [UC-14](../requirements/functional-requirements.md#uc-14-delete-an-account)), written in the phase that completes the use case: roughly 10–15 tests in total. They read like the requirements and prove the pieces work together. Edge cases and error paths stay in faster, lower layers. Smoke tests alone leave the main journeys unproven; broad E2E coverage is slow and fragile (the "ice-cream cone" anti-pattern). |
| 5 | E2E viewports | Desktop only; desktop and phone | **Every journey runs twice: desktop Chromium and an emulated Android phone (Pixel, Chromium).** The in-store scenario ([UC-3](../requirements/functional-requirements.md#uc-3-shop-in-a-store)) happens on a phone. A WebKit (Safari engine) project can be added if Safari-specific bugs appear. |
| 6 | Optional kinds of testing | Automated accessibility checks; visual regression; mutation testing; load testing | **Accessibility checks and mutation testing are in.** axe-core checks every page the E2E journeys visit (missing labels, low contrast and the like): cheap, and it finds real bugs. Mutation testing measures whether tests actually check anything, which is a good way to judge tests Claude wrote (see decision 19). **Visual regression is out:** its screenshot baselines need upkeep, and fonts render slightly differently locally and in CI. **Load testing is left to the hosting topic**, where there is something real to load. |
| 7 | Property-based testing | Example-based tests only; property-based tests where rules are general | **fast-check property tests for the domain rules**, in particular ordering ([ORD](../requirements/functional-requirements.md#list-display-and-ordering-ord)): generate hundreds of random lists and category trees and check that the rules always hold, for example "a parent category always comes before its children". Hand-picked examples miss the odd cases; generated ones find them. |
| 8 | Test runner | Vitest; Jest | **Vitest** for unit, API and component tests. It shares Vite's configuration and handles ESM and TypeScript natively; Jest's ESM support is still awkward. One root Vitest config defines a project per package. |
| 9 | Where component tests run | jsdom (a simulated DOM in Node); Vitest Browser Mode (a real browser) | **jsdom.** It is the most common setup and what nearly all tutorials and the Testing Library documentation assume, which matters while the stack is new. It is fast. It has no layout engine and lacks a few browser APIs (these need small polyfills). Browser Mode is more realistic and shares Playwright's locator style, but is newer, with fewer examples, and starts more slowly. The E2E journeys already cover realism in a real browser. Browser Mode can be adopted later with a new ADR. |
| 10 | Component test library and network | Testing Library with Mock Service Worker (MSW); mocking the API client module | **Testing Library** (with `user-event` and the `jest-dom` matchers) renders components and finds elements the way a user does: by role, label and text. **MSW** intercepts requests at the network level, so the real API client, TanStack Query hooks and forms run unchanged. Mocking the API client module would skip exactly that code. MSW handler responses are typed with the shared Zod schemas, so a fake that drifts from the contract fails the type check. |
| 11 | E2E tool | Playwright; Cypress | **Playwright**, with **@axe-core/playwright** for the accessibility checks. It runs Chromium, Firefox and WebKit, emulates phones, parallelizes for free and has a trace viewer for debugging failures. Cypress is Chromium-first and puts parallel runs behind a paid service. |
| 12 | Test database | Reuse the Docker Compose PostgreSQL; Testcontainers; PGlite (PostgreSQL compiled to WebAssembly) | **The Docker Compose PostgreSQL**, never the development database. Before a run, a setup step creates a **template database** and runs the migrations on it once. Each Vitest worker gets its own database copied from it (`CREATE DATABASE … TEMPLATE`, a fast file-level clone), so test files run in parallel. In CI, PostgreSQL runs as a service container, with no change to the test code. If the container is not running, the tests stop with a clear message saying so. Testcontainers needs no manual start and isolates fully, but adds a library, a few seconds per run, and hides the database behind code. PGlite is fast and needs no Docker, but it is not the real server (one connection, differing behavior), which defeats decision 2. |
| 13 | Isolation between tests | Roll back a transaction after each test; empty the tables (`TRUNCATE`) | **`TRUNCATE` the tables between tests.** It works whatever the code under test does. Rollback is faster, but services open their own transactions and Better Auth runs its own queries, so an outer transaction would need savepoints threaded through everything. The exact mechanism is settled in the setup phase. |
| 14 | Fakes and test data in API tests | Mocking modules; fakes passed in as dependencies. SQL fixtures; helpers using real code paths | **Tests build the app with the same `buildApp(deps)` function as production**, passing the worker's database, a **recording email sender** (tests assert that an email was sent and read links from it) and a **controllable clock**. Time-based rules ([ACC-7](../requirements/functional-requirements.md#acc-7), [ACC-8](../requirements/functional-requirements.md#acc-8), the hourly `last_active_at` update) are tested by moving the clock forward and calling the cleanup function directly, never by waiting. Rate limits come from configuration: generous in tests, except in the tests of rate limiting. **Setup goes through real code paths:** helpers such as `signUpUser()` and `createList()` call the API or services, so a schema change breaks one helper rather than dozens of SQL fixture files. The real seed data is used. |
| 15 | E2E environment | Against the development servers; against a production build | **A production build:** the built SPA and the compiled API on one origin, with their own `szop_e2e` database, started by Playwright's `webServer` setting. How the SPA and the API share an origin follows the hosting decision. **Tests isolate themselves instead of resetting data:** each starts in a fresh browser context (a fresh guest) and registers users with unique emails, so journeys run in parallel and the database is reset once per run. **Emails** are read through a test `EmailSender`, never a real provider; whether it is a file "outbox" or a local mail catcher such as Mailpit is decided in the phase that delivers [ACC-2](../requirements/functional-requirements.md#acc-2). Time-dependent behavior is left to the API tests. |
| 16 | Rules for writing tests | — | **Test at the lowest layer that can prove the behavior:** an ordering edge case gets a domain test, a permission check an API test, not an E2E journey. **No `vi.mock` of our own modules:** fakes go in through explicit dependencies; module mocking couples tests to file structure and hides wiring bugs. **No snapshot tests of rendered markup:** it is too easy to "update the snapshot" without reading it; small inline snapshots of stable values (an error body) are fine. **Flaky tests are bugs:** fixed or deleted promptly. Playwright retries once in CI only to capture a trace, and a test that needed the retry shows as flaky in the report. |
| 17 | Where tests live | Next to the code; separate test folders | **Unit, API and component tests sit next to the code** (`service.ts` → `service.test.ts`), so a test is found and moved with its code. **E2E tests live in their own workspace package `e2e/`**, so their dependencies are declared (pnpm's strictness, ADR 0005), with one file per use case: `uc-03-shop-in-store.spec.ts`. |
| 18 | Scripts | — | `pnpm test` (all Vitest projects), `pnpm test:watch`, `pnpm test:e2e`, `pnpm test:coverage` and `pnpm test:mutation`. CI runs the same scripts as developers. Whether red tests block merging belongs to the git workflow and CI/CD topics. |
| 19 | Coverage and mutation score | A coverage threshold that fails the build; measured and reviewed, not gated | **Measured, not gated.** Coverage (Vitest's built-in V8 coverage) is reported without a threshold: a threshold rewards tests written to touch lines rather than to check behavior. **Mutation testing** with StrykerJS changes the code on purpose (flips `<` to `<=`) and checks that a test fails. It is slow, so it runs on `packages/shared` when a phase changes domain rules, and the surviving mutants are reviewed at the end of that phase. It is not run on every commit. |
| 20 | Definition of done | — | **"The tests pass" (ADR 0004, decision 7) means:** new behavior has tests at the right layer; a phase that completes a use case adds its E2E journey; bug fixes have regression tests; every suite is green. |
| 21 | Editor | — | The **Vitest** and **Playwright Test** VS Code extensions join the recommendations in `.vscode/extensions.json` (ADR 0005, decision 14). |
| 22 | Documentation of testing | — | **`docs/development/testing.md`** is the living guide to how Szop is tested *now*: the layers, the rules of decision 16, how to run each suite and how to write each kind of test. This ADR explains *why*; the guide explains *how*. Following ADR 0005 decision 15, each tool gets a page in `docs/development/tools/`: `vitest.md`, `testing-library.md`, `msw.md`, `playwright.md`, `fast-check.md`, `stryker.md`. |
| 23 | Deliberately left out | — | **Visual regression and load testing** (decision 6), **Vitest Browser Mode** (decision 9), **Testcontainers and PGlite** (decision 12), **a WebKit or Firefox E2E project** (decision 5), **a coverage threshold** (decision 19). Each can be added when a real need appears. |

## Consequences

- The development environment setup phase adds the test tooling and configuration, `docs/development/testing.md` and the tool pages. The walking skeleton phase writes the first test of each layer, including the first E2E journey on both viewports, and so tries out every decision above end to end.
- `CLAUDE.md` points to `docs/development/testing.md` once it exists, since its rules are instructions for whoever writes the code.
- `buildApp(deps)` and the explicit dependencies in [architecture.md](../architecture/architecture.md) are now a requirement for testing, not only a style: the API must be assembled from one function that accepts its database, email sender and clock.
- The CI/CD topic must provide a PostgreSQL service container, the Playwright browsers, and a place to keep Playwright traces and reports from failed runs.
- The hosting topic decides how the SPA and the API share one origin in production; the E2E environment follows it. It also revisits load testing.
- The phase that delivers [ACC-2](../requirements/functional-requirements.md#acc-2) decides how E2E tests read emails.
