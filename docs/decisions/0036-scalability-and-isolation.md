# ADR 0036 — Scalability and isolation

- **Status:** ✅ Accepted
- **Date:** 2026-10-19
- **Supersedes:** [ADR 0008](0008-hosting.md), decision 10, in part (one task, never more: two tasks from PH-37, up to four with autoscaling from PH-38; see decisions 1 and 13)
- **Refines:** [ADR 0008](0008-hosting.md), decisions 14 (migrations at startup run under a lock, see decision 2) and 32 (more than one instance and autoscaling are no longer left out, see decisions 1 and 13); [ADR 0012](0012-security-baseline.md), decision 15 (the rate-limit counters live in Redis, see decision 8); [ADR 0020](0020-database-details.md), decision 11 (the load balancer checks a liveness route, `/api/health` stays the readiness check, see decision 4)

## Context

The design assumed exactly one task: [ADR 0008](0008-hosting.md), decision 10 ran "one task, never more", decision 14 migrated at startup because "with exactly one instance nothing can race", and [ADR 0012](0012-security-baseline.md), decision 15 kept the rate-limit counters in memory for the same reason. The owner wants Szop built the way a scalable system is built, and running at least two tasks, so that the challenges this brings surface and can be learned from, though Szop will never be widely used. The owner also wants to know whether Szop's footprint in AWS lets another app share the account, each app going up and down, and moving elsewhere, on its own.

[PH-36](../roadmap.md#ph-36-scalability-and-isolation-analysis) analysed both before [PH-12c](../roadmap.md#ph-12c-app-on-ecs-and-rds) builds the ECS service and RDS. The analysis, with its options, three throwaway local checks and the day's prices, is [the scalability and isolation analysis](../audits/2026-10-19-scalability-and-isolation-analysis.md); its aspects S1–S15 and I1–I7 are referred to below. Its cost guides, set by the owner, were $0.50 per demo hour and $2 a month for the change as a whole, as guides, not cutoffs. The owner took its recommendations with three changes: the health check is split (decision 4), the event bus and the rate limits use Redis (decisions 6 to 8), and no isolation change is made now (decision 16).

## Decisions

| # | Topic | Options considered | Decision |
|---|---|---|---|
| 1 | How many tasks | One task (ADR 0008, decision 10); two fixed tasks; two, then autoscaling | **Two tasks, from [PH-37](../roadmap.md#ph-37-two-tasks), then autoscaling between two and four from [PH-38](../roadmap.md#ph-38-autoscaling).** No part of the architecture has to be rewired: every change is a layer added next to what exists, or a setting, and most land in phases not yet built, so they are built for several tasks from the start ([analysis, summary](../audits/2026-10-19-scalability-and-isolation-analysis.md#summary)). PH-12c still runs one task, with its deploys built the way two need (decisions 3 to 5). The extra cost is $0.037 per demo hour and nothing a month ([Costs](#costs)). |
| 2 | Migrations at startup (S1) | A PostgreSQL advisory lock around the check and the migration; a one-off ECS task per deploy; idempotent migrations without a lock | **A PostgreSQL advisory lock**, taken on a connection of its own before the migration check and released after the migration. The other tasks wait, then find nothing pending. Without it, two tasks that start together apply a data migration twice, silently, and the migration check of [ADR 0033](0033-app-ready-for-the-cloud-details.md), decision 3 does not notice ([check A](../audits/2026-10-19-scalability-and-isolation-analysis.md#check-a-two-migrators-at-once)). A one-off task is the better shape for long migrations, but needs a migrate-only entry point, `demo-up` steps and permissions; the lock keeps "the app migrates itself", which development, the tests and the demo rely on. Built in PH-37. |
| 3 | Deploys with two versions at once (S2) | Rolling deploys with backward-compatible migrations; stop-first deploys ([OP-043](https://github.com/luiki-dev/szop/issues/84)'s 0% / 100%); blue/green through CodeDeploy | **Rolling deploys at a minimum of 100% and a maximum of 200% healthy, the deployment circuit breaker without rollback, and migrations that are safe for the previous version (expand, then contract).** Old and new tasks serve side by side for a minute or two; a failed deploy is fixed forward, since a rollback would start the old version on a schema it refuses (ADR 0033, decision 3, kept for the branch switches it was made for). Stop-first takes the site down at every deploy; blue/green adds CodeDeploy for a demo. Built in PH-12c, whose OP-043 part changes accordingly; the rule goes into `drizzle.md` there, before PH-16's first table. |
| 4 | Health checks (S3) | One combined check, tuned; a liveness route for the load balancer and `/api/health` as the readiness check | **Split** *(the owner's choice)*: the load balancer checks a process-only liveness route; `/api/health` keeps checking the database and reporting the schema version, for `demo-up`'s wait and for people. During a database outage the tasks stay up, serve the SPA and answer API calls that need the database with an error, and their pools reconnect when it returns ([ADR 0020](0020-database-details.md), decision 12); a combined check would replace every task in a loop, which never brings the database back. RDS itself recovers the database. Built in PH-12c, with [OP-075](https://github.com/luiki-dev/szop/issues/87)'s grace period sized for decision 2's wait. |
| 5 | Shutdown and draining (S4) | ECS's default deregistration delay of 300 seconds; a short one | **A 30-second deregistration delay** on the target group, so a rolling deploy does not wait five minutes per batch for requests that last milliseconds; ECS takes a task out of the target group before it sends SIGTERM, which closes the gap [check C](../audits/2026-10-19-scalability-and-isolation-analysis.md#check-c-two-api-instances-behind-a-proxy) showed. **WebSocket clients reconnect and refetch the lists they watch** after a disconnect, since an open connection closes when its task stops. The delay in PH-12c, the reconnect in [PH-33](../roadmap.md#ph-33-live-updates). |
| 6 | Redis | PostgreSQL only (`LISTEN/NOTIFY`, counters in a table); ElastiCache Valkey; ElastiCache Serverless; ElastiCache Redis OSS on a node | **ElastiCache for Redis OSS, one `cache.t4g.micro` node** *(the owner's choice)*, in `infra/demo`'s private subnets, created and destroyed with the demo, with encryption in transit and an AUTH token; a Redis container in `compose.yaml` for development and CI. It serves decisions 7 and 8. PostgreSQL could carry both at no cost, and Valkey would cost $0.0144 an hour instead of $0.018, but the owner chose Redis OSS, the dedicated broker and store common at larger scale, as the thing to learn. It brings a new concept, so it has a phase of its own, [PH-39](../roadmap.md#ph-39-redis-in-the-stack), before PH-20, its first user ([ADR 0014](0014-roadmap.md), decision 6). |
| 7 | The event bus (S5) | PostgreSQL `LISTEN/NOTIFY` behind the bus; Redis publish/subscribe behind the bus; sticky sessions | **Redis publish/subscribe behind the in-process bus** *(the owner's choice)*: every task subscribes to the channel; a service publishes after its change commits; each task's WebSocket hub forwards what it hears to its own subscribers. Unlike `NOTIFY`, publishing is not part of the transaction, so an event can be lost if a task stops between the commit and the publish; the refetch on reconnect (decision 5) and the next change cover it, which live updates accept. Sticky sessions do not help: two people on one list may sit on different tasks. Built in PH-33. |
| 8 | The rate-limit counters (S6) | PostgreSQL stores; Redis for both limiters; counters in memory | **Redis for both limiters** *(the owner's choice)*: `@fastify/rate-limit`'s `redis` option, and Better Auth's `rateLimit.customStorage` over the same client. *(Claude's call:)* not Better Auth's `secondaryStorage`, which would also move sessions and verification values into Redis ([check B](../audits/2026-10-19-scalability-and-isolation-analysis.md#check-b-better-auths-state)); they stay in PostgreSQL. In memory, two processes allowed 6 requests against a limit of 4 (check B). Built in [PH-20](../roadmap.md#ph-20-quotas-and-rate-limits). |
| 9 | The cleanup job (S7) | A PostgreSQL try-lock per run; a scheduled task outside the API | **A try-lock per run** (`pg_try_advisory_lock`): the task that gets it cleans up, the others skip the round. A scheduled task outside the API would add a schedule, a role and permissions for nothing it does better. Built in [PH-31](../roadmap.md#ph-31-automatic-cleanup). |
| 10 | Request IDs (S11) | Fastify's default counter per process; IDs unique across tasks | **Unique across tasks:** the load balancer's `X-Amzn-Trace-Id` where present, a random UUID otherwise. With the default, two tasks both log `req-1`, `req-2`… for different requests (check C). Built in PH-37. |
| 11 | Database connections (S12) | A connection budget; RDS Proxy; a larger instance | **A pool of at most 5 connections per task, and a budget:** the worst case, every task doubled by a deploy at autoscaling's maximum, stays under about 80% of `max_connections`: 8 × (5 + 1, the lock's connection at startup) = 48. `db.t4g.micro` allows at most 112, somewhat less in practice, read with `SHOW max_connections` on the first demo. RDS Proxy costs $0.036 an hour and pins the connection that holds decision 2's lock; a larger instance doubles the database's price. Built in PH-37, checked again in PH-38. |
| 12 | The database's availability (S13) | Single-AZ; Multi-AZ; read replicas; Aurora | **Single-AZ for the demo, as ADR 0008, decision 19 has it.** Multi-AZ (+$0.022 an hour) protects data and uptime the demo does not keep; it joins backups in [OP-033](https://github.com/luiki-dev/szop/issues/116) as a step for an always-on Szop. |
| 13 | Autoscaling (S14) | ECS Service Auto Scaling with target tracking; a fixed count | **Target tracking on average CPU, between two and four tasks**, shown with a short load test from the owner's machine, in a phase of its own after two fixed tasks run cleanly: PH-38. Whether to track CPU or requests per target is left to its brainstorm. |
| 14 | Testing with several instances (S15) | Tests at each layer as each feature arrives; end-to-end tests against two instances only | **At each layer, with each feature:** integration tests in one Vitest process where the shared channel is outside the process (two migrators, two cleanup runs, an event across two app instances through Redis); and a Compose profile `scale` with two app containers behind nginx, run by a script locally and in CI's `docker` job, for what one process hides, since two instances in one process share module-level state (check B). The profile and the migration test in PH-37; each feature's test in its phase. |
| 15 | Sessions, seed data and quotas (S8–S10) | — | **No change.** Sessions are in PostgreSQL and Better Auth keeps none in a process (check B); every task loads the same seed data; the quota race exists within one process already and does not grow with the number of tasks. |
| 16 | Isolation from other apps in the account (I1–I7) | A shared stack for the account-wide pieces now; no change now | **No change now** *(the owner's choice)*. Szop's stacks own the account's GitHub OIDC provider, an unfiltered budget, the hosted zone with its domain-wide records, SES's domain identity and the state bucket; everything else is Szop's alone, its deploy role reaches only what is tagged `project` = `szop` and `group` = `demo`, and no account ID is in the code ([analysis, part 2](../audits/2026-10-19-scalability-and-isolation-analysis.md#part-2-isolation)). Moving the shared pieces into a stack of their own costs the same later as now (Terraform's `removed` and `import` blocks move them without recreating them), except for whatever is added to them meanwhile. The findings and the options (a shared stack, a budget per app, SES identities per app, one account per app) wait in a new candidate open point, **OP-100**, for a second app. [PH-34](../roadmap.md#ph-34-landing-page-and-demo-status) is unchanged. |
| 17 | The roadmap | — | **Three new phases and four changed ones**, in [Roadmap changes](#roadmap-changes): PH-37 Two tasks right after PH-12c, PH-38 Autoscaling at the end of Stage 3, PH-39 Redis in the stack before PH-20; PH-12c, PH-20, PH-31 and PH-33 build their parts for several tasks. |

## Consequences

- **The one-task assumption is gone from the design.** `architecture.md` describes two tasks, Redis behind the event bus and the rate limits, the locks and the split health check; the stack overview explains running several instances. Until PH-37, one task still runs, and nothing that needs a lock or Redis is built yet.
- **Every migration from PH-12c on must be safe for the previous version** (decision 3), a rule in `drizzle.md` and a point for reviews.
- **Redis is a new component to run and secure** from PH-39: a second data store in the threat model, an AUTH token, and a container in development and CI.
- **The demo costs $0.037 more an hour**; its runbook's figures change with PH-37 and PH-39, which add the cost.
- **Isolation is deferred, not dismissed:** OP-100 holds what a second app would need, and every shared piece added before then (PH-34's front page, PH-18's mail) is one more to move.
- **The analysis stays as written** in `docs/audits/`, a record of the options and that day's prices.
