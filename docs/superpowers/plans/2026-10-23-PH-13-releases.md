# PH-13 Releases Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Merging release-please's PR tags a version, publishes a GitHub Release with notes from GitHub (one entry per PR) and pushes the image as `szop:<version>`; the walking skeleton is released as `v0.1.0`.

**Architecture:** `release-please.yml` runs on every push to `main`: a `release-please` job, authenticated as the `szop-release` GitHub App from the `release` environment, keeps the release PR up to date and, once it is merged, tags and publishes the release; a `build` job without AWS credentials builds the release commit's image; a `publish` job in `release` assumes the new `szop-ci-release` role and pushes or re-tags it in ECR. `infra/base` gains the role, shields `X.Y.Z` tags in ECR's lifecycle policy and closes OP-102.

**Tech Stack:** release-please (`googleapis/release-please-action`, `release-type: node`, `changelog-type: github`), `actions/create-github-app-token`, GitHub Actions, Docker Buildx, Terraform (AWS provider), the AWS CLI in the workflow.

**Spec:** [`docs/superpowers/specs/2026-10-23-PH-13-releases-design.md`](../specs/2026-10-23-PH-13-releases-design.md)

**Order:** the spec's tasks 2 to 6 are regrouped as PH-35's were: the ADR is written with the other docs (Task 4), after building has settled the spec's *To verify* list, so it records what was found. Nothing in the spec's scope moves.

## Global Constraints

- release-please settings, exactly: `release-type: node`, `bump-minor-pre-major: true`, `include-component-in-tag: false`, `initial-version: "0.1.0"`, `changelog-type: github`, one package `"."`; manifest `{ ".": "0.0.0" }`; root `package.json` `"version": "0.0.0"`.
- The image's version tag is the version **without** `v` (`szop:0.1.0`); the git tag keeps it (`v0.1.0`).
- Names, exactly: environment `release`; variable `RELEASE_APP_ID` (or the client-ID name the token action requires, Task 3, Step 1) and secret `RELEASE_APP_PRIVATE_KEY`, both in `release`; repository variable `AWS_RELEASE_ROLE_ARN`; role `szop-ci-release`; output `ci_release_role_arn`; label `skip-changelog`; App `szop-release`.
- The role's subject, exactly: `repo:luiki-dev@290870182/szop@1380292421:environment:release`, with `ref` `refs/heads/main`.
- Workflows: `permissions: {}` at the top, per-job permissions with a comment saying why, actions pinned to a full commit SHA with the version as a comment, a version at least two weeks old; `id-token: write` only in `publish`; no job with AWS credentials runs `pnpm install` or a project script; the release build restores no cache.
- This session has **no AWS access and no GitHub GraphQL**: never run `terraform apply` or `destroy`, never `gh workflow run`, never trigger `demo-up` or `demo-down`, never merge, never delete a remote branch. GitHub through REST (`curl` with `GH_TOKEN`) or the GitHub MCP tools; the project's fields are the owner's.
- Nothing that identifies the owner's account goes into a commit: no account ID, no ARN with the account number, no email address.
- `pnpm check` passes after every task; `pnpm check:workflows` after every workflow change; `pnpm check:infra` after every `infra/` change.
- Commits follow Conventional Commits and end with `Co-Authored-By: <the model that wrote the commit> <noreply@anthropic.com>` and `Claude-Session: https://claude.ai/code/session_012FvCB3pEaRV16UPk6rc8vR`. The branch is `feat/ph-13-releases`; never commit to `main`.
- Docs: niche acronyms spelled out on first use and in `docs/glossary.md`; every status with its icon; requirements linked, never plain IDs; long docs keep their `## Contents` in sync; ADR notes in three places (`CLAUDE.md`, "Documentation").
- **After each task:** tick its step boxes (`- [ ]` → `- [x]`) in this plan within the task's own commit, `git push` the phase branch, then stop and summarize the task for the owner; start the next task only when the owner says so (`docs/superpowers/plans/CLAUDE.md`).

## Review Focus

1. **An ordinary push to `main` building or publishing an image.** Only a merged release PR may run `build` and `publish`. Task 3, Step 5 checks both jobs' `if` compare the output to the string `'true'` and walks a push where `release_created` is empty.
2. **The release PR failing its own CI.** The manifest release-please writes compactly must not fail `format:check`. Task 3, Step 3 writes `{".":"0.1.0"}` into the manifest and runs `pnpm format:check`.
3. **An AWS error read as "the image is missing".** `publish` must push only on `ImageNotFoundException` and fail on any other error from `describe-images`, as `demo-up` does. Task 3, Step 4 states the branch for each outcome.
4. **A role nobody can assume on release day.** A typo in the subject or the ref fails only after the merge. Task 2, Step 2 compares the trust's strings with `szop-ci-deploy`'s character by character.
5. **Dependabot's PRs in the notes.** The author's spelling in `.github/release.yml` decides it. Task 3, Step 2 asks GitHub's notes API for the notes the first release would get and checks no Dependabot PR is listed.

- [x] **Step 4: The workflow**

- `release-please` (`environment: release`): the token step, then the action with `token:` from it; job outputs `release_created`, `tag_name`, `version`, `sha` from the action's outputs as Step 1 found them.
- `build` (`if: needs.release-please.outputs.release_created == 'true'`, `contents: read`): as `demo-up`'s `build`, checking out `needs.release-please.outputs.sha` with `persist-credentials: false`, `GIT_COMMIT` from it, no `cache-from`/`cache-to`, `provenance: false`, `sbom: false`, artifact `image` with `retention-days: 1`.
- `publish` (`needs: [release-please, build]`, same `if`, `environment: release`, `contents: read`, `id-token: write`): `configure-aws-credentials` with `vars.AWS_RELEASE_ROLE_ARN`; then one step whose script, with `SHA` and `VERSION` from `env:` (never interpolated into the script):
  - `describe-images --image-ids imageTag=$SHA` succeeds → `batch-get-image` its manifest (`--query 'images[0].imageManifest'`, with its media type) → `put-image --image-tag "$VERSION"` with that manifest and media type;

  - any other error → print it and exit 1;
  - in every successful branch, write the tags and the digest (`describe-images --image-ids imageTag=$VERSION --query 'imageDetails[0].imageDigest'`) to `$GITHUB_STEP_SUMMARY`.
