# PH-37 Two tasks Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the demo runs two tasks, one per availability zone, which migrate the database one at a time; two instances run locally and in CI too.

**Architecture:** each process draws a random instance ID that `/api/health` reports; request IDs become random UUIDs; the pool is capped at 5; the migration check and the migration run under a PostgreSQL advisory lock held on a pooled connection. A Compose profile `scale` runs two app containers behind nginx, checked by `pnpm check:scale` locally and in CI. `demo-up` starts the service at two tasks.

**Tech Stack:** Node 24 with TypeScript run directly, Fastify 5, `pg` 8, Drizzle (`drizzle-orm` 0.45), Zod 4, Vitest; Docker, Compose and nginx (official Alpine image); GitHub Actions; bash and `curl`.

**Spec:** [`docs/superpowers/specs/2026-10-21-PH-37-two-tasks-design.md`](../specs/2026-10-21-PH-37-two-tasks-design.md)

## Global Constraints

- Instance ID: 8 lowercase hexadecimal characters, `randomBytes(4).toString("hex")`, drawn once per process; `instance` in both `/api/health` bodies, after `commit`: `{"status":"ok","commit":"…","instance":"…","database":{…}}` and `{"status":"error","commit":"…","instance":"…","database":{"status":"down"}}`.
- Request IDs: `genReqId: () => randomUUID()`; nothing from the request (no `request-id`, no `X-Amzn-Trace-Id`) becomes the ID.
- Pool: `max: 5`. The lock: `pg_advisory_lock` / `pg_advisory_unlock` with the key `0x537a6f7000000001` ("Szop" in ASCII, then 1), on a connection from `db.$client.connect()`, no timeout; log lines `waiting for the migration lock` and `migration lock taken`.
- The `migrations applied` line logs `{ schemaVersion, commit, instance, maxConnections }`.
- Compose profile `scale`: services `app-a`, `app-b` (database `szop_scale`, no published ports) and `nginx` on `127.0.0.1:8081`; the `app` profile and its port 8080 unchanged.
- `pnpm check:scale` = `scripts/check-scale.sh`; CI's `docker` job runs `scripts/check-scale.sh --no-build` after `check-image.sh --no-build`.
- `demo-up` wants 2 tasks; Terraform's `desired_count = 0` and `ignore_changes` stay.
- `pnpm check` passes after every code task.
- Never run `terraform apply` or `destroy` against AWS, never `gh workflow run`, never trigger `demo-up` or `demo-down`, never merge, never delete a remote branch. Read-only AWS calls with the owner's SSO profile `szop` are allowed.
- Nothing that identifies the owner's account goes into a commit: no account ID, no ARN with the account number, no email address.
- Commits follow Conventional Commits and end with `Co-Authored-By: <the model that wrote the commit> <noreply@anthropic.com>` and `Claude-Session: https://claude.ai/code/session_01StaHEo5YGx7QbYKpjetkEd`. The branch is `feat/ph-37-two-tasks`; never commit to `main`.
- Docs: niche acronyms spelled out on first use and in `docs/glossary.md`; every status with its icon; requirements linked, never plain IDs; long docs keep their `## Contents` in sync; ADR notes in three places (CLAUDE.md, "Documentation").
- **After each task:** tick its step boxes (`- [ ]` → `- [x]`) in this plan within the task's own commit, `git push` the phase branch, then stop and summarize the task for the owner; start the next task only when the owner says so (`docs/superpowers/plans/CLAUDE.md`).

## Review Focus

1. **A lock left held by a pooled connection.** A session-level advisory lock survives `release()`; if unlock is skipped on some path, the next migrator waits for ever. Task 3 tests that after the locked work (and after work that throws) `pg_locks` holds no advisory lock with the key.
2. **A failed migration under the lock.** The error must still stop startup as today, and the other task must then get the lock. Task 3 tests that a throwing `work` rejects with its own error and that a second `withMigrationLock` call afterwards runs.
3. **A client choosing its request ID.** Task 2 tests that `request-id` and `x-amzn-trace-id` headers do not become the logged `reqId`.
4. **nginx serving one app only** (an upstream misnamed, or both names resolving to one container). Task 4's script requires exactly two distinct instances in 10 answers.
5. **A demo started before this phase** (count 1) or a retry after a failed deployment staying at one task. Task 5 sets 2 on every branch of the start step.
