## Goal

A guest's first change creates their workspace as a copy of the default units, categories and products, the catalog page then shows that copy, and two tabs making their first change at once end up in one workspace with one copy ([PH-16b](../../roadmap.md#ph-16b-workspace-from-the-default-data)).

## Decisions

[ADR 0060](../../decisions/0060-workspace-from-default-data-phase-details.md#decisions).

## The design

The phase is API-only: the SPA, the screens and the E2E journeys do not change.

### The default data's IDs

`parseSeed` (`apps/api/src/catalog/seed.ts`) stops numbering entries (`u1`, `c12`, `p34`) and gives each one a UUIDv5 of its name (decision 2):

- the name as the seed's duplicate check compares it: `toLocaleLowerCase("en")` of the trimmed name;
- one fixed namespace UUID each for units, categories and products, written as constants in `seed.ts`, so a category and a product with the same name get different IDs;
- the names are unique per kind, case-insensitively, already (the duplicate check), so the IDs are too.

The `Catalog` it returns keeps its shape; only the ID strings change. `parentId`, `categoryId` and `unitId` point at the new IDs. `@szop/shared`'s schemas already accept any string as an ID and need no change.

UUIDv5 is SHA-1 over the namespace and the name, with the version and variant bits set (RFC 9562). `node:crypto`'s `createHash("sha1")` is enough; the builder may use a package only if one already in the workspace provides it.

### The tables

Three workspace-owned tables in `apps/api/src/db/schema.ts`, one migration generated by `pnpm --filter @szop/api db:generate`, following [ADR 0057](../../decisions/0057-guests-first-list-phase-details.md), decision 14, and [ADR 0060](../../decisions/0060-workspace-from-default-data-phase-details.md), decision 3:

| Table | Columns besides `workspace_id`, `id`, `created_at`, `updated_at` | References |
|---|---|---|
| `units` | `name text NOT NULL` | — |
| `categories` | `parent_id uuid NULL`, `position integer NOT NULL`, `name text NOT NULL` | `(workspace_id, parent_id) → categories (workspace_id, id) ON DELETE CASCADE` |
| `products` | `name text NOT NULL`, `category_id uuid NULL`, `unit_id uuid NULL` | `(workspace_id, category_id) → categories ON DELETE SET NULL (category_id)`; `(workspace_id, unit_id) → units ON DELETE SET NULL (unit_id)` |

Every table: `id uuid NOT NULL` with no default (the IDs come from the seed now and from the browser later), primary key `(workspace_id, id)` named `<table>_pkey`, `workspace_id` referencing `workspaces (id) ON DELETE CASCADE`, a `CHECK` that `name` is 1 to 100 characters, and `position >= 0` on `categories`. Constraints are named in PostgreSQL's style (`products_workspace_id_category_id_fkey`); a name over 63 characters is shortened by hand, keeping the table and the column.

Drizzle's `foreignKey()` cannot write `SET NULL (column)` (PostgreSQL 15 and newer). If it cannot, the generated migration is edited by hand to add the column list, and the migration check (`db:generate` writes nothing) must still pass; see [Risks](#risks).

No uniqueness of names is added here: the seed guarantees it, and the rules for names a user types are [PH-26](../../roadmap.md#ph-26-catalog-and-units)'s.

### The copy

`ownWorkspace` (`apps/api/src/access/workspace.ts`) inserts the workspace with `ON CONFLICT (user_id) DO NOTHING RETURNING id`. When a row comes back, this call created the workspace, and it inserts the seed's units, then categories, then products, each as one multi-row `INSERT`, on the same executor (decision 4). It then returns the context as today.

- `POST /api/lists` already calls `ownWorkspace` inside its transaction, so the workspace, its copy and the list commit together or not at all.
- Two first changes of one user race on `workspaces_user_id_key`: the second insert waits for the first transaction to commit, then does nothing and returns no row, so it copies nothing and finds the workspace. One workspace, one copy ([ACC-1](../../requirements/ACC-accounts-and-guest-mode.md#acc-1).6).
- Categories go in one statement with their parents: PostgreSQL checks a non-deferred foreign key at the end of the statement, so a child before its parent in the same `INSERT` is accepted.
- `ownWorkspace` needs the parsed seed. It reaches it the way the builder chooses (an argument, or a dependency passed where the lists routes are registered), as long as the catalog route and the copy use the one `Catalog` that `loadSeed` returned at startup.
- **Test catalogs carry UUIDs.** The new `id` columns are `uuid`, and `ownWorkspace` copies whatever `Catalog` the app was built with, so `testCatalog` in `apps/api/src/test/catalog.ts` and any other hand-made catalog use UUIDs as IDs, and the tests that assert on its IDs change with it _(Claude's call)_.
- `ownWorkspace` must be called inside a transaction when it may create the workspace. Today every caller that writes is; the comment on `ownWorkspace` says so.

### The catalog route

`GET /api/catalog` (`apps/api/src/catalog/routes.ts`) looks up the visitor's workspace with `findOwnWorkspace(db, request.user)` (decision 5):

- no user, or a user with no workspace: the seed `Catalog` from memory, as today;
- a workspace: its `units`, `categories` and `products`, read with the workspace's context, mapped to the same flat shape (`parentId`, `categoryId`, `unitId`, `position`). The order of the rows does not matter; the SPA orders them.

The response schema stays `catalogSchema`. The route reads only: it creates no session and no workspace and sets no cookie ([ACC-1](../../requirements/ACC-accounts-and-guest-mode.md#acc-1).3).

The SPA keeps the catalog cached for the session (`staleTime: Infinity`) and needs no change: before and after the first change it gets the same IDs and names.

### The access layer

The rest of [OP-054](https://github.com/luiki-dev/szop/issues/102) and [OP-118](https://github.com/luiki-dev/szop/issues/321) (decision 6):

- **Repositories take the context.** Every function of `apps/api/src/lists/repository.ts` and the new catalog repository takes the existing `WorkspaceContext` instead of a bare `workspaceId: string`, so passing an arbitrary ID does not compile _(Claude's call: the type stays as it is)_.
- **A list is read once.** `GET /api/lists/:id` reads the list in one query, not once in `requireListAccess` and again in `findList`. The builder chooses how (for example `requireListAccess` returning the row it read); the 404 for a missing and a foreign list stays byte-identical.
- **The two-workspace test helper** (in `apps/api/src/test/`): creates two users, each with a workspace made by `ownWorkspace` (so with its copy), and returns their contexts and a way to send requests as each. Later phases use it for "a reference into another workspace gets 404".
- **The schema test over PostgreSQL's catalog** (`pg_constraint`, `information_schema`), run on the migrated test database:
  - every table with a `workspace_id` column has it `NOT NULL`, references `workspaces (id)`, and has a primary key or unique key starting with `(workspace_id, id)`;
  - every foreign key that targets a table with a `workspace_id` is composite and includes `workspace_id` on both sides;
  - a table that should be workspace-owned but has no `workspace_id` fails it: the test names the tables that are not workspace-owned (Better Auth's four and `workspaces`), so a new table must be one or the other.

### The database tests under load

[#317](https://github.com/luiki-dev/szop/issues/317): `CREATE DATABASE` and `DROP DATABASE … WITH (FORCE)` in `beforeEach` and `afterEach` time out after 10 seconds when the machine is loaded. The builder reproduces it (for example with `stress` or a parallel `pnpm test` while another runs), finds whether the cause is the hook timeout, PostgreSQL's speed at creating databases with many Vitest workers, or connections left open, and fixes that cause. Raising the hook timeout alone, fewer workers for the database tests, or a template database are fixes for a cause, not a choice made up front: a longer timeout alone would hide a cause CI could hit too, and this phase's tests, each writing a workspace of about 600 rows, add to the load. The cause and the fix go into the plan's ledger and the PR's description, and into `docs/development/testing.md` if a rule for writing database tests changes.

## Tests

Each criterion's test name starts with its ID.

- **API, the seed (Vitest):** `parseSeed` gives every entry a version 5 UUID; the same name gives the same ID in two parses, and in another case (`Milk`, `milk`) too; a category and a product with the same name get different IDs; adding an entry before another leaves the other's ID unchanged; references point at the new IDs. Known values: the ID of one unit, one category and one product, written in the test, so a change to the namespaces or the algorithm fails it.
- **API, the copy (Vitest, PostgreSQL):**
  - ACC-1.4: a new guest's first `POST /api/lists` makes one workspace whose units, categories and products equal the seed's, IDs, names, parents, positions and references included, and the list;
  - UNT-1.1: the new workspace has the seed's units, pcs, kg, g, l, ml and pack;
  - ACC-1.6: two concurrent first `POST /api/lists` of one user: one workspace, each table holding the seed's count once, both lists in it;
  - a failed copy (a `Catalog` built by hand in the test, whose product names a unit not in its units, passed to `buildApp`, which does not check it again) rolls back the workspace and the list;
  - a second `POST /api/lists` copies nothing.
- **API, the catalog route:**
  - without a session, and with a session but no workspace: the seed, and no `Set-Cookie`;
  - with a workspace: its own rows; a row renamed in one workspace's table shows in its catalog and not in another's (the two-workspace helper);
  - ACC-1.9: two `buildApp` instances on one test database, one with seed A and one with seed B (an added product and a renamed one); guest 1, a user of the first, gets a workspace; guest 2, another user of the second, gets one; through the second app, guest 1's catalog is still A and guest 2's is B _(Claude's call)_.
- **API, the access layer:** the list repository's functions refuse a bare string at compile time (a `// @ts-expect-error` line in a test); `GET /api/lists/:id` sends one query for the list (counted or spied on); the existing NFR-4.10 tests still pass.
- **API, the schema:** the schema test above; and the database refuses a product in workspace A whose category exists only in workspace B (a category with a fresh ID inserted in B), and the same for a category's parent and a product's unit.
- **Web and E2E:** unchanged. `e2e/tests/catalog.spec.ts` and `lists.spec.ts` must still pass.
- **Mutation testing:** the run over the changed logic (`seed.ts`, `access/`, `catalog/routes.ts`, the repositories), each survivor killed or accepted with a reason ([definition of done](../../development/definition-of-done.md), item 2).

## Risks

- **`SET NULL (column)` in Drizzle.** `drizzle-kit` may not express it; a hand-edited migration then differs from what `db:generate` writes, and the migration check fails. The builder checks Drizzle's current support (context7) first. If no way keeps the check green, the builder stops and reports: the options are plain `SET NULL` on these FKs (wrong: it would null `workspace_id`, which is `NOT NULL`, so the delete fails), or leaving the `ON DELETE` to the phase that deletes.
- **Copy time.** About 600 rows in three statements should take milliseconds; if the first `POST /api/lists` becomes noticeably slower in the API tests, the builder measures before changing the approach.
- **Test load.** Every test that makes a workspace now writes about 600 rows, which adds to [#317](https://github.com/luiki-dev/szop/issues/317)'s load; the fix for #317 should be in place before the copy's tests multiply.

## Out of scope

- Adding a product to a list, and ACC-1.5's and NFR-4.10's references in requests ([PH-17a](../../roadmap.md#ph-17a-list-items)). Creating a list is this phase's only first change; a criterion is checked through behavior a user has, and a test-only route would check something no user can do.
- Adding, renaming and deleting catalog products, categories and units, and uniqueness of names a user types ([PH-26](../../roadmap.md#ph-26-catalog-and-units) and the categories phase).
- The new list's Create button, the session check before writes, the raccoon's position ([OP-115](https://github.com/luiki-dev/szop/issues/318), [OP-116](https://github.com/luiki-dev/szop/issues/319), [#323](https://github.com/luiki-dev/szop/issues/323), moved to [PH-16c](../../roadmap.md#ph-16c-managing-lists), which changes the lists screens and the SPA's writes anyway).
- Moving a guest's workspace to an account (PH-18, PH-19).
- Any change to the SPA.
